# Changelog

The running list of what changed in every version of the Ants remake, newest first. The version number lives in
`include/ants_app/version.hpp` and is shown on screen next to the FPS meter (bottom right of every screen).
This file is updated with every release, together with the [README](README.md); it is also published on the beta site at
[beta.playants.org/changelog.html](https://beta.playants.org/changelog.html).

How to read it: versions before v0.0.24 approximated the original 1998 game; from v0.0.24 on every system was re-derived from
the disassembly of `Ants.exe` and replaced (the "Original ..." series). "Rewritten tests" are old tests that encoded behaviour
the original does not have; they were changed to the verified behaviour, never deleted or disabled (each commit message lists them).
Ground truth for every entry is in [`docs/GAME_REVERSE_ENGINEERING.md`](docs/GAME_REVERSE_ENGINEERING.md); the network port is described in
[`docs/NETWORK_PORT.md`](docs/NETWORK_PORT.md).

## Unreleased - The room leader can start early

The owner asked: "the first player to join the lobby should get a start button in case they want to start the game with less players". A room on the game server used to wait for every seat that it was made for (two to four players, up to ten minutes for a demo room). Now **its leader, the first player who joined, can start the match with the players who are there**. Nothing else about the room or the match changed. This is **network protocol 7**, which does not speak with protocol 6 (a game of the old version is refused with "version mismatch", by a LAN host as by a server).

- **Who leads** (`HostLobby`): in a room of the dedicated server (the server holds no seat) the player who was welcomed first leads; when it leaves (it quits, is kicked, is thrown out for garbage, or its connection dies) the earliest of the players who are left leads. The order is the order of the welcomes, not the number of the seat (asking for a seat with `--seat` or `?seat=` gives no lead), a player who comes later never takes the lead, one who comes back is the newest, and when everybody has gone the next one to come leads. A computer player never does. The Room message names the leader to everybody, and the new leader is already named in the message that tells about the departure of the old one. A LAN / direct room has no leader: its host starts, as before, and its guests keep the guest's screen.
- **The wire**: `RoomMsg` has a last byte `leader` (a seat, or 255 for nobody) and there is a new message `StartRequest` (type 24, player to server, **no payload: one byte**). The decoder is strict like the others: a leader is 255 or the seat of a player who joined as a guest (an empty seat, a bot and a host are refused), a Room message of protocol 6 (no such byte) is no Room message, and a StartRequest with a payload is garbage (a violation: eight of them throw the sender out). A request that cannot be honoured is no offence: it is ignored and counted (`ignored_start_requests`), whether it comes from a player who is not the leader, from any guest of a LAN host, from a room without early start, with fewer than two players, or when the match is loading already (the leader's second click on START arrives after the Start). In a running match a server ignores a late request, a LAN host counts it as a violation.
- **The server**: `RoomSpec::early_start` (the control interface's `"early_start": true|false` in `POST /rooms`, true when left out, a value of another type is a 400; demo rooms have it on). When the leader's request arrives in a waiting room that can start (two players at least), the room starts at once with the seats that are taken (the roster is those seats; `expected` keeps what the room was made for, `joined` shows who came). A room whose seats are all taken still starts by itself. With `early_start` off the room has no leader and waits for every seat. The status of a room (`GET /rooms`, `GET /rooms/<code>`) has three new keys: `early_start`, `leader` (the seat while the room waits or loads, otherwise null) and `ignored_start_requests`. Where the early start meets the rest of the room: a request in the two seconds of pause after a cancelled start is lost (the leader presses START again), a leader who asked and left in the same breath asked for nothing, and seats that the map cannot be played by (a start marker outside the grid) are not started early and do not fail the room (a full room still fails with the reason, as it always did).
- **The leader's screen**: the first player's setup screen is the original's **host screen** (`st_screen`: Up / Down, START, Fog of War) in a **server room mode**: the map label shows the room's map (the description from this machine's copy of the file, "???" without it), Up, Down and the wrap change nothing, the Fog buttons show the room's choice and change nothing (they still show their hover and pressed pictures and click), **START (the button, `Enter`, the keypad's Enter, `S`, `s`) sends the request**, Leave works as everywhere, and the rows are the guest's (itself first: nothing jumps when the lead moves). Its prompt is the host's own text ("Press START when all players' thumbs have appeared."); no new text appears on any original screen. **With fewer than two players START does what the host's START does on a LAN room with too few players: the can't-go cue, no message, nothing sent.** Everybody else keeps the guest's screen; when the leader leaves, the next one's screen turns into the host's with the next Room message. When the server's Start arrives every screen is locked (a second click on START while the map loads sends nothing) and a cancelled start unlocks it.
- **The Play online page** (`web/four.html`): its hints say that the first player in the room can start early with START once at least 2 players are in.
- **A test hook**: `--start-when N` (2 to 4, off by default) makes a client that leads a server's room press START itself once N players are in (a headless client has nobody to click); `tests/scripts/test_ants_server.sh` uses it.

## v0.0.92 - 2026-10-01 - The black bars of a wide window scroll the map, fullscreen keeps the mouse, a safety net for the widescreen work, the review fixes of the bots, and four games in the corners of their hills

Five things ship together; the classic 640 x 480 picture stays exactly what it was. **For the player**: a wide window (fullscreen on a wide monitor) no longer ignores the pointer over its black bars, and fullscreen keeps the mouse in the window. **For the widescreen work that follows** (a parametric screen layout, a 16:9 picture, a wider HUD, the wheel zoom, touch gestures): milestone M0, a new test program that pins what the classic 640 x 480 picture draws and what the pointer does, so that every later step can prove that the classic picture stays pixel for pixel what it is. **For the build**: GCC 12 now builds the whole project with warnings as errors. **For the computer players**: the 35 fixes of the adversarial review of bot milestone B2 (the view, the map analysis, the arena, `bot_arena`), and the worker bot of B3 on the fixed interfaces; nothing in the simulation changed. **For the page with four games and the four-window start script**: the games lie by colour, in the corners of their hills (black top left, green top right, red bottom left, blue bottom right). The pointer fix and the safety net were made side by side on v0.0.88 and meet here on top of v0.0.91; they agree: of the 307 numbers of the safety net **none changed** (the fix works on SDL events, which none of the fingerprints feeds through the application's loop; checked on macOS with clang and on Debian 12 with GCC 12; the reasoning is in [`docs/audit/M0_notes.md`](docs/audit/M0_notes.md)).

**The black bars and the mouse.** The game draws its 640 x 480 picture in the middle of a bigger window: fullscreen on a wide monitor, or a window of any shape, shows black bars beside or above the picture. The pointer over a bar used to count for nothing (no edge scrolling there, no cursor), and in fullscreen on a machine with a second monitor the pointer slipped off the screen at the edge, so the edge scrolling stopped.

- **A pointer over a black bar is the pointer on the nearest edge pixel of the picture** (`include/ants_app/pointer_clamp.hpp`, at the top of the event loop, so every screen gets it: the match, the setup screen, the quick help): pushing the mouse into a bar scrolls the map like the edge does, and the game's cursor stays drawn on the edge. That is what the original shows on the one monitor of its time: it switches the screen to an exclusive 640 x 480 mode, so the whole desktop is the picture.
- **Fullscreen keeps the mouse in the window** while the game has the focus: `--fullscreen` and a macOS fullscreen Space (the green button, Cmd+Ctrl+F) both do; Cmd+Tab, another window taking the focus or leaving fullscreen frees it at once. A window (also a maximized one) never holds the mouse, so several games on one screen and other programs stay reachable. The original never confined the pointer itself (it only had the one screen); with a second monitor its pointer could leave too.
- **When the pointer has gone, the map stops**: a mouse button released outside the window (after a drag that left it: macOS reports no "pointer left" then), or a finger lifted from a touch screen, no longer leaves the pointer on an edge where the map kept scrolling on its own. While a button is held (a rubber band, the minimap) the pointer stays on the edge as before. This also ends an older quirk: a tap in the picture's 5 px edge strip used to scroll until the next touch.
- **Limits**: the fullscreen toggle of a Linux window manager (F11, a menu) is not detected, so that window does not hold the mouse (start with `--fullscreen` instead); on X11 SDL waits up to 5 s for the mouse when another program holds it at that moment (a menu, a screenshot tool), and then gives up holding it for the rest of the run; the web build cannot keep the mouse in the page (the browser decides).
- **The documents**: `docs/GAME_REVERSE_ENGINEERING.md` 5.43 said the original clamps the pointer to 0..639 x 0..479; it does not. Verified with Capstone: `GetCursorPos` is stored as it comes (0x1030a80), the file imports no `ClipCursor` or `SetCapture`, the exclusive DirectDraw mode (`SetCooperativeLevel` 0x53, `SetDisplayMode(640, 480, 8)`) is what keeps the pointer on the picture, and the only clamp (the relative move 0x103071a) is reached only through an input flag that no code sets.
- **Tests**: `test_pointer_model` group pillarbox (the clamp, after which events the pointer has gone, the grab table: 428 checks, 387 before) and `test_app_integration` 7.8 (bars on every side, the exact position of a pointer on the picture), 7.8b (the setup screen and the quick help), 7.8c (a release outside the window, the web's release after a "pointer left", a release over a bar), 7.8d (touch), 7.8e (the grab, with a real window of SDL's dummy video driver): 218 tests and 8,138 assertions, 213 and 8,027 before (8,127 where SDL's dummy driver gives no window the focus, as with Debian 12's SDL 2.26: the focus part of 7.8e is not run there). 21 deliberate mutants of the fix are each caught. The suite's temporary files carry the process id (7.6b, 7.6c, 8.8, 9.12, 9.13, 12.9b: the names only, nothing else of those tests), so two runs at the same time no longer share them.

## v0.0.88 - 2026-10-01 - Bots B3: the worker bot

The third milestone (B3) of the computer players of [`docs/BOTS.md`](docs/BOTS.md): the first bot that plays, and the fixes of an adversarial review of it. ## v0.0.47 - 2026-09-29 - Network port: host migration (the match goes on when the host leaves)

- **Host migration**: as in the original, where nobody is special once a match runs, the host may leave (or crash, or lose its network) and the others play on. Every machine already holds the whole simulation, so
  only the role of sealing turns moves. While the map loads every guest connects to the guests above its seat (it announces a port in its `Hello`, the host passes the addresses on in `Start`, an inbound link says
  `PeerHello{seat}` and is accepted only from a lower seat of the roster, once, from the address the host reported); every machine keeps the last 300 turns (30 s).
- **Detection and election**: the host's connection closes (everything it sent before is read first) or it is silent for 10 s. The guests elect the lowest seat they still see alive: it proposes `epoch + 1`, every
  guest accepts the lowest seat it sees alive (one candidate per election) or names the lower seat that lives, a guest that had not noticed yet that the host is gone is asked again after a second (three such
  refusals mean that only this machine lost the host: it stops), a guest that does not answer within 3 s is given up, an election that lasts 30 s ends. A link speaks only for its own seat and messages of another
  election are ignored.
- **Resync**: the winner takes the highest position that the accepting guests report, fetches the turns it lacks from the one that has them (a source that dies is given up), becomes the host with the same runner
  (`promote_to_host`), sends every follower the new host's `Resume` and the turns it lacks, and seals on from there. Its first turn drops the old host and every seat that did not follow, so all machines drop them at
  the same tick. Orders given in the last ~300 ms before the host went are lost (`NetGame::submit` reports them as ignored while there is no host, so no acknowledgement sounds).
- **In the game**: the overlay says "The host left. Choosing a new host..." while it happens and "Bob is the host now." (or "You are the host now.") for five seconds afterwards; the events `HostChanged` and
  `PlayerLeft` report it, `HostLeft` now only means that no new host could be agreed (the match returns to the setup screen with "The connection to the other players was lost."); a match with one machine left goes
  on for it alone; once the match is over (`freeze()`) a leaving host is no reason to elect anybody.
- **Protocol version 3**: `Hello` carries the guest's listen port, `Start` carries the guests' endpoints, six new messages (`Propose`, `Accept`, `Refuse`, `Resume`, `Request`, `PeerHello`), every decoder checks its
  ranges (seats, positions, addresses). `Sequencer::resume` starts a new host's sequencer at the resume turn with nobody active.
