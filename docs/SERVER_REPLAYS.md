# The game server's replays and its own matches of computer players

This page is the part of [`SERVER.md`](SERVER.md) that belongs to the matches that the server keeps as replays and to the matches of computer players that it plays itself.

## Replays

The server keeps the matches that its rooms play, so that they can be watched again ([`REPLAYS.md`](REPLAYS.md) says what a replay is and what plays it). The referee's own runner is watched while the match runs (it changes no hash), and when the match is over the file goes to a folder of the results volume (`replays` in `--results-dir`; `--replays-dir` chooses another folder and `--no-replays` keeps none). The numbers of the replays are here; the other documents point to this section.

- **What is kept.** A match that ran at least 600 turns (30 seconds), however it ended: the rules ended it, a player quit, an operator closed the room, its time limit, a desync. A shorter match is not kept, so rooms that start and are closed at once leave nothing; the room's status says why (`replay.note`). A longer match whose recording failed is not kept either: the note says why (a recording is limited to 1 MiB, for one) and the log has one line. Demo rooms are kept with `--replay-demo` (the stack file has it; a demo room is a room that a visitor's create block made, the games of the front page, and never one that the control interface made), and a room of the control interface may say `"record": false`. A solo game in a browser tab is not played on the server and is not kept. When the server is stopped, a room that holds a restart record stays in the record and is not saved now, and a match that the server brought back from a record is not recorded from then on (the recorder did not see the part of it before the restart); any other room is closed, and its match is kept like that of a room that an operator closed.
- **Names.** A person's seat keeps the name that the room showed everybody, the name that the player typed: plain ASCII (the letters from the space to the tilde; every byte of anything else becomes a `?`, so a letter with an accent, which is two bytes, gives `??`), at most 32 characters, the blanks at both ends cut (`replay_person_name` in `room.hpp`). The readers show it after the color, "Green (Ann)". A seat with no name of its own shows the color alone, "Green": nothing was typed, or only the words that the game itself uses for a player without a name, "Player" and "Player 1" to "Player 4" (a name that only starts like them, "Players" or "Player 5", is a name and is kept). A computer player's seat has its display name, "Bot (Easy)", "Bot (Medium)" or "Bot (Hard)". The front page plays a visitor who is logged in under the login's name and any other visitor under a guest name ("Guest" and six digits); both are kept like any other name. **The names are public wherever the public door (below) is on, which it is in the stack file:** anybody can read them in the list and in the file, so a page that shows them must show them as text. No address, room code, key or chat is in a file or in the list. The file's name is the map and the time the match ended: `ants-TREASURE-20261008-143209Z.antsrep` (UTC; `-2`, `-3`, ... when two matches of a map end in one second).
- **The notice on the pages.** A line says what the server does with an online match. The front page shows "Online matches are recorded. Recordings are kept for up to 90 days. Results and names are kept for good and are public." in its footer and under the name field of the card that a shared link opens (the element `who-notice`); the game page's name card says "Online matches are recorded. Anybody can watch them, live or later. Recordings are kept for up to 90 days. Results and names are kept for good and are public." (not in the step of a game on this computer: the server does not record that game). The pages are static, so the line is true only for a server that runs as the stack file runs it: `--replay-demo` (the front page's matches are kept), `--replay-port` (the public door below, which the site's nginx passes `/replays` to) and 90 days (`--replays-days`, `ANTS_REPLAY_DAYS`). A server with other settings (`docker-compose.server.yml` has the first two off) changes the words in `web/lobby.html` and `web/shell.html`, and leaves the element `who-notice` of the first where it is. The pages say "up to 90 days", because the store gives way before the disk does ("How long and how much").
- **Only its own files.** The server touches nothing in the folder but files with a name of that form: another file is left alone and is not counted. A file is written whole under a temporary name and renamed, and an existing file is never replaced, so a crash of the server leaves a whole file or none (a power cut may leave a short one: the operator's list shows it as unreadable, and it goes when it is old). A name is looked up in the server's list, never opened as a path. When the server starts it lists the folder (the name and the size of each file: the age and the order are in the names; 0.3 s for 100,000 files) and the loop reads the head of every file a few at a time, the newest first (`ReplayConfig::index_in_background`; 40 files or 4 ms a pass at the most, so the longest pass of a store of a gibibyte was 2.4 ms; reading everything first took 5 to 11 s for 100,000 small files and held the server back). Until a file's head is read it is listed as not read yet: the history does not count it, the public list does not show it, and a request for it by name reads it at once. The tests, the history service and the tools read everything at once. After that nothing takes longer than one small file write, one pass over the list or one look at the folder (a `stat` for every file, and the reading of at most 100 new ones). A file that somebody else puts in the folder (`bot_arena --save-replays`, [`REPLAYS.md`](REPLAYS.md#matches-of-computer-players)) is listed within half a minute: every 30 seconds the folder's change time is looked at, and only when it moved (or moved a moment ago) is the folder read again (at most 100 new files at a time; a file that changed in the last two seconds waits for the next look, and a known file is read again only when it could not be read or its size moved); a file that was taken away is forgotten and nothing is deleted for it, while a file that came from outside is under the limits like any other (one older than the keep time is deleted at once). A file of the store is "never replaced" by the store itself; another program that writes into the folder with the same name in the same second could replace it (a rename replaces on Linux), which is why only one writer is meant to run at a time ([`REPLAYS.md`](REPLAYS.md#matches-of-computer-players)). Opening the folder deletes the `.tmp` of a crash but not one that changed in the last two seconds, which is the write of the other program.
- **How long and how much.** A file is deleted `--replays-days` days after its match ended (30 by default, **90 in the stack**: `ANTS_REPLAY_DAYS`), and all the files together stay under `--replays-max-mb` (100 MiB by default, **1,024 MiB in the stack**: `ANTS_REPLAY_MAX_MB`), the oldest first. The limits are applied when the server starts, before every file is written (so that the new one fits) and once an hour. The age of a file is the time in its name, so it is as right as the server's clock: a clock that jumps ahead by the kept days deletes the files at the next look, and one that is set back files new matches among the older ones and starts the hour's allowance again. A person's recording is kept for **up to** its days: it goes sooner only when the store is full of people's recordings, or the disk is short, and no recording of computer players is left to go first (the pages say "up to 90 days").
- **A budget for the matches of computer players.** A recording is a *match of computer players* when every seat that played has a name that a person cannot take (`ai::is_reserved_bot_name`: the head of the file says it, so a file found in the folder is classed the same way; `ReplayEntry::bots_only`). The server's own matches ([below](#matches-of-computer-players)) must never crowd people's recordings out, so they have a budget inside the store's: **at most 30 of the hour's 120 saves** (`max_bot_saves_per_hour`; they count among the 120, so people always have 90) and **at most a quarter of the bytes** (`bot_share_percent`, 256 MiB of the stack's 1,024). Whatever has to be deleted for room goes in this order: the files past their days; then the files of computer players, the oldest first, while they are over their quarter, the store is over its limit or the disk is short; then, only when the match that comes is a person's, the oldest files of people. A match of computer players **never deletes a person's file**: when it does not fit among the bots' files it is not kept (and is refused before anything is deleted for it), and the server does not start one for which the hour has no room left (`ReplayStore::bot_saves_left()`: a match that would not be kept is not played). A recording of a bot match is about 10 KiB on the shipped maps, so a quarter holds some 26,000 of them. The numbers are guesses to be changed from what the real server shows.
- **A full disk never stops the server.** The folder shares a volume with the control secret and the restart records, so the server keeps nothing new when the disk would be left with less than 256 MiB free, or when it has kept 120 matches in the last hour, and a match is 1 MiB at the most (2 MiB with a map). **When the volume is smaller than the size limit asks for** (the guard is reached before the 1,024 MiB are), the store gives the disk what it needs: the files that may go for the match go, the bots' first and a person's oldest only as far as that helps, and the log says how many (`the disk had 40 MiB free and keeps 256 MiB free: 3 older file(s) were deleted to keep a match`). When deleting could not help (the files that may go hold less than the disk lacks: the volume is too small for the store, or something else fills it) nothing is deleted and the refusal says so. At the start and once an hour the log says, while it is true, that the volume has less free than the size limit still has room (`the store can grow by 344 MiB, not up to its limit of 1024 MiB`); a bigger volume or a smaller limit ends the line. The log tells a refusal once and counts its repeats: one line when another line follows, once an hour, and at the stop.
- **The public door.** `--replay-port N` opens a second door, read only, with no secret: `GET /replays` gives `{"replays": [...], "count", "keep_days", "sim_rules"}` (the last is the rules number of this server's build for the original's game, 9; a 187 match has 12 and its entry says `"mode": "187"`; the site's list page shows the files that this build plays (the original's game 5, 8 or 9; 187 6, 7, 10, 11 or 12) to watch and the others as older versions, [`REPLAYS.md`](REPLAYS.md#the-file)) (the newest 200 files that this build can read, each with the fields of the control interface's entry except `readable`; `count` is the number of such files, not of the 200), `GET /replays/<file>` gives the file of one of them, and everything else is 404 (any other method is 405 with `Allow: GET`, a request with a body is 400 for a plain `Content-Length`, 411 for a chunked one, 413 for one that is too large and 417 for an `Expect` that is not `100-continue`, and `GET /healthz` is answered by the server itself as on the control port). It is off unless the option is given (the program's own default). **`docker-compose.stack.yml` gives it, on port 4020 of the container (not published on the host): the list and the files of the stack's site are public, and so are the names of the players in them (Names, above).** `ANTS_REPLAY_PORT=0` switches it off; leave any other value alone, because the nginx of the site passes to 4020 only (a server that listens elsewhere looks like one without the door: the site answers 404).
- **Live matches.** The same door shows the matches that run now ([`REPLAYS.md`](REPLAYS.md#on-the-game-server), "Live"): `GET /live` and `GET /live/<id>`, the same rules as the rest (GET only, a query is 404, no secret, nothing from a request is ever made into a path). A room that records its match puts it on the *live board* (`live_board.hpp`, owned by the room manager next to the replay store) when the recording begins and takes it off when the recording becomes a file or is dropped; the board holds a pointer to the room's recorder and nothing else of the room, and the room takes the match off before the recorder goes (a closed room, a match that ended, the manager's destruction). So a room that does not record (`"record": false`, no store, a match brought back from a restart record) is not on it, and neither is a match played with Fog of War (a live view would show what the fog hides from its players; the site offers no fog, and the match is public when it is over like any other).
  - **The list**, `GET /live`, is `{"live": [...], "count", "sim_rules"}`: the matches whose recording has not failed, **from the moment their room starts them** (one that has run no turn yet, in the room's countdown, is on it with `turns` 0 and the page says it is starting), the newest start first, **50 at the most** (when there are more, the matches that have run 600 turns, 30 seconds, the length the store keeps, come before the younger ones, so that rooms that start and close at once cannot push the others off the list; `count` is the number of entries listed). An entry is `{"id", "map", "mode", "started", "turns", "seconds", "players"}`: `mode` is the match's game mode in the words of the list of games and the history (`"highest-score"` or `"187"`), `started` is seconds since 1970 UTC, `seconds` is the turns divided by 20, and `players` are the strings of the replay list ("Green (Ann)", "Green", "Red (Bot (Medium))": the names of "Names" above, public here too). The `id` is `<MAP>-<YYYYMMDD>-<HHMMSS>Z`, the stem of the map's file name (letters, digits and `_`, 24 at the most) and the UTC second in which the match began, with `-2`, `-3`, ... when two matches of a map began in one second; it holds nothing of the room (no code, name, address or key), and it is all a visitor can ask for.
  - **The snapshot**, `GET /live/<id>`, is 200 `application/octet-stream`: the match so far as an incomplete replay file (no `ENDS` chunk) with one more chunk, `live`, that holds the turns run when it was made ([`REPLAYS.md`](REPLAYS.md#the-file)), so that the code that plays a replay plays it up to that turn. **A match with two or more people in it is shown 30 seconds late** (`--live-delay-seconds`, 0 to 300, default 30; 0 shows every match as it is): the people are the seats that people hold, counted by the room once, from its seats, when it starts the match (computer players are not people; a name is never looked at; a person who leaves, a link that is cut and comes back, a room that is left with one person change nothing), and the snapshot is the match as it was 600 turns before, which `Recorder::snapshot(turns)` cuts: no order given and no turn run after that moment is in the bytes, whatever a request says, because the door takes no query and no header of a request into account and the bytes are made from the cut and from nothing else. A match of computer players, or of one person with computer players, is shown as it is (the snapshot of the last second). Private matches are listed and watched like any other, with the same rule. The answer carries the header `X-Ants-Live: now=<turns the match had run>; shown=<turns the bytes show>; delay=<turns the match is shown late>` (`shown` is `now` less the delay, not below 0), which the page says how late its picture is from; nginx passes it and caches it with the bytes. A match that has run no turn has a snapshot of the head and a `live` chunk of 0, so that a page can show the opening. The snapshot is made with `Recorder::snapshot`, which changes nothing in the recording. It is made again at most once a second for a match, however many watch it (the board keeps the bytes for as long as its clock stays in the second in which they were made), so a crowd costs one encode of at most 1 MiB a second for each match that is watched, and the same bytes go to all of them.
  - **When it is not there:** 404 with `{"error": "no such live match", "ended": false, "replay": ""}`. For 15 minutes after a match of at least 600 turns has ended (at most 256 matches are remembered, the oldest forgotten first) its id answers `"ended": true`, `"turns"` (the turns it ran) and `"replay"` is the name of the file that the store kept it as (`""` when it was not kept, or when the file is no longer in the store), so that a page that watched finds the replay. A match that ended before 600 turns (a room that was closed in its countdown or soon after, a Quit: it is never kept) is remembered for 2 minutes (at most 64, a count of their own, so that a stream of them forgets none of the others) and answers the same, with `"replay": ""` and the few turns it ran: the page says that it ended too soon to be kept. Every other failure of a `/live/...` request has the same body with `"ended": false`: a method other than GET, a query, an id of another shape (checked before any lookup), an id that is not on the board, a server without a replay store. `GET /live` itself answers 404 `{"error": "not found"}` for a method other than GET, a query, or a server without a replay store.
- **The match history.** The recordings go after `--replays-days`; what the matches came to stays, in the database ("The database", [`REPLAYS.md`](REPLAYS.md#the-match-history) says what a record holds, who won by the rule of each game mode, a draw, and the states of the recording). Three tables (migration 2): `history_matches` (one row for each match, with a column and an index for everything that the list filters or sorts by), `history_seats` (one row for each seat) and `history_markers` (the matches that an operator deleted while their recording is kept). The id is the recording's file name without `.antsrep`. Nothing is counted while a match is played: the feeder in `RoomManager::update` plays the recordings of the replay store once more, one at most every 250 ms and only while no room runs or loads a match and none is being restored, the newest first, and adds the record in one transaction. A recording takes 0.4 - 0.5 s to count for a match of 10 - 12 minutes (more for a longer one), so the gap after it is counted from the END of the work and is at least 250 ms and four times what the work took: the main thread is free most of the time; the recordings found when the server starts, up to the kept days of them, are the backfill, and a file the arena puts in the folder is found by the replay store's look every 30 seconds and counted like a room's own match. The same play counts the stats of the record (`details`, [`REPLAYS.md`](REPLAYS.md#the-match-history): 1 to 3.5 KB at most 5,000 bytes), and, when no new file is left, a backfill gives them to the records that were counted without (the rules are in `REPLAYS.md`). The same play finds where each lost ant stood, kept in `history_deaths` for a match counted here only (no backfill). The match's map is looked for in the maps folder and then in the community folder (`--community-maps`), the first that holds the name being the map's, like the lobby's list. A recording that cannot be counted (a map that is missing, a map of the same name that is another file, a file that does not play out) is left out and told in the log, the first ten by name and the rest in a summary; one of other simulation rules is not played and only counted in the summary. **Everything happens on the server's one main thread** (SQLite is built without mutexes); the work of a pass is one recording and one transaction. **A database that stops answering never takes the server down and never touches the match path:** the first error is logged once, the history is *unavailable* (the routes answer 503 with a clear body, and the feeder waits), it looks again every minute with a cheap read, and the log says once when it answers again; a record that the database refuses as such (a constraint) is told in the log and left out for this run, and the history stays available. **A list is time boxed and paid for:** a visitor's list is stopped by the database (`sqlite3_progress_handler`) after 15 ms of wall clock and answers 503 `that search is too heavy for the server: narrow it`; the operator's box is 100 ms. The public door has a *budget* on top, a token bucket of milliseconds of query time (100 ms in a burst, 50 ms earned for each second, each list paid for by the time it took); when it is empty a list with a query is a 503 `the match history is busy: try again in a moment` at once, without touching the database. **The list without any query is not held back by the budget** (it keeps the 15 ms box; it takes under a millisecond and the site's nginx keeps it for five seconds, serving the old copy while the server says 503), so a flood of heavy searches cannot lock the page's own list out; a match by its id is no list and has no budget either. So the public door can take about 5 % of the main thread whatever the number of visitors. A request's words never become SQL: a statement is made of fixed pieces and every value is bound; the search `q` escapes `%`, `_` and `\` so that a name is found as typed. An operator takes a match out with `DELETE /history/<id>` ("The control interface"); the server never deletes a record by itself. `GET /history` and `GET /history/<id>` are on the public door too, with the same rules as the rest (GET only; the list takes the query of its filters, every other query is 400 or 404; nothing from a request is ever made into a path), and the names in them are public for good. A writer outside the server (a tool run on the file while it runs) makes a write wait for the database's busy timeout (5 s) at the most; the history is written only while no match runs.
- **The site's nginx** (`docker/nginx.conf`) passes `/replays` (an exact location) and `/replays/<file>` (a prefix location) to that door, like `/busy`: GET only (405), no query (404), a file name of the wrong shape is 404 at once (the store decides which names exist), and nothing of the visitor's request but Host and Connection is passed on. The allowances count each visitor's address (behind a reverse proxy that ends TLS, name the proxy in `docker/trusted-proxies.conf`; the image's list names one at a private address, [below](SERVER.md#behind-a-reverse-proxy)): 20 requests a second for the list with a burst of 100, and 10 a second for the files with a burst of 20 (503 beyond), one zone each. The list is cached for five seconds for everybody (an entry of its own in the cache of `/stats`), so a crowd of visitors asks the server about once in five seconds; a file is asked of the server each time. Timeouts are 3 seconds to connect and 10 to read and send. The server's `Cache-Control: no-store` still goes to the browser. When the server has no such door, or is not there, the site answers `404` with `{"error": ...}`, never a 502 page. `/live` (an exact location) and `/live/<id>` (a prefix location) go the same way, with the same checks (an id of the wrong shape is 404 at once: `[A-Za-z0-9_]{1,24}-[0-9]{8}-[0-9]{6}Z(-[0-9]{1,4})?`) and the same timeouts and fallback, but with allowances of their own, so that a crowd that watches does not use up the downloads' (a page asks for the list every 5 seconds, at once when a room has gone from the list of games, and for the match it watches every 2 seconds): 20 requests a second for the list with a burst of 100 and 30 a second for the snapshots with a burst of 60 (503 beyond), one zone each. **Both are cached for one second** (the list in one entry, a snapshot in one entry for each id, in the cache of `/stats`, which holds 8 MB; only a 200 is kept, so made-up ids fill nothing; the header `X-Ants-Live` is kept with the bytes). An entry that is being renewed is served old, but not one when the server does not answer: a snapshot that is repeated for minutes looks like a match that goes on, and the 404 is the truth. So the server is asked about once a second for each match that is watched, and makes the snapshot (an encode of the file, 3 microseconds for each KB) once a second at the most. `/history` (an exact location) and `/history/<id>` (a prefix location) go the same way too, with allowances of their own (`ants_history`: 10 requests a second for a list without a query with a burst of 50; `ants_history_query`: **2 a second for a list with a query, a burst of 5**; `ants_history_deaths`: 2 a second for `/history/deaths`, a burst of 5, its answer kept 30 seconds; `ants_history_items`: 20 a second for single matches with a burst of 40; 503 beyond), a GET only (405), an id of the wrong shape or a query on a match 404 at once, and a list query of the characters that the filters are made of and 400 characters at the most (400 otherwise). The list without a query is cached for five seconds, in one entry for everybody, an old list served while a new one is fetched and when the server does not answer; a list with a query is cached for five seconds too, one entry for each distinct query, in a cache of its own (`ants_history`, 8 MB), so that made-up queries cannot fill the small cache of the numbers; a match is asked of the server every time. `/lobbies` ([above](SERVER.md#lobby-rooms)) goes the same way as `/live`, with the zone `ants_lobbies` (100 a second, burst 200, for each address as above) and a read timeout of 3 seconds; without the door it answers `404` with `{"error":"lobbies_off"}`.
- **In the log** the line of an ended room ends with `, kept as <file>` when its match was kept. The start prints where the replays are, for how long and how much, and (with the door) `public replays on port N` (the line names the routes, the live ones too).

### Matches of computer players

The server plays matches of its own, so that the site's list of live matches ([`REPLAYS.md`](REPLAYS.md#matches-of-computer-players)) is not empty when nobody is playing. A schedule starts them ([Schedules](#schedules)), and so does "Start now" on the admin page ([`MAP_SUBMISSIONS.md`](MAP_SUBMISSIONS.md#bot-matches-on-the-admin-page)); both ask for the same choices. A match is a room like the others whose seats are all bots (`RoomSpec::bots_only`; the control interface cannot make one, and such a room is no lobby and no public room and holds no seat). It is played at the normal speed, so it lasts as long as the map's own time limit (6 to 20 minutes on the maps of the lists: [`GAMEPLAY.md`](GAMEPLAY.md)) unless the rules end it sooner, and it is kept like any other match, in the same store under the same limits as the matches of people. The room's own limit is 25 minutes, or five more than the map's own when that is longer. A room without a person is not closed for "everybody left", a stopped server ends it, and a restart brings no record of it back (it holds no seat). It is no game that anybody played, so the site's statistics (`/stats`) do not count it, and `/busy` counts no match for it (a restart may interrupt it).

**The choices** (`BotMatchSpec` in `bot_match_spec.hpp`; the page's words are in brackets). Each is fixed or left to a draw, and the draws are made in an order that never changes (the map first, then the number of bots, each seat with its level, the seed, the teams, and the rules last), so the first match of a seed with every choice open is the same as it was before there were choices:
- **The map:** a map of the list of the rules that are dealt (`random:rotation`, the default: the lists below), one of the original's six (`random:original`: ISLANDS only in the original's game), one of the approved maps of the players (`random:players`), or **one named map of any that the server has**: the original's six, the whole library (`Community-Maps/`) and the approved maps of the players (`GET bot-options` lists them: the catalog, below). The name is the file's exact name and is looked up in the catalog, never on the disk as a path, so a name that the catalog does not have (another letter case, a path, a map of the test store) is `NoMap` (409 `no_map`). The random picks of the original's six and of the players' maps, and a draw from the players' maps, are as likely as any other **for a map that plays 30 minutes or less** (`kBotRandomMaxMinutes`): a map with a longer time limit (the community's longest play 33 to 60 minutes) is never drawn by those choices and is skipped with a line in the log like a map that cannot be played; a choice that names it plays it, **and so does a list of the rotation that an admin put it in** (below), and the page shows its minutes before the match starts (`GET bot-options` gives `minutes` and `random` for each map). A named map that a room cannot play now refuses the match; a named ISLANDS in 187 is refused before anything is drawn, and with the rules left to the coin it is dealt the original's game.
- **The rules:** the original's game, 187 ([`GAMEPLAY.md`](GAMEPLAY.md#187-a-game-type-of-the-remake)), or a fair coin for each match, drawn after the others and with no memory of the last match (so two or three of a kind in a row come up).
- **The bots:** two, three or four, or a draw of the number; they sit on seats chosen at random (every set of that many seats as likely as any other) and are numbered from 1 in the order of their seats.
- **Each bot's level:** Medium or Hard by a draw (the default, what the server's own matches always did), Easy, Medium or Hard by a draw, or one of the three.
- **The teams:** free for all, **a split** (three or four bots: "bots 1 and 2 against 3 and 4", "1 and 3 against 2 and 4", "1 and 4 against 2 and 3"; "bot 1 against 2 and 3", "2 against 1 and 3", "3 against 1 and 2"), or a draw over free for all and every way to make teams of the seats that play: with four bots one of the three ways to split them in two teams of two (on TINY, SMALL, TREASURE and ISLANDS, whose hills sit at the four corners of a rectangle: top against bottom, left against right or across the corners; MEDIUM's hills sit north, east, south and west and GAUNTLET's along a diagonal), with three bots any two of them as a team against the third, and with two bots only free for all (a team of both would be the whole match). The room has the teams as its own, so they are made before the first turn like a room's teams in the create block ([`NETWORK_PORT.md`](NETWORK_PORT.md#the-room-code-is-only-a-name-and-the-create-block-makes-the-room)), the replay's head has them, and the live view and the replay play them.

**The lists** (`bot_rotation_defaults()` in `bot_match_spec.cpp` is where the defaults are written; `BotRotationStore` in `bot_rotation.hpp` keeps what an admin changed): the original's game has nine maps, TINY, SMALL, MEDIUM, GAUNTLET, TREASURE, ISLANDS and three of the library, `POPcOrN.lvl`, `HELLRAISER.lvl` and `Bombz Away.lvl` (the community folder, `Community-Maps/`); 187 has six, TINY, SMALL, MEDIUM, GAUNTLET, TREASURE and `Fight Island.lvl`, an approved map of the players (Extended, 150 x 150, four hills). A server that nobody has edited draws from exactly these lists, in this order, so its draws and its seeds are what they always were. The match is dealt its rules first, then a map of that rules' list, each map as likely as any other. A 187 match is on ISLANDS only when an admin put it in the 187 list after the page's warning (its water joins no two hills by a walk, so nobody can be struck there: [`BOT_187.md`](BOT_187.md)); by name it is still refused. The approved map is found as a lobby finds one, in the store of the approved maps ([`MAP_SUBMISSIONS.md`](MAP_SUBMISSIONS.md)), so a server whose door for the submissions is off (`--submit-port` 0) has none, and neither has one that took the map down. A map that the server does not have or that a room cannot play (this engine cannot load it, it is over a limit of the online size, or it has no place for four seats) is skipped: the others of the list are as likely as before, the log says `bot match: the map NAME is skipped (reason)` once (and again if the map comes back and goes), the admin page shows it as skipped, and no match fails for it.

**Editing the lists** (the admin page, [`MAP_SUBMISSIONS.md`](MAP_SUBMISSIONS.md#bot-matches-on-the-admin-page); the routes `GET bot-rotation`, `POST bot-rotation` and `POST bot-rotation/reset`): a list is replaced whole, as the file names in the order of the draws. **A list has at least one map** (a list with none would never be drawn: 400 `empty`) **and at most 100** (`kBotRotationMax`: 400 `too_many`); every name is a file of the catalog and only once (400 `bad_map`); a map that the list does not have yet must be one that a room can play when it is saved (409 `no_map`, with the file and why), while one that the list has already stays when the server loses it or cannot play it (it is skipped, and the admin takes it out with Remove). A long map (over 30 minutes) and ISLANDS in 187 are accepted: the page asks once and the server trusts that the admin answered. A save that changes nothing writes nothing and is not logged; the others are in the admin log (`bot_rotation_changed`: the list, `+2 -1, 10 maps`) and "Back to the defaults" (`bot_rotation_reset`) deletes the list's row. The lists are in the table `bot_rotation` (migration 10, `rules` 'highest-score' or '187', `maps` the JSON text of the list, `updated_at`; no row is the defaults, nothing is written at the first start) and in memory; a server without a database keeps them in memory only, and a row that cannot be read is told once and its rules have the defaults. The first match after a start and the hourly schedule draw from the lists as they are then.

**The catalog** (`RoomManager::bot_map_options`): every map that the server has, for the page's list and for a named choice, each with its file, group (`original`, `library` or `players`), size, seats, minutes (the map's own time limit), places, whether a random pick may take it (`random`) and whether a room can play it now (`playable`, with a plain `reason` when it cannot). **Judging a map is done once per file** (`bot_match_map_refusal`): the file is loaded, validated and its time limit and places counted the first time, and the verdict is kept by the file's name, path, size and time (and, for an approved map, the hash of the approval); the lists and the draw of a map ask the disk for the file's size and time only. A map that was taken down is refused before the kept verdict is looked at, and one that was replaced or rewritten is judged again. **The one thread is never made to wait for the whole library:** a call loads and judges at most 48 files that have no kept verdict (`kBotCatalogLoads`) and lists the others with `checked` false (the answer's `checking` counts them, and the page asks again in two seconds), and the main loop judges four more files in each pass in which it starts no match (`BotMatches::update`, `kBotWarmLoadsPerPass`), so a server that has run for a minute has them all and the first visit of the page finds them kept. A verdict is dropped only for a name that the catalog does not list (a map that was taken down), so listing the whole store keeps all of them.

**The limits** keep the matches of computer players from taking the server from the people who play on it (every room runs on the server's one thread). Measured on the real server with the real bots (a development Mac, 10 cores): an idle server uses 1.3 % of its thread, and a match costs the thread about 2.4 ms for each second it plays on the maps of the rotation (1.2 to 1.7 ms in its first minutes, more as it ages and its ants multiply) and 2.4 to 8 ms with four Hard bots, TINY the least and ISLANDS the most; 192 matches at once took 35 to 38 % of the thread with the slowest pass at 69 ms, and a match is about 1.2 MB.
- **Eighty at once** (`kBotMatchesMax`), from the schedules and the admin page together: the measured number on a host that is taken as 2.5 times slower than the Mac, so that eighty are about half of its thread. A start while eighty go waits (a schedule's run does not wait: it is skipped, and its log line says so).
- **The busy guard** (`kBotBusyGate`, `LoopLoad` in `loop_load.hpp`): the main loop times each of its passes and a start waits while the loop was busy more than 40 % of the last ten seconds (`BotRefusal::Busy`). It is why the number above is safe for what the admin chooses: four Hard bots on ISLANDS cost three times the average match, the host may be slower than was assumed, and people's rooms are busy time too, and the guard slows the queue for each of them without a rule of its own. Matches that go are never stopped for it, and the matches already running get dearer as they age, so the gate is below the 50 % that the measurements allow. `GET bot-matches` says `busy` (a percent) and `gate`.
- **160 places together** (`kBotPlacesMax`): a match takes the places of its map as a match of people does (`OnlineLimits::weight`: a started 10,000 cells or 400 starting ants a place, so every shipped map one place, `Fight Island.lvl` three). They do not take places of the matches of people (a lobby's START never says "no place" because of them), and they are counted against these alone.
- **People first:** a start waits while the matches of people use more than three of every four places of the server (`--demo-rooms`; 36 of 48 in the stack). The matches that go are not stopped. A server with no places for people (`--demo-rooms 0`) never holds a start back for this.
- **One a second:** matches that are made one after another start a second apart (`RoomSpec::start_hold_ms`), so that setting up their engines is spread over the passes of the main loop. A request starts eight matches before it answers (`kBotStartsNow`) and the loop makes the rest of a batch at most two a pass (`kBotStartsPerPass`), so that a batch of thousands never holds the thread.
- **The store's room is not a limit any more.** The hour's budget of recordings of computer players (30 an hour, [above](#replays)) no longer refuses a start: a match is PLAYED whatever the budget, and it is KEPT as a replay only while a slot is reserved for it (`RoomSpec::keep_replay`, decided when the match starts: `ReplayStore::bot_saves_left()` more than the kept matches that go, `RoomManager::bot_kept_count()`). A match without a slot is recorded in memory (the live list needs the recording) and writes no file at its end; it never pushes a person's recording out. A match that is stopped within its first 30 seconds is not kept and gives its slot back.
- A start is refused when the server keeps no replays (a match that nobody could look at again).

**The queue.** A batch is one count (1 to 10,000 from the admin page and the chat's `/bots`, `kBotCountMax`; 1 to 8 from a schedule, `kBotScheduleCountMax`), the choices above and an optional spacing. The request starts what the limits allow now, at most eight (`kBotStartsNow`), and keeps the rest as ONE queue (`BotMatches::Queue`: the choices, how many starts remain, how many were made, ended and kept as replays, the spacing, who started it): never a refusal for a limit, a start that a limit holds back waits and is not dropped. At most 10,000 starts wait in all the queues together (`kBotQueueMax`) and at most 50 queues exist (`kBotBatchesMax`): a batch that would pass either is refused whole, 409 `queue_full`, with `waiting`, `asked` and `max`. A schedule's batch never queues what does not fit (that run is skipped), except the starts that its spacing puts in a queue. A queue is listed by `GET bot-matches` (`queues`: `id` (`q1`, ...: never a room's code), `name`, `what`, `total`, `remaining`, `started`, `finished` (done), `running`, `kept`, `every_s`, `at` (the second of the wall clock at which the next start of a batch with a spacing is, 0 for a batch without one), `held` and, then, `why` (`cap`, `places`, `people` or `busy`), and `by` or `schedule`); its row stays while its matches go. `GET bot-matches/summary` gives the counters only (`at_once`, `running`, `waiting`, `busy`, `gate`, and the same rows without `what`, `name` and `at`, with `next_in`): what the chat's `/bots status` asks, small whatever the number of matches. `POST bot-matches/<queue id>/stop` cancels the rest of one queue (`{"stopped": 0, "dropped": K}`; the matches that go finish), `POST bot-matches/stop-all` ends the matches and cancels every queue (`stopped`, `dropped`). The loop looks at the queues every pass (`BotMatches::release_queues`): a start of a batch with a spacing is made when its time has come, one without a spacing whenever there is room; one that is held makes the loop ask again once a second; a start that can never be made (its map was taken down, the rules refuse it) ends its queue with one line in the log (`bot queue q3: the rest was dropped (...)`). The matches that ended are counted as done once a second (`BotMatches::sync_started`). **A queue does not survive a restart** (a schedule is the durable tool). What a match is dealt is drawn when it starts, not when the batch was made: a list of the rotation that changes meanwhile is the list of the later match. The admin log has one line for a batch (`bot_started`, the whole of it, "1000 matches", with the spacing in its words) and one for each queue that was cancelled by hand (`bot_waiting_stopped`, "648 starts cancelled").

**Start one every X minutes** (`every_s` of a batch; "Start one every [X] minutes" on the admin page and `every` of the chat's `/bots`): with a spacing the first match starts now and each of the others `every_s` seconds after the one before it (counted from when that one really started: a start that a limit held back moves the ones after it): 0 is as fast as there is room (the default), up to 7,200 (two hours) in steps of 30 seconds (400 `bad_spacing` for another number or a text), and a spacing of one match is nothing. The batch's queue holds the rest (`at` says when the next start is, the admin page says "starts in 6 min"). A schedule's `what` may carry a spacing too (the API takes it, its form does not): its run starts its first match when it runs and lets the others wait in a queue, and the log line says so (`started 1 of 3, 2 waiting for their time`). The queue goes on while the operator's off switch holds the schedules (`--bot-match-every-min 0`): the switch is for the schedules.

**How long a batch takes.** By Little's law a match of the rotation lasts about 9.5 minutes on average, so eighty at once make about 500 matches an hour: a batch of 1,000 takes about two hours and one of 10,000 about twenty. Of those only the hour's slots are kept as replays (30 an hour, so about 60 of the 1,000), and only a kept match becomes a row of the match history (about 4 KiB), so the history grows by the kept ones, not by the number played. The 50 newest running matches are on the live list (`kMaxListed`) and have a Watch link; the others play without one.
**What they add to the match history.** The feeder counts the recordings of the store, the matches of computer players too: a record of a bot match took about 4 KiB of the database (the details and the map of deaths included) and 60 ms of the one thread, paced like any other. The database keeps its records for good, so the growth is bounded by the budget above: at its ceiling of 30 matches an hour (720 a day) it is about 3 MB a day, a gibibyte a year; the old timer's one match an hour is 35 MB a year and eight an hour 280 MB. Nothing prunes the history of bot matches yet: if that growth matters, deleting the records of matches without a person is a decision for the maintainer.

**Stop.** The admin page ends one match or all of them (`RoomManager::stop_bot_match`, `stop_bot_matches`: the room is closed, and a match that ran 30 seconds is kept as a replay up to where it stopped, as the room of an operator is). The rest of a queue is cancelled the same way (by the queue's name), and Stop all cancels every queue too. Only a match of computer players can be stopped this way, never a room of people.

The log says what a schedule did (`bot schedule 3: started 2 of 4 (8 matches of computer players go already)`: by the schedule's number, never its name) and a map that is skipped; the admin page's own actions are in the admin log ([`MAP_SUBMISSIONS.md`](MAP_SUBMISSIONS.md#bot-matches-on-the-admin-page)).

### Schedules

A schedule starts matches by itself: **when** (every N minutes, or at times of the day by the Pacific clock), **what** (the choices above, how many matches each time, 1 to 8, and an optional spacing, [above](#matches-of-computer-players)) and whether it is **on**. At most 20 schedules, each with a name of 1 to 40 characters that an admin typed (cleaned: no control or direction characters; data on every page that shows it) and at most 12 times of the day. They are rows of the table `bot_schedules` (migration 9: `src/ants_server/db_schema.cpp`) and in memory (`BotScheduleStore`); a restart reads the table back, and a server without a database keeps them in memory only. The code is `bot_schedules.hpp` and `bot_matches.hpp`; the main loop asks once a pass whether a schedule is due (`BotMatches::update`: no thread of its own).
- **The first schedule.** `--bot-match-every-min N` (`ANTS_BOT_MATCH_EVERY_MIN` in the stack) makes "Hourly rotation" (N = 60; "Rotation, every N minutes" otherwise), tagged the default on the page: one match every N minutes, every choice open (the match that the server's old timer made), the first a minute after the server starts. A server with a database makes it once, when the table has no rows and the database has never made it (a row of `meta`), so a schedule that an admin deleted is not made again; a server without one makes it at every start. The option and the variable only start the list: they stay for two releases and are then removed. **`0` is the off switch** (`ANTS_BOT_MATCH_EVERY_MIN=0`, `--bot-match-every-min 0`): no schedule starts a match on this server, whatever the database holds; the admin page still lists and edits them and says that they are switched off, no row promises a next start, and Start now (not a schedule) works. Left out, the option does nothing and the schedules run as the admin page has them.
- **Every N minutes** (5 to 1440) counts from the schedule's last start, as the old timer did. A schedule that is saved or turned on counts from its last start (from now when it never started) and never starts inside the request that saved it: its first run is a minute away at the soonest. After a restart the next run of a schedule that is on is the later of the time that was kept and a minute from now, so a server that was down does not start a match the moment it is up, and a run that was due meanwhile is not made up.
- **At times of the day** ("18:30", every day, no weekdays) runs at the next of the times by the Pacific clock. The server's image holds no time zone data, so the clock is written by hand (`pacific_time.hpp`): the United States rule since 2007, daylight time from 02:00 on the second Sunday of March to 02:00 on the first Sunday of November, checked against the zone database for 2026 to 2028. The two days of the change are settled once: a time inside the hour that does not happen (spring forward, 02:00 to 03:00) runs at 03:00, and a time inside the hour that happens twice (fall back, 01:00 to 02:00) runs at the first, once.
- **Times that cannot be true are mended.** When the rows are read, and once a minute, a last start more than an hour after now was never made and is ignored, and a next run later than one period from now (every N minutes) or later than the next time of the list (times of the day) is brought back to it, so that a clock that was far ahead once or a damaged row cannot keep a schedule away for good (`bot_schedule_repair_clock`).
- **Numbers and double clicks.** The number of a schedule is never used again in a run of the server, with a database or without one. A schedule saved a second time within ten seconds with every choice the same as the newest one's (a double click on Save, which the page also guards) is that schedule, not another, and a change that changes nothing writes nothing, keeps the next run and is not logged.
- **A run** starts the schedule's matches one after another, as many as fit. A run that a limit holds back (the eighty, the 160 places, the people's share, the busy guard) is **skipped, not queued**: the next run is the next one by the rule above. A run that comes late (a loaded server, or a clock that jumped) is made once and never repeated for the time that passed.
