# Network Port

Status: **the core, the room, a native TCP transport, the application integration and host migration are done and tested (v0.0.43 command layer and state hash, v0.0.44 protocol, sequencer, lock-step
runner and sessions, v0.0.45 room and start barrier and framed TCP, v0.0.46 host / join in the game, v0.0.47 host migration).** Open: NAT traversal is no longer planned inside the game (an external launcher or lobby provides the path between
players and starts the game with the addresses on its command line; raw TCP works on a LAN, a VPN or with a forwarded port, and v0.0.78 adds the discovery of rooms on the local network); a single-player game applies its commands at once.

## What the original does

See `docs/GAME_REVERSE_ENGINEERING.md` 5.46: an external lobby starts the exe with the roster on its command line, WinSock 1.1 blocking TCP in a full mesh, and every machine simulates only its own team
and broadcasts the results (the game is not lock-step). Its lobby flow, texts and rules are kept; its transport, trust model and sync model are not.

## The remake's design

* **Sync model: deterministic lock-step of player commands** (the Age of Empires / StarCraft / Warcraft III lineage). Every machine simulates everything with the same shared PRNG; only intent crosses the wire.
  A turn is one tick (50 ms since protocol 8, v0.0.94; before it, two ticks of 100 ms) and a command is applied in the first turn that the host seals after the command reaches it; every
  machine runs a turn after a jitter buffer of one to four turns (50 - 200 ms, one on a steady link, see "What the player feels"), so a click reaches its effect about a round trip + 25 ms + 50 ms later; the local
  player gets immediate click feedback (voice, marker, pedestal flash) from a prediction on its own state. The commands of a turn are applied in canonical order (by issuer, stable). Every 20 ticks (every 20 turns,
  one second) every peer hashes the gameplay state; a mismatch freezes the match and dumps the per-subsystem hashes.
* **Commands** (`include/ants_sim/command.hpp`, milestone 1): `GroupMove`, `GroupSpecial`, `GroupAttack`, `Stop`, `Hatch`, `AllianceInvite`, `AllianceAccept`, `AllianceDeny`, `AllianceWithdraw`, `AllianceBreak`
  (`Leave` and the drop-out stamped by the sequencer come with milestone 3). `SimulationEngine::apply_command` is the only way a player changes the simulation; the HUD sends its commands through a
  `CommandSink` (`HUD::set_command_sink`; null means the engine itself).

  | field | bytes | meaning |
  |---|---|---|
  | type | 1 | `CommandType` (1 .. 10) |
  | issuer | 1 | the player; stamped by the transport, never trusted from a payload |
  | other_player | 1 | alliance commands: the other side |
  | tile_x, tile_y | 2 + 2 | group orders: the clicked tile (little endian, signed) |
  | count | 1 | ants: 1 .. 32 for group orders and Stop, 0 for every other type |
  | ants | 4 * count | ant ids (little endian), in selection order |

  Validation (`command_system.cpp`): the issuer is a player; a group order keeps only the issuer's own ants (each once, order kept); the tile is on the map; an answer to an invitation needs that invitation;
  nothing changes once the match is over. Rejections are reported (`CommandResult::Status`), never trusted, never fatal.
* **Topology and NAT traversal** (milestone 2; the WebRTC part of this plan was dropped on 2026-09-30, see milestone 5: internet play comes from outside the game, browsers reach a dedicated server over WebSocket): a star with the room owner as sequencer (with a mesh of links behind it for host migration, below); the plan was one WebRTC data channel per player (ICE with STUN and a TURN relay as the fallback, DTLS-encrypted, reliable ordered
  channel for commands and one for keep-alive and hashes) so the same protocol runs natively (libdatachannel) and in the browser (built-in RTCPeerConnection); a small WebSocket signaling service for rooms
  and the SDP / ICE hand-shake. TURN credentials are issued per session (the standard TURN REST scheme); the shared secret, host names and STUN / TURN URLs are configuration, never committed.
* **Kept from the original**: the lobby flow and strings (latency thumbs, host picks map and fog and presses START, LOADED and READY barriers, "Get ready" for at least 5 s), a drop-out timeout (60 s in
  the original), kick, quit, alliances, chat (100 characters, team-only filter), no late join, no pause, no bots in the simulation (the alliance auto-accept of the old simulation is removed; bots, when they come, are virtual clients that send ordinary commands: `docs/BOTS.md`), and **the match goes on when
  the host leaves**: the original is a mesh in which nobody is special once the match runs, so the remake moves the sequencer role to another machine (host migration, below).

## Host migration (milestone 4b, shipped in v0.0.47)

In the original the machine that picked the map can drop out while the others play on. The remake keeps that: the host is a role (the sequencer), not the place where the state lives, because every machine
already runs the whole simulation and holds the same state. What moves is sealing turns, the reference hash, the chat relay and the drop decisions. Code: `include/ants_net/session.hpp` /
`src/ants_net/session.cpp` (`ClientSession` election state machine, `HostSession::resume`, `promote_to_host`), `protocol.hpp` (the wire messages and the protocol version, 9 since v0.0.95; the rule that moves it is under "Protocol version 9"), `netgame.cpp` (the TCP mesh and the events).

1. **Peer links.** While the map loads every guest connects to the guests above its own seat (one link per pair; the ones below connect to it). A guest listens on an ephemeral port that it announces in
   `Hello.listen_port`; the host passes what it saw (the guest's address and that port) to everybody in `Start.endpoints`. An inbound link starts with `PeerHello{seat}` and is accepted only from a lower seat of the
   roster, once per seat, and only from the address the host reported for that seat; everything else is closed. The links carry a ping every second (`peer_silence_ms` = 5 s tells "alive") and, when the host goes,
   the election. The sessions only need a `Connection*` per seat (`ClientSession::set_peer`), so any other transport would plug in the same way (the WebRTC mesh that was planned here was dropped, see milestone 5).
2. **Turn log.** Every machine keeps the last 600 turns (30 s) it received (`LockstepRunner::logged_turn`; the host those it sealed), commands included.
3. **Trigger.** The host link is closed (everything the host sent before is read first) or the host has been silent for `host_silence_ms` (10 s; the host answers a guest's ping every second and seals a turn
   every 50 ms, so silence means gone). A guest that receives a proposal while it has not noticed yet re-reads its host link first, and believes "the host is alive" only if it heard the host within
   `host_alive_ms` (2 s). After `NetGame::freeze()` (the match is over) a leaving host is no reason to elect anybody.
4. **Election** (bully algorithm with epochs; `Propose`, `Accept`, `Refuse`, `Resume`, `Request`, `PeerHello`). The candidate is the lowest seat that a survivor still sees alive on its peer links; it proposes
   `epoch + 1` to every live peer. A peer accepts the proposal of the lowest seat it sees alive and only one candidate per election (a second one is refused with the name of the first); a candidate that
   receives "a lower seat lives" waits for that seat's proposal (and asks anyway after `elect_timeout_ms`); one that receives "the host lives" (the peer had not noticed the loss) asks again after a second and
   gives up after three such refusals (`Lost`: it is this machine that lost the host); a peer that does not answer within `accept_timeout_ms` (3 s) is given up. Every message carries the epoch; a message of
   another election is ignored, a link speaks only for its own seat, and an election that takes longer than `election_limit_ms` (30 s) ends as `Lost`.
5. **Resync.** A survivor stops reading its old host at the moment the election begins, so the receive position it reports in `Accept` (`next_receive`, `next_execute`) is the history it offers. The candidate takes
   `resume_turn` = the highest position among the accepts and its own, fetching the turns it lacks from the peer that has them (`Request`; a source that dies is given up and the plan is made again without it),
   becomes the host (`promote_to_host`: the same runner, so the log and the presentation hooks stay), sends every follower `Resume{epoch, host, resume_turn}` followed by the turns it lacks, and seals
   `resume_turn` next. The first turn holds the `Drop` of the old host and of every seat of the roster that did not follow (a seat that already dropped stays as it is), so every machine drops them at the
   same tick. Nobody can be ahead of `resume_turn` by construction, so nobody diverges; followers adopt the link to the new host as their host link (`Resume` is honoured only from the candidate they accepted).
6. **What is lost.** Commands given in the last ~300 ms that were not yet in a sealed turn (the player gives the order again; while there is no host `NetGame::submit` reports the command as ignored, so no
   acknowledgement sounds). The game stalls for the detection time plus a round trip (the overlay says "The host left. Choosing a new host..."), then goes on and says "Bob is the host now." for five seconds.
   A second failure during the election is handled by the same rule; a match with one machine left goes on for it alone (as in the original, where the last team standing plays on).
7. **Limits.** A host that dies in the first second of the match, before the links between guests are made, can split the match (each guest then plays on alone). Two guests that cannot reach each other while both
   reach the host, or a network partition, split the match into groups that each play on consistently (as in the original's mesh). A guest that is on the same machine as the host is reachable for other guests
   only under the address the host saw (127.0.0.1 in that case); NAT traversal is not part of the game (see milestone 5).
8. **Tests** (`tests/test_net/test_lockstep.cpp` N2.22 - N2.36 on the simulated network, `test_netgame.cpp` N3.7 - N3.12 and `test_network_app.cpp` N5.4, N5.6 over real sockets): the host dying abruptly and
   silently, the host and the next seat dying together, the successor dying while it is being accepted, guests that are behind or ahead of the new host, the only holder of the missing turns dying while they are
   fetched, a silent guest, a partitioned old host that keeps playing alone, a guest whose own link broke while the host lives for the others (it is lost, nobody takes over), chat / leave / commands through the new
   host, three host changes in a row, forged, stale and garbage messages between guests (20000 of them), strangers on a guest's port, the runner's turn log, the sequencer's resume; the states of all survivors are equal
   to the end, twice with the same result.

## The lock-step core (`src/ants_net`, v0.0.44)

Everything below is pure logic over a `Connection` interface (message oriented, reliable, ordered, non-blocking; WebRTC data channels, WebSocket, framed TCP and the tests' in-memory link all fit) and is
driven from the game's main loop with a monotonic millisecond clock: no threads, no blocking calls.

* **Messages** (`protocol.hpp`, one datagram each: `u8 type`, payload, little endian; every decoder checks every length, count and range and rejects trailing bytes): `Hello` (version, name), `Welcome`
  (slot), `Reject`, `Command` (client -> host), `Turn` (turn number and the sealed commands in canonical order), `TurnAck`, `Hash` (state hash after a turn, all seven parts), `Desync`, `Chat` (100 printable
  characters), `Ping` / `Pong`, since protocol 7 `StartRequest` (type 24: the leader of a server's room asks it to start the match now) and since protocol 8 `Lag` (type 25, the last: a dedicated server tells a room that a player is far behind). Messages are limited to 64 KB and turns to 512 commands.
* **Sequencer** (`sequencer.hpp`, host only): stamps the issuer from the connection (a client cannot speak for another player), refuses inactive slots and floods (64 commands per peer and turn), seals a
  turn every 50 ms with the queued commands in canonical order (by issuer, each issuer's commands in submission order), compares every peer's hash report with the host's own and names the peer and the
  subsystem that differs, and, for a host with a seat, stops sealing while a peer's acknowledgement is more than 60 turns (3 s) behind (flow control; `laggard()` says who). A host without a seat never stops: "Who waits for whom" below.
* **Runner** (`lockstep.hpp`, every machine): queues the turns (in order, no gaps), waits until the jitter buffer's turns are in hand (`target + 1` queued: a turn runs `target` turns after it arrived; `jitter.hpp` decides
  the target, 1 to 4), then runs a turn, one tick, every 50 ms of real time; it waits at a missing turn without owing the wait, collects its buffer again after a stall, and runs faster, up to four times, while more is queued
  than the buffer asks for. Every 20th turn it returns the state hash. What it does after a stall, a bunch of turns or a slow frame is in "What the player feels" below.
* **Sessions** (`session.hpp`): `HostSession` (sequencer, broadcast of turns, its own runner, relay of chat, violation counting: a client that sends garbage, host-only messages, oversized messages or floods is
  thrown out after 8 violations, dropping a client reports it once through `on_player_left`, a desync or `freeze()` stops sealing; for a host without a seat the lag policy) and `ClientSession` (sends commands, executes turns, acknowledges
  (once per frame, for the last turn it ran), reports hashes, pings for the round trip, sees a `Desync` and the server's `Lag` notices).
* **Tests** (`tests/test_net/test_lockstep.cpp`, 49 tests): every message round-trips and rejects any missing or extra byte, out-of-range fields, 400000 random and mutated messages; the loopback link is
  ordered and respects latency; sequencer stamping, canonical order, flood limit, flow control, hash comparison; the runner's buffering, tick cadence, stall and catch-up; whole matches of a host and three
  clients over 60 ms links with jitter for 90 s and over 40 / 150 / 300 ms links, all bit-identical at the end, ticks steady at 20 Hz; a client cannot issue commands as another player; a corrupted client is
  named within a second with the differing subsystem and the match freezes; a frozen peer stalls the game of a host with a seat after 3 s and it goes on when the peer catches up; a cut connection reports the drop-out once; a
  hostile client is thrown out without anybody else noticing; chat is relayed with the sender stamped by the connection; a server's room that does not wait for a client that stops for 5 s, tells the others, lets it catch
  up at up to 4x and ends with every state hash equal (S2.7), the numbers of the lag policy (S2.8) and a round trip of 200 - 400 ms that is never called lag (S2.9); and what an honest client sends with turns of 50 ms against the flood budget (N2.39: the busiest second held 27 messages in steady play, 48 for a person who gives 20 orders a second, 89 while a window catches up at 4x, and an uplink that was stuck for 25 s delivered 637 at once; the budget is 1000 and a burst of 1000).

## The room and the start barrier (`lobby.hpp`, v0.0.45)

The original has no host / join interface (an external lobby starts every machine with its roster on the command line). Its rules are kept, the flow is new: a client sends `Hello` (protocol version,
name) and gets `Welcome` (its seat) or `Reject` (`Full`, `VersionMismatch`, `MatchRunning`, `Kicked`, `BadRequest`); the host broadcasts `Room` (seats and names, map file name, fog option, and the
receiver's own seat) on every change. `HostLobby::start` sends `Start` (seed, map file name and FNV-1a 64 hash of the file, fog, roster mask, names); every machine loads the map and answers `Loaded`
(a machine whose file differs answers not-ok); when the host and every guest are loaded the host sends `Begin` and hands the connections (seat -> connection) to the `HostSession`. A load failure,
a leaver, a host cancel or a 60 s load timeout sends `Cancel` and returns to the room; a guest that says nothing for 10 s, sends garbage first, or breaks the rules 8 times is closed. Map names travel
only as plain names of the maps folder (since protocol 6 any printable ASCII character except `/ \ : * ? " < > |`, up to 64 characters, ending in `.lvl`; see "Protocol 6" below). Seats go to guests in the order their `Hello` reaches the host, unless the guest asks for one: `Hello` carries `want_seat` (protocol 5, `--seat N`; 255 = any), a free seat that was asked for is given, a taken one (or the host's own) gives the first free seat. `decode` of a `Hello` is exact (this protocol's layout, so decode -> encode round-trips and the fuzz test holds); `decode_hello_prefix` reads only the version and the name, which lead every version's layout, so that a guest of another protocol gets `VersionMismatch` instead of `BadRequest`. No late join
(as the original); the host leaving is handled by host migration (below).

**Connection quality (v0.0.46, protocol version 2).** The host pings every seated guest once a second (`Ping` / `Pong` with the send time echoed, up to eight pings in flight, so a link slower than
the interval is still measured) and puts the measured round trip of every seat in the `Room` message (`RoomMsg::Slot::rtt_ms`, 0 for the host, `0xFFFF` before the first answer). `link_quality()` turns it
into the thumb of the setup screen with the original's thresholds (`Ants.exe` 0x1013289): below 1200 ms good (`netgood`), below 1800 ms ok (`netok`), more bad (`netbad`), not measured `netunk`, the question
mark. The host re-broadcasts the room only when a seat's tier changes. START needs a second player and every guest measured ("Press START when all players' thumbs have appeared"), which `NetGame::can_start()`
checks.

## TCP for LAN and development (`tcp.hpp`, native builds, v0.0.45)

`TcpConnection` / `TcpListener`: non-blocking sockets (POSIX and Winsock), `u32` length + payload framing, a length above 64 KB fails the connection without allocating for it, a sender whose peer never
reads is cut off when its queue passes 512 KB, an orderly close still delivers what was sent before it, `TCP_NODELAY`, and **the messages that wait to be polled are bounded** (4096 messages and 1 MiB, as in the
WebSocket connection: at half of either the socket is not read until the game has taken what is there, so the bytes stay in the kernel and TCP holds a flooding sender back; v0.0.93, see "Flood control"). It implements the same `Connection` interface as the in-memory link, so the sessions,
lobby and tests run unchanged on real sockets (`tests/test_net/test_tcp.cpp`: message boundaries and order for every size up to the limit, 20000 small messages, hostile length prefixes, truncated frames, dead
ports, the never-reading peer, a 40 s match of a host and three clients over real sockets, the room from `Hello` to `Begin`, and a burst of 48 connections that come while nobody accepts, all of which wait for the server when it looks: the listener holds 64, `kListenBacklog`; with 8 a macOS listener kept 8 and the other 40 never came: N3.8; the WebSocket listener holds 64 too, it was 32: `test_ws` W1.23).

## LAN discovery (`lan.hpp`, native builds, v0.0.78)

A room on a local network announces itself so that nobody has to type an address. **Datagram** (UDP, port 4001 like the game's TCP, little endian, at most 131 bytes; the limit is 160): `"ANTL"`, format 1, type (1 announce, 2 goodbye), protocol
version u16, room id u32 (drawn at random when the room opens), the room's TCP port u16, players u8, seats u8, then three strings (u8 length + bytes): the game's version text, the host's name, the map file. The decoder is strict because it
reads the open network: exact length, magic, known type, `1 <= players <= seats <= 8`, a port, printable ASCII only, every string within its limit; whatever does not fit is ignored (20,000 fuzzed datagrams in `test_lan`).
**Announcer** (the host, only while the room is open in the room phase, never during a match: no late join): one datagram per destination each second and at once when the room changes, to the directed broadcast address of every IPv4
interface that is up (`getifaddrs`, `SIO_GET_INTERFACE_LIST` on Windows), to the limited broadcast 255.255.255.255 and to this machine (a second copy of the game, tests); a goodbye (twice) when the match starts, the host leaves or the room
closes; a host that vanishes says nothing and is dropped after 3.5 s. **Browser** (the guest's side, `LanBrowser`): binds UDP 4001 with address and port reuse (two copies on one machine share it), keeps at most 64 rooms, tells rooms apart by
room id (a room heard on its LAN address and on its loopback is listed at the LAN address), marks rooms of another protocol version, sorts by host name. A guest connects over TCP to the address the datagram came from and the port it
names; the usual join checks (protocol version, full room, map hash at the start) still decide. `NetGame::set_discovery(port)` (0 turns it off; `--lan-port N`, `--no-lan`), `ants --lan-list [seconds]` prints what is on offer.
Firewalls: the host needs UDP and TCP 4001 open; macOS may ask once for permission to use the local network. An in-game screen for hosting and joining comes next (implementation plan, section 38).

## The application (`netgame.hpp`, `Application`, v0.0.46)

* **`NetGame`** (`src/ants_net/netgame.cpp`, no SDL, no threads): owns the listener and the connections and runs the room and then the session behind one small interface: `host(port, name)` /
  `join(address, port, name)` / `leave()`, `update(now_ms)` every frame, `take_events()` (`RoomChanged`, `StartRequested`, `Begun`, `Cancelled`, `PlayerLeft`, `HostLeft`, `Desync`, `Failed`, `HostChanged`), the host's
  `set_map` / `set_fog` / `start_match(seed, map_hash)`, `report_loaded(ok)`, and in the match `submit()` (the HUD's `CommandSink`), `chat()`, `freeze()`, `stalled_ms()`, `laggard()`, `sub_tick_ms()`.
  `NetGame::status_text()` is the setup screen's status line, in the original's words (`docs/GAME_REVERSE_ENGINEERING.md` 5.48). A WebAssembly build has no TCP, so `host()` / `join()` return false there.
* **Commands from the HUD**: `NetGame::submit` stamps the local seat, predicts the acknowledging ant with `SimulationEngine::predict_order_ack` (the click's voice and pedestal feedback are immediate although the
  order is applied a few turns later; the prediction equals the engine's answer for 2000 of 2000 random orders in `test_commands` N1.21) and queues the command for the next turn.
* **The setup screen is the room** (`MapSelectScreen::RoomView`): the host (and the local screen) show a row per seat (portrait in the seat's colour, name, thumb) and the map / fog / START controls; **a guest has the original's other
  screen** (`nh_start`: no Up / Down / START / Fog buttons, a fixed "Fog of War?" box that shows the host's choice, the host's map name, keys Q / X only), its own row first (then the host, then the others), LEAVE for everybody.
* **The match**: the ticks come from the `LockstepRunner` (`Application::pump_network` runs `NetGame::update`, every tick calls `Application::post_tick`: HUD, events, audio, the end of the match); the frame is
  drawn at the runner's sub-tick position; a machine that waits for a turn says so after one second (remake text) and a desync stops the match and says so; which line the playfield shows is decided by `net_overlay_line` (`ants_app/net_overlay.hpp`: desync, election, waiting, "Catching up...", "Bob is lagging (12 s behind)", the match notice, in that order; tested in `test_hud_layout`). There is no pause and no team switching.
* **The room's map**: no map is named in the network layer: a room's map name is empty until its host chooses one (the application chooses the first map of the setup screen's list at once), a Room message may carry the empty name, a Start may not, and START needs a chosen map (v0.0.64).
* **Roster and drop-out**: `Start` carries the roster mask; a team without a player has no hill (`LevelData::for_roster` also removes its hill art for the renderer), no start markers and no eggs. A player that
  leaves, is thrown out or is silent for 60 s is dropped by a host-only `Drop` command in the next turn (`SimulationEngine::drop_player`, `FUN_0100d03b`), so every machine drops the team at the same tick.
  **The end of the match (v0.0.62, protocol version 4)**: a drop that leaves one team, or an allied pair, decides the match at once (the original's win test, 0x100d172); CHECKGO ends it when nobody has an egg,
  a hatch or an ant left, or when the live teams are one alliance whose combined score is strictly the best. The quit dialog's Yes is the player command `Quit` (wire type 11, `Drop` is 12 now): with
  exactly one other side left it ends the match for everybody and names the quitter (its row goes last on every results screen), otherwise it is a drop-out (`FUN_0101453f`, docs 5.47).
* **Names**: `--name`, the original's `-N<team><name>` and `--team-name` reach the room (the `Hello`), the HUD's score labels, the results rows, the chat headers and the simulation's alliance and drop-out
  texts. A network game says "Player" unless `--name` is given: it never sends the user and machine name by default.
* **Command line**: `--host [port]`, `--join host[:port]`, `--port`, `--name`, `-N<team><name>`, `--team-name <team> <name>`, `-pnum:<team>` (or `-pnum=<team>`), `--loopback` (accept only this machine); port 4001 by default (the original's).
* **Group order acknowledgement**: the ant that answers a group order is now decided by GoTo's real result (`issue_order` returns it), as in the original (`0x10289b2 .. 0x10289c0`); before, a stale path request
  of a refused order could still make an ant answer.
* **Teaming (v0.0.50)**: the three modal dialogs of the original (the invitation question, the proposer's waiting dialog and the confirmation before a team is broken, `docs/GAME_REVERSE_ENGINEERING.md` 5.42)
  are driven by the shared simulation's state, not by an event: `WorldState::pending_invite_from[invitee]` says who has an offer for whom, so every machine that holds the invitee or the proposer shows the dialog
  at the same tick and a dialog cannot be missed. The answers are commands of the answering seat (`AllianceAccept / Deny / Withdraw / Break`, and `AllianceInvite` or the attack order after the confirmation) that
  travel through the turns like every other order; while an answer is on its way the question does not come back. A team message (`Chat` with the team flag) goes to everybody through the host and every machine
  shows it only when it is the sender or an ally of the sender by its own alliance table (`HUD::receive_chat_message`), in the sender's team colour. `drop_player` also clears the offers to and from the dropped team.
  Tests: `N5.9` / `N5.10` of `test_network_app` (an offer from another machine reaches the application as the question, Accept makes the team on all three machines, a team message reaches only the ally, a
  refusal closes the waiting dialog, Withdraw takes the offer back everywhere, equal state hashes at the end).
* **Limits of this release**: no NAT traversal (raw TCP: a LAN, a VPN or a forwarded port), a machine returns to the local setup screen when a network match ends, a player has one pending team offer at a time
  (the original queues several). Since v0.0.47 the host may leave and the match goes on (see Host migration: `HostChanged` reports it, `HostLeft` only says that no
  new host could be agreed).

## What the player feels: ping, delay, the jitter buffer and the laggard (v0.0.94, protocol 8)

**The readout** (`latency.hpp`, `latency_corner.hpp`): next to the frame rate, in the room of a network game and during its match (never in a game of one machine), the corner shows `ping NN ms` and `delay NN ms`
in the frame rate's style and size (a dash while nothing is measured, for a ping whose last answer is older than three seconds, and for a delay whose last command was applied more than ten seconds ago: orders are
given now and then, the ping is measured once a second). On the setup and results screens they stand in the corner row to the left of the version; in a match the bottom row of the screen holds the
score boxes, so they stand on two lines above the row, right aligned with the frame rate (they touch only the right rim of the "Send to: All" button). The web build shows them too.

* **ping** is the round trip to the host, measured by this machine: a `Ping` goes out once a second (in the room from the moment the guest has a seat, in the match from its first frame), the host answers with a
  `Pong` that echoes the nonce and the send time, up to eight pings may be in flight (a link slower than the interval is still measured) and an answer counts only with the send time that was recorded for its
  nonce. The number is the mean of the last five answers; when the last answer is older than three seconds (`PingMeter::kStaleAfterMs`: the host answers nothing, the link is stuck, the page was not run) the corner
  says `ping -` instead of an old number. **No protocol change**: the room's host (`HostLobby`, also a server's room) and a running match (`HostSession`) have answered a guest's `Ping` since
  protocols 1 and 2. A host has no link to itself: its ping is 0.
* **delay** is what the player feels of a click: the real time from the moment one of the player's own commands is sent (a guest: written to the link; the host: handed to the sequencer) to the moment the tick that
  applies it runs on this machine, **the median of the last five commands** (it was the mean over the last ten, which kept showing a stop of one second for as long as ten more commands took: 25 s for a player
  who gives an order every 2.5 s; one command that waited out a stall does not show in a median, and a change shows after three). A command is found again in the turn by its content and its issuer (the host keeps one player's commands in the order they were sent, so the
  oldest sent command of that content is the one; a command that the host refused or that a host change lost leaves the list when a later command of the player is applied, or after 20 s). It is the sum of
  everything between the click and its effect: the way to the host, the wait for the next 50 ms turn to be sealed (0 - 50 ms, 25 on average), the way back and the jitter buffer.
* **What the frame clock does to the two.** Both are measured with the machine's frame clock, so each end is rounded to the frame it happens in (16.7 ms at 60 frames a second). The **delay** includes the frame in
  which the command was sent (input is handled at the start of a frame, before that frame's clock is taken: a command is stamped with the clock of the next frame) and the frame in which its tick runs: that is
  what the player's screen can show, so that is what is measured. The **ping** used to include the frame in which the answer is read, too, which is not the link's: at 30 frames a second it read 11 - 30 ms too high,
  at 15 frames a second 31 - 64 ms, in a hidden tab (a frame a second) about a second. Now each message is stamped with the real clock where the transport receives it and the ping takes off the time that the Pong
  waited to be read (`Connection::last_message_age_ms`, `PingMeter::on_pong`): **the browser build** stamps every WebSocket message with `emscripten_get_now()` in the event that delivers it (`wasm_ws.cpp`), and the
  readout is the link's round trip at any frame rate (measured: the table below); a Pong that waited longer than the frame clock has run since its ping (the application hands the network at most a second of a
  frame, so after a hidden tab the clock and the stamps no longer refer to the same time) is no measurement and is dropped. **A native window** reads its socket when the frame polls it, so it cannot tell when the answer
  came: at 60 frames a second the ping reads up to one frame (16.7 ms, 8 on average) too high (polling the socket while the frame limiter waits would cut that to a millisecond or two, but it would put the network's
  clock into the limiter's sleep, and `SDL_Delay(1)` slices are 15 ms on Windows: not done). The headless clients of the tests and the server's measurements are not frame-bound.

**The jitter buffer** (`jitter.hpp`, `lockstep.hpp`). A machine must run a turn at the same tick as every other, one tick per turn, so a turn that runs the moment it has arrived stalls whenever a later one comes late. Keeping a
few turns in hand lets a late turn still be on time, and every turn in hand is 50 ms between a click and its effect: the buffer is as small as the link allows. The rule is a pure piece of logic (`JitterBuffer`: it is told when
the host's turns were read and when the runner had none, it says how many turns to keep) and is tested without a clock or a simulation (`test_jitter`, suite 2.24, 26 tests):

* **What it measures.** The turn numbered k is sealed at k * 50 ms of the host's clock, so `read time - k * 50` is the same number for every turn of a link that does not change (its value is the link's delay and the offset of the
  two clocks, which do not matter); its variation is the **lateness** of a turn. The buffer is the 95th percentile of the lateness of the last 200 turns (10 s of play) plus a margin of 10 ms, rounded up to whole turns, between
  one and four. The one turn in twenty that is later than that (a lost packet that the link resends: 300 ms late, a handful of turns at a time) is not worth a buffer that would cost every command 150 ms: it is a stall.
  Frames that stood for more than 100 ms (a hitch, a window that is hardly drawn) read a bunch of turns at once: their read times say how long the machine slept, not how late the link was, and they are not counted; nor is
  the first update of a runner (whatever waited for it to exist), nor anything before a second of turns has been read.
* **Grow at once.** The lateness needs more turns than the buffer has: the buffer is that big at once. Or a tick was due and no turn was there, and the late turn came within 100 ms: one more turn at once, whatever the numbers
  say. A later turn than that is not bridged by one more turn; the stall is its price, and the buffer stays as it was. A wait of 1.5 s or more (a link that froze, a host that stopped sealing) starts the measuring afresh:
  what was seen before it describes a link that is gone.
* **A freeze is not jitter (review fix).** The turns that a freeze held back come in one bunch: the first of them waited the whole freeze, the others are what it held, so the bunch says how long the freeze was, not how
  rough the link is. Counted, a bunch of ten turns or more (the 5 % that the 95th percentile leaves out) made the buffer four turns for the next ten seconds, and then a turn fewer every ten seconds: half a minute of
  100 - 150 ms more delay after one freeze of the link, for a buffer of 200 ms that could not have bridged it anyway. Now a wait of **400 ms or more** (as the runner counts it: the link froze for about 450 ms or more) is
  a freeze, and the turns that are read in the **next 500 ms** are left out of the percentile (`JitterBuffer::Config::freeze_ms`, `freeze_skip_ms`); a wait of 1.5 s or more also forgets what was read before it, as
  before. Shorter waits, recurring spikes and a link that is jittery before or after the freeze are counted as ever (periodic freezes of 120 ms every 5 s, jitter of 0 - 20 ... 0 - 300 ms: the table of the closed-loop
  driver is byte for byte what it was). **Measured** (a closed loop of the runner and the rule on a scripted link, 60 Hz frames, 300 s; "wait" is the time from a turn's arrival to its tick, the delay that the buffer adds): one freeze of 1.5 / 3 / 5 / 10 s at t = 30 s used to move the buffer 1 -> 4 -> 1
  (four changes, the mean wait 70 / 72 / 83 / 124 ms, its 95th percentile 163 / 164 / 196 / 213 ms) and now leaves it at one turn (no change; the mean wait 58 / 64 / 74 / 116 ms, the 95th percentile 66 ms); a freeze of 1.2 s
  every 5 s took the mean wait from 208 to 102 ms and one of 3 s every 5 s from 364 to 329 ms, with the same 57 stalls in both: a buffer of four turns does not bridge them, it only costs 150 ms for nothing. The buffer
  also takes no step down without evidence (fewer than 20 turns read since a forget): a link whose history was forgotten asks for nothing.
* **Shrink slowly.** One turn down after ten seconds without a stall (and without growth) during which the lateness would have needed fewer; the next step ten seconds later. A spike is not forgotten at once: the next may be near.
* **The runner uses it** (`LockstepRunner`): it starts when `target + 1` turns are queued (the first one runs at once, `target` stay behind it). **A stall** (a tick is due and there is no turn) is waited out without owing the wait:
  the accumulator holds one tick at most, so a late turn runs the moment it comes and never in a burst; and the runner collects `target + 1` turns again before it goes on, so that the buffer that the stall used up is back (a
  bunch of turns behind a late one, a link that frees at last, finds the queue full and costs no extra wait). **That wait is bounded** (review fix, the HIGH one): once the oldest queued turn has waited `target + 1` turns'
  time (50 ms each: what a healthy stream needs to bring them) the runner goes on with what it has. A host stops sealing when the match ends (the room freezes its session), so after a stall that had grown the buffer or
  made the last turns late, fewer than `target + 1` turns stayed queued for ever and **the last turn or two of the match were never run**: the player saw "Waiting for the other players..." for ever, and after the
  server's grace period "The connection to the other players was lost.", instead of the results. Measured with the real client against a fake room (`last acknowledged turn`, 200 turns, the last one late): 60, 100,
  150 and 300 ms late: turn 198 of 199, never the last; with the bound: 199, at 0 / 60 / 100 / 150 / 300 ms. At the runner (a stream that ends, 19 shapes of lateness near its end, three frame phases each): the last
  1 - 2 turns unexecuted in 9 of 19 shapes before, none after. In whole rooms over a spiky link (a message held up by 120 - 250 ms with probability 0.2 - 5 %, 400 matches of two guests in each of eight rows): **in a
  server's room 6 - 59 of 800 guests (0.75 - 7.4 %) did not reach the final tick before, none of 6,400 now, and none of 6,400 in a game with a host's seat** (v0.0.93: none). **More turns queued than the buffer asks for** (a stall that ended in a bunch, a window that was not drawn for a
  second, a lagging player's backlog, a buffer that shrank) is run down at up to four times normal speed, in proportion to the time that the newest queued turn is further away than the buffer wants (`target * 50 ms` and 10 ms
  for the frames): every 50 ms more adds a quarter of the speed (1.25x, 1.5x, ...), 550 ms more and up to 4x. The count is in time, not in whole turns: a whole turn's dead zone left the queue up to 49 ms longer than the buffer for good.
  **A long frame is run down the same way** (review fix): a frame that stood for more than 100 ms (a window that is hardly drawn) runs the turns that its own time covers and the standing backlog beyond them at up to 4x,
  and may run as many ticks as its time holds at that speed (8 for each 100 ms of it: 80 for the second that the application hands the network at most). At normal speed a long frame ran only the turns that arrived while
  it stood, so **a window drawn once a second stood 1 - 2 s behind the match for ever** (and one drawn every 1.5 - 2 s, whose clock the application cuts at 1 s a frame, fell behind by 0.3 - 0.5 s a second until the server
  called it a laggard and dropped it): measured in a room with a window drawn every 1 / 1.5 / 2 s (the server's view, by the acknowledgements), **it stood 1.95 s behind for ever / 4.95 s after 10 s and 41.95 s after 120 s
  and still falling behind / 6.95 s after 10 s, falling behind, dropped at 116 s, and is now 1.0 / 1.5 / 2.0 s behind, level for good**; the speed is still 4x at most, so a window drawn less often than once in 4 s cannot
  keep up (a frame that is told one second runs 80 ticks, 4 s of the match: a window drawn every 5 s falls behind by 0.2 s a second and is dropped after about four minutes). A long frame is not counted as a stall, and a stall that begins in one is counted from the frame that follows it (the "Waiting" message needs it: pinned by `test_jitter` J2.12).

**What used to go wrong with the buffer** (found with the readout; each is reproduced by a test that fails without the fix, and all three now follow from the runner above):

1. *"Waiting for the other players..." stayed on the screen after a real stall.* The runner called itself stalled while its accumulator of unspent time (up to 400 ms after a stall) held a tick and no turn was
   queued; after a stall that is true for ever, although turns arrive on time. `NetGame::stalled_ms()` grew without end and the message never went. Now `stalled_ms()` is the time since a tick was due and had no
   turn, while that goes on: a turn that arrives and runs ends it at once. (Reproduced with a host and two guests, one of which draws no frame for 5 s: the host stops sealing after 3 s of missing acknowledgements, the
   other guest waits, and its count rose to 21 s. N9.19, N9.21.)
2. *A stall used the buffer up for good.* The 400 ms of unspent time were paid back against the turns that arrive afterwards, so every later turn ran the moment it arrived, with both its ticks at once: no buffer, the game
   stepping 10 times a second instead of 20, and every bit of jitter a visible stall (179 stalls over 100 ms in 40 s with jitter up to 60 ms). Now nothing is owed for a wait and the buffer is collected again (N9.22, N9.23, J2.1).
3. *A queue left standing was never run down.* A bunch of turns after a frozen link, a frame that took 400 ms, a window that is hardly drawn: the turns pile up, the runner ran at double speed only while more than
   five were queued and stayed at five for the rest of the match: half a second of delay for good, and two windows of one match running 0.5 s apart (the match clock shows it as 6:41 against 6:40). Now every queue
   longer than the buffer is run down at up to 4x, down to the buffer and 10 ms (N9.24, N9.25, N9.26, J2.3, J2.4).

Two more changes belong to the same cause. **The network's clock keeps real time**: `Application::run_frame_with_delta` clamps a frame to 100 ms for the local simulation, which also cut the network's clock; a hitch of 400 ms left
three turns standing for good. The network now gets the real frame time up to one second (N5.30). **A long frame runs the ticks that its time stands for** (above; N9.28): a window that is drawn once in 0.75 s (the built-in browser pane of the owner's
desktop tool draws a hidden page at about one frame a second: measured 1.3; **Chrome draws a hidden tab not at all**, see "A hidden tab" below, which since v0.0.96 the server's messages run all the same) used to run 8 of the 15 ticks that its time holds, so its game ran at 40% of the speed, and the host, which did not seal more than 30 turns ahead of the slowest peer, held
every other player's game back to that speed.

**Who waits for whom: the lag policy (protocol 8).** "I'm not a fan of making the other players' experience worse because somebody lags" (the owner). A game on the local network is between friends: the host (it has a seat) stops sealing
while a peer is more than 3 s behind, shows "Waiting for Bob..." and goes on when the machine is back, as before (60 turns instead of 30, the same 3 s; `laggard_drop_ms` is 0 there: it waits for ever, until the connection or the silence
timeout of 60 s ends it; host migration is unchanged). A **dedicated server's room is made of strangers, and one machine that stalls (a window in the background, a laptop that went to sleep) must not slow down the others**: the
server's host has no seat, never stops sealing, and punishes the lagger only:

| | |
|---|---|
| the others | their game goes on at 20 ticks a second. From the moment a player is more than **3 s** behind (`kLagNoticeMs`; its acknowledgements are measured against the turns sealed) they get a `Lag` message about it once a second (`kLagNoticeEveryMs`), and see one line, "**Bob is lagging (12 s behind)**" (the seconds are the server's number, rounded); when it is within **1 s** again (`kLagClearMs`) they get `Lag` with 0 and the line goes. A notice that is not renewed for 3 s (`kLagNoticeStaleMs`) is gone anyway. The line never hides the player's own state: a machine that is itself cut off says "Waiting for the other players..." first |
| the lagger | its commands go to the server at once and apply when they arrive, in the turn that is being sealed then (the others' present, not its own screen's past); its runner finds the backlog of turns in its socket and runs it at up to **4x** normal speed (above: the first frame after a stop stands for what the application hands the network, one second, and runs that second's ticks, then 4x), and its screen says "**Catching up...**" while it is more than 3 s behind, until it is within 1 s. A player dropped for being slow on the downlink (nothing queued) gets the generic line |

* **A burst of orders is carried, not refused** (review fix, `Sequencer::submit`): a turn takes 64 commands of one player at the most. A stuck uplink that is let go (5 s stuck while the player gives 15 orders a second: 76 orders in one message burst) used to
  hit the cap, and the 12 refused orders were 12 violations, of which 8 throw a player out: **a player lost its seat for an uplink that hiccuped**. Now the commands beyond the turn's 64 wait in a queue of the player's own in the
  sequencer, up to 256 of them (four turns' worth, `Sequencer::Config::max_carried_commands`), and go into the next turns in the order they were sent, behind the commands that wait already; only a peer with more than that

**Limits of the lag policy and the readout (known, not fixed in v0.0.94).**

* A client that acknowledges turns it has not run (a modified program) is never called lagging: the server measures lag by acknowledgements, not by proof of execution. It gains nothing in the simulation (the state it computes is its
  own, and the referee compares every state hash: a machine that really diverges is named and the room fails), so it is accepted.
* **A page that is reloaded, or a window that is closed, forfeits its seat**: the new page is a new connection, a running match takes no new connection (`MatchRunning`), and the old one is dropped after its silence. Coming back to
  the same seat is the job of the reconnect release.
* **A rejected join is invisible on the web page**: its reason (the room is full, a match is running, the wrong version, no such room) is written on the setup screen, which the quick help of a freshly loaded page covers until it is
  closed. The desktop game's start menu release deals with the desktop; the page still needs its own word for it.
* A window that is drawn less often than once in 4 s cannot keep up (a frame is handed one second of the match and runs it at 4x at the most); the ping of a native window reads up to one frame too high (see "What the frame clock does to the two").
* "You were away too long ..." is what a machine infers from what it holds (a closed link and 20 s or more of the match unplayed in its queue): a server that goes away at the very moment that a laggard holds that much is read as a
  drop, and a player dropped over a slow downlink (nothing queued) gets the generic line. A laggard's own notice ("You are lagging") is the server's word about the past by the time it arrives on a slow link.

**The server's turn clock.** `ants_server` seals by a schedule of its own (`next_seal_ms += kTurnMs`, not "50 ms after the pass"), so the turns cannot drift or bunch; the loop sleeps 2 ms a pass, so each turn goes
out when the first pass after its time runs. Measured with a client that polled without sleeping: in Docker (Linux, through the published port) the turns reached a client that polled without sleeping every **50.00 ms, sd 1.11 ms, 47.7 - 53.0 ms over 740 turns** (natively on macOS: sd 1.16, 47.6 - 53.7); with 12 rooms of 4 clients playing, at the 48 clients: sd 1.56 ms, 1st to 99th percentile 46.4 - 53.5, **worst 56.9 ms, none bunched, none later than 7 ms from its place**. The mean is exact (no drift); the spread is the pass: a turn waits for the first pass after its time, uniformly 0 - 2.2 ms, sd 1.1. Nothing to fix. The server of v0.0.91 (turns of 100 ms, built from
the base commit, the same stack and the same clients) gave **100.00 ms, sd 1.12 ms, 97.5 - 102.8 ms over 371 turns**, and with the 12 rooms sd 1.51 ms, worst 109.8 ms: the spread in milliseconds is the same before and after (the code of the clock is unchanged), so it is twice as large a
share of a turn now (2.2 % against 1.1 %) and still far below a frame (16.7 ms). A variant that slept until the next turn was due (`sleep_for` the remaining microseconds, at most 2 ms) was tried and
dropped: on macOS the timer wakes late and unevenly (sd 4.2 ms, worst 79 ms against 1.2 and 54), on Linux the fixed pass is already within a millisecond.

**The server's load.** 12 demo rooms of 4 headless clients (`room_load`: Hello, loaded, a turn read and acknowledged per poll, a ping a second, a `Hatch` every 700 ms; the match runs on the referee's engine) at 50 ms turns: **the server container used 8.5 % of one core on average (6.2 - 12.8 % over 32 samples; 1.4 % idle: the 2 ms pass) and 3 - 4 MB of memory**, the turns reached all 48 clients 50.0 ms apart (above), and nobody was ever called a lagger or dropped (64,320 turns read). Natively on macOS the same load took 2.4 % of a core.
**Before, the same measurement against the server of v0.0.91 (turns of 100 ms; the same stack, the same clients, `docker stats` once a second for 32 s): 5.7 % of one core on average (4.4 - 7.8 %; 1.4 % idle; 3.0 - 4.0 MB), the turns 100.0 ms apart, 32,175 read.** Halving the turn costs 1.7 times the work above the idle pass (7.1
points of a core against 4.3, 2.8 points more for 48 players: the simulation is the same 20 ticks a second, the turns, the acknowledgements and the writes are twice as many), about 0.6 % of a core per room. The load is one thread: by extrapolation (not tested) a core carries more than a hundred rooms
before a pass takes longer than a turn.
A finding, fixed in v0.0.94: the TCP listener's backlog was 8 (`tcp.cpp`), so a burst of 48 connections in a few milliseconds lost some on macOS (they come 25 ms apart in the tool); the WebSocket listener had 32, and the proxy hands connections on as they come. Measured with a bare listener and 48 non-blocking connects, 0.3 s before the first `accept()` (macOS, `somaxconn` 128): a backlog of 8 gave 8 connections, 16 gave 16, 32 gave 32 and 64 gave all 48; with 8 the other 40 had not come after 12.5 s. Both listeners hold 64 now (`kListenBacklog`; the control interface's had 64 already): `test_tcp` N3.8 and `test_ws` W1.23.

**The frame loop: what a machine can do about its own part.** Every frame polls the network, runs the ticks that are due and then draws, in that order (`Application::run_frame_with_delta`: `handle_events`, `pump_network`, the simulation,
`render_frame`), so a turn that has arrived is run by the frame that follows it, never one frame later, and drawn in that same frame. Running a tick between frames would change the state earlier than the screen can show it: the
picture only changes at the frame, so a tick that waits for its frame costs the player nothing he can see (it costs the readout up to a frame: the delay is measured to the tick). The rest of the 17 - 21 ms that a window at 60 frames a
second adds (measured above) is the input being read at the start of the next frame (a click waits 0 - 16.7 ms for it before it is sent, 8 on average) and the frame that polls the turn and runs its tick (0 - 16.7 ms after the turn arrived, 8 on average). The browser has the same order inside `requestAnimationFrame`
(display rate, 60 - 144 frames a second; a WebSocket message waits in the page's queue until the next frame polls it, and the ping readout takes that wait off: above) and a page that is drawn rarely (the built-in browser pane's hidden page: about once a second; Chrome's
hidden tab until v0.0.95: not at all, see "A hidden tab"; since v0.0.96 the server's messages run it) keeps its game in step with real time by the long-frame rule above.
What would cut the input wait is reading the pointer's events between frames (a native loop that sleeps in slices) or a WebSocket that is read by the page's own event and sent at once: not done, for 8 ms of 100 - 160.

**Recommendations, with their numbers.**

* **Keep the buffer rule as it is** (1 - 4 turns, 95th percentile, grow at once up to the number that bridges a late turn, shrink a turn per 10 s): gain 75 ms on a steady link (50 for the buffer, 25 for the seal), nothing lost on a jittery
  one (0 - 60 ms of jitter: no stall, delay 164 against 252 - 301), and on a link with lost packets the same stalls as before (a spike of 250 ms stops the game for 150 - 200 ms in both). The risk is a link whose lateness is
  between 50 and 150 ms in one turn in twenty: it gets two or three turns (100 - 150 ms) until it calms down for 10 s per turn; a steady 50 ms jitter costs 50 ms more than a clean link, not more.
* **Do not go below 50 ms per turn**: a turn is a tick (the engine runs at 20 Hz, a command applies at a tick boundary); a half tick would need a different simulation. The cost of the shorter turn is twice the messages: 20 turns and 20
  acknowledgements a second per client (about 3 KB/s per client with the WebSocket, TLS and TCP headers), and the server's CPU measured above (12 rooms of 4: 5.7 % of a core with turns of 100 ms, 8.5 % with 50 ms).
* **TCP_NODELAY** is set on every socket (`tcp.cpp`, `ws.cpp`) and `nginx` forwards `/ws` with `proxy_buffering off` (`docker/nginx.conf`): the path adds nothing measurable (1 ms of jitter to beta, turn spacing at the relay sd 1.0 ms).
* The TCP listener's backlog was raised from 8 to 64 (and the WebSocket listener's from 32 to 64) for bursts of connections on a server's ports: done in v0.0.94.
* The browser's frame loop is the largest part of what is left (17 - 21 ms): a page that handles `pointerdown` and sends at once would cut it further (a hidden tab has no frame at all since v0.0.96: the server's messages run it, and nobody sees its readout).

## Protocol 6, the WebSocket transport and the pieces of the dedicated server (v0.0.81)

* **Protocol 6** (`protocol.hpp`): a map name may hold any printable ASCII character except `/ \ : * ? " < > |` (the community's names hold spaces, `!`, `~`, `#`, `&`, quotes and even `..`; a name cannot hold a separator and ends in `.lvl`, so none names a path), up to 64 characters (`kMaxMapNameChars`; 348 of 586 community names were refused by the old rule of letters, digits, `_ - .` and 32 characters; the LAN datagram grew to at most 160 bytes); **Hello carries a room code and a token** (`room`: letters, digits, `_`, `-`, up to 32, empty for a LAN or direct host; `token`: up to 64 printable characters without spaces, carried and never interpreted by the game) and a lobby with a room code answers a Hello for another room with `Reject NoSuchRoom`; the slot state `Bot` (a computer player, `docs/BOTS.md`) is allowed in the Room message. Client: `--room CODE`, `--token T`.
* **WebSocket server transport** (`ws.hpp`, native builds; v0.0.81): `WsListener` / `WsConnection` implement `Connection` over RFC 6455 (binary messages, masking checked, fragmentation reassembled up to 64 KB, ping / pong, close handshake, a server ping every 20 s, 1 MB send backlog limit, an 8 KB / 5 s handshake limit, an optional origin allow-list and path), with a socket-free frame parser for fuzzing. It is checked against Node's and Python's WebSocket clients and through an nginx proxy (the header comment has the proxy lines). It is the transport for browsers and Electron: the page connects out to the server, so no NAT traversal is needed.
* **Control interface primitives** (`ants_ctl`, native builds): a strict JSON library and a minimal HTTP/1.1 server on the loopback address with a bearer secret (constant-time compare, `GET /healthz` without it), with which a lobby backend will create and inspect rooms.
* **Map sweep** (`tools/map_sweep.cpp`, an optional target): plays every map of a folder headless in child processes (crash and hang isolation, three plays per map compared by hash). Over the 586 community maps it found no crash or hang, a determinism defect (a second match on one engine object began with the first match's attack times: `last_attacked_ms_` was not reset by `init`), the undefined float-to-int conversion of one map's flower probabilities (now the original's `__ftol`, 0x1034580: truncate to 64 bits, keep the low 32), and loader / start-marker issues that v0.0.86 fixed: the loader now reads what the original reads (547 of 586 maps load), a start marker outside the grid makes the map unplayable only for rosters that contain that team (`LevelData::validate(roster)`; a room checks it when it is about to start), and the invented 40 x 40 rule is gone.
* **The dedicated server** is described in the next section (v0.0.83).

## The dedicated server (`src/ants_server`, v0.0.83)

Decision (owner, 2026-09-30): **no NAT traversal in the game**. The game has no real lobby of its own; an external lobby launches it, and for internet play a server that everybody can reach hosts the matches. `ants_server` is that server: a headless program, one process, many rooms, no threads (one `update(now)` per pass over the sockets and the rooms, like the rest of the network code).

* **Room** (`room.hpp`): a seatless `HostLobby` (room code, `min_players` = `max_players` = the expected players) that becomes a seatless `HostSession` with its own `SimulationEngine`, the **referee** (`Sequencer::on_referee_hash`: every client's hash of a turn is compared with the referee's own; the room fails and says why when one diverges). It is made from outside (`RoomSpec`: map file, fog, players 2 - 4, code, seed, wait / load / keep times) and starts by itself: when the expected seats are taken the lobby sends Start, every client loads the map and reports, and the match begins when all have. A client that cannot load or that leaves cancels the start (back to Waiting; at most a few tries, with a 2 s back-off so a client that can never load the map does not loop); a room that nobody completes fails after `wait_ms`. Finished and failed rooms are kept for status calls (`keep_ms`) and written to `<code>.json` in `--results-dir`. The result rows are the results screen's (an alliance is one row).
* **The door** (`room_manager.hpp`): every connection (TCP from native clients, WebSocket through a TLS proxy for browsers and Electron) arrives without a room; the first message must be a Hello within 10 s and its room code (protocol 6) names the room. A Hello for a room that does not exist or is over (`NoSuchRoom`: a finished or failed room is not "a match that has started"; a demo room that is over is made again, see `web/four.html` below), for a match that is running (`MatchRunning`), another protocol version, or anything else is answered with a Reject and the connection is closed after a short linger so the answer arrives. Limits: 256 rooms, 128 connections that have not said Hello.
* **The map store** (`map_store.hpp`): the folder of `.lvl` files from `--maps`; a name is only a name in the folder (the protocol's `valid_map_name`: never a path), a room is refused (404 / 400) when the map is missing or does not load, so a room that exists can always be played. The Docker image carries the six maps of the original game in `/maps`; a folder mounted there replaces them (the lobby keeps the library and syncs it).
* **The control interface** (`control.hpp`, HTTP + JSON, `ants_ctl`): `POST /rooms`, `GET /rooms`, `GET /rooms/<code>`, `DELETE /rooms/<code>`, `GET /stats`, every call behind the bearer secret (constant-time compare). The secret is never read from the command line (a command line is visible to every user): it is `ANTS_SERVER_SECRET`, or, when that is not set, a random secret (32 bytes of the operating system's generator, 64 hex digits) that the server makes the first time it starts and keeps in a file (`--secret-file`, default `control-secret` in `--results-dir`, an explicit `--secret-file` wins) (`src/ants_server/secret.cpp`). It is shown in the log once, the moment it is made (before the ports are opened), and read from the file at every later start. The file is made all at once: the complete secret goes to a temporary file next to it, which is linked to the final name (POSIX `link()`, Windows `MoveFileEx` without replacing), so servers that start at the same moment share one secret and a crash leaves no half-written file. On POSIX only its owner can read it (mode 600); **on Windows the server sets no permissions and the file takes those of its folder**. A file that already exists is used as it is (its owner and mode are the operator's responsibility, a symbolic link is followed); one that is no usable secret (not a regular file, empty, outside 32 - 256 characters, a space or control character, more than one line, bigger than 1,024 bytes) stops the server and is never overwritten. It listens on the loopback address; a deployment that needs more says so explicitly (`--ctl-any-interface`, for a container whose host maps the port to its own loopback address). The lobby's backend calls it; room codes first, per-player tokens (the Hello carries one already, the game never interprets it) when the lobby wants to check who joins.
* **Clients**: the same game, `--join HOST:PORT --room CODE` (a Hello with the room code; a lobby launches it with the code). `NetGame` recognises a server's room by its **missing Host slot**: no host migration (a client whose server link dies loses the match, it does not elect itself the host of a one-player game; the server drops the seat at the same tick for everybody else), and the match starts when the room says so: when every seat is taken, or, since protocol 7, when the room's **leader** (the first player who joined) presses START (below). Everybody else's screen waits.
* **A room never waits (protocol 8)**: the room's host has no seat, so it keeps sealing a turn every 50 ms whatever a seat does; a seat that falls behind is announced to the others (`Lag`, "Bob is lagging (12 s behind)") from 3 s, catches up alone at up to 4x ("Catching up..."), and is dropped at 60 s behind or after 30 s without an acknowledgement (the old rule held the room up for 3 s and then for 20 s). `RoomStatus::turns` is one per tick now (turns of 50 ms). See "What the player feels: ... Who waits for whom".
* **Deployment**: `Dockerfile.server` (debian:12-slim, builds the program alone with `-DANTS_BUILD_APP=OFF`, runs unprivileged, healthcheck = a connection to the game port), `docker-compose.server.yml` (example). Only the TCP port is public; the WebSocket port goes behind the nginx that ends TLS (the proxy lines are in the header of `ws.hpp`), the control port is for the lobby's backend only. Capacity: a match costs about 83 microseconds of one core per tick on average (map sweep, 586 maps), so a core holds hundreds of games; the memory of a room is the engine (a few MB).

## Protocol 7: the room's leader starts early (the first player of a server's room)

Request of the owner: "the first player to join the lobby should get a start button in case they want to start the game with less players". A server's room waits for every seat that it was made for; its **leader** can start it with the players who are there. Nothing else about the room or the match changes, and a LAN / direct game has no leader (its host starts, as ever).

* **Who leads** (`HostLobby`, `src/ants_net/lobby.cpp`): in a room of a dedicated server (the host holds no seat, `Config::host_seat = kNoSeat`) the guest who was welcomed first leads; when it leaves (it says Leave, is kicked, is thrown out for violations, or its connection dies) the earliest of the guests who are left leads. The order is the order of the Welcomes (`Guest::join_order`), **not** the number of the seat (a seat asked for with `--seat` or `?seat=` does not give the lead), a guest who comes later never takes the lead from one who is there, a guest who comes back is a new, last guest, and when everybody has left the next one to come leads. A bot seat is never a leader. The leader is chosen again (`elect_leader`) whenever somebody joins or leaves, **before** the room is broadcast, so the Room message that tells about the change already names the new leader. A host that holds a seat has none (`leader()` is `kNoLeader` = 255), and neither does a server's room made with `early_start` off. The lead is no authority beyond that one request, which only asks for what the room would do by itself with every seat taken; whoever knows the room's code and joins first leads it, so a lobby that wants to decide who may start makes its rooms with `early_start` off.
* **Wire** (`protocol.hpp`, `kProtocolVersion` 7 in v0.0.93; the history comment lists 2 .. 8, protocol 8 of v0.0.94 kept all of this and added `Lag` = 25, which is `MsgType::Last` now): `RoomMsg` has a last byte `leader` (a seat, or 255 = nobody; the same value goes to everybody, `you` is still per receiver) and a new message type `StartRequest = 24` (`MsgType::Last` in v0.0.93; client -> server; **no payload: exactly the type byte**). The decoder of the Room message is strict like the others: `leader` is 255 or a seat in 0 .. 3 **whose slot is a guest** (`SlotState::Client`; an empty seat, a bot and a host's own seat are refused), so the layout of protocol 6 (no such byte) and anything longer are no Room message; `decode` of a StartRequest accepts the single byte 24 and nothing else. Protocol 7 is **not compatible with 6**: the Hello still has its layout, so a client of protocol 6 gets `Reject VersionMismatch` from a LAN host and from a server alike. (Rewritten tests: N2.2 listed 24 as an unknown type, N4.1 changed the byte before the last one (`you`) and now also the last (the leader).)
* **The StartRequest rules** (`HostLobby::handle_guest_message`): a request from the leader, while the room is open (`Phase::Room`) and `can_start()` holds (at least `min_players` seats taken, one of them a person, a map chosen), becomes the event `LeaderStart` (with the leader's seat) for the owner of the lobby, which decides (the lobby never starts by itself). **Every other well-formed request is ignored and counted** (`ignored_start_requests()`): from a guest who is not the leader, from any guest of a host that holds a seat, in a room without early start, with too few players, or when the room is loading already (a leader who clicks START twice has its second request arrive after the Start). **That is no offence as long as one connection does not send more of them than a person could** (`kIgnoredStartRequestsAllowed` = 16 per connection: a double or triple click, a few tries on a slow link); **each one after the sixteenth is a violation** like any message that a guest may not send, so the 24th throws the sender out (v0.0.93: they used to be free, and a connection that sent them as fast as it could was never dropped; see "Flood control"). A request **with a payload is garbage**: a violation at once (eight of them throw the sender out, and then the lead moves on). In the match the same rule holds for the session: a dedicated server's `HostSession` ignores a late StartRequest (the leader's click that crossed the Start on the wire) with the same allowance (`HostSession::ignored_start_requests()`, which the room's status adds to the lobby's count), a host that holds a seat counts it as a violation at once (nobody sends it one).
* **The room** (`ants_server`, `src/ants_server/room.cpp`): `RoomSpec::early_start` (default true; demo rooms have it on) is the control interface's `"early_start": true|false` in `POST /rooms` (a value of another type is a 400 naming the key). With it on the lobby is made with `min_players` = 2 and a leader; with it off `min_players` = the players expected, no leader is named and every request is ignored. When the leader's request arrives in a **Waiting** room whose lobby can start, the room starts at once with the seats that are taken (`Start` carries the roster mask, every client loads the map and reports, the match begins as for a full room; the map is checked against **that** roster, see below). A room whose seats are all taken still starts by itself, as before, with no request. `RoomStatus` (and the JSON of `GET /rooms`, `GET /rooms/<code>`) keeps `expected` as asked, shows `joined`, and has three new keys: `early_start`, `leader` (the seat while the room waits or loads, otherwise null) and `ignored_start_requests`. Rules where the early start meets the room's others: a request that arrives while the room is in the **pause after a cancelled start** (2 s, `Room::kRetryMs`) is lost, the leader presses START again; a request of a leader who has left in the same pass is void; seats that the map cannot be played by (a start marker outside the grid, `LevelData::validate(roster)`) are **not started early and do not fail the room** (a full room still fails with the reason, as it always did): the room goes on waiting.
* **The leader's screen** (`MapSelectScreen`, `Application`): the first player's setup screen is the original's **host screen** (animation `st_screen`: "Host Game Set-Up", Up / Down, START, Fog of War On / Off) in a **server room mode** (`RoomView::leader`; `is_guest()` is false, `leads_server_room()` is true): the map label shows the room's map (its name, the description from this machine's own copy of the file, "???" without it, exactly the guest's label), Up, Down and the wrap change nothing, the Fog buttons show the room's choice and change nothing (the buttons still show their hover and pressed pictures and click: they do nothing, as when a list has one map), **START (the button, Enter, the keypad's Enter, `S` and `s`, as on the host screen) sends `StartRequest`** instead of starting here (`MapSelectScreen::set_on_request_start`, `Application::net_request_start`, `NetGame::request_start`), `Q` / `X` / the Leave button leave as everywhere. The rows are the guest's (itself first, then the others in ascending order: nothing jumps when the lead moves). The prompt line is the host's own text (`kPressStart`, "Press START when all players' thumbs have appeared."); nobody else sees it (a guest keeps `kWaitingForHost`). **Too few players** (fewer than two in the room): the same as the host's START on a LAN room (`net_start_from_setup`): the can't-go cue (sound 63), no message box and no change of the screen, and nothing is sent (`NetGame::request_start` is false); the thumbs are not asked for (the host's START waits for them, a server's room does not). A request that the server cannot honour (a player left in the meantime, the pause above) gets no answer: nothing happens, the screen stays and the leader presses again. When the server's `Start` arrives (the answer to a request, or the room filled up) every screen is locked, a second click on START while the map loads sends nothing, and a cancelled start unlocks it. **A player who is not the leader keeps the guest's screen** (`nh_start`, only Leave works). **When the lead moves** (the leader left) the Room message that says so makes `NetGame::is_leader()` true on the new leader's machine and its screen turns into the host's at the next frame; the status line follows. No new text is shown on any original screen: every string is the original's (`src/ants_sim/game_strings.cpp`). **The quick help does not press the leader's START** (v0.0.93: START! of the quick help (529, 437) - (627, 464) lies under the setup screen's START (526, 439) - (624, 466)): a double click on START! has a second click that would press the new START, so on a machine that joined a room a left press that continues the click that closed the quick help is not given to the screen (`Application::swallow_closing_click`): one that SDL counts as part of the sequence (`clicks` above 1) and one that comes within SDL's double-click time of the closing click (`Application::kDoubleClickMs`, 500 ms), because SDL gives up its count when the pointer has moved more than a pixel between the clicks, which a hand does; a press after that time that SDL counts as a first click begins a new click: it is the screen's and ends the rule, as does creating the setup screen again; a held Enter or S that closed the quick help repeats into START, so **the leader's START ignores the auto-repeat of a key** (`MapSelectScreen::handle_key_down(key, repeat)`, `SDL_KeyboardEvent::repeat`), and the quick help's button is let go of when the window closes. **The original's own screens are not touched**, because the original does not have this protection (verified in `Ants.exe`, `docs/GAME_REVERSE_ENGINEERING.md` 5.61): its window class (`FUN_01031989`, style 3: `CS_VREDRAW | CS_HREDRAW`) has no `CS_DBLCLKS`, so the second click of a double click arrives as an ordinary press, and its key translation (`FUN_01031bbd`) never reads the repeat bit of a key message. A local game and a LAN host therefore act on the second click and on a repeated Enter exactly as the original does.
* **A test hook** (`--start-when N`, N = 2 .. 4): a headless client has nobody to click START, so a client that leads a server's room presses START itself (the `S` key of the screen: the same path as a click) once N players are in the room, and again every second until the match starts. Off by default; anything but 2 .. 4 is no option. `tests/scripts/test_ants_server.sh` uses it.
* **Not in scope (still open)**: bots in server rooms, short room codes, host migration for server rooms (the leader is the server's notion, the match has no host to move).
* **Tests**: `test_lockstep` N2.3b (the Room message with every leader value and every byte in the leader's place, the strictness, StartRequest as one byte and nothing else, 20,000 mutated Room messages), N2.1 / N2.2 / N2.3 (the new messages join the round trips, the type check and the 400,000-message fuzz), S2.5 (a late StartRequest in a match); ## Joining and hosting from the desktop start menu (`start_menu.hpp`, `application_menu.cpp`, Unreleased)

A native game that is started without a mode shows a start menu (README "Start Menu"); its **Join with a code** and **Host an online match** panels use the game server's TCP game port (default `beta.playants.org:4001`, `--server HOST[:PORT]`, the settings key `server`) through `NetGame::join(address, port, name, 255, room, "")`: the same path as `--join HOST:PORT --room CODE --name NAME`. The protocol, the server and the lobby are unchanged.

* **Steps of an attempt** (`Application::MenuConnection`): the name of the server is looked up on a worker thread (`HostLookup`; `getaddrinfo` is the one blocking step of `TcpConnection::connect`; an address is answered at once; IPv4 is preferred when a name has both, the server listens on IPv4); then `NetGame::join` with the numeric address; then the first Room message (`Phase::Room`; a room that is full when the player joins sends Welcome, Room and Start together, so the menu accepts `Loading` too). The whole attempt has one time limit (20 s, `ApplicationConfig::menu_connect_timeout_ms`: "does not answer"); Esc / Cancel abandons the lookup and closes the connection at once; nothing of an attempt stays when it fails.
* **Join**: the name (printable ASCII, 32; a name that starts with "Bot (" in any blanks and case is refused on the panel, the server renames such a player to "Player N") and the room code (as typed, blanks at the ends cut, never case-changed: the room manager's map is case sensitive and only a lower-case `demo-` prefix makes a demo room). On the Room message the quick help (the stored option) and the setup screen follow: the guest's, or the leader's host screen with START when the player was first.
* **Host**: the code is made the way `web/four.html` makes it, `demo-<map>-<n>p-<six characters of abcdefghjkmnpqrstuvwxyz23456789>` (at most 23 characters), so the server makes the demo room on the first Hello (`--demo-rooms`, the map and the player count ride in the code) and the player is its leader; the menu shows the code (large), the players in the room, Copy (the system clipboard) and Continue to the room. A room that fills while the code is shown starts by itself. A Hello that finds a room with that code already (about one in 900 million) makes the player a guest, not the leader: the menu leaves and says so. An abandoned demo room keeps its slot until it expires (the server's `demo_wait_ms`, ten minutes), so a player who hosts, leaves and hosts again on a server with few demo rooms may be told the server is busy.
* **Failures** (each has its own line; `NetGame::fail_reason()` and `reject_reason()`, new, tell them apart; `ClientLobby::was_open()` tells whether the connection was ever open): `Unreachable` (the connection was never made: "Cannot reach <server>"), `Lost` (it was made and closed before the room: "was lost before you were in the room"), `Rejected` with the server's `RejectReason` (`Full`, `VersionMismatch` ("This game is v0.0.N, but the server runs another version of the game"), `MatchRunning`, `Kicked`, `BadRequest`, `NoSuchRoom`: "There is no room with the code ... (capital letters matter)" for a join, "The server could not make a room now: it is busy, ..." for a host attempt), `Closed` (the room's connection ended once the player was in it).
* **After a match**: a network game that was reached from the menu goes back to it (`Application::return_to_start_menu`: the results screen's Leave, the setup screen's Leave, the quit dialog's Yes, `HostLeft`, a room that dies under the setup screen); the net object is destroyed and the next attempt makes a new one. The original's flow (Leave ends the program) stays for a game without the menu and for a single-player match.
* Tests: `tests/test_app/test_start_menu_app.cpp` (suite 3.12) runs all of it against a real `RoomManager` behind a real TCP listener and a raw server that answers each `RejectReason`, hangs up or stays silent; its `--real-server H:P` and `--probe H:P` modes run the host / join / START scenario and one join of a room that does not exist against a server that is already running.

## Flood control (v0.0.93)

The review of the leader's START (v0.0.92 + the leader) found that **one connection could peg the server's only thread**: type byte 24 was a violation before the leader, so a client that sent it as fast as it could was dropped after eight; as a valid message that is ignored and counted it was free. Measured with a raw client (`u32` length + one byte, 20,000 frames per write) against a real `ants_server`: 91 - 95 percent of a core, the process grew by **1.1 GB in four seconds**, the sender was never dropped, and the same held for every other valid message that nothing counts (`Ping`, `Pong`, `TurnAck`, `Hash` of a turn that was never sealed, `Chat`: 70 - 96 percent of a core and 1.1 - **3.4 GB** in four seconds, chat lines relayed to everybody all the while). The cause was not the handling of the messages (a lobby takes 64 of a guest per update, a session 256) but the transport: **every `TcpConnection::poll()` read up to 256 KB and parsed every frame in it into an unbounded queue**, however few messages the game took (the WebSocket connection had an inbox bound since v0.0.81, the TCP connection did not). Three layers now:

* **The transport holds the sender back** (`tcp.hpp`: `kMaxInboxMessages` 4096, `kMaxInboxBytes` 1 MiB): at half of either bound nothing is read until the game has taken what is there, at the full bound not even what was read is parsed, and unparsed bytes (at most a whole message and one read) wait in the connection. The bytes stay in the kernel and TCP stops the sender; nothing is lost or reordered (a million messages, and a 64 KB message in the middle of them, arrive whole and in order: `test_tcp` N3.7); a hostile length prefix behind a flood still fails the connection when the parser gets to it.
* **At most N messages of a connection are taken per update** (the lobby 64, the session 256, as before; now that the transport is bounded the rest really waits for the next update instead of piling up).
* **A budget of messages per connection** (`flood.hpp`, `MessageBudget`): a token bucket of **1000 messages a second with a burst of 1000** (`kMessagesPerSecond`, `kMessageBurst`; `HostLobby::Config` and `HostSession::Config` carry them). A real client sends an acknowledgement for every frame that ran a turn (20 a second with turns of 50 ms, 80 while it catches up at 4x: never more than one per turn), a state hash for every 20th turn, a ping a second, its commands (the sequencer takes 64 a turn, 1280 a second with turns of 50 ms, and a person gives a few) and now and then a chat line. **Re-measured for turns of 50 ms (v0.0.94, `test_lockstep` N2.39)**, with the real sessions over a simulated link and the host noting when it takes each message: the busiest second of a client held **27** messages in steady play, **48** for a person who gives 20 orders a second, **89** for a window that catches up at 4x after a freeze of 10 s, and an uplink that was stuck for 25 s (the longest that a server's room tolerates: a player with no acknowledgement for 30 s is dropped) delivered **637** at once, within the burst; so the budget is some 10 to 40 times above what an honest client says in a second, and it stays as it was. A client at the sequencer's 1280 commands a second is no person and meets the budget first (an hour at 1000 a second is never refused, an hour at 1100 refuses exactly the surplus: `test_lockstep` N2.37; honest traffic of 900 a second for twenty seconds and a burst of 900 after a pause are not touched). **A message that finds the bucket empty is not handled and is a violation** (eight throw the sender out: `Reject BadRequest` in the room, a `Drop` in the match). A flood of 3000 pings, pongs, acknowledgements, hashes or chat lines at once is therefore answered (or relayed) a second's worth at the most and ends with the sender out, and the others never notice (`test_lobby` N4.13, `test_lockstep` S2.6 / N2.38); a sender at 1500 a second is out after about two seconds.
* **The ignored StartRequests have a count of their own** (`kIgnoredStartRequestsAllowed` = 16 per connection, see above): they are the messages that a person sends twice, so a flood of them is dropped after 24, not after a second's worth.

The server's main loop and the control interface did not change. Measured again with the same raw client against the same kind of server after the change: the sender is dropped after **0.01 s** (StartRequests: out at its 24th request, `ignored_start_requests` 24) or **about 0.4 s** (pings: a second's worth of pongs, 1000 - 1300), the process stays at **3 MB** and 0 - 1 percent of a core, the control interface answers in 2 ms, and a match in another room keeps its clock of 20 ticks a second. The same experiment runs as tests: `test_server` S3.32 (the real server loop and real sockets in one process, a victim match in another room: dropped within two seconds, no pass of the loop slow, the process idle again and not grown by 200 MB, the victim's clock kept) and `tests/scripts/test_ants_server.sh` (the real `ants_server` and a raw client written in Python).

## The browser as a client: hidden tabs, and sound (v0.0.96)

**The problem.** A browser stops `requestAnimationFrame` in a page that is not shown (another tab in front, a minimised window, a window that is completely covered) and slows the page's timers: to once a second, and after a while hidden to once a minute (measured in headless Chrome 154: the 100 ms interval of a page that another tab covered ran once a second for the first 58 s and then once a minute, with one call 13 s later and none in the rest of a 130 s measurement; Chrome documents this "intensive wake up throttling" for a page that has been hidden for five minutes and has been quiet, and spares a page that plays audio). The game's frame loop (`emscripten_set_main_loop`, driven by `requestAnimationFrame`) was the only thing that polled the connection and ran the lock-step runner, so a hidden seat stopped executing turns and stopped acknowledging them. What a dedicated server's room does with such a seat is the lag policy of v0.0.94 (above): the room keeps its pace of 20 ticks a second, the other players read "<name> is lagging (N s behind)" from the moment the seat is 3 s behind (`kLagNoticeMs`), and the server drops the seat after 30 s without an acknowledgement (`kLagDropIdleMs`, `include/ants_net/session.hpp`; in a two-player match the other player then won): a hidden tab was a lost seat after 30 s, and its player found "You were away too long and were dropped from the match." (Before that, v0.0.93's sequencer held the whole room as soon as the seat was 30 turns (3 s) behind and dropped it 20 s later; measured with that build, the built-in browser, Chromium 152, two seats, one of them hidden: the room's tick count stopped 4 s after the seat was hidden and the match ended about 20 s later. A LAN host, which has a seat of its own, still stops sealing while a peer is 3 s behind.)

**While the page is hidden the network drives the match.**
* *The wake-ups.* A browser slows timers, but the page's WebSocket events still arrive, and every message of the server runs the game's callback at once (they are events, not timers). `WasmWsCallbacks` (`src/ants_net/wasm_ws.cpp`: a message, an error, the close) calls `WasmWsConnection::set_on_wake` -> `NetGame::set_on_wake` -> `Application::background_pump`. The server sends a turn every `kTurnMs` (50 ms) in a match and answers the page's ping every second (in a room too), so a hidden page is woken at about that pace. The fallback for a server that is quiet is a timer of the page that calls the exported `ants_background_pump()`: a Worker's interval of 250 ms (`web/shell.html`, `window.antsBackgroundWorker`), which the browser does not slow in a hidden page (measured in headless Chrome 154: 18 to 40 messages in every 10 s of 150 s hidden, while the page's own `setInterval` ran once a second and then once a minute); where a Worker cannot be made, the page's own `setInterval` (`window.antsBackgroundTimer`), which a hidden page slows. A step may end the session (the host or the server left): the callbacks copy the function before they run it, because ending the session deletes the connection whose callback is running.
* *What a step does* (`Application::background_run`; the same `pump_network` that a frame calls): the network clock moves on, the room or the session runs (the connection is polled, `LockstepRunner::update` executes the ticks that are due under its own rules: one tick per turn, the adaptive jitter buffer of one to four turns, a standing backlog run down at up to 4x, at most eight ticks for every 100 ms of the step; the acknowledgements, the hashes and the pings go back), and the room and start events are handled (a Start that arrives while the page is hidden loads the map and reports, and the match begins). `post_tick` runs for every tick as always (the HUD's state, the news, the end of the match). A step draws nothing, runs no music chain and no SDL events. The lag machinery of v0.0.94 needs nothing of its own for a hidden page: a seat that acknowledges every turn as it arrives is never 3 s behind, so the room never sends a `Lag` notice about it (checked in a real hidden tab: none reached either page in 120 s), and "Catching up..." and "You are lagging" never come on in a page that is shown again.
* *No sound, no music.* A step makes no sound and starts no music, whatever it does. The sound effects of its ticks (the events are drained and dropped: not played, not saved up), the start voice of a match that begins, the buttons' cues and the can't-go cue (`Application::play_effect`) are not played. The music that the beginning of a match, its end or the loss of the server would start or close (`enter_match`, `check_match_over`, `return_to_map_select`) is not touched either: the last such wish is kept (`pending_music_`) and carried out once, by the next frame (a hidden page that still draws: a frame is what a page that is heard runs) or when the page is shown (`apply_pending_music`). The piece that plays goes on meanwhile (its sound comes from the audio callback, which the browser keeps running for a page that makes sound), and a hidden period in which nothing happened starts nothing. A page that is shown again also gets the original's own reaction to the window's deactivation (SDL's focus events are processed with its first frame: the music closes and a new random piece starts). Checked in a real hidden tab by logging `Module.FS.open`: a tab that was hidden from its start opened `INTRO.mp3` when it started (the setup screen's music: that is not a step) and no music file after that, while the match began and after the server was stopped under it (a guard of the start voice alone left `ANTS2A.mp3` opened at the start of a match and `INTRO.mp3` after the server stopped, with the page still hidden).
* *Who drives.* `Application::set_page_hidden` (the web build registers `visibilitychange` itself with `emscripten_set_visibilitychange_callback`, asks the browser at start and at every wake-up, so a missed event cannot leave a match without a driver; the tests call it) says whether the wake-ups MAY drive: a shown page is driven by its frames only, a local game is never driven by wake-ups (it stands still while the page is hidden, as the native game does when minimised: `SDL_WINDOWEVENT_MINIMIZED`). A hidden page whose frame loop keeps up with the turns by itself, with a frame at least once per turn (`kFrameAliveSeconds` = `kTurnMs`: an embedded browser pane, such as the built-in browser used for testing, reports every page hidden while the pane is off screen and still draws it at 120 frames a second; any embedder with background throttling off does the same), is driven by its frames, with picture and sound, as before, and the wake-ups stand down. A frame loop that is slower than the turns is slower than the turns and still acknowledges only once per frame: the wake-ups step between its frames, so that the acknowledgements follow the turns (the first version stood down for a quarter of a second after every frame and counted a frame for at most 0.1 s: on v0.0.93's runner a hidden page that still got four frames a second, 215 - 260 ms apart, ran 16 ticks a second and fell behind, measured in headless Chrome with a Worker as the frame clock; v0.0.94's runner runs a standing backlog down at up to 4x also in a long frame, so on this base that window would keep such a page level too, but with one acknowledgement per frame). A step never starts inside another (`advancing_`: a frame or a step inside a frame or a step is refused), and frames and wake-ups share one timer (`last_frame_time_`): the time between two of them is counted once.
* *Time.* A wake-up counts for the real time since the clocks were last advanced (a clock that went backwards counts for nothing). The network's clock, and with it the lock-step runner, gets at most one second of it (`kMaxWakeSeconds`): a page that was asleep must not be paid back more than a second of play at once (and v0.0.94's runner then runs what waited down at up to 4x within that step). The rest of a long gap is not lost for **the silence of the host**. The step hands it to the session after the connection has been read (`pump_network(dt, gap)` -> `NetGame::note_gap` -> `ClientSession::note_gap`), so that what waited in the link is heard first and is no silence, and a host that said nothing in that update has been silent for the gap too: the session's 10 s of silence (`host_silence_ms`) are 10 s of REAL time, however seldom the browser wakes a hidden page. A host is called silent only after it has been ASKED: a page that sleeps sends no pings, and a live host that holds its turns (a LAN host that waits for a lagging player, a match that is paused) is quiet but answers pings. So a wake-up that finds the host unasked since it last spoke counts the gap only up to `kAskGraceMs` (3 s) short of the limit; the ping that update sent is the question, its answer is a message, which wakes the page and is heard, and a host that does not answer has the gap held against it by the next wake-up (the ping is outstanding by then: `asked_`, the oldest question that nothing has answered). A live host, whether it streams turns, holds them or has data waiting while the page sleeps, is never taken for silent. The page's timer is a Worker's and runs four times a second, so a silent server is noticed after its ten seconds, as a shown page notices it; measured with a paused server (`docker pause`: the connection stays open and nothing comes) on the images of this release: a shown seat at +10.0 to +10.1 s, and seats that had been hidden for 22 s, for 75 s (the page's own timer already at once a minute) and for 150 s, at +10.0 to +10.3 s each (the connections polled every 0.1 s; polled once a second they read +10.0 s, +11.0 s and +10.0 s). Counting a second per wake-up, as the first version of this change did, would need ten wake-ups, which with Chrome's page timer at once a minute are ten minutes (measured with the first version and a paused server, on v0.0.93's 100 ms turns: a shown seat closed at +10 s and a hidden one at +606 s in the review, and at +10.0 s and +610.6 s when it was measured again, the seat hidden for 75 s before the pause: the silence rule does not depend on the length of a turn). Without the Worker (a browser that slows it, one that cannot make it) the same rule decides at the second wake-up after the ten seconds: with Chrome's page timer at once a minute, up to two minutes. When the page is shown again the last wake-up brings the clocks up to date, the frame timer restarts from that moment (the hours that the page was hidden are not one huge frame: the frame statistics and the FPS display never see them) and the frame loop has the match. (Measured: a seat that had been hidden for 57 s read "ping 3 ms" one second after it was shown, at 60 frames a second, and its screen showed neither "Catching up..." nor a lag line.)
* *The console.* One line per hidden period of a second or more in which the wake-ups stepped, at most one every ten seconds (`Application::hidden_period_line`; a tab that is flicked through says nothing): `The page was hidden for 45.1 s; the match advanced by 901 ticks and 1126 wake-ups stepped it in the background`, or, for a period spent in a room, `The page was hidden for 25.0 s; 51 wake-ups kept the connection going in the background (no match tick ran)`.

**What the browsers do** (what is said of Chromium was measured here, the rest is what the browsers document: Firefox and Safari have not been run): *Chrome and Edge*: `requestAnimationFrame` stops in a hidden or fully covered page; timers run once a second, and then once a minute (intensive wake-up throttling: chained timers only; a page that plays audio is exempt): in headless Chrome 154 the 100 ms interval of a page that another tab covered ran once a second for the first 58 s and then once a minute, with one call 13 s later and none in the rest of a 130 s measurement, and Chrome documents the minute for a page hidden for five minutes and quiet for 30 s. WebSocket events are delivered at once (measured, turns of 50 ms: a page hidden for 45 s was woken 1,126 times for 901 ticks: one wake-up per turn (900), one per pong (45) and four a second of the page's Worker timer (180); in a really hidden tab of headless Chrome 154, a tab opened behind another with its seat in a room for two, the room ran 2,404 ticks in 120.2 s, 20.00 ticks a second, the hidden seat's own hash reports gave 20.00 as well, all 24 hash reports that both games posted agreed, and no `Lag` notice reached either page (2,619 and 2,611 messages)). *Firefox*: the same (animation frames stop, timers are clamped to a second in a background tab, network events are delivered). *Safari* (macOS): the same, and a background tab may be slowed further or suspended to save energy. *Safari on iOS and every phone browser*: a page that leaves the foreground is suspended within seconds and its connections are closed by the system: the seat is dropped (its connection closes, or after 30 s without an acknowledgement) whatever the page does (a phone that locks its screen leaves the match). A computer that sleeps stops every page it has.

**A tab that the browser freezes** (Chrome's tab freezing, a page frozen through the DevTools protocol) stops completely: nothing in the page can prevent it. Its WebSocket does not survive it: the connection closes at the thaw with the close code 1006 (measured with a page frozen for 8 s, and a plain `WebSocket` in the same page does the same), the server sees the connection close and drops the seat at once, and the room's match goes on without it (in a two-player match it ended 0.3 s after the thaw, the finest the check could see). The server's own rule (it drops a seat 30 s after its last acknowledgement, `kLagDropIdleMs`; the others are told that it lags from the third second) only comes first for a tab that stays frozen longer than that: with a page frozen for 45 s the match ended 30.3 s after the freeze, before the thaw, and 29 `Lag` notices (one a second from the third second) had reached the other seat. The reconnect work that comes next (a seat that rejoins its match) is what will let such a seat come back; until then a frozen tab is a lost seat.

**Sound and the autoplay rules.** A browser lets a page make sound only after the person has done something on it, so the game's Web Audio context (SDL's, `Module.SDL2.audioContext`, opened when the game starts) begins suspended and the game's sound and music begin the moment it is resumed; the game itself does not wait for it, and there is no start overlay any more (the page used to hide the game behind a card that said "Click anywhere to play!" until a click). SDL's own Emscripten audio already resumes the context at the first `keydown`, `mousedown` and `touchstart` (`autoResumeAudioContext`: once each, on the document and the canvas); the old page's own tries did nothing (it looked for a global `SDL2`, which does not exist, and made a second context that played nothing). `web/shell.html` now keeps trying until the context really runs (no `once`: a press that grants nothing, such as the Esc key or a shortcut of the browser, or a press before the context exists, would use the attempt up), on `pointerdown`, `mousedown`, `click`, `touchend` and `keydown`, and takes its listeners off as soon as the context runs; a context that stops later is resumed by the next press (`statechange`, `visibilitychange`). What each browser needs: *Chrome and Edge*: a context created before any user activation starts suspended; `resume()` works after a user activation (`mousedown`, `pointerdown` of a mouse, `pointerup` / `touchend` of a finger or a pen, `keydown` of a key that is not Esc or a shortcut of the browser), and the activation is sticky: after the first press anywhere on the page a context created later starts running; a frame needs `allow="autoplay"` (the frames of `web/four.html` have it). *Firefox*: the same rule (a suspended context, `resume()` in an input event: click, keydown, touchend; the person may also allow audio for the site, then the context runs at once). *Safari* (macOS and iOS): the strictest: `resume()` must be called inside the handler of a gesture (`click`, `touchend`, `keydown`), it is not sticky, `touchstart` does not count on iOS, a context that a phone call or the lock screen interrupted (`interrupted`) needs a new press, and the ringer switch silences Web Audio on an iPhone. The built-in browser lets pages play at once (its context was `running` before any press), so the check there exercised the page's logic with a real context that was suspended by hand: a trusted click resumed it, a second suspension was resumed by the next click, with the context running the listeners were gone (no `resume()` call), and a press while no context existed raised nothing and the next press resumed it. The keyboard focus: the canvas takes it when the game is ready, and again at the first press inside the game.

**Known gap, and the checks that cover it.** No automated test reaches the code that exists only in the web build: `WasmWsCallbacks` and its wake-ups (`wasm_ws.cpp`), the wiring of `NetGame::set_on_wake` in `join_url` (`netgame.cpp`), `ants_background_pump` and the visibility registration (the `__EMSCRIPTEN__` blocks of `application.cpp`), and the logic of `web/shell.html` (the fallback timer, the sound unlock, the keyboard focus). A native test cannot receive a browser's events, so `test_network_app` plays the browser (`HiddenDuo` wakes the application once per turn, a virtual clock stands for the browser's time) and checks everything that is not the browser's. What covers the rest, by hand: bring up the stack (`docker-compose.stack.yml`), open a demo room for two players (`?join=/ws&room=demo-tiny-2p-xyz&seat=0`, then the same with `seat=1`) with seat 0 in one tab and seat 1 in another, put seat 1's tab in front so that seat 0's is hidden (`document.hidden` is true in its console), and read the room's `ticks` from the control interface (`GET /rooms`, the bearer secret from `docker exec ants-server cat /results/control-secret`) at the start and two minutes later: 20 ticks a second with both players still in it, and the hash reports that both games post on the broadcast channel `ants-sync` (every 100 ticks) equal. `tests/scripts/test_web_hidden.sh` does exactly this against a stack that is running, with a throwaway headless browser, and also checks that no `Lag` notice (message type 25) reaches either page and that the hidden page opens no music file (opt-in, not part of `./run_tests.sh`; it needs a Chromium-based browser and Python 3 and skips with a message without them).

**Tests.** `test_network_app` (suite 3.6, `N5.32` - `N5.44`, a native test cannot receive a browser's events, so `HiddenDuo` plays the browser: it seals the host's turns and wakes the application once per turn, and `VirtualClock` is the clock of its frames and wake-ups, so that no test sleeps for a window): the match runs 30 s with no frame and the host compares every hash, nothing is drawn, the machines end bit-identical, the console line says how far the match went (N5.32); one driver at a time, the wake-ups stand down while frames come at least once per turn (pinned a hair either side of one turn), a step inside a step or a frame inside a frame is refused (N5.33); a wake-up gives the network clock exactly one second at most (a gap of ten minutes, of five seconds, of one, of 0.4), never less than nothing, and the runner pays that second out under its own limits (at most the ticks that a second holds at its fastest speed), frames and wake-ups share one timer (N5.34); the hidden hours are not a frame (N5.35); no sound effects in a step, none of the buttons' either, sound in a frame (N5.36); the last wake-up when the page is shown (N5.37); a local game is not driven by wake-ups (N5.38); a page that is hidden before the match starts goes through the room, the start and the match on wake-ups alone, with no start voice (N5.39); no music starts, closes or changes in a hidden page, a match that begins hidden, one that ends hidden and a server that is lost hidden each leave their music for the page, once (N5.40); a seat whose hidden page gets a frame a second, four, 220 ms apart, fifty a second or none runs 20 ticks a second (N5.41); a host that was asked and does not answer is called silent by the wake-up after its ten seconds of real silence however long the page slept (2.9 s after the question no, 3.1 s yes; wake-ups a minute, ten minutes, 1.5 s apart), a host with data waiting and one that holds its turns but answers pings are never taken for silent with a wake-up a minute for three minutes, and the frames of a shown page hand over no gap (N5.42); Every test of the suite is independent of the turn length (`net::kTurnMs`, `LockstepRunner::kTickMs`): it passed on v0.0.93 with turns of 100 ms and two ticks and passes here with turns of 50 ms and one tick.

## State hash (`SimulationEngine::state_hash`)

FNV-1a 64 over the gameplay state in seven parts (engine, players, grid, food, ants, paths, droppers). Everything that can influence a later tick is in it (both PRNG states, clocks, every ant field, the
occupancy grid, every map cell, hills, food objects, statistics, eggs, alliances, invitations, queued path requests, flower droppers); what only presents the simulation (audio and news queues, effects, the
per-viewer fog, names) is not. `tests/test_sim/test_commands.cpp` changes every listed field in turn and demands a different hash, runs two engines with permuted command arrival for 600 ticks and three
seeds and demands the same hash every tick, and demands that an engine that played another map equals a fresh engine (`init()` used to leave stale cell flags behind).
