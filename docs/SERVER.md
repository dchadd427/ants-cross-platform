# The dedicated server

`ants_server` is a headless program that hosts many online matches at once. Players only need to reach it: there is no NAT traversal and no port forwarding on their side. This page covers its rooms, options, control interface, public status, flood limits and Docker stack; the network rules, numbers and tests are in [`NETWORK_PORT.md`](NETWORK_PORT.md), and the game's side of network play (LAN, joining, bots) is in [`MULTIPLAYER.md`](MULTIPLAYER.md).

## What the server is

- A **room** is a host that plays nobody: it seals a turn every 50 ms, runs the match on its own engine as the **referee** and compares every client's state hash with its own. A room is `waiting`, `loading`, `running`, `finished` or `failed`.
- Rooms come from a lobby's backend, which makes them with the control interface, or from a public page that has no secret and makes **demo rooms** by itself ("Demo rooms" below).
- The players' game windows start with `--join HOST:PORT --room CODE` ([`COMMAND_LINE.md`](COMMAND_LINE.md)); a browser joins through the site's `/ws`.
- There are two doors: a TCP port for native clients, and a WebSocket port for browsers and Electron behind a reverse proxy that ends TLS. Each holds 64 waiting connections. A connection that does not say Hello within 10 s is closed. A Hello for another protocol, or for a room that does not exist, is rejected.
- How a room's match starts, by itself when the seats are taken or earlier by the leader's START, is described in [`NETWORK_PORT.md`](NETWORK_PORT.md#protocol-7-the-rooms-leader-starts-early-the-first-player-of-a-servers-room).

## Starting a server

```bash
cmake --build build --target ants_server
./build/src/ants_server/ants_server --maps Original-Ants/Maps --port 4001 --ws-port 4002 --ctl-port 4010 --results-dir results
```

[`BUILD_AND_RUN.md`](BUILD_AND_RUN.md) has the build. Without `ANTS_SERVER_SECRET` in the environment this run makes the control secret itself: it creates `results/control-secret` and prints the secret once in its log (see "The control secret" below). `.gitignore` covers `results/` and `control-secret`, so they are never committed by mistake.

The log goes to the standard error, and the number after `ants_server` is the seconds since the start. On that first start it begins like this (the build id is the short git commit):

```text
[ants_server 0] control secret made now and stored in results/control-secret (owner-only); it is shown here this once: <64 hex digits>
[ants_server 0] ants_server vX.Y.Z build abc1234 (network protocol N), maps in Original-Ants/Maps
[ants_server 0] ...
[ants_server 0] TCP game port 4001 (this machine only)
[ants_server 0] WebSocket port 4002 (this machine only: put a TLS proxy in front)
[ants_server 0] control interface on port 4010 (this machine only, bearer secret)
```

A later start does not print the secret again. With demo rooms, a line "public rooms on: ..." comes before the version line.

### Options

| Option | Default | Meaning |
|---|---|---|
| `--maps DIR` | required | The folder of `.lvl` files that rooms may use. A room whose map is missing, invalid or does not load is refused. A folder that does not exist stops the server with status 2. The Docker image brings the six maps of the original game in `/maps`; a mounted folder replaces them. |
| `--community-maps DIR` | none | A second folder of maps, the players' maps: the `.lvl` files of `Community-Maps/` with its `maps.json` and `previews.json` (the image has them in `/community-maps`, outside the volume at `/maps`). The lobby may choose every map of `--maps` and of this folder, and `GET /maps` lists them ("The list of maps"). The maps folder is asked first when both hold a name. A folder that does not exist stops the server with status 2. |
| `--port N` | 4001 | TCP game port of native clients (0: none). This machine only unless `--public`. A server needs a game port: `--port 0` without `--ws-port` stops it with status 2. |
| `--ws-port N` | 0 (none) | WebSocket port of browsers and Electron behind a reverse proxy that ends TLS. This machine only. It also answers the public status `GET /busy` and the site statistics `GET /stats` and `POST /stats/local` (below). |
| `--ctl-port N` | 0 (none) | Control interface: HTTP + JSON on this machine only, `Authorization: Bearer <secret>`. The secret comes from the environment variable `ANTS_SERVER_SECRET`; without it the server makes one ("The control secret"). |
| `--public` | off | The TCP game port accepts other machines. |
| `--ws-any-interface`, `--ctl-any-interface` | off | For containers only (a published port does not reach a program on the container's loopback address): listen on every interface and let the host's port mapping decide who may connect. |
| `--results-dir DIR` | none | An ended room (not a demo room) writes `<code>.json` there. The site statistics (in the database, see `--db`; `site-stats.json` only with `--no-db`), the control secret that the server makes (`control-secret`), the restart records (the folder `restart`, see `--restart-dir`) and the replays (the folder `replays`, see `--replays-dir`) are kept there too. The log has one line for every ended room (a demo room that never ran a tick has none). |
| `--secret-file PATH` | `control-secret` in the results folder | Where the server keeps the control secret that it makes when `ANTS_SERVER_SECRET` is not set. An explicit `--secret-file` always wins over that default, also when `--results-dir` is given (the Docker image always gives `--results-dir /results`). A file that exists there is used as it is. |

On by default since v0.6.0. `--no-reconnect` turns it off: a lost player is dropped at once, and no restart record is kept except for a room that asks for `"reconnect": true`. The last of the two options wins. |
| `--hold-vote-seconds N` | 30 | The others may vote on going on without a seat once it has been away N seconds in all (5 - 3600). |
| `--max-pause-seconds N` | 1800 | The cap on a match's total paused time: at the cap every seat that is not present is dropped (60 - 86400). A demo room takes the smaller of this and 10 minutes. |
| `--max-catch-up-seconds N` | 300 | The time that one absence may spend catching up, over all its attempts: then the catch-up fails, the seat is absent (the vote and the cap apply) and its key is refused (10 - 3600). |
| `--resume-countdown-seconds N` | 10 | After a pause of 3 s or more the match is held this long before it goes on; the players are told the seconds (0 - 60, 0 = none). |
| `--start-countdown-seconds N` | 30 | A room with two or more people (not the computer players) holds the first turn of its match this long, with the chat open, instead of the 5 s "Get ready" dialog; the Begin tells the seconds (network protocol 21; 0 - 60, 0 = none). A room of one person never counts down. |
| `--log-mb N` | 16 | The limit of one room's turn log, which a returning player is given the match from (1 - 256 MiB). All the rooms' logs together may take 256 MiB. |
| `--restart-dir DIR`, `--no-restart-records` | the folder `restart` in `--results-dir` | Where the restart records of the rooms that hold seats are kept, and the option that keeps none (a running match then ends with the server). Without a results folder the server keeps none and its log says so. A `--restart-dir` that cannot be used stops the server with status 1. The two options exclude each other (status 2). |
| `--restart-vote-seconds N` | 90 | After a restart the others may vote on going on without a seat that has not come back once it has been away N seconds (30 - 3600; never less than the room's own vote time). |
| `--restart-budget-mb N` | 256 | The disk that all the restart records together may take (1 - 4096; one record is at most 48 MiB). |
| `--replays-dir DIR`, `--no-replays` | the folder `replays` in `--results-dir` | Where the server keeps the replays of the matches that its rooms play ("Replays"), and the option that keeps none. Without a results folder the server keeps none and its log says so. A `--replays-dir` that cannot be used stops the server with status 1. The two options exclude each other (status 2). |
| `--no-history` | the history is kept whenever there is a database | Keeps no match history ("The match history"). The history lives in the database (`--db`), not in a folder of its own, so `--no-db` leaves it nothing to live in and the log says so. It is counted from the replays, so it needs them to add to it (`--no-replays` leaves what the database holds to be listed). A database that stops answering does not stop the server: the history is unavailable until it answers again. |
| `--db FILE`, `--no-db` | `ants.db` in `--results-dir` | The database file ("The database") and the option that keeps none. Without a results folder and without `--db` the server keeps none and its log says so. A file that cannot be opened, is damaged or was made by a newer program stops the server with status 1 and is left as it is. The two options exclude each other (status 2). |
| `--replay-demo` | off | The matches of demo rooms, the games of the front page, are kept too (the rooms of the control interface always are, unless the room says `"record": false`). |
| `--replays-days N` | 30 | A replay is deleted N days after its match ended (1 - 3650). |
| `--replays-max-mb N` | 100 | All the replays together may take N MiB; past it the oldest are deleted first (1 - 4096). |
| `--replay-port N`, `--replay-any-interface` | 0 (none) | A public, read-only door for the list and the files of the replays, the match history and the matches that run now: `GET /replays`, `GET /replays/<file>`, `GET /history`, `GET /history/<id>`, `GET /live`, `GET /live/<id>` and `GET /maps`, no secret, nothing else answers ("Replays"). This machine only unless `--replay-any-interface` (for containers, like `--ws-any-interface`). The stack file starts it on 4020 and the site's nginx passes `/replays`, `/history`, `/live` and `/maps` to it. |
| `--bot-match-every-min N` | 0 (none) | The server plays a match of computer players of its own every N minutes (5 - 1440; 0 = none), so that the site always has a match to watch (["Matches of computer players"](#matches-of-computer-players)). It needs the replays. The stack file asks for 60 (`ANTS_BOT_MATCH_EVERY_MIN`). |
| `--demo-rooms N`, `--demo-map NAME`, `--demo-maps A.LVL,B.LVL,...` | off | Demo rooms for a public page that has no secret (`web/lobby.html`): see "Demo rooms" below. |
| `--demo-lobbies N` | 200 with `--demo-rooms` and reconnect, else 0 | The most lobby rooms (network protocol 16) that wait at a time, for a page that waits in a room from its first second: see "Lobby rooms" below. 0 switches them off. |
| `--help`, `-h`, `--version` | | `--help` prints the usage and exits. `--version` prints the version, the build id and the network protocol, for example `ants_server vX.Y.Z build abc1234 (network protocol N)`, and exits. The server's log says the same near its start. |

A value outside its range, or one that is no number, stops the server with status 2.

### Exit statuses

- `0`: the server was stopped by `SIGTERM` or `SIGINT` (its log says "stopping"), or `--help` or `--version` was asked.
- `1`: a port cannot be opened (the log says "cannot listen on ... port N"; the control port also refuses an `ANTS_SERVER_SECRET` that holds anything but visible ASCII characters), an explicit `--restart-dir` or `--replays-dir` cannot be used, or the database cannot be opened or brought to this program's schema ("The database").
- `2`: a mistake in the options (an unknown option, a missing or out-of-range value, `--maps` missing or not a folder, no game port, `--restart-dir` together with `--no-restart-records`, `--replays-dir` together with `--no-replays`, `--db` together with `--no-db`, a demo-room or lobby-room mistake), a secret file that is no usable secret, or a control port with no secret and no place to keep one.

### Demo rooms

`--demo-rooms N --demo-map NAME` let a public page that has no secret (`web/lobby.html`) make rooms by itself: a Hello that brings a **create block** (network protocol 15) for a room that does not exist makes it, at most N at a time. Whoever reaches a game port (the TCP port, or the WebSocket port through the site) can fill these rooms.

- N is 1 up to one less than `--max-rooms` (255 with the default 256), so that rooms made by the control interface keep their places. Leave the option out to switch demo rooms off (the default); 0, or a number that is too large, stops the server at startup.
- `--demo-map` must name a map of the maps folder: it is the map of a room whose block names none that the server lists. `--demo-maps` needs `--demo-rooms`.
- What a create block chooses (the map, the seats, the room's own teams, whether a full room waits for its leader), how a room code is made and which Hello makes a room are described in [`NETWORK_PORT.md`](NETWORK_PORT.md#the-room-code-is-only-a-name-and-the-create-block-makes-the-room).
- `--demo-maps` takes file names separated by commas (blanks around a name are dropped, at most 64 names). Every name must be a map of the maps folder, or the server stops at startup. It is the list of what a create block may choose; a lobby room (below) may choose any map of the store, whatever this list says.
- A demo room waits ten minutes for its players (a friend on another computer needs time), and the pauses of its match may last ten minutes in all (see `--max-pause-seconds`). A match that nobody comes back to gives its place up: when a Hello needs a place and none is free, the demo room that nobody has been at for the longest (a minute at least) is ended.
- A Hello that brings a block for the code of a demo room that is over (finished or failed) makes a new room at once (the old one's end is still reported): a late friend, a reload, a rematch with the same link (the links of a room that the front page made carry the block). A Hello without a block, and a Hello that shows a key, is not served this way: that player's match is gone, and it is told so (`NoSuchRoom`). A room made by the control interface that is over answers `NoSuchRoom`.
- A demo room writes no `<code>.json`.

### Lobby rooms

The lobby room, in which the front page waits from its first second (`--demo-lobbies N`, network protocol 16), and the Hello that makes or joins one are described in [`NETWORK_PORT.md`](NETWORK_PORT.md#protocol-16-the-lobby-room-the-front-page-waits-in-v0120).

- **It lives while a person is in it.** The first player to join leads. The leader sets the plan (the map, what each colour is: the next player, an easy, medium or hard bot, or nobody, and the teams) and everybody sees every change; the players who join take the colours that the plan calls open. When the leader goes, the player who has been in the room the longest leads; a bot never does. Any player can change the name they go by (a name that looks like a bot's is not taken). The leader can take another player out of the room, also while the START waits for a game that never opens: the player is told, their colour is free at once, and they can come back through the link as a new player (except while the START waits, when nobody new is taken).
- **A seat whose link ended is held for a minute**, with its colour and its key, and a link that has said nothing for 30 seconds is closed (a page whose machine sleeps): a reload or a lost connection comes back to its seat with the key. A player who leaves (the Leave message) goes at once. A lobby lives as long as its players stay, so a player is forgiven one violation and one ignored request of each kind every minute: only a connection that gets messages wrong faster than that is thrown out.
- **An empty lobby is forgotten a minute after the last player has gone**, without a line in the log (no match was begun: nobody played) and with no result file. There is no timer while a player, or a seat that is held, is in it. A Hello for its code then makes a new lobby.
- **The leader's START waits for every player's game.** The pages go to the game page and take their seats over with their keys; the room starts the match when every person is a game, and the leader is told whose game did not come when 90 seconds are over. Then the server loads the plan's map (it must be one of `--demo-maps`, or `--demo-map`), seats the plan's bots and takes a place among the public matches. What it cannot do (the map is lost, the colours cannot play the map, no place is free) ends the START with a notice for the leader, and the lobby goes on waiting. A match that is cancelled (a game cannot load the map, a player leaves) is tried again after two seconds, three times in a row; after that the leader is told so and the lobby waits a minute (a lobby never fails for cancelled starts), and the count is forgotten after fifteen minutes without one.
- **A waiting lobby holds no place among the `--demo-rooms`**; its START asks for one (a place that is free, or one that a public match which nobody has been at for a minute gives up), and the match is a public room like any other. A lobby is no match, so the people in lobbies are in the `players` of `GET /busy` but never in its `matches`, and never hold a deploy back (a restart ends every lobby: the page makes its room again).
- **The pool.** At most N lobbies wait at a time. When all are taken (or `--max-rooms` leaves no place for another room), the lobby that has been empty the longest is forgotten to make room for a new one; when none is empty, the lobby in which nothing has been done for ten minutes (no plan, colour move, rename, removal, line of chat or START; answered pings are not use), the longest idle first, whose players are dropped and whose pages make a room again; when every lobby is in use, the new page is told `NoSuchRoom` (the page says that the server is busy).
- **N** is 0 up to `--max-rooms` - `--demo-rooms` - 1, so that rooms made by the control interface keep their places. Without the option a server that has `--demo-rooms` and keeps seats (reconnect, the default) offers 200 (fewer where `--max-rooms` leaves no more room; none where it leaves none, and the log says so); a number above 0 needs `--demo-rooms`, `--demo-map` and reconnect, and a lobby room together with `--no-reconnect` stops the server at startup, as does a number that is too large. `--demo-lobbies 0` switches lobbies off.
- Whoever reaches a game port can fill the pool and hold it with connections that stay: that is the price of a page that needs no secret, as for the public rooms (nothing behind the site's nginx tells one address from another). A waiting lobby is cheap (no thread, no match, one copy of the map), the people in it are not counted among the matches, a lobby that nobody is in goes after a minute and one in which nothing is done gives its place up after ten, when it is needed. How fast one address makes lobbies is not limited here (a lobby costs about 0.3 ms to make, and making one is what every page view does): that belongs in front of the server, and the site's nginx has no limit for the game's WebSocket yet.

### The list of maps

The server lists and hashes every map of its two folders once, when it starts (`MapStore::scan`; the log says how many, and notes a `maps.json` or `previews.json` that cannot be read or describes a file with another hash: the map is then described by its own header). A map is a file name of 5 to 64 printable characters that cannot name a path (`valid_map_name`), and the file must be a regular file of 1 byte to 4 MiB. Two things follow from the list:

- **The lobby's choice of map.** A lobby room (`choose_map`) accepts the name of any map the store has: the maps folder and the community folder (`--community-maps`), in the spelling of the list or in any letter case. The six maps of `--demo-maps` keep their spelling, and a name that cannot be a file, or is not there, is refused as before. The 64-name limit of `--demo-maps` no longer limits the lobby. No change of the network protocol: the map still travels as a file name, and the start barrier still compares the hash of the file.
- **`GET /maps`** on the replay port (public, read only, no secret; `docker/nginx.conf` passes it to the site): `{"format": 1, "maps": [{"file", "width", "height", "minutes", "players", "description", "plays", "thumb", "original"}]}`. The six originals come first, in the order of the page (Tiny, Small, Medium, Gauntlet, Treasure, Islands) with `"original": true`; the community maps follow by file name (the page sorts them as it likes). The numbers and the description are those of `maps.json` (for a file it does not know or describes with another hash: of the level file's header and its start markers). `plays` is the map's row in the database's `map_plays` (file name and hash, [The database](#the-database)); 0 for a map that was never played, for another version of the file, and for every map while the server has no database. `thumb` is the address of the preview picture on the site, already percent-encoded: `/maps/previews/<name>.webp` for a community map (from `previews.json`, when the picture is of the same file), `/front/preview_<name>.png` for an original (the front page's own pictures: no second copy); a map without a picture has no `thumb`. A query, another method or a path below `/maps` is a 404.
- **The site's nginx** passes `/maps` like `/history` (GET only, no query, 20 a second with a burst of 100, one cache entry of five seconds for everybody, a server with no such door answered 404 with a JSON body) and serves the files itself, from `/srv/community-maps` of the web image (outside the web root): `/maps/previews/<name>.webp` (558 small pictures) and `/maps/files/<name>.lvl` (the level files, for the browser to fetch the chosen map). Both: GET and HEAD only, no query, a name of printable ASCII without a slash or a backslash (1 to 80 characters, the right ending) checked before the disk is asked, so that `%2F`, `..`, a double encoding or a NUL cannot make a path; no directory listing; `Cache-Control: public` for an hour (files) or a day (pictures) with revalidation by ETag; their own allowances (pictures 200 a second with a burst of 400, files 20 a second with a burst of 40). The names hold spaces and `! # $ & ' ~`: write them percent-encoded. Tests: `tests/scripts/test_nginx_maps.py`, `tests/test_server/test_map_list.cpp`.
- **In the images.** `Dockerfile.server` copies `Community-Maps/*.lvl`, `maps.json` and `previews.json` into `/community-maps` and starts the server with `--community-maps /community-maps`; that folder is not the volume at `/maps` (which the stack fills from the image once and then keeps), so an update that adds maps shows them without removing the volume. `Dockerfile` copies the pictures and the `.lvl` files into `/srv/community-maps/previews/` and `/srv/community-maps/files/`.

## The control secret

- `ANTS_SERVER_SECRET` in the environment is used as it is (any length; a character that is not a visible ASCII one, such as a space, a control character or an accented letter, stops the server with status 1, "cannot listen on control port").
- Without it the server makes a random secret (32 bytes of the operating system's generator, 64 hex digits) the first time it starts, stores it in the secret file and prints it once in its log, **the moment it is made**: after the options are read, and before the ports are opened, the demo-room checks and the restart folder, so a start that fails at those has shown it all the same. A mistyped option stops the server before any secret is made.
- Every later start reads the same file, so a container needs no setup. `docker exec ants-server cat /results/control-secret` shows the secret again; keep `/results` in a volume.
- On POSIX the file is for its owner only (mode 600; a umask can only make that stricter). **On Windows the server sets no permissions: the file takes those of its folder, which must be private.**
- The file appears all at once and complete (the server writes a temporary file next to it and links it to its name), so servers that start at the same moment get the same secret and a crash never leaves half a secret. This needs a file system with hard links; otherwise the server says so: give `ANTS_SERVER_SECRET`, or `--secret-file` a place on another file system.
- **A file that already exists is used as it is, whoever made it:** its owner and its mode are your responsibility (the server neither checks nor changes them), and a symbolic link is followed (a mounted secret is often one; a link to nothing is an error, and nothing is made behind it).
- A file that is no usable secret stops the server with a message and is never overwritten; delete it to get a new secret. Unusable are a directory, a device or a FIFO; an empty file; one shorter than 32 or longer than 256 characters; one with a space, a control character or a byte that is not ASCII in it (a second line is one: only the line end and the blanks at the end of the file are dropped first); and one of more than 1,024 bytes (the server never reads more than 1,025 bytes of a file).
- With neither the variable nor a place for the file (`--results-dir` or `--secret-file`), a control port refuses to start (status 2, with a message).

## The control interface

HTTP + JSON on `--ctl-port`, on this machine only unless `--ctl-any-interface`. A lobby's backend makes, inspects and closes rooms with it. Every call except `GET /healthz` needs `Authorization: Bearer <secret>`; a missing or wrong secret is 401. Another method on a known path is 405, and an unknown path is 404.

| Call | Answer |
|---|---|
| `POST /rooms` with a JSON body | Makes a room. 201 with the room's status, or 400 (a bad body or value; the reason says which), 404 (no such map), 409 (the code is taken), 422 (the map is in the folder but does not load) or 503 (no room for another room: `--max-rooms`). |
| `GET /rooms` | 200 `{"rooms": [status, ...]}`. An answer is at most 1 MiB (a room's entry is about 1 KB, so a list of a thousand rooms or so fills it), and the entry of a room leaves out its `replay` unless the match was kept: the room's own call has it. |
| `GET /rooms/<code>` | 200 with the room's status, or 404. |
| `DELETE /rooms/<code>` | Closes the room: 200 with its status after the close (a room that was not finished is `failed`, with the reason "closed by the owner"), or 404. |
| `GET /stats` | 200 `{"rooms", "pending", "created", "refused", "log_bytes", "log_budget_bytes"}`: the rooms now, the connections that have not said Hello yet, the rooms made so far, the connections that the door refused, the bytes that the rooms' turn logs hold, and the bytes that they may hold together. This is the control interface's own `GET /stats`; the site statistics of the same name are on the WebSocket port (below). |
| `GET /replays[?limit=N]` | 200 `{"enabled", "count", "bytes", "keep_days", "max_bytes", "replays": [...]}`: the newest N (default 200, at most 1000) of the replays that the server keeps ("Replays"); `count` and `bytes` are of all the files, not only the N that are listed. Each is `{"file", "bytes", "ended" (seconds since 1970, UTC), "readable", "map", "players" (the seats that played, in seat order: "Green (Ann)" for a person who has a name, "Green" for one who has none, "Red (Bot (Medium))" for a computer player: ["Green (Ann)", "Red", "Blue (Bot (Medium))"]), "turns", "seconds", "finished" (the rules ended the match), "game" (the version that recorded it), "mode" (the match's game mode as a word: "highest-score", the original's game, or "187"), "rules" (its network protocol), "sim_rules" (the simulation rules number it plays on: `replay::sim_rules_of`, 0 when unknown)}`; a file that this build cannot read (damaged, cut short by a power cut, or made by a newer format) has only `file`, `bytes`, `ended` and `readable: false`. `enabled` is false and the list empty when the server keeps none. Another query is 400. |
| `GET /replays/<file>` | 200 with the `.antsrep` file (`application/octet-stream`), or 404 (a name that is not in the list: no path ever comes from a request). |
| `DELETE /replays/<file>` | 200 `{"deleted": "<file>"}`, 404, or 500 when the file is in the list but the system would not delete it (the log says why). |
| `GET /history[?filters]` | 200 `{"history": [...], "count", "total", "offset", "limit", "keep_days", "sim_rules"}`: the records of the match history ("The match history"), newest first, 50 at a time (`limit` 1 - 100); the filters are `offset`, `sort`, `format`, `result`, `who`, `rec`, `colour`, `mode` (`all`, `highest-score`, `187`) and `q` ([`REPLAYS.md`](REPLAYS.md#the-match-history) has every word), each at most once; a word that is not one, a key twice or an unknown key is 400 with the key named. 404 `{"error": ...}` when the server keeps no history, 503 while its database does not answer (the owner is told why). The public door answers it too. |
| `GET /history/<id>` | 200 with the record (all its numbers, `mode`, what a later version added under `details`) and `recording` (`watch`, `old` or `removed`), `file` and `keep_days`; 404 for an id that is not one or not in the history; 503 as above. The public door answers it too. |
| `DELETE /history/<id>` | 200 `{"deleted": "<id>"}`, 404, 500 when the database would not take the change (503 when it does not answer at all; the log says why). The record is taken out of the history for good; if its recording is still in the replays a marker row stays, so that the match is not counted again from it, and the marker goes when the recording does. The public door cannot do this. Any other method on `/history` is 405 (the HTTP layer answers before the route: `Allow: GET, POST, DELETE` on this door, `Allow: GET` on the public one). |
| `GET /healthz` | 200 `{"ok": true}`. It is the one call that needs no secret. |

### The room specification

The body of `POST /rooms` is a JSON object, and only `map` is required:

```json
{"map": "TINY.LVL", "players": 3, "fog": false, "mode": "highest-score", "early_start": true, "bots": [{"seat": 2, "bot": "medium"}],
 "reconnect": true, "hold_vote_seconds": 30, "max_pause_seconds": 1800, "max_catch_up_seconds": 300, "resume_countdown_seconds": 10, "countdown_seconds": 30,
 "code": "ROOM-1", "seed": 1}
```

| Key | Default | Meaning |
|---|---|---|
| `map` | required | The map's file name in the maps folder. |
| `players` | 2 | 2 to 4: the match starts when this many seats are taken, and takes no more. |
| `fog` | false | Fog of War. |
| `mode` | `"highest-score"` | The game mode of the room's match (network protocol 17): `"highest-score"`, the original's game, or `"187"` ([`GAMEPLAY.md`](GAMEPLAY.md)). It is the word, nothing else: a number, another spelling or any other value is a 400 that names the key and makes no room. The Start of the match carries it to every machine, which makes its engine with it before the first tick; the status, the list of rooms and the file of the match say it (below, "Replays"). The leader of a lobby room (`--demo-lobbies`) chooses the mode with its plan, so a specification made for one with a mode is refused. |
| `early_start` | true | The room's leader may start the match with the players who are there ("The leader and the early start"). `false`: the room has no leader and waits for every seat. |
| `bots` | none | `[{"seat": 2, "bot": "medium"}]`: at least one seat is left for a person, the seats are distinct and there is no fog (each mistake is a 400 that names the key). `"bot"` is what the game's `--bot` takes after the seat ([`BOTS.md`](BOTS.md#running-bots)). |
| `code` | drawn | What a client puts in its Hello: letters, digits, `_` and `-`, up to 32 characters. |
| `seed` | drawn | 0 to 4294967295: the match's random seed. |
| `wait_seconds` | 120 | 1 - 86400: a room that has not started after this long fails. |
| `load_seconds` | 60 | 1 - 600: everybody must have loaded the map this long after the start. |
| `keep_seconds` | 600 | 0 - 86400: a finished or failed room stays visible to the status calls this long. |
| `max_run_seconds` | 7200 | 60 - 86400: a match that is still running this long after it began is ended. The limit counts the time that the match ran, not the time that it waited for a seat that was away. |
| `reconnect` | the server's setting (on unless `--no-reconnect`) | Whether the room holds the seat of a player whose connection is lost ("Reconnect"). |
| `hold_vote_seconds` | 30 | 5 - 3600, as `--hold-vote-seconds`. |
| `max_pause_seconds` | 1800 | 60 - 86400, as `--max-pause-seconds`. |
| `max_catch_up_seconds` | 300 | 10 - 3600, as `--max-catch-up-seconds`. |
| `resume_countdown_seconds` | 10 | 0 - 60, as `--resume-countdown-seconds`. |
| `countdown_seconds` | 30 | 0 - 60, as `--start-countdown-seconds`. |
| `record` | true | Whether the match is kept as a replay when the server keeps replays ("Replays"). `false`: this room's match is not. (The room's status has an object of the same name, `record`: that one is about the restart record.) |

When the body leaves a key out, the five reconnect keys take what the server was started with (`--reconnect` or `--no-reconnect`, and the four numbers); the table shows the defaults of a server started without those options. Any other key is left to the table's default.

* **The room's specification** (`POST /rooms`, `RoomSpec::bots`): `"bots": [{"seat": 2, "bot": "medium"}]`, `bot` being what `--bot` takes after the seat (`easy`, `medium`, `hard`, `idle`, `worker`, `KIND:LEVEL`, and a pinned style of the standard bot: `LEVEL:STYLE` or `standard:LEVEL:STYLE`, e.g. `hard:raider`; the styles are `aggressive`, `economic`, `raider` and `defensive`, a Hard bot plays the first and the third only); a mistake is a 400 that names the key (an entry that is not an object with a seat 0 - 3 and a bot, a bot that does not parse (a style on the worker or the idle bot, or one that the level may not play, names `style`), a seat twice, **no seat left for a person** (at least one of the room's players must be a person), **bots with Fog of War**). The bots sit in the room from the start, count towards `players` and are shown like the fill's; a person who asks for their seat gets the first free one; a room whose people have all come starts by itself, a leader's START with no fill starts the people and the bots that are there.

### The room's status

`GET /rooms/<code>`, the list and the result file `<code>.json` all hold the same JSON. Every key of the reconnect and the restart records is an addition; a lobby that ignores them works as before.

| Key | Meaning |
|---|---|
| `code`, `map`, `fog` | As the room was made. |
| `mode` | The game mode of the match, the word `"highest-score"` or `"187"` (network protocol 17): as the room was made, or for a lobby room as its leader's plan has it. |
| `state` | `waiting`, `loading`, `running`, `finished` or `failed`. `reason` says why for a finished or failed room. |
| `expected`, `joined` | The seats as asked, and as there are (bots count). |
| `players` | `[{"seat", "name", "bot"}]`: the players of the room; a bot says so. |
| `bots` | The room's computer players: `seat`, `bot`, `kind`, `level`, `style` (standard bots only), `name`, `fill`. |
| `early_start`, `leader`, `ignored_start_requests` | `leader` is the seat of the room's leader while the room waits or loads, and null while nobody leads and once the match runs. `ignored_start_requests` counts the START requests that the room did not honour. |
| `lobby`, `starting`, `plan` | Only for a lobby room (network protocol 16; the keys are absent otherwise): `lobby` is true, `starting` says whether the leader's START waits for every person's game, and `plan` is the leader's plan as a letter for each colour (`o` the next player, `e`, `m` or `h` an easy, medium or hard bot, `n` nobody), a blank and the teams (`-` for none, `0+1`): `omne 0+1`. |
| `seat_moves`, `ignored_seat_moves` | The colours that the leader moved a player to (a swap counts once), and the SeatMove requests that the room did not honour (network protocol 14; since protocol 15 also one whose guard is not the room's seating). |
| `ticks`, `turns`, `age_seconds` | How far the match has run, and how old the room is. |
| `state_hash` | A finished room: the referee's state at `ticks`, as 16 hex digits. |
| `result` | A finished room: `quitter` and the rows of the results screen (`names`, `seats`, `score`, `lost`, `killed`, `hatched`, `winner`; an alliance is one row). |
| `reconnect`, `hold_vote_seconds`, `max_pause_seconds`, `max_catch_up_seconds`, `resume_countdown_seconds`, `countdown_seconds` | The room's own settings. |
| `paused`, `resume_seconds` | `paused` says that the match is held: a seat is missing, or the countdown after a pause runs. `resume_seconds` is what is left of that countdown. |
| `absent` | The seats that are missing, longest away first: `[{"seat", "name", "state", "away_seconds", "progress"}]`. `state` is `absent` or `catching_up`, and `away_seconds` is the seat's total time away. |
| `vote` | `{"seat", "continue", "voters"}`, or null. |
| `paused_seconds`, `rejoins`, `drops_by_vote`, `drops_by_cap`, `rejoins_refused`, `catch_up_expired`, `streamed_bytes` | What the pauses of the match came to. Never a key. |
| `log` | `{"turns", "bytes", "usable"}`: the turn log that a returning player is given. |
| `record` | `{"kept", "stale", "bytes", "note"}`: whether a restart of the server would bring this match back, and why not when it would not. |
| `replay` | `{"kept", "file", "bytes", "note"}` (in the list `GET /rooms`, only for a match that was kept): whether the match is kept as a replay and under which name; `note` says why not (the server keeps none, the room was made with `"record": false`, it is a demo room and the server does not keep those, the match ran less than 30 seconds, the disk or the limits refused it, the room was brought back from a restart record or its record was refused) and is empty while the match may still be kept ("Replays"). |
| `restored` | `{"turns", "replay_ms", "state_hash"}`, or null: the room came back from a record. |

A room that a restart could not bring back (another network protocol, a changed map, ...) is a `failed` room whose `reason` says so.

* **The status JSON** (`GET /rooms/<code>`, the list, the result file): `bots` is `[{"seat", "bot" (as the specification says it: "medium", "hard:raider" with a pinned style, "worker:easy", "idle:medium"), "kind", "level", "style" (the standard bot's only: the pinned style, "random" for one that draws its own at the start of the match; the key is absent for the worker and the idle bot), "name", "fill" (true: seated by the leader's START)}]` by seat, empty for a room with no bot; `players` and `joined` count the bots (a bot is a player; each entry of `players` has a `bot` flag, true for a bot's seat); a finished room keeps the list. `state_hash` (16 hex digits) is for a finished room: the referee's state hash at `ticks`, which every player's game stands at the same tick (a lobby that keeps results can compare it; the tests do).

* **The status** (`GET /rooms/<code>`, the list, the result file `<code>.json`; every key is an addition, a lobby that ignores them works as before): `"reconnect"`, `"hold_vote_seconds"`, `"max_pause_seconds"`, `"max_catch_up_seconds"`, `"resume_countdown_seconds"`, `"countdown_seconds"` (the room's rules), `"paused"` (the match is held: a seat is missing, or the countdown after a pause runs), `"resume_seconds"` (the seconds left of that countdown, 0: none), `"absent": [{"seat", "name", "state": "absent|catching_up", "away_seconds", "progress"}]` (longest away first; running rooms only), `"vote": {"seat", "continue", "voters"} | null` (null when no vote is open **and when nobody can cast one**: a room whose only persons are the ones who are gone, the rest being bots, has an open vote with no voter, and that is shown as no vote), `"paused_seconds"` (the match's total pause so far, kept at the end), `"rejoins"`, `"drops_by_vote"`, `"drops_by_cap"` (the counters: they tell a seat dropped by the others' vote from one that left), `"rejoins_refused"` (Hellos with a key that a budget refused), `"catch_up_expired"` (absences whose catch-up time ran out), `"streamed_bytes"` (the log, streamed to returning players: at most three times its size per seat in ten minutes), `"log": {"turns", "bytes", "usable"}` (what the log held at the end of a finished match). **A seat's key is in none of it**, nor in a log line (the server logs a room's end with its pause, rejoins and drops, never a key; N: S3.46 searches the status, the list, the statistics, the result text and everything written to stderr for the keys' hex).

## `/busy` and `/stats`

Besides the upgrade to a WebSocket, the WebSocket port answers `GET /busy`, `GET /stats` and `POST /stats/local`. None of them needs a secret, and the answers hold numbers only.

### The public status, `GET /busy`

- `GET /busy` (no query, no body; any other method is 405) returns `200` with `{"matches": N, "players": M}` and `Cache-Control: no-store`, and closes the connection. There is no name, room code, address or secret in it, and it costs a pass over the rooms.
- `matches` is the number of rooms whose match is loading or running with a person in it. A room that only waits for players is not a match. A room that a restart of the server brought back counts for its first five minutes, whether or not its players are back.
- `players` is the number of people in rooms that wait or load, and who are there in a match. Bots are no people. Somebody who has not yet said Hello is in no room and is not counted. A room that a restart brought back also counts its held seats for its first five minutes.
- `docker/nginx.conf` forwards `https://<site>/busy` to it like `/ws`: an exact location, GET only, no query, one request a second per address with a burst of 5, a 3-second connect timeout and 5-second read and send timeouts.
- The deploy job of CI polls it and restarts the site when no match runs (after three hours at the most by default, `DEPLOY_MAX_WAIT_MINUTES`), so that a deploy does not end games that people are playing: [`WORKFLOW.md`](WORKFLOW.md#deploy-from-ci-and-the-staging-site), "Deploy from CI and the staging site".

### The site statistics, `GET /stats` and `POST /stats/local`

- **The site statistics, `GET /stats` and `POST /stats/local` (on the WebSocket port, `site_stats.hpp`)**: the front page shows how many games were played. Two counters, each for the **last 24 hours** (24 buckets of an hour on the server's clock: the hour that runs and the 23 before it) and **in all**, and `since`, the UTC day they count from. **`online`** is a match that ran **at least 600 ticks (30 seconds of play)** and ended, in any room (demo rooms too: every web match is one), counted once when `RoomManager::take_ended` tells its end (`SiteStats::kMinTicks`): a match that the owner closed, a desync or the room's time limit ended counts once it has run that long; a shorter one counts nothing, nor does a room that never began (nobody came, closed while it waited or during the "Get ready" dialog), so a start-and-quit loop cannot pad the number; a match that a stop of the server cuts off is not told as ended and is not counted, and one that the server brings back from a restart record is counted when it ends (its ticks go on from the record's). **`local`** is a single-player game that a browser reports: **the game runs in the tab, so the server cannot see it, and a script can post as well; it is what browsers say, a figure for the page and no proof.** `GET /stats` is answered as `/busy` is (the same door rules; `Cache-Control: no-store`) with `{"now":{"matches":N,"players":M},"online":{"day":D,"total":T},"local":{"day":d,"total":t},"since":"YYYY-MM-DD"}`: `now` is `/busy`'s answer, the rest numbers and one date (it is not the control interface's `GET /stats`, which is behind the secret and never routed). `POST /stats/local` takes **no body and no query** (`WsServerOptions::post_path` and `post_action`: exactly that path, no `Upgrade`, one `Host`, `Content-Length` absent or 0, no `Transfer-Encoding`; another path or method is 405 and `Allow:` says what the path takes, a malformed request 400; the parser stays pure and only says `posted`, the listener runs the action once), counts one game and answers **204**; **at most 120 reports count in any 60 seconds**, the others get the same 204 and are not counted (the cap cannot be seen), and the server keeps nothing of a request but the count (the web server's own access log is what it is for every request). The counters live in **the database** ("The database": the tables `site_stats` and `site_stats_hours`, schema version 4), written whole in one transaction **at most every 10 s while something changed** and at a clean stop (a write that fails is rolled back and leaves the last numbers whole, the log says so once), read at start; a crash loses the last 10 s at most. **An older server kept them in `site-stats.json` of `--results-dir`** (`{"format":1,"since":...,"online":{"total":T,"hours":[[hour number,count],...]},"local":{...}}`): the first start with the tables reads that file into them at once (every number and the date) and leaves it as it was; later starts read the database and never the file again; a file that is no usable file (not JSON, a counter that is no number, buckets that hold more than the total, a date that is no day) is put aside as `site-stats.json.broken-<seconds>`, the counters start at 0 and a log line says so. With `--no-db` the counters are kept in that file as before (written whole to a temporary file, flushed to the disk and renamed); without a results folder they live in memory. `docker/nginx.conf` forwards both as exact locations like `/busy`, with **nothing of the visitor's headers** passed on (the server is sent `Host`, `Connection` and, for the POST, `Content-Length: 0`: a cookie never reaches it, however big): `/stats` GET only (405, a query 404), twenty a second per address with a burst of 100, **answered from a cache of 5 seconds** (one entry for everybody, so the game server is asked about once in 5 seconds however many people look; an old answer is served while the new one is fetched and when the server does not answer; the server's `no-store` still reaches the browser); `/stats/local` POST only (405, a query 404), a request that the browser says is cross-site (`Sec-Fetch-Site: cross-site`) is 403 before it counts against the limit (the game page's own report is same-origin), sixty a minute per address with a burst of 20 and **never a body passed on** (the server is given an empty POST; a body over 1 KiB is 413); 503 beyond the limits; a 3-second connect timeout and 5-second read and send timeouts. The limits are sized to hold for the whole site, because behind a reverse proxy that ends TLS every visitor may have the proxy's address (the server's own cap of 120 a minute is the bound that matters). **The web game reports its own games**: `Application::set_on_local_match_started` is told at the first tick of a game on this computer (once for each match, never in a match of the network; only the web build sets it, to a call of the page's `antsReportLocalGame()` in `web/shell.html`: one `fetch('/stats/local', {method: 'POST', keepalive: true})`, no retry, every failure ignored); a native game reports nothing. Tests: `test_ws` W1.25 (the door), `test_server` S3.140 - S3.149 (the counting, the window, the cap, the file, the answer, a real manager and a real listener), `test_site_stats_db` (the tables, the import of the old file, a write that fails), `tests/scripts/test_ants_server.sh` (the real program, its rooms part), `tests/scripts/test_nginx_stats.py` (the blocks, the limits and the cache, run in front of a stand-in server, and in front of the real program), `test_app_integration` 7.6h and `test_network_app` N5.90 (the hook), `tests/scripts/web_report_check.js` and `test_web_report.py` (the page's function).

## The leader and the early start

The room's leader, who may start the match early, is described in [`NETWORK_PORT.md`](NETWORK_PORT.md#protocol-7-the-rooms-leader-starts-early-the-first-player-of-a-servers-room), "Who leads".

- START starts the match at once with the players who are there, when the room is waiting and at least two players are in. One player is enough when the START asks for bots ([`NETWORK_PORT.md`](NETWORK_PORT.md#the-fill)). `expected` keeps what the room was made for and `joined` shows who came. A room whose seats are all taken still starts by itself, unless its create block says that a full room waits for its leader (`--room-leader-start`): then only the leader's START starts it, so that the leader can arrange the colours first, and a full room whose leader never presses START ends when the room's ten minutes are over.
- Which START requests a room ignores, and when one counts as a violation, are described in [`NETWORK_PORT.md`](NETWORK_PORT.md#protocol-7-the-rooms-leader-starts-early-the-first-player-of-a-servers-room), "The StartRequest rules".
- The leader may also **move a player to another colour** (network protocol 14, with swaps and a guard since 15: a press on the player's row of its screen). The room puts the guest, with its key and its place in the order of the Welcomes, in the empty seat, or changes places with the guest that holds the seat, sends every player the new room and tells each player that was moved, but the leader, in its chat. The press carries a number that stands for who sits where (the guard): a room that does not seat its people exactly so any more (somebody came or went) ignores it. A request from a guest that is not the leader, for a seat that a bot or the host holds, from a seat that holds nobody, with another guard, or in a room that has started is ignored and counted in `ignored_seat_moves` (the same 16 free, then violations, and it costs no part of the budget); the moves that are made have a budget of 6, then 4 a second. Details: [`NETWORK_PORT.md`](NETWORK_PORT.md#protocol-14-the-leader-of-a-room-moves-a-player-to-another-colour), "Protocol 14" and "Protocol 15".

## Bots fill the empty seats, and chat in the waiting room

- The fill level of the leader's START (`--fill-bots`, [`COMMAND_LINE.md`](COMMAND_LINE.md#--fill-bots---start-when-and---say-in-detail)), and the bots that the server seats for it, are described in [`NETWORK_PORT.md`](NETWORK_PORT.md#the-fill) and, for a level for each seat, [`NETWORK_PORT.md`](NETWORK_PORT.md#what-the-server-and-a-lan-host-do-at-the-leaders-start).
- **The room's teams are in its create block** (a pair such as `0+1`, see [`NETWORK_PORT.md`](NETWORK_PORT.md#the-room-code-is-only-a-name-and-the-create-block-makes-the-room)) and hold for every start, whether the room fills up by itself or the leader presses START. Details: [`NETWORK_PORT.md`](NETWORK_PORT.md#protocol-13-a-bot-level-for-each-seat-of-the-leaders-fill-and-teams-chosen-before-the-start), "Protocol 13".
- **Bots and Fog of War never mix**: with fog the room seats none and tells the leader why (a notice, sent as a chat line from the room). A cancelled start takes the bots away again.

Details, the screens and what the bots cost the server: [`NETWORK_PORT.md`](NETWORK_PORT.md#protocol-11-bots-fill-the-empty-seats-at-the-leaders-start-and-chat-in-the-waiting-room), "Protocol 11: bots fill the empty seats at the leader's START, and chat in the waiting room".

## Lag and lost connections

The lag policy of a room, and the different rule of a game on the local network, are described in [`NETWORK_PORT.md`](NETWORK_PORT.md#what-the-player-feels-ping-delay-the-jitter-buffer-and-the-laggard-v0094-protocol-8), "Who waits for whom: the lag policy".

- The others play on at full speed and are told once a second from 3 s of lag, "Bob is lagging (12 s behind)", until he is within 1 s. Bob's commands apply when they arrive; he runs the turns he missed at up to four times normal speed, and his screen says "Catching up...".
- A player 60 s behind, or whose machine has run no turn for 30 s although it is connected, is dropped like a player who left (the others see "Bob dropped out of the game!").
- **Lag is not a loss.** A slow link or machine, or a window frozen for less than 10 s, is lag. A client that says nothing for 10 s, or whose connection closes (a sleeping laptop, a stopped process), has lost its connection, and a room that holds seats pauses for that, and for nothing else ("Reconnect"). A hidden tab of a desktop browser keeps playing, and nobody is told that it lags; a phone browser that leaves the foreground, or a tab that the browser freezes, loses its connection.
- The room's leader is a player like the others once the match runs: if its window stops after the early START, the room does not wait for it. A finished room goes on answering until every player that is still connected has run the last turn (15 s at least, 30 s at most).

What a hidden tab of a browser does, and the sound: ["The browser as a client: hidden tabs, and sound"](NETWORK_PORT.md#the-browser-as-a-client-hidden-tabs-and-sound-v0096).

## Reconnect

A room that holds seats gives each player a **key** in its Welcome and holds the seat of a player whose connection is lost. Every room of a server does since v0.6.0, unless the server is started with `--no-reconnect` or the room's specification says `"reconnect": false`; demo rooms follow the server.

- The match is **paused for everybody**: nothing is sealed, chat is relayed, and commands are discarded without a violation. The room's status says so (`paused`, and `absent`: who, and how long away in all, `away_seconds`).
- The player comes back with its key. A Hello for a running match that shows a key goes to the room, instead of being refused (`MatchRunning`, "The match has already started."). The player is given the turns it lacks from the server's log, runs them at once without drawing them and says its state hash; the referee compares it with its own, and the match resumes.
- How the others vote on a seat that is away, and how the cap on the pauses drops the seats that have not come back, are described in [`NETWORK_PORT.md`](NETWORK_PORT.md#the-behaviour-that-is-decided) ("Reconnect (protocol 10)").
- A key is bounded, so that nobody can hold a room or the server's bandwidth with one: the catch-up time of an absence (`--max-catch-up-seconds`), twelve accepted Hellos a minute from one seat, and the turn log that is streamed to a seat (three times the log's size in ten minutes, at least 1 MiB). Beyond a bound the answer is `RejoinFailed`, and the seat stays held (the vote and the cap apply). The log itself has a limit (`--log-mb`; all the rooms together may hold 256 MiB): a room whose log cannot grow any more drops a lost seat at once, as a room that holds no seats does.
- How the key is kept secret, and why it travels in clear on the native TCP door, are described in [`NETWORK_PORT.md`](NETWORK_PORT.md#the-native-key-travels-in-clear-a-limit).

### What a player sees when the connection is lost

The game's own clients, the desktop game and the web page, come back by themselves (since v0.6.0).

- When its own connection is lost, the match stays on the screen with a line at the top, "Connection lost. Reconnecting... 0:12" (with " (attempt 2)", " (attempt 3)" and so on from the second attempt), and under it "Esc leaves the match" (Esc asks the quit question; its Yes leaves for good). When the server gives the game the match again, the loading screen shows "Catching up 45%", and then the match is back with the selection, the view and the chat as they were.
- The lines and buttons that the game shows when a connection is lost, and the file `rejoin.txt` and the browser storage that keep the key of a seat, are described in [`NETWORK_PORT.md`](NETWORK_PORT.md#what-the-clients-do-in-release-b).
- A game that is started again with `--join ADDR --room CODE` finds the key and takes its seat back. A reloaded web page does the same with its join arguments, and is not asked for a name again. The web front page ([`PLAY_IN_BROWSER.md`](PLAY_IN_BROWSER.md)) and the desktop start menu's first panel offer **"Rejoin your match (CODE)"** while a fresh key is kept.
- Closing the game on purpose, leaving through the web page's Menu button or link (the game is told first: the seat is dropped at once and nobody waits for it), a match that ends and being dropped let go of the key. A crash, a closed browser tab or window and a reload keep it. Closing the desktop game's window counts as closing on purpose.

Details, flows and limits: [`NETWORK_PORT.md`](NETWORK_PORT.md#reconnect-protocol-10-a-player-whose-connection-is-lost-can-come-back), "Reconnect (protocol 10)"; release B, in the section linked above, is v0.6.0, when the game's own clients began to come back by themselves.

## Restart records

**A running match survives a restart of the server.** A room that holds seats keeps a record of its running match in the folder `restart` of the results folder (`--restart-dir` chooses another one, `--no-restart-records` keeps none; a server with neither `--results-dir` nor `--restart-dir` keeps none and says so in its log). Only rooms that hold seats keep a record, so a server started with `--no-reconnect` keeps records only for the rooms that ask for `"reconnect": true`.

- There is one file per room, made when the room's start is accepted and deleted when the room is over. It holds the start message, the keys of the seats and every sealed turn, so **it is for its owner only** (mode 600, in a folder of mode 700 when the server makes it; no key is in any log line, status or result file).
- How and when the restart record is written, and why, is described in [`NETWORK_PORT.md`](NETWORK_PORT.md#writing-what-is-written-when-and-why).
- A server that starts again checks the records, newest first, and replays them in slices of 5 ms while it serves: the engine is rebuilt from the start message, every sealed turn is replayed, the state hashes that the old server stored are checked, and the bots sit down again. A Hello for a room that is not back yet waits for it.
- What a restart does to a running room, and how long the others wait, is described in [`NETWORK_PORT.md`](NETWORK_PORT.md#restoring).
- A record of **another network protocol is not restored** (a rules change would play the match out differently; the game version does not decide), and neither is one whose last write is more than an hour old. Its room is a `failed` room with the reason in the status and the log, and the record is kept for a day in `restart/refused/`, for the owner who moves it back. A deploy that wants to keep the running matches must not change the network protocol (the changelog says when a release does).
- A record is at most 48 MiB, and the records of the running rooms together 256 MiB (`--restart-budget-mb`). A disk that refuses a write ends that room's record: the match goes on without one, and its status says why (`record`).
- The lock that lets only one server use a records folder is described in [`NETWORK_PORT.md`](NETWORK_PORT.md#options-and-the-stack).
- **Keep the volume** (`ants-server-results` in the stack): a stack that is removed with its volumes loses the records.

The format and the limits: [`NETWORK_PORT.md`](NETWORK_PORT.md#restart-records-a-running-match-survives-a-restart-of-the-server), "Restart records".

## Replays

The server keeps the matches that its rooms play, so that they can be watched again ([`REPLAYS.md`](REPLAYS.md) says what a replay is and what plays it). The referee's own runner is watched while the match runs (it changes no hash), and when the match is over the file goes to a folder of the results volume (`replays` in `--results-dir`; `--replays-dir` chooses another folder and `--no-replays` keeps none). The numbers of the replays are here; the other documents point to this section.

- **What is kept.** A match that ran at least 600 turns (30 seconds), however it ended: the rules ended it, a player quit, the owner closed the room, its time limit, a desync. A shorter match is not kept, so rooms that start and are closed at once leave nothing; the room's status says why (`replay.note`). Demo rooms are kept with `--replay-demo` (the stack file has it; a demo room is a room that a visitor's create block made, the games of the front page, and never one that the control interface made), and a room of the control interface may say `"record": false`. A solo game in a browser tab is not played on the server and is not kept. When the server is stopped, a room that holds a restart record stays in the record and is not saved now, and a match that the server brought back from a record is not recorded from then on (the recorder did not see the part of it before the restart); any other room is closed, and its match is kept like that of a room that the owner closed.
- **Names.** A person's seat keeps the name that the room showed everybody, the name that the player typed: plain ASCII (the letters from the space to the tilde; every byte of anything else becomes a `?`, so a letter with an accent, which is two bytes, gives `??`), at most 32 characters, the blanks at both ends cut (`replay_person_name` in `room.hpp`). The readers show it after the colour, "Green (Ann)". A seat with no name of its own shows the colour alone, "Green": nothing was typed, or only the words that the game itself uses for a player without a name, "Player" and "Player 1" to "Player 4" (a name that only starts like them, "Players" or "Player 5", is a name and is kept). A computer player's seat has its display name, "Bot (Easy)", "Bot (Medium)" or "Bot (Hard)". The front page picks a plain word (such as "Maple") for a visitor who typed none, and that word is kept like a typed name. **The names are public wherever the public door (below) is on, which it is in the stack file:** anybody can read them in the list and in the file, so a page that shows them must show them as text. No address, room code, key or chat is in a file or in the list. The file's name is the map and the time the match ended: `ants-TREASURE-20261008-143209Z.antsrep` (UTC; `-2`, `-3`, ... when two matches of a map end in one second).
- **The notice on the pages.** A line says what the server does with an online match. The front page shows "Online matches are recorded. Recordings are kept for 30 days. Results and names are kept for good and are public." in its footer and under the name field of the card that a shared link opens (the element `who-notice`); the game page's name card says "Online matches are recorded. Anybody can watch them, live or later. Recordings are kept for 30 days. Results and names are kept for good and are public." (not in the step of a game on this computer: the server does not record that game). The pages are static, so the line is true only for a server that runs as the stack file runs it: `--replay-demo` (the front page's matches are kept), `--replay-port` (the public door below, which the site's nginx passes `/replays` to) and 30 days (`--replays-days`, `ANTS_REPLAY_DAYS`). A server with other settings (`docker-compose.server.yml` has the first two off) changes the words in `web/lobby.html` and `web/shell.html`, and leaves the element `who-notice` of the first where it is (the script hides it in the step of a game on this computer).
- **Only its own files.** The server touches nothing in the folder but files with a name of that form: another file is left alone and is not counted. A file is written whole under a temporary name and renamed, and an existing file is never replaced, so a crash of the server leaves a whole file or none (a power cut may leave a short one: the owner's list shows it as a file that cannot be read, and it is deleted when it is old). A name is looked up in the server's list, never opened as a path. When the server starts it reads every file once; after that nothing takes longer than one small file write, one pass over the list or one look at the folder (a `stat` for every file, and the reading of at most 100 new ones). A file that somebody else puts in the folder (`bot_arena --save-replays`, [`REPLAYS.md`](REPLAYS.md#matches-of-computer-players)) is listed within half a minute: every 30 seconds the folder's change time is looked at, and only when it moved (or moved a moment ago) is the folder read again (at most 100 new files at a time; a file that changed in the last two seconds waits for the next look, and a known file is read again only when it could not be read or its size moved); a file that was taken away is forgotten and nothing is deleted for it, while a file that came from outside is under the limits like any other (one older than the keep time is deleted at once). A file of the store is "never replaced" by the store itself; another program that writes into the folder with the same name in the same second could replace it (a rename replaces on Linux), which is why only one writer is meant to run at a time ([`REPLAYS.md`](REPLAYS.md#matches-of-computer-players)). Opening the folder deletes the `.tmp` of a crash but not one that changed in the last two seconds, which is the write of the other program. The `.tmp` of another writer and any other name are left alone, and the limits below apply to files from outside as well.
- **How long and how much.** A file is deleted `--replays-days` (30) days after its match ended, and all the files together stay under `--replays-max-mb` (100 MiB), the oldest first. The limits are applied when the server starts, before every file is written (so that the new one fits) and once an hour. The age of a file is the time in its name, so it is as right as the server's clock: a clock that jumps ahead by more than the 30 days deletes the files at the next look, and one that is set back files new matches among the older ones (they go first when the size limit bites) and starts the hour's allowance again.
- **A full disk never stops the server.** The folder shares a volume with the control secret and the restart records, so the server keeps nothing new when the disk would be left with less than 256 MiB free, or when it has kept 120 matches in the last hour, and a file is 1 MiB at the most (a heavy half hour of four players is under 200 KiB). The log tells a refusal once and counts the repeats of a line that keeps coming: one line when another line follows, once an hour, and when the server stops. The hour's allowance does not tell people from scripts: someone who plays one 30-second match after another can use the allowance, and with it the 100 MiB, so that the oldest files go first. The limit is on the disk, not on a person.
- **The public door.** `--replay-port N` opens a second door, read only, with no secret: `GET /replays` gives `{"replays": [...], "count", "keep_days", "sim_rules"}` (the last is the rules number of this server's build: the site's list page shows the files of that number to watch and the others under "Earlier versions"; a match of game mode 187 has the rules number 2 and the entry says `"mode": "187"`, which the page plays as well, [`REPLAYS.md`](REPLAYS.md#the-file)) (the newest 200 files that this build can read, each with the fields of the control interface's entry except `readable`; `count` is the number of such files, not of the 200), `GET /replays/<file>` gives the file of one of them, and everything else is 404 (any other method is 405 with `Allow: GET`, a request with a body is 400 for a plain `Content-Length`, 411 for a chunked one, 413 for one that is too large and 417 for an `Expect` that is not `100-continue`, and `GET /healthz` is answered by the server itself as on the control port). It is off unless the option is given (the program's own default). **`docker-compose.stack.yml` gives it, on port 4020 of the container (not published on the host): the list and the files of the stack's site are public, and so are the names of the players in them (Names, above).** `ANTS_REPLAY_PORT=0` switches it off; leave any other value alone, because the nginx of the site passes to 4020 only (a server that listens elsewhere looks like one without the door: the site answers 404).
- **Live matches.** The same door shows the matches that run now ([`REPLAYS.md`](REPLAYS.md#on-the-game-server), "Live"): `GET /live` and `GET /live/<id>`, the same rules as the rest (GET only, a query is 404, no secret, nothing from a request is ever made into a path). A room that records its match puts it on the *live board* (`live_board.hpp`, owned by the room manager next to the replay store) when the recording begins and takes it off when the recording becomes a file or is dropped; the board holds a pointer to the room's recorder and nothing else of the room, and the room takes the match off before the recorder goes (a closed room, a match that ended, the manager's destruction). So a room that does not record (`"record": false`, no store, a match brought back from a restart record) is not on it, and neither is a match played with Fog of War (a live view would show what the fog hides from its players; the site offers no fog, and the match is public when it is over like any other).
  - **The list**, `GET /live`, is `{"live": [...], "count", "sim_rules"}`: the matches that ran at least 600 turns (30 seconds, the length the store keeps) and whose recording has not failed, the newest start first, **50 at the most** (`count` is the number of entries listed). An entry is `{"id", "map", "started", "turns", "seconds", "players"}`: `started` is seconds since 1970 UTC, `seconds` is the turns divided by 20, and `players` are the strings of the replay list ("Green (Ann)", "Green", "Red (Bot (Medium))", the names of "Names" above, which are public here too). The `id` is `<MAP>-<YYYYMMDD>-<HHMMSS>Z`, the stem of the map's file name (letters, digits and `_`, 24 at the most) and the UTC second in which the match began, with `-2`, `-3`, ... when two matches of a map began in one second; it holds nothing of the room (no code, name, address or key), and it is all a visitor can ask for.
  - **The snapshot**, `GET /live/<id>`, is 200 `application/octet-stream`: the match so far as an incomplete replay file (no `ENDS` chunk) with one more chunk, `live`, that holds the turns run when it was made ([`REPLAYS.md`](REPLAYS.md#the-file)), so that the code that plays a replay plays it up to that turn. **There is no delay, on purpose.** Only a listed match has one (the list's rule), and it is made with `Recorder::snapshot`, which changes nothing in the recording. It is made again at most once a second for a match, however many watch it (the board keeps the bytes for as long as its clock stays in the second in which they were made), so a crowd costs one encode of at most 1 MiB a second for each match that is watched, and the same bytes go to all of them.
  - **When it is not there:** 404 with `{"error": "no such live match", "ended": false, "replay": ""}`. For 15 minutes after a match of at least 600 turns has ended (at most 256 matches are remembered, the oldest forgotten first) its id answers `"ended": true` and `"replay"` is the name of the file that the store kept it as (`""` when it was not kept, or when the file is no longer in the store), so that a page that watched finds the replay. Every other failure of a `/live/...` request has the same body with `"ended": false`: a method other than GET, a query, an id of another shape (checked before any lookup), an id that is not on the board, a server without a replay store. `GET /live` itself answers 404 `{"error": "not found"}` for a method other than GET, a query, or a server without a replay store.
- **The match history.** The recordings go after `--replays-days`; what the matches came to stays, in the database ("The database", [`REPLAYS.md`](REPLAYS.md#the-match-history) says what a record holds, who won by the rule of each game mode, a draw, and the states of the recording). Three tables (migration 2): `history_matches` (one row for each match, with a column and an index for everything that the list filters or sorts by), `history_seats` (one row for each seat) and `history_markers` (the matches that the owner deleted while their recording is kept). The id is the recording's file name without `.antsrep`. Nothing is counted while a match is played: the feeder in `RoomManager::update` plays the recordings of the replay store once more, one at most every 250 ms and only while no room runs or loads a match and none is being restored, the newest first, and adds the record in one transaction. A recording takes 0.4 - 0.5 s to count for a match of 10 - 12 minutes (more for a longer one), so the gap after it is counted from the END of the work and is at least 250 ms and four times what the work took: the main thread is free most of the time; the recordings found when the server starts, up to 30 days of them, are the backfill, and a file the arena puts in the folder is found by the replay store's look every 30 seconds and counted like a room's own match. The same play counts the stats of the record (`details`, [`REPLAYS.md`](REPLAYS.md#the-match-history): 1 to 3.5 KB at most 5,000 bytes), and when no new file is left a backfill gives them to the records that were counted without, whose recording is still kept and plays here (newest first, at the same pace; a recording that cannot be counted leaves a marker, so it is not played again at every start, and a line in the log). The match's map is looked for in the maps folder and then in the community folder (`--community-maps`), the first that holds the name being the map's, like the lobby's list (a match on a player's map was left out before, as a map that is missing). A recording that cannot be counted (a map that is missing, a map of the same name that is another file, a file that does not play out) is left out and told in the log, the first ten by name and the rest in a summary; one of other simulation rules is not played and only counted in the summary. **Everything happens on the server's one main thread** (SQLite is built without mutexes); the work of a pass is one recording and one transaction. **A database that stops answering never takes the server down and never touches the match path:** the first error is logged once, the history is *unavailable* (the routes answer 503 with a clear body, and the feeder waits), it looks again every minute with a cheap read, and the log says once when it answers again; a record that the database refuses as such (a constraint) is told in the log and left out for this run, and the history stays available. **A list is time boxed and paid for:** a visitor's list is stopped by the database (`sqlite3_progress_handler`) after 15 ms of wall clock and answers 503 `that search is too heavy for the server: narrow it`; the owner's box is 100 ms. The public door has a *budget* on top, a token bucket of milliseconds of query time (100 ms in a burst, 50 ms earned for each second, each list paid for by the time it took); when it is empty a list with a query is a 503 `the match history is busy: try again in a moment` at once, without touching the database. **The list without any query is not held back by the budget** (it keeps the 15 ms box; it takes under a millisecond and the site's nginx keeps it for five seconds, serving the old copy while the server says 503), so a flood of heavy searches cannot lock the page's own list out; a match by its id is no list and has no budget either. The budget earns whole milliseconds and keeps the rest. So the public door can take about 5 % of the main thread whatever the number of visitors (a database of 16,000 matches had searches of 25 - 150 ms on the main thread before this). The `rec` filter looks the state of a recording up in a hash set made from the replay store's list, and a page reads its seats with one statement. A request's words never become SQL: a statement is made of fixed pieces and every value is bound; the search `q` escapes `%`, `_` and `\` so that a name is found as typed. The owner takes a match out with `DELETE /history/<id>` ("The control interface"); the server never deletes a record by itself. `GET /history` and `GET /history/<id>` are on the public door too, with the same rules as the rest (GET only; the list takes the query of its filters, every other query is 400 or 404; nothing from a request is ever made into a path), and the names in them are public for good. The one way a pass of the loop can wait is a writer outside the server (a tool run on the file while the server runs): a write waits for the database's busy timeout (5 s) at the most, and the history is written only while no match runs.
- **The site's nginx** (`docker/nginx.conf`) passes `/replays` (an exact location) and `/replays/<file>` (a prefix location) to that door, like `/busy`: GET only (405), no query (404), a file name of the wrong shape is 404 at once (the store decides which names exist), and nothing of the visitor's request but Host and Connection is passed on. Behind the reverse proxy that ends TLS every visitor reaches nginx from the proxy's address, so the allowances are the whole site's: 20 requests a second for the list with a burst of 100, and 10 a second for the files with a burst of 20 (503 beyond), one zone each. The list is cached for five seconds for everybody (an entry of its own in the cache of `/stats`), so a crowd of visitors asks the server about once in five seconds; a file is asked of the server each time. Timeouts are 3 seconds to connect and 10 to read and send. The server's `Cache-Control: no-store` still goes to the browser. When the server has no such door, or is not there, the site answers `404` with `{"error": ...}`, never a 502 page. `/live` (an exact location) and `/live/<id>` (a prefix location) go the same way, with the same checks (an id of the wrong shape is 404 at once: `[A-Za-z0-9_]{1,24}-[0-9]{8}-[0-9]{6}Z(-[0-9]{1,4})?`) and the same timeouts and fallback, but with allowances of their own, so that a crowd that watches does not use up the downloads' (a page asks for the list every 10 seconds and for the match it watches every 4): 20 requests a second for the list with a burst of 100 and 30 a second for the snapshots with a burst of 60 (503 beyond), one zone each. **Both are cached for two seconds** (the list in one entry, a snapshot in one entry for each id, in the cache of `/stats`, which holds 8 MB; only a 200 is kept, so made-up ids fill nothing, and the 404 of a match that is over is the server's each time). An entry that is being renewed is served old, but not one when the server does not answer: a snapshot that is repeated for minutes looks like a match that goes on, and the 404 is the truth. So the server is asked about once in two seconds for each match that is watched, on top of its own snapshot of one second. `/history` (an exact location) and `/history/<id>` (a prefix location) go the same way too, with allowances of their own (`ants_history`: 10 requests a second for a list without a query with a burst of 50; `ants_history_query`: **2 a second for a list with a query, a burst of 5**; `ants_history_items`: 20 a second for single matches with a burst of 40; 503 beyond), a GET only (405), an id of the wrong shape or a query on a match 404 at once, and a list query of the characters that the filters are made of and 400 characters at the most (400 otherwise: no other byte reaches the server). The list without a query is cached for five seconds, in one entry for everybody, an old list served while a new one is fetched and when the server does not answer; a list with a query is cached for five seconds too, one entry for each distinct query, in a cache of its own (`ants_history`, 8 MB), so that made-up queries cannot fill the small cache that the numbers of the front page share; a match is asked of the server every time (a list with a query is not cheap for the game server, which is why it has the low allowance and the box above).
- **In the log** the line of an ended room ends with `, kept as <file>` when its match was kept. The start prints where the replays are, for how long and how much, and (with the door) `public replays on port N` (the line names the routes, the live ones too).

### Matches of computer players

With `--bot-match-every-min N` the server plays a match of its own every N minutes, so that the site's list of live matches ([`REPLAYS.md`](REPLAYS.md#matches-of-computer-players)) is not empty when nobody is playing. The match is a room like the others whose seats are all bots (`RoomSpec::bots_only`; the control interface cannot make one, and such a room is no lobby and no public room and holds no seat): two to four standard bots, Medium or Hard each, on seats chosen at random, on a random one of the original's six maps and with a random seed, and free for all or in teams. For the bots that play, free for all and each way to make teams are equally likely: with four bots one of the three ways to split them in two teams of two (on TINY, SMALL, TREASURE and ISLANDS, whose hills sit at the four corners of a rectangle: top against bottom, left against right or across the corners; MEDIUM's hills sit north, east, south and west and GAUNTLET's along a diagonal), with three bots any two of them as a team against the third, and with two bots only free for all (a team of both would be the whole match), so about half of all matches are teams. The room has the teams as its own, so they are made before the first turn like a room's teams in the create block ([`NETWORK_PORT.md`](NETWORK_PORT.md#the-room-code-is-only-a-name-and-the-create-block-makes-the-room)), the replay's head has them, and the live view and the replay play them. It is played at the normal speed, so it lasts as long as the map's own time limit (6 minutes on TINY, 8 on SMALL, 10 on MEDIUM and GAUNTLET, 12 on TREASURE and ISLANDS) unless the rules end it sooner, and it is kept like any other match.

The first match begins a minute after the server starts, the next ones N minutes after the one before began. While a match of this kind still goes on, the timer makes no other, and it makes none when the server keeps no replays (a match that nobody could look at again). The log says each time what it did (`bot match: room CODE started`, `bot match: not started (the last one is still going)`). A room without a person is not closed for "everybody left", a stopped server ends it, and a restart brings no record of it back (it holds no seat). It is no game that anybody played, so the site's statistics (`/stats`) do not count it, and `/busy` counts no match for it (a restart may interrupt it). The page of the list says that the computer players "start one every hour", which is the stack's default of 60.

## Flood control

A client that is no game can send valid messages as fast as its line allows, so every connection is limited.

- The TCP connection holds at most 4096 messages (1 MiB) for the game and leaves the rest in the kernel, where TCP slows the sender (the WebSocket connection always did the same). A lobby takes at most 64 messages of a guest per update, and a match 256 of a client.
- Every connection has a budget of **1000 messages a second with a burst of 1000**. A real client sends a few dozen: with turns of 50 ms its busiest second held 27 messages in steady play, 48 for a person who gives 20 orders a second and 89 while a window catches up at 4x. A message beyond the budget is not handled and is a violation, and the sender is out after eight of them: a flood at line rate in well under a second, a sender at 1500 a second after about two.
- Chat has a budget of its own, in the waiting room and in the match: a burst of 5 lines, then one a second. A line beyond it is dropped. A talker who keeps on above two lines a second uses up an allowance of 20 dropped lines, and after that every line is a violation; two lines a second are tolerated for ever. It is a protection of the remake.

Details and the tests: [`NETWORK_PORT.md`](NETWORK_PORT.md#flood-control-v0093), "Flood control".

## The protocol version keeps two builds from playing each other

What moves the network protocol number, and how a game of another number is refused at the Hello, are described in [`NETWORK_PORT.md`](NETWORK_PORT.md#what-the-player-feels-ping-delay-the-jitter-buffer-and-the-laggard-v0094-protocol-8), "Protocol version 9 (v0.0.95) and the rule that moves the number".

- The game says "This version cannot play with the host's version." (the web page adds "Reload the page to update."; the desktop start menu says "This game is vX.Y.Z, but the server runs another version of the game. Update the game, or wait until the server is updated.").
- So update the game, the server and the page together. The current number is `kProtocolVersion` in `include/ants_net/protocol.hpp`, which also holds the rule and what each number changed; `ants_server --version` prints it.

## The database

The server keeps one SQLite database file for its records (the restart records are meant to move into it later: they stay files for now, see below). **Today it holds the match history, the play counts of the maps and the site statistics** ("The match history" under "Replays": the tables `history_matches`, `history_seats` and `history_markers`, `map_plays` and `site_stats` with `site_stats_hours`, schema version 4) and the foundation: a `meta` table with the time the file was made and the table `schema_version`.

- **Where**: `ants.db` in `--results-dir` (the Docker image: `/results/ants.db`, on the volume), or the file named by `--db`; `--no-db` keeps none. The library is SQLite 3.53.4, vendored in `third_party/sqlite/` (public domain, [`README`](../third_party/sqlite/README.md)), behind the small wrapper `ants_db` (`include/ants_db/`): no exceptions, one `Database` object, used from the server's one main thread (SQLite is built without mutexes).
- **How it is opened**: in WAL mode with `synchronous=NORMAL` and foreign keys on, so a crash loses at most the last transactions and never corrupts the file. Beside `ants.db` the server therefore has `ants.db-wal` and `ants.db-shm` while it runs; they belong to the file. WAL needs a shared-memory file, which a network or some bind-mounted volume cannot give: then the server **does not stop**, the file keeps SQLite's ordinary rollback journal, and the log line says so (`journal mode delete; the file system gave no WAL ...`). Keep the volume local to get WAL. WAL is asked for only **after** the file passed the checks below, because switching it writes to the file's header.
- **Start**: the server opens the file, brings it to the schema of this program and logs one line, `database <file>: schema version N`. The causes of a startup failure (status 1, one message naming the file) are: the folder cannot be made or written, the file is not a database or is damaged, it is a SQLite file that this program did not make (tables and no `schema_version`), it was made by a **newer** program (its version is higher than this program's last migration), or a migration fails. Until a migration runs (every cause but the last) the file is left **byte for byte as it was** (no WAL switch, no side files, nothing deleted); a failing migration is rolled back whole, and `--no-db` starts the server without a database.
- **Schema versions**: the list of migrations is in `src/ants_server/db_schema.cpp`; each is a number and SQL, applied in order, each in a transaction with its row in `schema_version`, so a migration that fails leaves the database as it was. A change to the schema is a new entry at the end, never an edit of an old one. Version 1 makes `meta`; version 2 makes the three tables of the match history (an index for every filter and sort of the list, checks that keep a bad row out, a nullable `details` column reserved for the match details of a later step); version 3 makes `map_plays`; version 4 makes `site_stats` and `site_stats_hours`.
- **Map play counts**: `map_plays` has one row for each map that was played: the file name and the hash of the file (FNV-1a 64, 16 lower-case hex digits: the `file` and `hash` of `Community-Maps/maps.json`; the six original maps are keyed the same way, by the hash of the `.LVL` the match used, so another file under the same name is another map), `plays` and `last_played` (the end of the newest match that counted). A match is one play when a person took part (a match of computer players only is not) and it ran at least 600 turns (30 seconds), however it ended: a draw, a quit and a time-out count as the history records them. It is added in the very transaction that keeps the match in the history, the first time the match is kept, so one match is one play whatever happens to the server (a restart, a record that is kept again, a match the owner took out) and nothing is counted for a match that the server never recorded (a cut-off by a redeploy). The recordings that the history has not counted yet when the server first runs with this table (up to 30 days) count too, as the history backfills them; matches already in the history have no hash and are not counted. `HistoryStore::map_plays` reads every row (for the list of maps; nothing serves it yet). With `--no-db` or `--no-history` nothing is counted and nothing is lost: the match path never touches it.
- **Site statistics**: `site_stats` has one row for each counter (`online`, `local`) with its `total`; `site_stats_hours` one row for each hour of the last 24 in which something was counted (`hour` is the hour number on the server's clock, `games` at least 1); the UTC day the counters count from is the `meta` row `site_stats_since`. The server rewrites the three in one transaction (a failure rolls back and leaves the last numbers), which keeps the limits and the rules of "The site statistics" as they were. The counters are numbers only, and no retention applies beyond the window of 24 hours. The first start with the tables reads the `site-stats.json` of an older server into them (once; the file is left as it was, so a rollback to the older server finds its numbers, a little behind), see there. With `--no-db` the file is used as before.
- **Not in the database yet**: the rooms' restart records (`restart_record.hpp`, "Restart records" in [`NETWORK_PORT.md`](NETWORK_PORT.md)) stay files in the folder `restart`. A record is appended one turn at a time with one `write()` before the turn is sent to anybody, which is what lets a restart lose no turn; moving it needs a design of its own for that guarantee (a transaction for each turn of each room at 20 a second, or a log that is still a file), so it is a step of its own.
- **Backup**: copy the file while the server is **stopped** (a clean stop leaves one self-contained `ants.db`; copy `-wal` and `-shm` with it if they are there), or let the program make a consistent copy while it runs (`Database::backup_to`, SQLite's online backup; nothing calls it yet).

Tests: the suite `test_db` ([`TESTING.md`](TESTING.md), 2.31) and the options part of `tests/scripts/test_ants_server.sh`.

## The stack (Docker)

### The server image and the example service

`Dockerfile.server` builds the program alone (no SDL, no game assets except the six maps: `-DANTS_BUILD_APP=OFF`) and runs it as an unprivileged user with a healthcheck (the game port accepts a connection). The image carries the six maps of the original game in `/maps` and the players' maps in `/community-maps`, and the server makes its control secret when none is given. Its entry point already passes `--maps /maps --community-maps /community-maps --public --ws-any-interface --ctl-any-interface --replay-any-interface --results-dir /results`, and its default command is `--port 4001 --ws-port 4002 --ctl-port 4010`.

`docker-compose.server.yml` is an example service. A secret and a maps folder may come from a `.env` file next to it (`.gitignore` keeps that file out of the repository). Only the game port is public; the WebSocket and control ports are published on the host's loopback address only.

```bash
docker compose -f docker-compose.server.yml up -d --build
```

The service joins the external network `proxy-network`, which must exist: for a server alone, create it first with `docker network create proxy-network`. Other containers on that network can reach the control port (it is behind the secret) and, in the stack file, the replay port (read only, no secret), so put no container there that you do not trust.

### One stack for the site and the server (Portainer)

`docker-compose.stack.yml` holds both services, `ants-beta` (the web game) and `ants-server`, on the network `proxy-network`, which must already exist on the host (it is declared `external`). `docker-compose.staging.yml` is a second copy of it that runs next to it for trying finished work ([`WORKFLOW.md`](WORKFLOW.md#deploy-from-ci-and-the-staging-site)).

In Portainer: Stacks, Add stack, Repository, this repository, reference `refs/heads/main`, compose path `docker-compose.stack.yml`. Let the stack's webhook do the updates and leave the stack's own Git polling off, or it deploys by itself: the deploy job of CI calls the webhook after the tests pass and the server is idle ([`WORKFLOW.md`](WORKFLOW.md#deploy-from-ci-and-the-staging-site), "Deploy from CI and the staging site"). The first deployment builds both images and takes several minutes.

Nothing else has to be set. The server uses the maps of the image (a volume `ants-maps`, filled the first time, for the six; the players' maps are read from the image itself), makes its control secret, and allows the demo rooms of `web/lobby.html`: 48 at a time, each waiting up to ten minutes for its players and each with a turn log of at most 4 MiB (`--log-mb 4`, so that the rooms cannot use up the 256 MiB that all the logs share). The page chooses the map among the six of the original, and every match that its card starts takes a demo room, a game against bots only too (since v0.8.0). Whoever reaches a game port, the site or TCP port 4001, can fill them. The server also keeps the matches that ran 30 seconds or more, the demo rooms' too, for 30 days and 100 MiB together, and the site lists them and gives them out: `/replays` is public and read only, and the names that the players typed are in it ("Replays").

Optional environment variables, set in the stack's "Environment variables" (they are not part of the repository):

| Variable | Default | Meaning |
|---|---|---|
| `ANTS_SERVER_SECRET` | the server makes one | The control secret ("The control secret"). |
| `ANTS_MAPS_DIR` | the volume `ants-maps` | A host folder instead of the maps of the image. It must hold the demo map and every map of `ANTS_DEMO_MAPS`, or the server stops at startup. To refresh the volume after an update that changes the six, remove it; to add maps, copy them into it. The players' maps (`/community-maps`) are not in the volume and need none of this. |
| `ANTS_DEMO_ROOMS` | 48 | How many demo rooms the page may make at a time: 1 to 255. **0, or 256 and more, make the server exit at startup, and with `restart: unless-stopped` that is a restart loop.** Keep the number times the stack's `--log-mb` (4) under 256, the MiB that all the turn logs share. No variable switches the demo rooms off: delete the three demo options from the `command` in your copy of `docker-compose.stack.yml`. |
| `ANTS_DEMO_MAP` | `TREASURE.LVL` | The map of a room whose create block names none that the server lists. |
| `ANTS_DEMO_MAPS` | the six maps of the original | The maps a create block may choose: file names separated by commas, blanks around a name are dropped. The page offers the six maps of the original, so list them all: a block with a map the server does not allow gets the default map, with the seats the page asked for. |
| `ANTS_REPLAY_DAYS`, `ANTS_REPLAY_MAX_MB` | 30, 100 | How long the server keeps the replays (1 to 3650 days) and how much room they may take together (1 to 4096 MiB, the oldest go first). **A value out of range makes the server exit at startup, and with `restart: unless-stopped` that is a restart loop.** |
| `ANTS_REPLAY_PORT` | 4020 | The port, inside the container, of the public list and files of the replays. **Leave it at 4020 or set `0`**: 4020 is where `docker/nginx.conf` passes `/replays` to, and any other number leaves the server listening where nginx does not look (the site answers 404, as if the list were off). It is not published on the host. `0` switches the public list off, and with it the public names of the players. |
| `ANTS_BOT_MATCH_EVERY_MIN` | 60 | Minutes between two matches of computer players that the server plays itself (5 to 1440; 0 plays none): see ["Matches of computer players"](#matches-of-computer-players). **A value out of range makes the server exit at startup, and with `restart: unless-stopped` that is a restart loop.** |
| `ANTS_PORT` | 19980 | The host port of the web page. |
| `ANTS_SERVER_PORT` | 4001 | The host port of the game port: TCP only, and only native clients use it; the browser pages reach the server through `/ws` of the site. |
| `ANTS_SERVER_WS_PORT`, `ANTS_SERVER_CTL_PORT` | 4002, 4010 | The host ports of the WebSocket port and the control interface, both on the host's loopback address only. |
| `ANTS_BUILD_ID` | the commit of the clone's git files, else the UTC build time | The build id that the page's footer, the changelog page and `ants_server --version` show. |

The server's container is given **15 s to stop** (`stop_grace_period`, in the staging stack and the example service too; docker's default is 10 s). On `SIGTERM` it makes the restart records of its running rooms durable and exits within a moment. A redeploy recreates the container, and the server that starts again brings the matches back. **Keep the volume `ants-server-results`**, which holds the restart records, the replays and the control secret: a stack that is removed with its volumes loses them.

The server container is read-only, with no capabilities and no new privileges, and it may run at most 64 processes (`ants-beta` also runs with `no-new-privileges:true` and `pids_limit: 256`): it needs nothing but its sockets and the results folder. The WebSocket port is reached by the site's nginx over `proxy-network` (`/ws`, `/busy`, `/stats` and `/stats/local`), and so is the replay port (`/replays`).
