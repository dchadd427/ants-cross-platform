# Setting up a match in the browser: players' maps, the map, Game type and Fog of War

Part of [Play in the browser](PLAY_IN_BROWSER.md): the front page, the room and the game page. The picture, the sound and the asset catalog are in [PLAY_PICTURE.md](PLAY_PICTURE.md).

## Players' maps in the browser

The game's file system holds the six original maps only (the data package), so a room that plays a map of the community needs its file in the browser first. The site serves each one at `/maps/files/<percent-encoded name>` (`docker/nginx.conf`, from a folder of the web image that also holds the six originals, so that the Map Maker can open one as a starting point; the game itself never fetches an original; the list is `GET /maps`, [SERVER.md](SERVER.md#the-list-of-maps)). `web/map_files.js` does the fetching; the game (`src/ants_app/map_fetch.cpp`, `application_maps.cpp`) only asks and polls once a frame, so the lock-step never waits inside a call.
- **In the room:** when the room names a map that the maps folder lacks, the game asks for it (no hash yet), so it is usually here when START comes.
- **At the Start:** the game asks again with the Start's FNV-1a 64 hash and the match does not load until the file is written into `Original-Ants/Maps` and its hash is the host's (the script checks it, and the game checks it again as for every map). The room's load barrier (60 seconds) is the only wait: every machine reports when its file is in, and the match begins when all have.
- **When it fails** (404, no connection, a 5xx twice, a page that is not a map, a file over a megabyte, 25 seconds without an answer, another file than the host's): nothing is kept, the machine reports that it cannot load, the start is cancelled for the whole room, and the reason is on the status line and in a toast. The leader's next START asks again (the HTTP cache keeps a good file for an hour, the page for the visit).
- **Recordings:** the page reads the map's name and hash from the recording's head and writes the map in the game's `preRun` before the game starts: the recording's own copy when it carries one (`tmap`, [REPLAYS.md](REPLAYS.md#the-file)), else the file, fetched and checked the same way; a map that cannot be had is the card "can't show this match". A recording of a map taken off the site cannot be watched.
- The other ways into a match (a rejoin after a reload) go through the same Start, so they fetch the same way. Native builds have no fetcher: their maps folder is all there is.

## Choosing a map

The map side of the lobby is one **map card**: the picture, the name, chips (the kind, then the players, minutes and size that the list knows) and the host's **Change map** button (a guest sees the card without it), which opens the list of every map that the game server offers (`web/front/map_picker.js`, built from `GET /maps` once for the visit, [SERVER.md](SERVER.md#the-list-of-maps)) under **The six originals** and **Players' maps** (default sort), the room's map tagged **In this room**, and a preview of the picked map beside it on a wide screen or a phone on its side. It is a dialog on a wide screen and a sheet at the bottom of a phone (720 px and narrower).
- **Views:** Detail (default: a 64 px picture, the name with the Original badge, players, minutes and size, the description and the play count) and Thumbnails (130 px pictures with the name and the count). The switch is kept in this browser (`localStorage` key `ants.mapview`; a browser that blocks storage forgets it).
- **Pictures:** every page that shows a map's picture (the card and this list, Open games, the match history and a match's page, the map of deaths) gets it from `AntsMapPicker` (`previewPath`, `thumbFor`, `showPicture` in `web/front/map_picker.js`): the list's own address when the list is there (`/front/preview_<word>.png` for an original, `/maps/previews/<name>.webp` for the library, `.png` for an approved map, which the server draws with the game's own renderer: [`MAP_SUBMISSIONS.md`](MAP_SUBMISSIONS.md#pictures)), else the address that the file name makes (a test map of the Map Maker, `<name> ~test-<8 hex>`, has only the `.png`, so it asks for that first). An address that does not answer is asked again once in the other ending, and then (a map of the players: the server draws its picture behind the request, [`MAP_SUBMISSIONS.md`](MAP_SUBMISSIONS.md#pictures)) the PNG address is asked again after a pause, six times in about 50 seconds, before the square is left plain (an address that ran out of tries is not waited for again for a minute), a picture that came is remembered for the next time that its name is asked for (a list that is drawn again makes no second 404), and a page that gets the list late (the match history) draws a square again at the list's address. A picture is shown whole in its square (`object-fit: contain`), so a map that is not square is not stretched.
- **Search and sorts:** the search takes words that must all be in the name or the description. The sorts are *Originals, then plays* (default: the six originals in the server's order, then the players' maps by plays, most first, ties by name), *Most played*, *Name* and *Size* (the map's area, smallest first). A search waits for the typing to pause; one with no result says `No map is called "<text>".` and "Try fewer letters.". The search box says how many maps there are; the fine print under the list says that plays count only matches with people in them that lasted 30 seconds or more.
- **Choosing:** a click or the arrows pick a row, **Choose map**, a double click or Enter choose it, Esc closes, also with the focus on the page's body (Tab stays in the dialog, the page behind it is `inert`, the focus goes back to the button). On a touch screen the search box does not take the focus; the sheet follows `dvh` and the safe area, and the sorts are one row that scrolls sideways. A choice is sent only if the page is still the room's host and START is not pressed; the list closes by itself if the room changes hands. An original sets the room's map; a map of the players is sent by its file name in the same Plan message, shown under its own name and picture on the card, and fetched into the browser's cache at once so the game page finds it ([Players' maps in the browser](#players-maps-in-the-browser)).
- **Random map:** a row under the sorts (the die, "Random map" and a button, **Pick one**, which becomes **Pick another** after a pick). The button hands the room one map that the list shows at that moment (a search narrows it), that is not the room's map now, not the one that was just picked and not one that the room cannot play ("Too many ants to play online"), at once and as a click on Choose map does (the same check that the room is still the host's, the page then shows it on the map card like any pick); the list stays open, the pick is the picked row and, when the room has answered, marked *In this room* (the page calls `refresh()` of the picker when the room's map changes), so that the button can be pressed again. Nothing is on offer when no other map is shown. A phone's sheet leaves out the words after "Pick one now". Tests: `tests/scripts/web_map_picker_check.js` (group 16) and the mutants of `test_web_map_picker.py`.
- **A game for one** (no other person, no computer player) is the game page's own single player, on a map of the players too: START takes the tab to `/play?mapfile=<file name>&name=<name>&aspect=<shape>`, the page fetches the file from the site while the game's data downloads (`fetchOnly` of `web/map_files.js`, no hash to check: nobody else plays it) and writes it into the game's maps folder before the game starts, and the match is the same `--alone` game as on an original (it ends with the clock or when your last ant and egg are gone, never because nobody else is left). The line under START reads "A game for one" as for an original. A file that cannot be had is a card ("The map could not be downloaded"): with a network error it has a Reload button, and when the server says the map is gone (404 or 410) it says so ("... is not on the server (it may have been taken off). Choose another map.") and the button is Menu. A room whose map is a text the game does not take as a file name (neither one of the six nor a valid file) is not started alone: the lobby says so in a line and keeps the room, instead of playing Treasure under another map's name. A map that is broken (a color it claims has no start marker, so no ant, or a world of water) or that lacks a hill or starting ants for any of the four seats (the 1 v 1 maps among them) is not kept in `Community-Maps/` ([its README](../Community-Maps/README.md), "Taken out again"). A removed map is gone from the lobby's map list and the map picker (they list what the server's maps folder holds), and a kept replay (90 days) of a match played on one can no longer be watched, as the player fetches the map by its name. The beta picks the smaller set up at its next deploy: the images copy the maps and nothing of them persists.
- **Until the list is there, or when it cannot be had** (an error, or no answer in 12 s) the dialog holds the six originals, from the page's table (no play counts), under the loading note or a failure message with Try again; without `map_picker.js`, Change map steps to the next of the six; opening the list again, or a room that is on a map of the players, asks again (the latter at most every 15 s).

## Game type

The match side of the lobby has one **Game type** field under the map (`web/front/game_type.js`, `game_type.css`), made from a list of rows in `web/front/game_modes.js`: a game type is **one row of data** (its number in the plan and Room messages of network protocol 17, its word, the name, a short tag, a one-line explanation and an optional note), so the page needs no new button or code path for a new type. A new type is more than the row: its number must also become the protocol's last game mode (`LAST_GAME_MODE` in `web/front/lobby_net.js`, `sim::kLastGameMode` and `valid_game_mode` of the server; the codec refuses a Room message above it, which is by design, so an older client refuses a newer room: a protocol bump) and the simulation must play it. Today there are two: **Highest score** (the original game, the default, no tag) and **187** (tag `187`; note "No food and no power-ups. The most kills wins."; [GAMEPLAY.md](GAMEPLAY.md#187-a-game-type-of-the-remake)).

- **The leader** sees the field with the chosen type's name and its line under it, and the note when the type has one. A click, a tap, Enter, Space or Down opens the list: a drop-down under the field that scrolls inside itself after about five rows (300 px) and opens on the chosen row, or, on a phone (600 px and narrower), a bottom sheet of at most 60% of the screen with the title "Game type" and rows of at least 64 px over a dimmed page. It is the ARIA select-only combobox (the field keeps the focus and names the row under the cursor with `aria-activedescendant`; the list is a listbox, the chosen row `aria-selected`): the arrows, Home and End move, Enter or Space chooses, Escape or a click outside closes without choosing, Tab takes the row under the cursor (the select-only pattern) and lets the focus go on, a focus moved away by a script closes, and typing the first letters of a name jumps to it. A choice is the leader's plan with the new mode (the plan always carried one; the room applies it at once and tells everybody), so there is no protocol change. Until a Room message says the new mode, the page keeps it as the pending mode and every plan it sends in between (a bot's level, the map, the team mending) carries it, so a quick second change cannot put the old mode back. The field is disabled once START is pressed.
- **A guest** has no field: one read-only line under the map, "Game type: Highest score" or "Game type: 187", with the type's line under it. It changes by itself when the leader chooses.
- **The tag** (the type's short name, none for the default) sits by the room's name in the room panel's heading, for the leader and the guests. The lobby has no list of open rooms, so the header is the one room summary that carries it.
- **A new room starts with the leader's last choice,** kept per browser in `localStorage` under `ants.lobby.gameType` as the type's word. Only a room that this page made takes it (not a room that was joined, nor a rematch, which keeps the type that the server kept); a word that no row has gives the default, and a browser that refuses its storage simply starts every room with the default.
- **A number that no row has** is shown as **New mode** (its tag, its name for the leader and, when a name is given, the guest's line says that name instead); no row is marked and nothing is thrown. This is a defensive display only: it cannot reach the page over the wire today, because the codec of `lobby_net.js` refuses a Room message with a mode above the last one it knows, by design. The control and the functions take any number.
- **Tests:** `tests/scripts/web_game_modes_check.js` (the rows, the pure functions and the control on a fake of the DOM, with the mutants of `test_web_game_type.py`) and the opt-in browser check `web_game_type_browser.py` (`tools/web_without_docker.py -- tests/scripts/test_web_game_type.sh [--shots DIR]`: the leader and a second browser that joins, the keys, the phone's sheet, the remembered choice, and a list with added rows).

## Fog of War

The leader of a room switches **Fog of War** in the **Rules** sheet, the second row after Who can join (`web/front/room_fog.js`: a button with the role `switch`, the look of the Direct connection switch, in `lobby_direct.css`; Space and Enter work). It is the room's rule: the leader's plan carries it (the last byte of the plan, network protocol 28: [`NETWORK_PORT.md`](NETWORK_PORT.md#protocol-28-fog-of-war-in-the-leaders-plan)), the Room message shows it to everybody, and the match is made with it. A new room starts with fog off; the browser keeps no choice of it.

- **The leader** has the switch, and the row's line says what it does ("Hides the map on players' screens. Not cheat-proof yet. No bots with fog."); while fog is on the **Rules** button says "Fog" after who can join. The line's honesty: (every machine of a match still holds the whole state, so a changed game can see through it; the server-side redesign will remove the note). The switch shows what the Room message says, never the press; a press that no Room has answered yet is kept as the page's pick, so that the next plan (a color, a map, the teams, two colors that swap their plans) does not carry the old value back; the same holds for the game type, which every one of those plans carries. While START waits the switch is off.
- **A guest** reads the switch (it shows the room's state and takes no press), and the **Rules** button says "Fog" while it is on. The room's chat says it to everybody when the leader switches it ("Hazel turned Fog of War on."); the marks of Ready stay as they were ([`READY_UP.md`](READY_UP.md)).
- **No computer players with fog** (the rule of [`BOTS.md`](BOTS.md): a bot would see through it): while fog is on, the menu of a color has Easy, Medium and Hard bot off (Open and Closed stay) and says why when one is pressed anyway, and a plan with fog and a bot color is refused as a whole by the room with the notice "Bots cannot play with Fog of War." When the leader presses the switch with bots planned, the Games list's own notice asks "Fog of War has no computer players. Set Blue to Open and turn fog on?" with the button **Turn fog on**: one plan then sets the bot colors to Open and fog on. A rematch of a fog match is a fog room.
- **The Games list** says it: the tag **Fog** beside the map's name on an open card and in the tags of a locked card ([Home](HOME_GAMES.md#games-quick-join-quick-host-and-the-public-room); the rows carry `fog`, [`PUBLIC_ROOMS.md`](PUBLIC_ROOMS.md)). A match with fog is not on the live board while it runs ([`SERVER.md`](SERVER.md)).
- **The room still fits** at 1920 x 1080, 1600 x 900, 1366 x 768 and 1280 x 800 with the sheet open as well as closed (`tests/scripts/web_room_in_home_browser.js` measures it).
- **Tests:** `tests/scripts/web_room_fog_check.js` (the switch, the plan bytes, the guest, the question, the menus, the pending pick, the swap of two colors; the mutants of `tests/data/room_fog_mutants.json` through `test_web_room_fog.py`), `web_lobby_net_check.js`, `web_lobby_client_check.js`, `web_lobby_rules_check.js`, `web_home_games_check.js`, the C++ `test_lobby` N4.65 - N4.68, `test_lockstep` N2.115 and `test_server` S3.308 - S3.310.
