# Counting the site's visits

The site counts its own visits, with no cookie, no address kept by the counter and no third party (the web server's own log is another thing: see "What is never kept"). The numbers are for the administrators only, in the **Analytics** tab of the admin page ([`MAP_SUBMISSIONS.md`](MAP_SUBMISSIONS.md#the-admin-page)). This page is the one home of how the counter works and what it keeps; the words that the visitors read are the Legal page's panel "Counting visits" (`web/legal.html`).

Built so far (part 1 of three): the counter, and the views **Overview**, **Visitors** and **Health**. Not built yet, and not shown: the **Game** view (matches by map and mode, peak players online, Quick join waits; part 2) and the **Paths** view (buttons pressed, funnels; part 3), the Matches tile of the Overview, and the disconnects panel of Health (the game server's restart and reconnect records are not at hand in the hub: part 2).

## What is counted

The pages tell the hub, with `navigator.sendBeacon`, a few small events (`web/analytics.js`, loaded by every public page after the update notice; not by the admin page, not in a frame):

| Event | What it holds | What it is for |
|---|---|---|
| `view` | the page's path, the host of the site that sent the visitor (never the page), the width of the window, the browser's language | visits, entry and exit pages, referrers, screen sizes, languages |
| `leave` | the path | ends a visit (the time on the site) |
| `perf` | `load` or `game`, milliseconds, the site's own version | the page's load time, and how long the game took from the page's start to the first picture |
| `error` | `Page` or `Game`, the class of the error, its message, the site's own file and line | the grouped list of errors |
| `visit` | nothing | all that a browser that asked not to be tracked sends |

Nothing else is sent: no cookie, no local or session storage, no id, no mouse, no keys, no fingerprint (the script reads none of the browser's properties for one; `tests/scripts/test_web_analytics.py` pins that it does not touch them). A request that comes from a crawler, a monitor or a script (the User-Agent) is not counted.

The hub checks every field and keeps only the cut-down form (`hub/analytics_events.py`): a path is one of the site's pages (`/`, `/play`, `/matches`, `/match`, `/mapmaker`, `/map-library`, `/legal`, `/changelog`, `/map` for any `/map/<name>`, else `other`); a referrer is a lower-case host name of letters, digits, dots and dashes (no `www.`, no address, never the site itself) cut to its **registered name**, so that a personal address does not name a person (`mail.google.com` is `google.com`, `alice.github.io` is `github.io`, `www.shop.example.co.uk` is `example.co.uk`; the public endings of two labels such as `co.uk` are a short list in `hub/analytics_events.py`, and a name under an ending that is not on it only loses a label, never keeps one); a width is one of five sizes; a language is its first part (`de`); a timing is a whole number of milliseconds from 1 to 600,000; an error message is plain printable ASCII of at most 160 characters with every URL, email, address, long number and token and the text inside double quotes replaced, and a word in single quotes kept only when it is short with no blank (a property name); the file is the site's own script and its line.

## What is never kept

The visitor's **IP address** and **User-Agent** are in the hub for the length of one request (`hub/analyticsdoor.py`, `Collector.take`): the country is looked up, the browser, the system and the kind of device are read, and both are dropped. They are in no table, no file, no log line and no event. Neither is the Referer header (nginx does not pass it) nor a cookie. The log line of the hub for a failure holds the class of the error and nothing else, as the hub's other doors do. The nginx block of the door writes no access log ([`SITE_STATS.md`](SITE_STATS.md) has the other blocks' rule).

**The web server's own log is not the counter's, and it does hold the address.** nginx's access log (`docker/nginx.conf`, `ants_noquery`: the time to the second, the client address, the method, the path without its query, the status, the size and the browser; [`BUILD_AND_RUN.md`](BUILD_AND_RUN.md#what-the-images-nginx-sends-checks-and-logs)) is written for every page that is opened and is **deleted after 14 days**, as is nginx's error log, which names the address of a request that failed (the image does it, not Docker's log: how, and where to read it, is in that section of `BUILD_AND_RUN.md`). The Legal page says so. Because that log has the second, the address and the browser of a page load, an event of the counter that kept its second could be joined to a line of it, and the visitor's code would then name an address. So **the counter keeps no moment finer than the hour** (`events.at` is the start of the hour; the moment of the last event is the hour in the file and the exact second in memory only; an error keeps the day it was last seen). What the sums need of the time is worked out in memory as an event is taken and kept as two small marks on it (below); a restart of the hub forgets where each visit stood, so a visit that a restart cuts in two is counted as two. The order of the events (their row numbers) is kept, because a visit's pages need it; the hour and the order together are far less than the second, but at a quiet hour they still narrow a join, which is why the counter is not described as unlinkable from that log, only as keeping no more time than the hour.

## The visitor's code, the secret of the day

A visitor is a code, `HMAC-SHA-256(secret of the day, address, 0, User-Agent)` cut to 16 hex digits, kept on the events of that day only. The secret is 32 random bytes, **made fresh every Pacific day** and **deleted when the day is over**: the file is written with `secure_delete` so the deleted bytes are overwritten, and the write-ahead log is truncated, so that neither file holds the old secret (`Store.salt_of`; `tests/scripts/test_hub_analytics.py`, `TheVisitorsCode`). From the next day on nothing can say which address a code came from, or that two codes of two days are one browser. The secret of today is kept in the file while the day runs, so that a restart of the hub in the day does not split one visitor in two. A reader that holds the file (a backup, a shell left open) keeps the log from being cut: the cut is tried again every 10 seconds (`Store.settle`, called by the hub's clock) until it is made, so that the old secret does leave the log file. **The day never goes back**: a clock that is found up to 2 days before the day that the counter is in (stepped back across midnight, or a hub that starts with such a clock) is not a new day, so no secret is made or deleted for it and no visitor becomes two (a correction of more than 2 days is taken as a real change of day).

The day is the **Pacific day** (UTC-8, and UTC-7 from the second Sunday of March to the first Sunday of November), made by `analytics_events.pacific_day` without a time zone database, as the admin page's days are.

## New and returning

"Returning" is a link between days, and the only one: a second code (a keyed hash made with a key that exists only in the hub's memory) of each visitor is kept **in memory only** for the last 7 days (`Collector.week`; at most 100,000 codes), so that a visitor's first event of a day can be marked as seen on one of the 6 days before. What is written is one flag on the events. A restart of the hub forgets the memory: the visitors that follow count as new until they come back. The tab says so.

## A browser that asked not to be tracked

Do Not Track (`DNT: 1`, `navigator.doNotTrack`) and Global Privacy Control (`Sec-GPC: 1`, `navigator.globalPrivacyControl`) are respected by the page (it sends one `visit` and nothing else) **and** by the hub (a `DNT` or `Sec-GPC` header makes any event the one minimal visit, whatever the body says). The event holds a time, the day and the **country**, and nothing else: no code, no path, no referrer, no browser, system or device, no timing, no error. To count a visit once and not every page of it, the hub remembers a short code of the address and the User-Agent **in memory only** for 30 minutes (`Collector.nt_seen`; at most 30,000), never written anywhere; a restart forgets it. The tab shows these visits hatched, as "not tracked", in the totals and in the countries, and in no other list.

## The country list

The country comes from a local file made from **DB-IP Lite, "IP to Country Lite"** (<https://db-ip.com>, CC BY 4.0; the Legal page carries the credit line the licence asks for and `THIRD_PARTY_NOTICES.md` names it). `hub/geodata.py` turns the published CSV into a small binary table (IPv4 ranges, and IPv6 ranges by their top 64 bits: a few megabytes, read into arrays of numbers) that is read once at the start. The hub never fetches it: **the image's build does** (`Dockerfile.hub`, a stage `geo`: `python -m hub.geodata build /geo/country.bin GEO_MONTH`). `GEO_MONTH` is the month (`2026-12`); empty is this month, else the one before. The stack passes `ANTS_GEO_MONTH` (`docker-compose.stack.yml`): an operator who sets the new month once a month gets a new list with the next build, and the layer is kept while the month and `hub/geodata.py` stay the same. A build that cannot reach db-ip.com goes on without a list: every country is then "Unknown" and the Health view's panel "The counter itself" says "none". The settings `ANTS_HUB_GEO_FILE` (the file; `geo/country.bin` of the program's folder when not set) and the tests' small fixtures make no network call.

## What is kept, and for how long

One file, `analytics.db` next to `hub.db` (`ANTS_HUB_ANALYTICS_DB`; mode 0600; WAL; `secure_delete` on), so that the chat's schema, its size limit and its purge are untouched (`hub/analytics_store.py`):

| Table | Holds | Kept |
|---|---|---|
| `events` | the hour (never the second), the Pacific day, the kind, the visitor's code of that day (empty for a not-tracked visit), the new-or-returning flag, the two marks of a visit (`vs`: this page view starts a visit; `lb`: the bin of seconds that the visit had run, in `DURATION_EDGES`), the country, the browser, the system, the kind of device, and the checked fields of the event | **30 days** (less if the file reaches its limit, below), then deleted for good (the pages overwritten, the log truncated) |
| `days` | the sums of a finished day: numbers and short lists, no code, no address, no time of an event (an error has the day it was last seen), and a referrer by name only when 3 visitors came from it that day (`hub/analytics_sums.py`) | for good |
| `counters` | the day's events let in and refused and crawlers left out, the sign-ups | 30 days (the sign-ups are in the day's sums) |
| `salt` | the secret of today | until the day is over |
| `meta` | the moment of the first start, the moment of the last event | for good |

The sums of a finished day are made before its raw events go (the hub's hour work, `Store.maintain`), and are made on demand for a day that has none yet. A **visit** is a run of one visitor's pages with no gap of 30 minutes (a page view with `vs` starts it); its entry page, exit page, referrer and country are those of its first page and last page; its time on the site runs from the first page to the last event and is kept as a bin, the bin of that last event's `lb`, so the Overview's average is made from the middle of each bin. **A referrer is named in the sums only when at least 3 visitors came from it that day** (`REF_MIN_VISITORS`; a visitor counts once however many visits it made): the sums are kept for good, and a site that one person came from can name that person. The visits from the other sites are one `other` row, so no visit is lost. The raw events, which go in 30 days, still have the name. A **visitor** is a code that sent a page view that day. A day's top lists keep 60 entries and one `other`; errors keep 200 groups.

The **sign-ups** are the people who log in for the first time (the Discord login's callback finds no profile): a number a day, no name (`Collector.signup`). A person who used Forget me (which deletes the profile) and logs in again is counted as a sign-up again: the count is of first logins of a profile, not of people.

## The door

`POST /hub/a` (`hub/analyticsdoor.py`): one JSON object of at most 1,024 bytes, `Content-Type: text/plain` or `application/json`, from a page of the site only (`Origin` the site's, `Sec-Fetch-Site: same-origin`). The answer is `204` with no body for an event that was kept **and** for one that was dropped on purpose (a crawler, a visit counted a moment ago), so that a page cannot tell. Refusals: 404 (another path, or a query), 405, 400 (no address, a body that is not one JSON object with no duplicate key and no `NaN`, or not an event of a known type), 403, 413, 415, 429 (an address's allowance: a burst of 40, then one every half second, in the hub; nginx has a wider one in front, `ants_hub_a`: ten a second, a burst of 60; and a limit for all addresses together, 100 a second), 503 (`off`). The refused events are counted (`refused` of the day) and shown in "The counter itself". Three more limits keep a flood from filling the day's room or the memory, and each is answered like the others (a `204`) and counted under "Over the day's limit" when there are any: a day keeps at most **30,000 events** for all visitors together (`DAY_MAX`); one address **range** (a /24 of IPv4, a /48 of IPv6) may make at most **50 new visitors a day** (`RANGE_NEW_MAX`; a browser that asked not to be tracked counts too), so that one address that changes its User-Agent at every request cannot take all of the day's room (600 ranges are needed to fill it; a site of this size has a handful of visitors in a range, and a big shared network, such as a mobile provider's, may count fewer visitors than it has: the number is for a site with some hundreds of visitors a day); and the file's own size, below. The range is a keyed hash that exists in memory for the day and is never written; an entry needs a kept event, so the table never holds more than `DAY_MAX` entries. nginx passes the hub only the headers it needs: `Origin`, `Sec-Fetch-Site`, `Content-Type`, `User-Agent`, `DNT`, `Sec-GPC` and `X-Client-Address` ([`docker/nginx.conf`](../docker/nginx.conf), `tests/scripts/test_nginx_hub_analytics.py`).

`ANTS_HUB_ANALYTICS=off` switches the counter off (the door answers 503, nothing is kept, no file is made); it is the kill switch and stays. A file that cannot be opened does the same and says so once in the hub's log; the chat never stops for the counter. The one hook outside the counter is a call in the login's callback for the sign-up count.

## The Analytics tab

`web/admin_analytics.js` and `web/admin_analytics.css`, the page's third file after `admin_bots.js`, in the order **Maps, Chat, Bot matches, Analytics, Log, Status**. One call fills it: `POST /hub/admin/api/analytics {"from", "to"}` (the hub's admin door, same fences as a change, the page's token, no change made: [`HUB_ROLES.md`](HUB_ROLES.md#the-admin-pages-door)); the hub answers the days (visitors, visits, not-tracked visits, sign-ups, errors, timings, versions), the lists of the range added up, the grouped errors, the totals of the same number of days before, and the state of the counter. The range is 7, 30 or 90 days or two dates (up to 400 days; the days are Pacific days; the first day of a custom range may be up to 400 days back).

- **Overview**: tiles for Visitors, Visits (with the not-tracked share), Sign-ups and Errors, each against the days before; a note that a visitor is counted for each day on its own (30 days of visitors are the sum of 30 daily counts); the chart "Visitors per day" (SVG bars, a hatched cap for not-tracked visits, weekends shaded, a card for the bar under the pointer or a tap, "Show as a table" as the accessible reading).
- **Visitors**: countries (bars; the hatched part is the not-tracked share; ten, the others in one row, unknown last), new and returning, where visitors came from, entry pages, exit pages, time on the site (six columns, the middle in gold), browsers, systems, devices and screen width, languages.
- **Health**: page load and game download-and-start (p50 solid, p75 dashed, p95 dotted, per day; a day with fewer than 20 timings has no point; a dotted vertical line on the day a new version of the site first sent a timing), the grouped errors (where, message, file:line, times, visitors, first and last seen, New), and **The counter itself** (last event, events today, refused, crawlers left out, raw days kept, daily totals since, the country list and its month).
- **Export CSV**: Daily totals; Countries, browsers, systems, devices; Pages and referrers; Timings; Errors; or all of them as one `.zip` (a stored zip, no compression). Made in the page from the answer; numbers and the names of the lists only.

A site that sent a visitor and the message of an error came from a visitor's browser, so the hub's answer marks them `untrusted` and the page puts them in as text with `data-untrusted` ([`MAP_SUBMISSIONS.md`](MAP_SUBMISSIONS.md#untrusted-text)). "First seen" of an error is the first day **of the range**.

## Sizes

`web/analytics.js` is about 5.6 KB (2.3 KB gzipped; budget in `tools/size_limits.py`). A raw event takes about 270 bytes in the file, so a busy day of ten thousand events is 2.7 MB and 30 days some tens of MB; the sums of a day are a few kilobytes and kept for good.

**The file is limited as `hub.db` is** (`DB_MAX_BYTES`, 64 MiB: the pages that hold something and the log file; `Store.size`). From 90% the oldest raw days go, once a minute at the most and down to 80% (`Store.make_room`: the sums of a day are made first, so only its events are lost, and yesterday's and today's events never go for room); at the limit new events are dropped and counted until there is room. A day of 30,000 events from 30,000 visitors is 8 MB.

**Memory.** The hub's container has 192 MB (it also holds up to 300 chat sockets: [`HUB.md`](HUB.md)). Measured with `tracemalloc` at every cap together (`tests/scripts/test_hub_analytics.py`, `TheSizeOfTheFile`): a full day of 30,000 events from 30,000 visitors, the week's 100,000 codes, the 30,000 ranges: **17 MB** (the week's codes 9 MB, the visitors' state 7 MB, the ranges 2.5 MB; a day of not-tracked visits only is 15 MB, as their memory is 3.4 MB); and the report's rebuild of that day, which reads the events one visitor after the other and holds none of them, takes under 0.1 MB more. Before these caps (100,000 events a day, 300,000 codes in the week, 100,000 not-tracked visits) the same measure was 36 MB resident and 65 MB more for the report's rebuild, which held every event of the day: about 100 MB of the 192. The test fails when the counter takes more than 25 MB, or its rebuild more than 3 MB, so a cap that is raised must be measured again.
