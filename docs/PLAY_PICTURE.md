# The browser's data, picture and sound, and the asset catalog

Part of [Play in the browser](PLAY_IN_BROWSER.md): the front page, the room and the game page. The map, Game type and Fog of War of a room are in [PLAY_MATCH_SETUP.md](PLAY_MATCH_SETUP.md).

## Authentic 1998 Asset Pipeline

The page downloads one data package, `index.data` (19.3 MB: the whole `Original-Ants/` folder and `assets/hud_art/`), and packs it into the browser's in-memory file system, where the game reads it as it is. It holds the original `ants.chd` (8.4 MB: the sprites, sounds and animations), the six maps, the four pieces of music as MP3 and MIDI files, the bundled font (Libre Franklin and its licence), and the new pictures of the HUD ([`VIEW_AND_HUD.md`](VIEW_AND_HUD.md#hud-art): four files, 4.5 MB; the game decodes only the sheet that its screen needs).

## A 16:9 picture that fills the page

- **The picture**: the game draws a fixed 960 x 540 canvas (`?aspect=16:9` on the page's address), shown in a game box that is 16:9 and as large as fits: its width is `min(100%, the shape's widest slot, (window height - the page's header and bar) x 16 / 9)`, so the whole picture is on the screen without scrolling. The widest slot is a column of `web/shapes.js` (`test_web_shapes.py` states the rule): 1280 CSS pixels, 960 for the classic picture, and a canvas wider than 1280 its own width (32:9: 1920, so that a wide monitor shows it at 1x).
- **Exact pixels**: the box takes the screen's own resolution (CSS size x `devicePixelRatio`, in whole steps of the shape's smallest whole numbers, which `web/shapes.js` works out from its canvas: 16 x 9 device pixels for 16:9, 3 x 2, 8 x 5, 20 x 9, 7 x 3, 32 x 9 and 4 x 3 for the classic picture), so the canvas has exactly the picture's shape and there is no black bar inside the box. The picture and the pointer stay right when the window is resized, the page is zoomed or fullscreen is toggled. On a display of about 100 Hz or more the frame rate is held to 60 a second.
- **Seven shapes, one dropdown away**: the **Picture shape** row of the settings menu, Video (Esc in a match, or the Settings button in the header on every screen of the game, where outside a match it opens a small form with only the page's rows; a button and a list that the page makes, `web/shape_picker.js`, so it opens in fullscreen too; nothing sits under the game for it, so the picture gets that height) lists, first, **Automatic (now 20:9)** ("now" is the shape that Automatic gives at this moment) and then the table's shapes from the narrowest to the widest: Classic 4:3 (the original's picture, 640 x 480), 3:2 (960 x 640), 16:10 (960 x 600), 16:9 (960 x 540), 20:9 (1200 x 540), 21:9 (1260 x 540) and 32:9 (1920 x 540), each as "shape · width x height". A choice changes the picture **at once, in the running game**: no reload, no "Leave the match?" question, no new connection (a joined match keeps its seat and its room), and the simulation is not touched. The browser remembers the choice and the address gets `?aspect=` (without a new entry in the history), so a reload or a link has it. A quiet line under it in the menu, "16:10 fills your screen", names the shape nearest to the computer's screen (within 8%). **Spectators choose too** (`?replay=` and `?live=`): the same remembered choice and `?aspect=` apply, else Automatic, and the replay bar has a **Back 30 seconds** button right of Play / Pause (replays only, not a live match; [`REPLAYS.md`](REPLAYS.md#watching-a-replay)) and a **Picture** button at its right end (on a phone beside the clock) that opens a small window above it with the same dropdown (Automatic first) and line; it closes on a click elsewhere or Esc, works in fullscreen (the window opens above the floating bar), and the bar is as wide as the picture in every shape (a short window, such as a phone on its side, keeps the bar full width so that its buttons fit). With the focus on the button Enter and Space open it and Esc closes it; in the dropdown Enter, Space, ArrowDown and ArrowUp open the list (no key changes the picture of a closed one); in the list the arrows, Home, End and a letter move the mark, Enter, Space or a click or tap chooses, and Esc closes the list alone, not the window (the game gets none of these keys, nor Tab: put the focus there by a click). **Why not a `<select>`**: in fullscreen the mouse is held ("Locked", the default): the real press goes to the canvas and the bar gets a synthetic click, which cannot open a native list; the page's own list is in the stage. A player's game has no Picture control on the page itself, only the menu's row.
- **Which shape**: only the table's shapes (`web/shapes.js`) count. The order: the address (`?aspect=`, for that tab: a shared link; it is never stored), then the hand pick that a dropdown stored under the browser's key `ants.aspect.v3` **for the way the device is held now** (a text that is no shape is nothing; the keys `ants.aspect` and `ants.aspect.v2` of earlier versions are not read, so every browser starts on Automatic once), then **Automatic**. Only a choice in a dropdown writes the key, so "nothing stored" and "picked 16:9" stay different; Automatic's own shape is never stored and never put in the address. **A pick holds only for the way the device was held when it was made**: a 20:9 picked sideways does not stop Automatic when the phone is turned upright, and comes back when it is turned sideways again (the key holds one shape for each way). Choosing the entry that is in use chooses nothing; choosing the shape that Automatic shows now **pins** it (it is stored and put in the address like any pick). Choosing **Automatic** forgets the pick of the way held now and the address's shape (a link's too), and the picture is Automatic's at once.
  - **The rule** (`AntsShapes.automatic`, asked by the game page; the front page only reads the picks): *the screen* is the device's own `screen.width` x `screen.height` in CSS pixels, not the window or the box (`devicePixelRatio` and zoom scale both numbers: only the ratio counts), **long side over short side** (the numbers swap on an Android phone when it is turned and stay on an iPhone). The nearest shape has the smallest ratio of ratios, no cutoff (1440 x 900: 16:10; 1280 x 1024: Classic 4:3; 2736 x 1824: 3:2; 3840 x 1080: 32:9); a new table row counts at once; a tie goes to the narrower. The line "fills your screen" keeps its 8% cutoff.
  - **Sideways and upright** (`AntsShapes.wayOf`): the way comes from `screen.orientation.type`, else `window.orientation` (90 and -90 are sideways), else the media query `(orientation: landscape)`, else sideways; **never** from the screen's numbers. A device held sideways picks by its landscape ratio (a 20:9 phone, 844 x 390, gets 20:9). One held upright gets 16:9, with the tip to turn it. A desktop window made narrow on a landscape screen is still sideways.
  - **When it runs**: at load, and again when the window's width, the way or the fullscreen state differs after `resize`, `orientationchange`, a change of `screen.orientation`, `fullscreenchange`, `webkitfullscreenchange` or a `resize` of `visualViewport` has been quiet for **300 ms** (`AntsShapes.watch`; a window that is dragged gives one switch at its end). A change of the window's height alone (the browser's address bar) is no new pick: the box follows it inside the shape. A hand pick for the way held now, or `?aspect=` in the address, wins over every event; a switch is made with the game's `ants_set_aspect`, the one way the page changes the game's shape, and the view keeps its middle point.
- **The pages in the bigger canvases** (3:2, 16:10, 20:9, 21:9, 32:9): the setup screen, the room, the loading screen, the quick help and the results are the 960 x 540 page centred in the canvas with black around it; the match fills the whole canvas and shows more map when the picture is wider or taller ([`VIEW_AND_HUD.md`](VIEW_AND_HUD.md)).
- **Fullscreen** (the header's button) shows the picture as large as the screen allows, with bars on a screen of another shape; a browser with no Fullscreen API for an element (Safari on an iPhone) gets the page's own fullscreen with a button to leave it (a round x at the top right of the screen; on a phone held sideways it lies in the black margin that the screen's safe area leaves beside the picture, centered, and not over the picture's minimap; a screen with no such margin has it at the corner, over the picture). The bars count as the picture's edge: a pointer over a bar scrolls the map like the edge, corners included.
- **The countdown** (a room with two or more people, 30 s, or one person alone, 10 s: the same card; network protocol 21; [`MATCH_COUNTDOWN.md`](MATCH_COUNTDOWN.md), [`VIEW_AND_HUD.md`](VIEW_AND_HUD.md)): when every game has loaded, the match opens with a card over the map, the seconds left of the count, who plays which color, and the game's own chat, which is open (type and press Enter, or tap the chat box on a phone: the page's field for the phone's keyboard works as in the match). The page lays a **Fullscreen** button on the card (`#countdown-fs`, made by `web/countdown_button.js`) in the place and size of the button that the game draws in the card (94 x 22 units of the card, about 141 x 33 game pixels at the usual scale), scaled with the picture, so it fits the card on a phone held sideways (about 28 x 85 CSS pixels at the page's 0.6); it is never less than 28 CSS pixels tall (the finger floor on a phone) or 80 wide (the word fits on one line), never wider than the card, kept inside the card's bottom edge and clear of the rows above it (the game says where they end, `ants_probe` 67 - 69); its text is 0.55 x the height (12 to 20 px) on one line: a browser grants fullscreen only to a real button's click, and the page that opened the game was another page, so the game cannot do it by itself. It asks for the same fullscreen as the header's button (the browser's, with the mouse held; the page's own on an iPhone) and goes away once the page is fullscreen. A card too small for it has no button of its own: when the finger-floor button would reach up over the card's rows (a picture narrower than about 365 CSS pixels: a phone held upright), the header's Full button is the way, and the card's sentence "Fullscreen is one press away" is true of it. The button fades with the card while the player looks around the map (`ants_probe` 66) and works at any level. A click on the game while the card is up takes no pointer lock (a locked pointer cannot click this button); the lock comes with the match. A game on this computer (the front page's Play and START for one) opens the same card for 10 s (`--start-card-seconds 10`); a room's rejoin, a reload into a running match, a recording and a live view have none. A phone held upright shows the card small (the picture is 350 px wide): turn it sideways and press Fullscreen; with the keyboard open the page scrolls the chat line above it and the count stays in the status line above the chat. The Quit button leaves.
- **The mouse in fullscreen and in a window**: the page holds the mouse for the game (the browser's pointer lock, taken by the click on the Fullscreen button, or by clicking the game during a match in a window; a replay or a live match watched is held the same way in fullscreen, and its bar is reached with the game's cursor, see [`REPLAYS.md`](REPLAYS.md#watching-a-replay)). The game's cursor cannot leave the picture, so every edge scrolls and a Mac's Dock and menu bar have no screen edge to come up at. The row "Fullscreen mouse: Locked / Free" of the settings menu (Video; not on a touch screen) turns the lock off (remembered under `ants.pointerlock`).
- **The settings menu**: Esc with nothing to cancel, or the **Settings** button (in the header after Menu at every width, the gear alone below 1140 px, and in a replay's bar; never over the picture, so none in fullscreen: leave fullscreen first on a phone, a known gap), opens a panel over the game, in a small form with only Fullscreen, Picture shape and Fullscreen mouse on the screens that are not a match ([`GAME_MENU.md`](GAME_MENU.md)); the pointer lock is let go while it is up and asked for again by Resume.
- **Releasing the mouse (`Ctrl+Alt` or `Esc`)**: holding **`Ctrl+Alt`** (in either order, `ANTS_PAGE.releasesMouseLock`) releases the captured mouse in a window or in fullscreen; with **Fullscreen mouse: Locked** (the default), a browser that has the Keyboard Lock API (Chrome and Edge) gives Esc to the game in fullscreen, and holding it leaves fullscreen; in other browsers (and in a window) Esc gives the mouse back first. With **Free** the fullscreen is the browser's plain one and the mouse stays unlocked in a window.
- **In a window** when the mouse is not locked, the map keeps scrolling while the pointer is just past the edge of the game, up to 96 CSS pixels (about an inch) beyond the box and corners included; it stops when the pointer goes farther, onto a button or link of the page, or out of the window (clicks, the wheel and the menu there are the page's).
- The page gives the game `--aspect` with the shape it shows (the desktop game's own option, which wins over the settings key `aspect`), and a choice in the dropdown calls the game's `ants_set_aspect`. **One table of shapes**: a shape's name, its words and its canvas are one row of a table on each side, `kAspectTable` in `include/ants_app/canvas_layout.hpp` for the game (the canvas, `--aspect`, the settings key, the words of a refusal and the Esc menu's Picture shape row are read from it, and `ants_set_aspect` takes a shape's place in it) and `web/shapes.js` for the pages (the game page, the front page and the settings menu read it; the front page uses it to check an address's or a remembered shape, the settings menu and the replay's Picture window make their dropdowns, `web/shape_picker.js`, from its rows; the box's steps, the CSS slot's ratio and width and "fills your screen" are worked out from its rows); `tests/scripts/test_web_shapes.py` fails when the two tables differ or a page keeps a list of its own.
- What the wider picture shows (the map view, the frame, the HUD) is in [`VIEW_AND_HUD.md`](VIEW_AND_HUD.md#169-by-default-a-wider-view-with-more-of-the-map-desktop-and-web-builds). The setup screen in the browser is the wide one with its map preview ([`CONTROLS.md`](CONTROLS.md#the-169-setup-screen-desktop-and-web-builds-the-960-x-540-picture)).
- The opt-in `tests/scripts/test_web_aspect.sh` and `tests/scripts/test_web_edge.sh` check the picture and the pointer in a real browser (they need a running page and a Chromium-based browser). `web_aspect_check.py --auto-only` turns an emulated phone both ways in a match (an Android-like screen whose numbers swap, an iPhone-like one that keeps them). Automatic's rules run without a browser in `tests/scripts/web_auto_shape_check.js` (fake phones, every event, the 300 ms wait, the picks of each way).
- The design and the measurements are in the three items that follow: "The page's picture", "The pointer in fullscreen" and "The margin of a windowed page".

* **The page's picture (widescreen milestone M5, `web/shell.html`, `web/lobby.html`)**: the game page starts in Automatic's shape (nearest the player's screen, for the way the device is held) and offers the table's seven shapes after Automatic; the page passes the choice to the game as `--aspect <name>` (the desktop's own option, `Application::choose_aspect`; `kWebDefaultAspect` is 16:9). **Which shape**: the address, the stored pick for the way the device is held, Automatic ("Which shape" above). The front page has no shape control; its START hands the game `&aspect=` only after a pick for the way held now (the game page works out Automatic at its own load). **The boxes**: `#game-stage` is the slot (CSS: width `min(100%, --stage-max, (100dvh - --chrome) x --ar-w / --ar-h)`, `--chrome` = the height of the header, the recording's bar or the rematch strip, the paddings and the room under the framed box (the ring's reach and the side space, under the strip while it is shown), measured by the page; the ratio and the widest width of the shape come from its row of `web/shapes.js` as three custom properties of `<body>`, `--ar-w`, `--ar-h` and `--stage-max`: 16:9 and 1280 px until the script sets the shape's own) and the element that goes fullscreen; `#game-container` is the picture's box inside it, sized by the page (`ANTS_PAGE.fitBox`) to a whole number of the shape's canvas steps with the largest that fits, centred. **Why exact pixels**: the game's window system (SDL's Emscripten driver) sets the canvas to `floor(CSS size x devicePixelRatio)` of the canvas's box on every `resize` of the window (measured: a box of 1000 x 562.5 CSS pixels gave a canvas of 1000 x 562, 853.33 x 480 gave 853 x 480, at 1.5x 853.33 x 480 gave 1279 x 720) and takes its first size from the box too; the game then draws its logical canvas into the real one with the largest scale that fits, centred, with black bars where the shapes differ, so a canvas of the wrong shape by a pixel has a black line of its own. With a box of exactly 16 x 9 steps the canvas has the picture's shape exactly and no bar of the game's shows. A CSS size that is exact stays exact (a device ratio with at most six binary places, 1, 1.25, 1.5, 2, 2.625, 3 ..., makes exact products with a size that is a multiple of 1/64, which is a whole or a half pixel, so that the floor cannot lose a pixel: 1600 / 1.25 = 1280), any other size gets a quarter of a device pixel more (`ANTS_PAGE.cssFor`) which the floor drops and the layout's rounding (1/64 px in Chrome and Safari, 1/60 in Firefox) cannot take away. **The bridge**: SDL listens to the window's `resize` event only (and reads the device ratio at that time: measured, a change of the ratio changes nothing until the next `resize`), and a fullscreen toggle, a header that wraps, or a move to a screen of another density does not always send one (reproduced in the research for the page). The page observes the slot, the header and the bar (`ResizeObserver`), the fullscreen change (`fullscreenchange`, `webkitfullscreenchange`: again after 150 and 600 ms, as browsers settle at different times), the window's `resize` and the device ratio (`matchMedia("(resolution: Xdppx)")`), sizes the box, and sends a `resize` of its own whenever the box's device pixels change. **The pointer**: the browser's mouse position reaches the game through Emscripten's SDL as `trunc( trunc(clientX - trunc(box.left)) x floor(box.width) / box.width )` (library_html5.js stores `clientX - (rect.left | 0)` as an integer; SDL 2.28's `Emscripten_HandleMouseMove` scales by `window->w / client_w`, and `window->w` is the CSS width cut to a whole number), and the same for y. Two terms of it move the reading by up to a pixel: the cut of the box's position (a box at 68.98 read one pixel too high) and, for a box whose CSS size is not a whole number, the scale `floor(width) / width`, a hair under 1, which turns every whole offset t into t - 1 (a box of 720.19 read one pixel low across the whole box). `ANTS_PAGE.snapOffset` says where the box must stand: a box whose size is whole (scale exactly 1) on a whole pixel, any other 1/64 px (the layout's step) short of one, which puts back the pixel that the scale takes away; `snapBox()` shifts the box by that (at most half a pixel, with `left` / `top`) after every layout and on every scroll. Measured with the real mouse (the hover edges of the setup screen's START button, `--pointer`): before, up to 0.94 CSS px off (1280 x 720 at 1x: top and bottom -0.94; 1536 x 864 at 1.25x: +0.94; 1000 x 640 at 1x: left and right -0.94); after, 0.06 (the bisection's own step) at every layout (1280 x 720 at 1x, 1000 x 640 at 1x, 1536 x 864 at 1.25x, 1500 x 844 at 1.5x, 1280 x 720 at 2.625x, 844 x 390 at 3x). The box keeps its size, so the picture is as large as before. **Fullscreen**: the stage goes fullscreen, black, and the box is the largest picture of the chosen shape that fits the screen, centred (bars are the stage's black, not the game's); a browser that has no `requestFullscreen` for an element (Safari on an iPhone) or refuses it gets the page's own fullscreen (`#game-stage.pseudo-fullscreen`: fixed over the window, the safe areas respected, a button to leave it; the page behind does not scroll). **The frame cap**: the game's loop is `requestAnimationFrame`; the page wraps it with `ANTS_PAGE.makeFrameLimiter`, which keeps measuring the display (the MEDIAN of the last 24 gaps between display frames: below about 100 Hz nothing is touched, above it the game draws 60 frames a second by a schedule that keeps its phase), so a 144 Hz display does not draw the game 144 times a second at its full resolution. A median, because the smallest gap would cap a jittery 60 Hz display by mistake (a short gap now and then), the first frames of the game (loading) would decide for ever if only the first ones counted, and a long frame of a hidden page is an outlier; a window that moves to a display of another rate is measured again within a dozen frames. **The data download**: the file packager of `index.js` downloads `index.data` (14.7 MB) with an `XMLHttpRequest` whose `onerror` throws, which nothing catches: when several frames of `web/lobby.html` (the page had frames until v0.12.0) asked for the file at the same moment the browser's cache refused one download (Chromium: `net::ERR_CACHE_WRITE_FAILURE`, reproduced on beta in v0.0.96 and in the built-in browser) and that frame stayed at "Downloading data (0%)..." for ever. `web/shell.html` therefore downloads the file with `fetch` before it loads `index.js` (`Module.getPreloadedPackage(name, size)` is called synchronously by the packager at that moment, with the bytes; if the page has none it falls back to the packager's own download, as a browser without `fetch` does): the first try with the browser's cache (a repeat visit is a 304), up to 3 retries (`ANTS_PAGE.downloadWithRetries`, after 0.4, 1.2 and 3 s) with `cache: 'no-store'` so that a cache entry that cannot be written cannot fail them again, progress as before (the size comes from `Content-Length` when the server sends one, else from the size that the last download left in `localStorage` "ants.datasize"), `index.js` and `index.wasm` asked for at the same time (the cache has them when the game asks; measured, the time to the running game does not change); after the last failure the card says so and has a Reload button (`showDownloadError`, also used for a `NetworkError` that the packager throws itself). **What comes back must be the data** (`ANTS_PAGE.badDownload`): a body whose `Content-Type` is `text/html` (a captive portal answers every address with "200 OK") is refused before it is read, and a body that is not the package's size is refused after it (the exact size, which the Dockerfile writes into the page after the build from `stat` of `index.data`; a build outside the Dockerfile has none and refuses anything under a megabyte); a refusal is a failed try like any other, so the retries and the card take care of it, and the file packager is only handed bytes of exactly the size that it names for exactly `index.data` (`Module.getPreloadedPackage(name, size)`), once. `window.antsDownloadLog` lists the tries. **The program's own files** can fail too, and each puts the card up instead of leaving "Downloading data" on the screen for ever: `index.js` that cannot be loaded (the script's `error`), `index.wasm` that cannot be fetched or compiled (Emscripten leaves that to a promise, `Module.ready`, that nobody listens to: the page's `unhandledrejection` handler, only while the game is not ready and no card is up), and a game that does not start `ANTS_START_TIMEOUT_MS` (60 s) after the data arrived (the watchdog); a game that starts after the card was up takes it away. `index.js` is asked for with a `<link rel="preload">` that the script added after the download takes over, so it is one request with one `?v=` (the Dockerfile's `sed` that adds the build's `?v=` now touches `<script src=index.js>` tags only: it used to add a second `?v=` to the page's own address of the script, and the warm-up request was wasted). **Checks**: `tests/scripts/test_web_aspect.sh` (opt-in, not part of `./run_tests.sh`; needs a running web page and a Chromium-based browser) runs the browser checks that the header of `tests/scripts/web_aspect_check.py` lists (the page's logic, the page at desktop and phone sizes, the address and the dropdown, a first visit, a running match, a wide window, the wheel zoom, the loading faults); the script's own exit statuses are checked first (`--exit-codes`: a page that is not there is a skip, a hang or a crash is never one); the game's 16:9 fallback (`kWebDefaultAspect`) by a unit test (suite 3.12).

* **Touch buttons for the keys (`web/touch_keys.js`, [`TOUCH.md`](TOUCH.md#the-hotkey-buttons))**: on a touch screen, during a match that you play, a row under the picture (upright) or a rail at the left edge (sideways) has buttons for All ants (Ctrl+A), Stop, Home, Next, None (Esc) and More; each sends the key a keyboard would, and the settings menu's Touch buttons row turns them off.
* **The pointer in fullscreen (edge-pan, `web/shell.html`, "The pointer in fullscreen: the bars, and the pointer lock")**: a report: on a 16:10 screen the 16:9 picture has bars above and below in fullscreen and the view no longer pans when the pointer goes off the edge of the game (left and right were fine: the picture fills the width). **What was wrong**: the stage, not the canvas, is the fullscreen element, so a pointer over a bar is over the stage: the browser sends the game's canvas nothing (SDL's Emscripten driver listens on the canvas), and the canvas's `mouseleave` becomes SDL_WINDOWEVENT_LEAVE, which sets the game's `pointer_outside_` (no more scrolling: the last position must not keep the map scrolling); measured with the real game in headless Chrome (`ants_probe`): the pointer in the top or bottom bar is gone for the game and the view stays. (SDL 2.28.4 also drops the FIRST leave of a page's life: its window starts with the mouse focus but with `SDL_WINDOW_MOUSE_FOCUS` clear, and `SDL_SendWindowEvent` drops a LEAVE that finds the flag clear; measured as flag 0 and focus 1 right after the game is ready. So the baseline sometimes kept scrolling on the first trip into a bar, and every trip after it stopped.) **The bars**: in fullscreen a pointer over a bar is at the nearest edge pixel of the picture, as in the desktop game, where the window maps the bars to positions outside the picture that `clamp_pointer_event` holds to the edge pixel (the native clamp needed no change; `tests/test_app/test_canvas_layout.cpp` pointer group and `test_app_integration_input.cpp` 7.8f pin the 16:10 screens 1440 x 900 and 1512 x 982, a real fullscreen window of the dummy driver and the 4:3 picture's pillarbox). The page (1) hands the game a `mousemove` at the clamped pixel for every pointer event over the stage outside the box (`ANTS_PAGE.edgePixel` is the pixel that Emscripten reads, `trunc(clientX - trunc(left))` held to `0 .. floor(size) - 1`: the position `size` would be a pointer that left SDL's window; `ANTS_PAGE.clientFor` is the client position that is read as exactly that pixel; mouse and pen only: a tap's emulated mouse events are not a pointer over a bar), (2) does not pass on the canvas's `mouseleave` towards the stage (a capture listener on the window, so it comes before SDL's whenever that was added) and reports a leave of the canvas when the pointer really goes (the stage's `mouseleave`: another monitor; the page's fullscreen left), and (3) leaves a click, a wheel and a context menu over a bar to the stage (the wheel and the menu are cancelled there). The first pointer that the page hands over is preceded by a leave of the same pixel, which takes SDL's focus away and gives it back (an ENTER sets the flag), so that SDL's flag and focus agree from then on and a leave that the page hands over later is delivered. The browser's arrow is hidden over the fullscreen stage (`cursor: none`: the game draws its own cursor at the edge). The windowed page has its own margin (the next item, "The margin of a windowed page"). **The pointer lock**: on a Mac the Dock and the menu bar come up whenever the pointer touches the screen's edge, even in browser fullscreen, and a page can only prevent that by locking the pointer. The click on the Fullscreen button asks for the lock (`canvas.requestPointerLock()` in the same gesture; once more at `fullscreenchange`; a click on the game asks again where the browser let it go, and where the page has held the lock before that click is only that, the game does not get it) when the browser's own fullscreen is made (not the page's own: an iPhone has neither) and the setting is on. While the pointer is locked the browser sends the canvas relative motion (`movementX / movementY`, the position frozen): the page swallows that (a capture listener on the window stops it before SDL's), keeps the game's own cursor (`ANTS_PAGE.lockStart`: the middle of the picture, or the click's position when a click took the lock; `ANTS_PAGE.moveLocked`: the same CSS pixels as the mouse moved, fractions kept, held to the picture) and hands the game that cursor as ordinary absolute motion, so every edge and corner scrolls from the clamped cursor, the way back from an edge is at once, and a click goes where the cursor is. **Why not SDL's own relative mode** (the page requests the lock itself; SDL's `pointerlockchange` listener sets `has_pointer_lock` for ANY lock, and SDL would then treat all motion as relative): Emscripten's `fillMouseEventData` stores `movementX` as an int32 (a browser that reports fractions would lose them on every event), SDL's relative motion needs the mouse focus and a start position that the page has to supply anyway, and a model in the page is a pure function that `tests/scripts/web_edge_check.js` runs (1000 steps of 0.1 px; the edges, corners and the way back; random motion in six sizes) while SDL's is not ours to test; so the page swallows the browser's `pointerlockchange` (window capture, before SDL's listener on the document) and SDL never hears of the lock. When the lock ends (`exitPointerLock`, Esc in a browser without the Keyboard Lock API, another window with the focus, fullscreen left) the pointer is the normal one at once: nothing is handed to the game (its cursor stays where it was: no jump, no click) and the first report of the free pointer over a bar, where it was when the lock began, is not acted on until it has moved by a pixel. **Esc**: in fullscreen with the setting on the page calls `navigator.keyboard.lock(['Escape'])` (Chromium; it needs a secure context and fullscreen) and `unlock()` when fullscreen ends: Esc then reaches the game and HOLDING it leaves fullscreen (and the lock), as the browser says; elsewhere Esc releases the lock first (Safari leaves fullscreen with it). **The setting**: "Fullscreen mouse: Locked / Free" next to the picture's selector (`.seg button[data-lock]`), remembered in `localStorage` under `ants.pointerlock` (`on` / `off`; only `off` turns the lock off, `ANTS_PAGE.lockSetting`; the control is not shown where there is no `requestPointerLock`); Free also leaves Esc to the browser; the bars' rules are the same in both. **For the tests** the game exports `ants_probe(what)` (read-only: the pointer's x, y, whether it is gone, the view's origin, whether a dialog is open, the zoom). **Checks**: `tests/scripts/test_web_edge.py` and `web_edge_check.js` (the quick tier: the pixel over a bar, `clientFor` against Emscripten's own arithmetic, the locked cursor, the setting's block with a page of fakes, the listeners that must exist), and `tests/scripts/test_web_edge.sh` (opt-in: real headless Chrome with a REAL fullscreen and a REAL pointer lock, whose input gives the page real locked motion): on 1440 x 900 every side and corner of the bars scrolls the right way and the game's pointer is the clamped pixel, a walk from the picture into a bar goes on scrolling, back in the picture it stops, a click, a right click, a wheel and a ctrl + wheel over a bar reach the canvas as nothing, the windowed page is unchanged, fullscreen left with the pointer over a bar and the stage left leave the game's pointer gone, 2560 x 1080 and the classic 4:3 picture have their side bars, the page's own fullscreen does the same and asks for no lock; with the lock: the click on Fullscreen gives both, the cursor starts in the middle and follows the motion exactly (an independent copy of the rule), every edge and corner scrolls, a click opens the Options when the cursor is on its button, the release and the way out of fullscreen leave the cursor alone and unlock Esc, a click takes the lock again, a browser that refuses the lock still has the bars, the setting and its key, a slow mouse at device ratios 1 and 2. (The new checks fail on the previous page: 10 of the 20 bar checks.) **Not tested headless**: the Dock and the menu bar themselves (a real screen), that Esc is the game's key and holding it leaves fullscreen (the browser's own interface does that), the browser's own bubbles, Safari and Firefox (no Keyboard Lock API; Safari wants its gesture inside fullscreen: the click on the game is the second chance), a real mouse's acceleration and fractional movement on a Retina screen, a lost focus. **macOS desktop game**: SDL 2.32.10's window delegate answers the system's fullscreen question with FullScreen | HideDock | HideMenuBar when the window has `SDL_WINDOW_FULLSCREEN_DESKTOP` (read from the installed library's disassembly: `window:willUseFullScreenPresentationOptions:`), so `--fullscreen` and Alt+Enter already keep both away for good; a fullscreen Space that the green button or Cmd+Ctrl+F makes carries no SDL flag when the system asks and gets the system's own proposal (auto-hide: both come up at the edge), so `Application::update_mouse_grab` asks for `FullScreen | HideDock | HideMenuBar` itself while the window is in such a Space (`wants_hidden_dock_and_menu_bar`, `-[NSApplication setPresentationOptions:]` through the runtime, an exception caught) and gives the system's behaviour back when it leaves and at shutdown. Not tried on a real Space here (the Mac's screen was locked): it remains to be tried on a Mac.

* **The margin of a windowed page (`web/shell.html`, "The margin of a windowed page")**: a request: going off the screen with the mouse must not spoil the scrolling (agreed: keep scrolling while the mouse is just past the game's edge, about an inch, stop when it goes farther). The same cause as the bars of the item "The pointer in fullscreen": the browser says that the pointer LEFT the canvas the moment it crosses the edge, and the game takes that for a pointer that went away. A pointer that is outside the box but within `ANTS_EDGE_MARGIN` (96 CSS pixels, one CSS inch; a band around the box with square corners: `ANTS_PAGE.marginPixel`) is handed to the game as a motion at the nearest edge pixel (`edgePixel`), the canvas's leave towards the margin is not passed on (a capture listener on the window; a leave with no `relatedTarget` is the pointer leaving the browser window and is passed on), and the pointer is gone, as it always was, beyond the margin, out of the window (`mouseleave` of the document element), over a control of the page (`ANTS_PAGE.overControl`: `a, button, input, select, textarea, summary, label` and the roles radio, button and option: hovering the picture's and the mouse's selectors under the game or the links above it never scrolls the map) and when a scroll or a resize of the page moves the box away from a pointer that did not move. Clicks, the wheel and the context menu in the margin are the page's (SDL listens on the canvas; a button release that SDL sees without a press changes nothing in it); the browser's arrow shows there while the game draws its own cursor at the edge. Not for touch, not for a locked pointer, not in fullscreen. SDL 2.28.4 drops the FIRST leave of a page's life (see "What was wrong" in the item "The pointer in fullscreen"), so before this change the first trip from the game onto a button of the page kept the map scrolling once; now the first motion of a mouse over the game is preceded by a leave of its own (`primeFocusOverTheGame`) and every leave is delivered. **Checks**: `tests/scripts/web_edge_check.js` (the quick tier: `marginPixel` on a table and on a sweep against an independent copy of the rule, `overControl`), `tests/scripts/test_web_edge.py` (the listeners and the constant), and `tests/scripts/test_web_edge.sh --only margin` (opt-in, headless Chrome in a 1800 x 1000 window: 1, 40, 90 and 96 px beyond every edge and 90 px beyond every corner scroll, 97 and 120 px do not, the selectors and links never scroll, a click, a right click, a wheel and a menu in the margin are the page's, leaving the window, scrolling the page under the pointer, a tap, the order of Chrome's and Safari's leave events, the first leave of a page's life).

## 32-Channel Spatial Sound & Soundtrack

The game mixes up to 32 sounds in its own mixer, with volume and left / right pan by distance; in the browser the sound goes through SDL's Web Audio. The sound effects are the 91 sounds of `ants.chd`: the units' voice cues, the explosions and the rest. The soundtrack is the original's four MIDI pieces, `INTRO`, `ANTS2A`, `ANTS2B` and `ANTSFUN3`, played from MP3 renderings of them that the game decodes itself and streams from memory. The sound law and the rest: [`VIEW_AND_HUD.md`](VIEW_AND_HUD.md#sound-and-music), "Sound and music".

## Interactive Asset Catalog

A page that shows every sprite, sound and animation that the game reads from the archive `Original-Ants/ants.chd`, as files you can look at, play and download: **[beta.playants.org/asset_catalog/](https://beta.playants.org/asset_catalog/)**, called "Sprites and sounds" on the site. It is one static page (`asset_catalog/index.html`) with its data (`asset_catalog/catalog_data.js`), the pictures (`asset_catalog/sprites/`) and the sounds (`asset_catalog/sounds/`).

**What it shows.** Three tabs, with a filter box above them that matches an ID or a name (press `/` to reach it, `Esc` to clear it). The page also works on a phone: it scrolls as a document and a table scrolls inside its box.

| Tab | Items | What you get |
|---|---|---|
| **Sounds** (the tab that opens first) | 91 | WAV sound effects (8-bit PCM). Each row has the sample rate, length and size, a play button, an audio player and a "⬇ WAV" download. The page draws no waveform. |
| **Animations** | 1,344 | Animation sequences on a stage, described below. |
| **Sprites** | 2,794 | 8-bit RGBA PNG files (`sprite_0000.png` and on), converted from the archive's paletted bitmaps. A card for each shows the picture, ID, BMP name, size, file name and the animations that use it, with a one-click "⬇ PNG". A click opens an inspector with zoom levels 1x, 2x, 4x and 8x (it opens at 2x) and "⬇ Download PNG". |

The counts are the archive's own (2,794 sprites, 91 sounds, 1,344 animations); the tests of the asset reader pin them.

**The animation stage.**

- The steps of a sequence are composited from their sprite layers, with the timing of each step and the sounds that a frame triggers (a toggle switches the sound off). The order of the layers is automatic ("Auto (Smart Layering)") or the order of the archive's animation table (Table 4, `chd_table4_animations.json`), reversed or forward.
- Stage background: a checkerboard grid, solid black, neutral gray or game turf green. The picture is centred on its bounding box or on its origin, and a crosshair and the bounds can be shown.
- Zoom: fit to the view, or 25% to 800%. Drag pans, the wheel zooms, a double click fits.
- Playback: play and pause (`Space`), the previous and next frame (arrow keys), a scrubber, and speeds from 0.25x to 2x (1x is 20 frames a second).
- A timeline strip lists the steps, and a table lists the layers of the active step, each with a show / hide box and a PNG download. "⬇ Frame PNG" downloads the whole composite frame.

**Opening it.** Online, at the address above. Locally, open the file in a browser: `open asset_catalog/index.html` on macOS, `xdg-open asset_catalog/index.html` on Linux, `start asset_catalog\index.html` on Windows. The data and the files are relative to the page, so it works from a checkout. Its look is the site's stylesheet, `/front/classic.css` (the same Classic look as the front page, with the site's bar at the top, whose Home button leads back to it); opened as a file it shows plain, without that sheet.

The web image serves it at `/asset_catalog/`; `tests/scripts/test_web_catalog.py` pins what the page must keep (the head's two links, the header, the ids that the script uses, the color contrast).
