# Architecture and source tree

Where everything is in the repository, and how the code fits together. The game is a set of C++17 libraries (assets, simulation, network, computer players, control interface, dedicated server, application); the tree says what each folder holds, and the diagram shows how a command travels through the layers.

## Directory Structure

The root folder is `ants-cross-platform/`. A comment says what a folder or file is for; the file's own header comment says the rest. Counts of files and tests are not kept here, because they go stale; `./run_tests.sh` prints the tests' own.

## Architecture Overview

The code is split into nine layers: `ants_assets`, `ants_sim`, `ants_net`, `ants_ai`, `ants_replay`, `ants_db`, `ants_ctl`, `ants_server` and `ants_app`. Each has its own folder in `include/` and `src/` and is built as a static library (`libants_<name>.a`, or `ants_<name>.lib` with MSVC; the server's is `libants_server_core.a`). A layer uses only the layers listed before it. Two programs sit on top: the game (`ants`, from `ants_app`) and the dedicated server (`ants_server`). `ants_db`, `ants_ctl` and `ants_server` are native only; the web build compiles the other six layers with Emscripten.

A command is how a player or a bot changes the simulation. A local game applies it at once; in a network game the host's sequencer seals the commands of every 50 ms into a numbered turn, and every machine runs the same turns on the same tick. The state hash, reported every 20th turn (once a second), shows when a copy of the match goes its own way.

Two small libraries sit beside them: `ants_version` (the generated `ants_app/version.hpp` and `ants::BUILD_ID`, linked by the game and the server) and `ants_test_paths` (where the checkout is, for tests and tools).

### Lookups in the tick loop

The tick asks six questions thousands of times, and none looks at every ant any more (as scans they made a map of thousands of ants cost about the square of its ants). Each gives exactly the answer of the scan it replaced, so no tick changes by a bit:

- **The ant of an id** (`SimulationEngineImpl::find_unit`). Ants are never removed and an id is `next_ant_id_++` at the push_back (both restart at 1 in `init`), so ant n sits in slot n - 1. The slot is checked, and a miss (an id never handed out, a table that stopped being dense) falls back to the scan. Id 0 is no ant (ids start at 1, nothing else makes one) and answers nullptr at once.
- **Whether an ant has a path request queued** (`PathManager::has_request_for`, and the replacement of an ant's first request in `request`). A byte for each ant id (a larger id is counted and scanned) changes with every push, pop and clear of the queue and is rebuilt from the queue after a copy. It is derived data: never copied, not in the state hash, so a copy of the engine (prediction) cannot carry a stale flag.
- **The ants on a tile** (`TileAntIndex`, `src/ants_sim/tile_ants.hpp`; asked by `occ_scan`, which `occ_move` and `occupant_at` call on a tile that holds several ants, and by `blast`, both in `occupancy.cpp`). For every cell of the occupancy grid, a list of the ants whose `occ_tile` is that cell, linked through the table of ants by slot (4 bytes a cell, 8 an ant, adding and removing O(1)). `occ_move` is the only place that writes `occ_tile` (and `occ_refresh`, which starts the lists again when the grid has another size), so a spawn, a hatch, a step, a knock-back, a landing and a death keep the lists right without a line of their own. They are derived data, not in the state hash and never sent; a copy of the engine copies them with the ants (a slot is a place in the copied table). A list has no order of its own: `occ_scan` takes the first ant in the order (team, slot) of the scan as the least of that key, and the last ant that stands without a path as the greatest, and `blast` sorts the slots, so each answer is the scan's. A tile off the grid has no list and takes the scan.
- **The ants that an order's refresh has to put right** (`occ_refresh_for_order`, `occupancy.cpp`; asked by `go_to`, which used to start with `occ_refresh()`, a walk over every ant: a live ant that is not registered on its pixel tile is registered there, a removed ant that is still registered is unregistered, any other ant is left alone). In a tick `go_to` visits only the ants that are marked: a bit for each slot of the table (`occ_dirty_`) that `occ_note` sets when an ant is out of step and clears when it is not. It runs at the end of `occ_move` (the one writer of `occ_tile`, so after `set_position` and every step), after `remove_ant` writes `removed`, and in `add_ant` (the one place that adds an ant). The marked ants are visited in the order of the table and each gets the walk's own rule (`occ_refresh_ant`), so the moves happen in the order the walk made them: the same grid, lists and ants. The marks are for the tick: `movement_tick` starts with the full walk (which empties them) and holds `occ_in_tick_` until it ends; outside a tick (commands, `stop_ant`, a test that moves or kills an ant by hand between two ticks) and in the engine of the scans alone `go_to` takes the full walk, so such a write is put right as before, and the public `occ_refresh()` stays the full walk. Derived data: never hashed or sent, copied with the ants, emptied by a new match.
- **The tiles that team-mates claim** (`order_claims.cpp`; asked by `can_enter`, rule R6, for every goal and ring tile that `adjust_goal` tries). An ant claims a tile while it is not removed and has a Move or Home order to it. For every cell of the grid a list (the `TileAntIndex` class again, `claim_ants_`) holds the ants that claim it, and `claimed_by_mate` looks at the list of the tile (a handful of ants) for another ant of the asker's team, where the scan looked at every ant. The lists are exact, not healed by the question: every write of an order goes through `set_order_kind`, `set_order_tile` or `clear_path_of`, the only writers (`tests/scripts/test_order_writers.py` fails for a direct write in the sources), a removal and `add_ant` note the ant too, and each `claim_note` puts the ant in the list its order says. Outside a tick `can_enter` scans; in a tick it asks the lists, after `movement_tick` has started by putting every ant right (`claims_catch_up_all`, the net for a test that pokes an order through `get_unit()` between two ticks: the shadow build stops at anything it has to put right in a match). Derived data: not hashed or sent, copied with the ants, made again for a grid of another size, emptied by a new match. `claimed_by_mate_scan` is the old scan.
- **The next timed event of an ant** (`AntEventHeap`, `src/ants_sim/event_heap.hpp`, `event_queue.cpp`; asked by `movement_tick` before each event). An ant has four events with a due time in its own fields: the end of the burn overlay (`burn_end_ms`), the combat timer (`combevt_due_ms`), the end of the animation frame (`loco.next_ms`) and the end of a pause (`pause_fire_ms`). The tick runs the earliest due at or before its end; ties go to the ant earlier in the table, then to the earlier of those four kinds, and a task (anthill queue, hatching, flower droppers) goes first only when strictly earlier. The heap is ordered by that key (time, slot, kind), so its first entry is the scan's answer. It is a binary heap with lazy deletion: each (ant, kind) has a record (pending, due time, version), `AntEventHeap::set` is the only writer and pushes an entry when an event becomes pending or its time changes, and an entry whose version is not its record's is dead and is thrown away when it reaches the top. `event_refresh` writes an ant's four records from its fields and follows every write of those fields (the sites are listed at the top of `event_queue.cpp`). The pass over every ant at the start of a tick (`event_catch_up`) is the net under the writers, and also what keeps right a write from OUTSIDE the tree: a test hook that pokes an ant's fields through `get_unit()` between two ticks (no production code does) gives the heap no word, and without the pass the engine plays such a poke differently from the scans. The shadow build stops at anything the pass has to put right in a match and counts it in the two tests that write from outside on purpose; `test_engine_event_heal` plays such writes in the product build against an engine that is told. It is derived data: not hashed, never sent, copied with the ants, emptied by a new match. `next_ant_event_scan` is the old scan.

`test_engine_lookups` ([`TESTING.md`](TESTING.md)) links `ants_sim_shadow`, the same sources compiled with `ANTS_SIM_LOOKUP_SHADOW` (no product build has it): every call also runs the scan (every 64th once the table or the queue holds more than 256; every blast) and stops the program on a difference, every list is rebuilt from the ants and compared at the end of a tick (every 16th once big) and after every copy of an engine, every selection of the next event is compared with the scan and the whole heap with the ants' fields at the start and end of every tick and after every copy, every refresh of marked ants is played again from the same state by the full walk and compared (grid, lists, every ant), every ant out of step must be marked at the end of every tick, every claims question is compared with the scan (every call up to 2,048 ants) and the lists with the ants' orders at the end of a tick and after a copy, and each match is played twice, with the scans alone and with the lookups, the state hash compared at every tick. A new index of this kind keeps its scan beside it and joins that check.
