# The map maker (the editor page)

A page of the site, `mapmaker.html`, where a player makes a map, opens one from their own computer, looks at it, checks it and saves it. It is built on the map core that runs in the browser ([`MAP_FORMAT.md`](MAP_FORMAT.md), "In the browser"): the page never judges a map itself, it shows what the core answers (the check, the limits, the refusal of a size) in the core's own sentences. This page says what the editor is, what each of its pull requests does and which are done.

## The rules of the editor

- **Two kinds of map.** A **Classic map** works in the original game and in the new version (a new one has at most 90 rows, 130 columns and 10,000 cells). An **Extended map** works in the new version only (at most 512 x 512 cells, and no side longer than 1,024); it wears the quiet blue-grey badge "New version only", which is a note and not a fault. The numbers on screen are the core's (`limits()`), never a copy in the page.
- **Nothing is ever written over.** Making a copy, starting an Extended map from a Classic one (any Classic map, the game's library maps too) and saving always make a **new** map under a name that is free; the name of a library map or of a draft that exists counts as taken. The page has no way to open a file for writing: the only thing that leaves it is a download, which the browser saves as a new file.
- **Everything stays on the player's own device.** A saved map (a draft) and the drawing that is not saved yet are kept in the browser's own database; the finished file is downloaded (E1 already does that), and a browser that keeps nothing leaves the page working as before. Sharing a map with other players is not part of the editor: sending a map for approval is described in [`MAP_SUBMISSIONS.md`](MAP_SUBMISSIONS.md) (E7 below is the player's half: the Submit button and My submissions; nothing a player sends is public until the owner approves it).
- **Rows and columns count from 0**, as in the checker's sentences ("row 12, column 40"), so a "Show me" link and the position line say the same numbers.

## How the page is made

All of it is static files (nginx serves `mapmaker.html` with a content security policy: scripts and the core's WebAssembly from the site only, no inline script, no `eval`, requests to the site only, no frame around it, no referrer; `docker/nginx.conf`, tested by `tests/scripts/test_nginx_submissions.py`): `web/mapmaker.html`, `web/MAPMAKER_VERSION` (the map maker's own semantic version `MAJOR.MINOR.PATCH`, printed in the bottom footer bar `#edfoot` as `Map Maker vX.Y.Z` alongside the build id, Pacific build date and links to the Lobby, Match history, Changelog and Legal pages), and, in `web/front/`, `mapmaker.css` and the scripts below (each a plain script that a page and node can load). The page loads the core's `lvl_core.js` and `lvl_core_api.js` first and the app last.

A map is read as a place that takes both kinds reads it (the core's profile `extended`), so a library map and an Extended map open alike; the limits of a **new** Classic map are those of the profile `new_map`.

**How drawing works.**

- **One copy of the map.** The bytes of the open file are the map: a stroke writes the words of the cells into them in place, the canvas reads them there, and the check and the download hand the same bytes to the core. There is no second model of the level to keep in step.
- **A stroke is a patch.** The first time a stroke touches a cell it notes the cell's three words (tile, flags, third word); when the stroke ends, the cells whose words differ go to the history as a patch (a key, the words before and the words after: 16 bytes a cell, so a brush of 9 is at most 81 cells, about 1.3 KB, on a map of any size). Undo and redo apply a patch backwards and forwards. The history keeps at most 200 strokes and 400,000 changed cells (the newest stroke is always kept), and the page asks before a map that was drawn on is left (replaced by New or Open, with Save as a new map first offered; closed or reloaded only when the browser could not keep the work) unless it was saved or downloaded as it is.
- **What a stroke writes.** Ground changes the tile of layer 1 and keeps the cell's other words. An object is a layer-2 cell with flag 1 (the origin) and the anchor of its kind: itself, as row (low byte) and column (high byte) in a version 8 file and as the offset 0 in a version 9 file ([`MAP_FORMAT.md`](MAP_FORMAT.md), "Version 9"). The Objects tool (a tap, a brush, Fill) never takes a hill, a team's starting ants or a food pile away: a brush that touches one is refused as a whole, with a sentence ("Blue’s hill is here. Move it first, or take it away with Erase."), and nothing changes. The palette of Objects holds only objects that stand on one cell (a hill, a team's ants and a pile have their own tools, and so have the bigger objects, below). An object whose tile is solid also sets the **solid bit** (bit 0 of the flags of layer 1) of the cell it stands on, as the original does when it puts an object, and whenever an object goes (the eraser, an object that takes its place, a pile taken away) the bit of every cell it leaves empty is cleared, whatever the tile (the library has bombs, plants and other tiles that are not solid in the game's table and stand on cells that carry the bit), except in row 0, whose bit the original never clears: the remake reads that bit from the file and from nowhere else, so a rock without it would not block ants and a power-up without it would do nothing. A hill's bits are left as they are. Fill works for one click, then is off again; it paints the ground of the same tile round the click, or the empty cells round it with an object (it does not fill over objects). Erase and a new object take a bigger object away whole (the cells round its anchor that hold its tile and name that anchor), so a hill is never left in halves.
- **The dictionary.** A tile that the file's dictionary does not have is refused by the checker, and a name of "." is a tile that the original game does not draw. Before a stroke uses a tile the page gives it its name (the game's own, from the table of `mapmaker_palette.js`, which the tests hold to `src/ants_assets/lvl_tile_names.inc`) and, when the dictionary is too short, makes it longer by the names between; it never shortens it (a name that stays after an undo is harmless, and the save writes the dictionary by the rule of [`MAP_FORMAT.md`](MAP_FORMAT.md), "The dictionary of a new map").
- **Painting only what changed.** After a stroke the canvas paints again only the cells that changed and the ones under the marked square before and after (a tile of 5 pixels or more: its own rectangle and grid lines; smaller: its pixels in the picture that the last whole frame kept); a frame that would paint more than 3,000 cells, or a view that moved, is painted whole. The small map is made again once the stroke ends. A stroke also ends when the browser loses its pointer (a button let go outside the window, a lost capture, a window that loses the focus, a hidden page), so undo and the tools never wait for a stroke that is over. A Fill over a whole 512 x 512 map holds the page for about 0.35 seconds (about 0.65 seconds with the processor six times slower) while it writes 262,144 cells and paints once.
- **Ground** (P1). There are five kinds of ground, and no grass and no sand: the first letter of a ground tile's game name is its kind, `g` Gravel (the brown-gray ground that covers most of the library), `d` Dirt (cream), `s` Slate (blue-gray stone), `m` or `M` Mud (dark gray) and `w` Water. The palette has one chip for each kind, painting its plain tile (485 `g01a`, 487 `d01a`, 571 `s01a`, 439 `M01a`, 476 `w01a`). A tap on a kind chooses it; a tap on the chosen kind opens **its sheet** (a sheet on a phone, with a button for it in the Ground sheet): the plain tile, then for each other kind that it blends into a 3 x 3 compass of the eight edge and corner pieces (NW, N, NE, W, E, SW, S, SE: shapes 02 to 09 of the game's names, the other kind lying on the side the picture shows), with the plain tile dimmed in the middle; the tiles that look the same (the `b` variants, `g01b`, the animated muds) are listed in one line, not as chips. The chip labels under the five kinds are 11 pixels; the chips themselves are the tap targets (44 pixels on a phone, where the one button opens a bigger sheet). Any single tile of the sheet can be painted ("completely custom"): the chip of its kind stays chosen, the line under the palette names it, and the game's own name goes into the dictionary. Water has edges against mud only; dirt next to slate has three tiles (`ds04a`, `ds07a`, `ds09a`) that no library map uses, dimmed in the sheet. A name is `<own kind><other kind><shape><variant>` (`gd03a`: a gravel cell with dirt on its north side); `tests/scripts/web_mapmaker_ground_check.js` holds the table to the game's names and the shapes to the 540 maps. The game does not blend: it draws each cell by its own tile id, so a boundary between two kinds that is painted with plain tiles is a hard square edge until the edge pieces are put in by hand. The Fix edges button (P2, below) chooses them; it reads the same table (`MapGround.edges(kind, other)` gives the eight pieces of a pair by shape, `kindOf` the kind of any tile) and needs no new picture.
- **Fix edges** (P2). `mapmaker_edges.js`, loaded with the other lazy scripts; the button is off until both it and `mapmaker_ground.js` are there. It changes only the map that is open in the editor (the library's maps are never touched; the tests only read them). **The rule** looks at the four sides of each ground cell of the area (the cells outside the area still count as neighbors; the border of the map has none): the other kind that touches it gives the piece, by the sides that touch: one side an edge piece, two sides that meet a corner piece (NW is the other kind north and west, and so on for the shapes 02 to 09 of the game's names); the other kind on opposite sides, on three sides or only at a diagonal gets no piece of its own (the game has none for that cell: the lower kind beside it wears instead, below). Only the pairs that the game has pieces for can get one (water only toward mud; water beside gravel, dirt or slate stays a hard edge, because the game has no piece for it). **Only one of the two cells at a boundary wears the piece**, as in the game's own maps (almost every boundary of the library that has a piece has it on one side only): the kind of the higher rank, in the order that those maps show for each pair, water over gravel over slate over dirt over mud (gravel and dirt split evenly in the library; gravel wears it). With two other kinds beside it the one with more sides wins, a tie goes to the lower rank. **Where the higher kind cannot wear, the lower kind does:** a strip of water one cell wide in mud, an inlet of gravel with mud on three sides, a lone cell: the higher cell has the other kind on opposite sides or on three, so no piece fits it, and the plain cells of the lower kind beside it wear the pieces toward it instead (water in mud: the mud wears `MW`, the way MEDIUM draws its lakes; the same for every pair that has pieces: gravel over dirt, mud or slate, slate over dirt or mud, dirt over mud). The lower cell wears only on the sides that its neighbor does not draw (a neighbor draws a side when its sides make a piece for that kind, or when it wears a piece that faces the cell), so the answer comes from the kinds and from the higher cell's own pieces and a second pass finds the same; a cell of the lower kind that stands in the inner corner of a staircase (the higher kind on two sides that meet) stays plain, because the higher cells beside it wear. **One boundary, one wearer:** a side whose neighbor already wears a piece that faces this cell (its other kind is this cell's kind and its shape points here) does not count, because the game's own maps never have both facing cells wearing a piece (0.0 to 0.1 in 100 boundaries; two pieces make a dark seam line). So the original Treasure map needs 0 changes, Medium (which draws its lakes from the mud side) 0 and Islands only its 2 plain cells that the author left, and the rule makes no boundary with two facing pieces (57 hand-made ones remain in 6 community maps). **The rule only adds pieces or replaces a wrong one where it has an answer; it never takes a piece away.** A piece that it cannot place (a `wm` piece on water beside gravel, a piece toward a kind that is not beside the cell, a piece of the lower kind) is the map maker's choice and stays; a cell that already has the right piece, in whichever look-alike (`a` or `b`), is left alone, so the rule is idempotent: a fixed map is left as it is (a neighbor counts by the tile it ends with in the same pass, worked out once per cell on the tiles as they were, so the result does not depend on the order of the scan; a test holds a second pass to nothing on 400 random grids of any tiles, on library maps after random edits and on random strokes of Auto edges). **Walking never changes:** a cell is not given a tile of another walking class (`MapGround.terrain`, the engine's `kTileTerrain`, held to it by a test), so the unused look-alikes of other classes stay as they are. A tile that is not in the ground table is no kind and is never changed, and neither is a cell's solid bit, its third word or its layer 2. **The change** is the `ground` list of a CHANGE (`mapmaker_edit.js`: tile words of layer 1 whose flags and third word stay) and ONE splice of the whole dictionary that gives each new piece its name (the original does not draw a tile that the dictionary names ".", and a tile outside the dictionary is refused by the checker; the dictionary grows when it ends before the piece, as a new map's ends at gravel), so Undo takes the names back and the bytes are exactly the ones before. **The box** has the two choices (the part you can see is first when something is on the screen), two pictures of at most 48 x 32 cells around the first change (a bigger area says so), "After: N cells change", a note, **Cancel** and **Fix edges** (off when nothing changes). The pictures are drawn from the sprite sheet of the ground, or in flat colors until the atlas is there. A 512 x 512 map is planned in about 0.4 seconds on a desktop (a test holds it under 3). On the 540 library maps the rule would change 2.6 in 100 ground cells (23,141 of 902,078: 20,798 put a piece on a plain tile and 2,343 swap a hand-placed piece for another one, all still one Undo; none taken away; no walking class changes), 244 maps would be left as they are, and a fixed map is left as it is on all of them (`tests/scripts/web_mapmaker_edges_check.js`, which only reads the maps, prints the numbers and holds the share under 3 in 100). **Known limits:** a one-cell concave notch (a cell of the lower kind with the higher kind on two sides that meet) stays a hard square, because the higher cells beside it wear; and a boundary that has no piece in the game (water beside gravel, dirt or slate) is a hard edge, and the editor says nothing about it. The library does not support a clear rule for it: such cells are plain in 85 in 100 (mud beside gravel), 76 (mud beside water), 64 (slate beside gravel) and 55 (dirt beside gravel; 44 wear the corner piece), so leaving them plain is what most maps do. **Auto edges (`Auto edges: On / Off`):** the switch next to **Fix edges...** (on a phone held upright, under the tool buttons while Ground is the tool, and in the phone's Menu under "Settings for this browser") is Off by default for a new visitor and remembered in `localStorage` (`ants_mapmaker_auto_edges`). When it is On and a plain ground kind is painted (tap, drag or Fill), `MapEdges.strokePlan` sets the edge and corner pieces in and around the painted cells inside the same stroke (`current.change`) and `finishAuto` records one dictionary splice when the stroke ends, so one Undo takes back both the ground stroke, its auto-placed edge pieces and the dictionary byte for byte; a single tile placed by hand from "all its tiles" (`custom: true`, or a neighbor cell outside `painted` whose before-stroke tile was not the rule's own answer on the before-stroke grid) is left alone until painted over directly or until **Fix edges...** is run. The stroke's plan works out the rule over three more cells all round than the cells it may change, so a piece that an earlier step of the same stroke put is never taken for a hand-placed one: painting the water and the mud in any order, in any number of strokes, leaves the map that Fix edges makes of the plain ground (a test paints the owner's scene both ways and random strokes, and holds the two to each other).
- **Sprites** (P1). A cell is 32 pixels and the picture of a tile is the first sub-item of an animation (`docs/chd_table4_animations.json`) with **all its parts** (frames) put together as the game draws them (the last stored part first, the first on top: a flower is its head, its stems, its leaves and its shadow, 9 of the 14 plants and three food stages have several parts), drawn at the cell's top-left corner plus the x/y offset of the box of the parts (often negative: a picture spreads beyond its cell; the plants are put on the middle of their cell, as the game does). **Which animation is the map's own dictionary's say, as in the game's renderer** (`Renderer::set_level`; `tableOf`, `ground`, `object`, `stage` and `place` in `web/front/mapmaker_tiles.js`): an entry that is the name of the animation of its own number (any case) is that number; any other name is looked up in the animation table (the exact name, then in lower case), so a map whose dictionary is shifted by one (a pile of jacks that the table calls a pink eraser) shows what its names say; `.`, an empty entry, a name that no animation has and a number beyond the dictionary draw nothing (a ground cell is then black); the start markers are never drawn; power-ups, original bombs, the fire wall, hills and bridges are drawn from their numbers; an object whose entry begins with `pu` is no static object; plants (block 1) are their numbers; a pile's stage falls back to its number when its entry gives no animation (`Renderer::food_stage_anim`). Ground, objects, pile stages, the flat colors, the see-through picture of the Bigger and Pick up tools (a tile that is put takes the number's picture when its entry is `.` or missing, because the tool names it) and the before and after of Fix edges all use that one table, which is made again when a name of the dictionary changes. The palette's chips are the game's own table, the small map and the thumbnails are the game's minimap (by number, as the game's own minimap is), and the pictures of Start from a game map are made by the game itself (`tools/map_previews.py`). Layer 2 draws only from its anchor cells (the flagged ones), in row order, as the game does, and a food pile of block 2 whose layer-2 cell is empty draws the picture of its starting stage in the same scan (and its gold mark on the small map). The pictures come from an **atlas** made by `tools/map_atlas.py` when the web image is built (the Dockerfile, `build_web.sh`; nothing generated is committed) from `asset_catalog/sprites/` and the animation table (read from the sprite viewer's data, `asset_catalog/catalog_data.js`, because the image's build has no `docs/`; a test holds it equal to `docs/chd_table4_animations.json`), and served at `/mapmaker_atlas/` (revalidated, never cached for a week): `ground.png` (the 239 ground tiles, 256 colors, about 35 KB), `objects.png` (the objects that the editor offers and the commonest small ones, about 298 KB) and `atlas.json` (where each picture is, its offset, its average color, the names of the 1,344 animations, and for every other animation of one part its sprite number: any animation can be named by a dictionary, and the page fetches those toys alone from `/asset_catalog/sprites/` the first time a map shows one; the ones of several parts that the sheet lacks, menu screens and pieces of ants, are not drawn; about 39 KB). The whole atlas is 372 KB (a test caps it at 375,000 bytes). The page fetches the two lazy scripts and all three atlas files right after it is up (at the start, not when the first picture is needed), then only the few toys that are not in the sheet, one by one; the canvas draws pictures from **10 pixels a cell** up and, below that, one flat color for each tile, which is the average color of its picture, so a zoomed-out 512 x 512 map is as cheap as before. The starting ants are the game's standing worker ant (`agst301`) with a ring in the team's color at its feet (black has a thin white edge) from 12 pixels a cell, and the team's dot below. The sprite frame is drawn from a **layer** that is kept between frames: a pan moves it and paints only the strip that came into view, a stroke paints again only the part round its cells (with the margin that a picture reaches), one scaled copy of the 239 tiles is made for each zoom (each tile the first time it is needed), a zoom that changes a little shows the last picture stretched and a crisp frame comes when it rests, and the objects are drawn with the same rules into the layer. Objects are scaled once to whole pixels and put at whole pixels, so the kept layer after any pan or stroke is pixel for pixel the frame that is made from nothing (the opt-in browser check compares them). The Bigger tool shows the object's own picture, see-through, under the pointer with its gold footprint cells. If the atlas does not load (a missing file, a bad index, no network) the page works as before in flat colors and says so in one plain line over the map; the editor's bytes, history, saving and drafts do not know about pictures at all.
- **Hills, ants and food** (E3a). A tap puts the whole thing and a drag looks around (they are tools that put, not paint: no brush, no Fill). Each is a CHANGE that `mapmaker_blocks.js` works out from the bytes as they are, and `mapmaker_edit.js` applies as one step of the history, the same history as the strokes.
  - **A hill** is the 4 x 4 cells round the cell that was tapped (one row and one column before it, two after), the tile of the team's hill on layer 2, each cell anchored at the tapped cell, which is the entrance and the only one flagged: the shape that the checker calls whole ([`MAP_FORMAT.md`](MAP_FORMAT.md), the original-safe profile). In a version 8 file the anchor is the absolute row and column, in a version 9 file the offset to the entrance. A team has one hill, so putting it again takes the old one away; an object under the new one goes whole, but another team's hill is never taken away: the page says whose hill is in the way and puts nothing; there is no hill with its entrance at the top or left edge or in the last two rows and columns (a plain sentence says so). The square under the pointer is the 4 x 4 cells with a dot on the door.
  - **Starting ants** are the records of block 1 whose tile is the team's start marker, one for each ant; the original starts one ant for each record. A tap puts the chosen number (1 to 64; the library's maps have 1 to 62 for a team) on the cell and the nearest ones, passing cells with an object, solid ground or another team's ants (on a map with fewer free cells the line under the palette says how many fit), and takes the team's ants that were there away; the plants and the other teams' records stay as they were, in their order.
  - **A food pile** is a record of block 2: the cell, the bites (`units`), the points of a bite, and the stages: the game's own 32 food items (`Burger`, `Lollipop`, `Chocolate bar`, `Pretzel`, `Skittles`, `Gummy worms`, `Single gummy worm`, `Cola cap`, `Froot Loop` in 7 colors, `PEZ candy` in 4 colors, `Lunchbox`, `Potted meat`, `Corn dog`, `Jell-O`, `Round crackers`, `Square crackers`, `Steak`, `Twinkie`, `Fried eggs`, `Pizza slice`, `Fish`, `Chicken leg`, `Cereal`), or by the number of stages (2 to 6: the pile shows the tile of the last stage whose number is not below the bites that are left, and the last stage, the empty tile, makes it vanish when it is eaten; a pile of one stage could not be eaten, so there is none). The Food picker sheet also lets the maker adjust **Bites (uses)** and **Points per bite** (`5..200` in steps of 5). A pile put on a pile replaces it.
  - **The eraser** takes, besides an object, the start of a team whose ant is on the cell (all that team's ants, together), and a pile whose cell, or whose object's body, it is; with the cells of layer 2 that show the pile. One drag is one step.
  - **Splices, not copies.** The records are in the file after the layers, so a change is `{rel, removed, inserted}`, the smallest piece of the file that differs, counted from the end of layer 2 (which does not move when the dictionary grows). A patch of the history holds its cells and its splices (the bytes that went out and came in, never the file); undo and redo apply them backwards and forwards, and a splice weighs a record for each 16 bytes in the bound of the history. A list that does not read where the count says (a file cut short, a pile without stages, where the original stops reading the food) is not changed, and the page says so; everything else of the file stays byte for byte. The tiles that these use are named in the dictionary first, which grows when it is short (the hill's tile 245 to 248, the start marker 152 to 155, the food tiles).
- **Bigger objects** (E3b). A tap puts the whole object; a drag looks around (a tool that puts, like Hills). The library's maps show how a bigger object is encoded: the **same tile on every cell it covers** on layer 2, every cell anchored at one cell (the origin, the only one flagged, which is also the cell that is tapped), and the solid bit under each cell. The Erase tool already takes such an object away whole (the cells round the anchor that hold its tile), so it needs nothing of its own. The footprints are measured, not guessed: a tile is on the list when it stands on more than one cell in at least 30 of the 540 maps (never a hill, a bomb, a power-up, food, or a plant of the flower droppers, which have tools of their own or come later), most used first, and its footprint is the one that the maps have most often (for 27 of the 29 it is also what the game computes from the sprite, `object_footprint.cpp`; for `can1` and `sling` the maps have one cell less, and the maps win). Each chip of the sheet draws the shape (a small square for each cell of its box, filled where the object stands, the anchor outlined), says the number of cells and the size ("10 cells, 5 x 2": columns by rows) and, as a small caption, the game's tile name (`grass4`, `grassmed1`, `bearbod`). `mapmaker_objects.js` works the CHANGE out from the bytes as they are: the cells of the footprint (those off the map are dropped, as the original drops them; the anchor stays on it), each anchored at the origin in a version 8 file (absolute) and in a version 9 file (the offset to the origin, so a map that grows keeps its objects whole), the solid bits, and the name for the dictionary. An object under the new one goes whole, never half of it left; a hill, a team's starting ants and a food pile (its cell, or the object that shows it) are never taken away without being asked: the page says "A hill is in the way" and puts nothing. The same object put on the same place changes nothing and is no step of the history. The canvas marks the object's box round the cell, with a dot on the anchor.
- **The properties** (E3c). One dialog (a box on a desktop, a sheet from the bottom on a phone) with four things: the **description**, the **length of a match** in minutes, the **eggs at the start** (one number, for each team: the file has one) and the **default ant type**. What is in the file is read by the core (`readReport`), what is set is made by the core (`setProperties`, [`MAP_FORMAT.md`](MAP_FORMAT.md), "In the browser"): the page never writes a header byte. Apply asks the core for the new file, takes the pieces of the old file that the core says changed (the match length, the description's field, the type word, the egg word: a few bytes, never a copy of the map) and puts them in the history as ONE step (splices with absolute places, `abs`, put on from the last to the first; in a version 9 file a longer description moves the layers, which the page reads again as it does when the dictionary grows), so undo and redo are exact and one Undo takes all four back. Cancel and Escape change nothing; Apply with nothing changed makes no step. The check line is run again as after any change.
  - **The counter says "characters" and counts bytes**, because the file holds bytes: a letter outside a to z takes 2 or 3 (the note "(letters like é count double)" shows only when the text holds such a letter). A Classic map has room for **29** (its 30th byte is the zero that ends the text; at 30 the checker warns `description_too_long`), an Extended map for **255** (256 is fatal); the numbers come from the core's answer (`description_limit`), not from the page. The box stops at what fits (a text that came in too long can only be made shorter), and a text that is too long gets the **core's own sentence** in red with **Cut it to 29** (or 255), as the check of the map would say it. A text typed is stored as UTF-8; a description of an old file that is not valid UTF-8 is shown one letter for each byte and goes back with the file's own bytes while it is not touched. An Extended map has a larger box of 3 lines (a line break becomes a space).
  - **The numbers** are a box with a minus and a plus (44 pixels on a phone) that takes digits only; minutes stay between 1 and 120 and eggs between 0 and 255 when they are changed, but a map that came with more (the library has a few) shows its value and keeps it until it is changed. The default ant type is one of six choices in a radio group (arrow keys move and choose); a file whose "none" is another id than the usual keeps its own.
  - **Where it is:** the **Properties** button between Open and Download of the top bar, the summary (the description in quotes, "12 minutes · 9 eggs for each team", "Thief ant by default" or "No default ant type") with its **Edit** link in the side panel of a desktop, the same under the map of a phone (one line, the description cut with an ellipsis, a 44 pixel Edit link), and **Properties...** in the phone's Menu. A phone held sideways has no room for the summary beside the map: its Menu has the line.
- **Copy, convert and crop** (E4). Nothing here writes: each step works on a copy of the open map's bytes (the open map is the one copy of the map and stays as it is), and only the last button (Make new map, Make the new Extended map, Make the new Classic map) hands bytes and a name to the page, which shows them as the open map after the question about unsaved drawing. The default names are "Treasure 2" (the next number; "Treasure 2" copies to "Treasure 3"), "Treasure Extended" and "Treasure Classic", never over 40 characters; the name of the open map is taken (a capital or a blank round it changes nothing). Whether a map fits a Classic map, why not and what to tell come from the core's `convertToClassic` (the sentences with a capital; the reasons are listed rows first, then columns, then the rest, and the choice that is dimmed in Copy says the first of them in short); the crop screen's limits come from the core's `limits('new_map')`. **Crop to fit** counts rows and columns from 0 like the position line ("Rows 15 to 104 · Columns 144 to 254"); the core's `crop` keeps an object **whole or not at all** (one that the frame cuts, or whose anchor it leaves out, goes with its solid bits, as the eraser does), moves the starting ants, food piles and waypoints that are inside, and says what it left out ("3 cells of objects were taken out because the frame cuts the object"), which the dialog tells. A second crop works on the part and counts its place from the whole map. Shorten the description opens the Map properties box on the copy: whatever closes it, the conversion is asked again.
- **Save as a new map and drafts** (E5). The bytes of the open map are the one copy: Save hands them (as the core writes them when the map was drawn on, as Download does) to `store.add`, which keeps them under the cleaned, lower-case name as a new record and answers `exists` for a name that is there, so a draft is never replaced, even by a second window; then the saved map takes the screen (a new history, the name taken from now on). The names that are taken: the open map's (a capital or a blank round it changes nothing), every draft, the six original maps and every library map of the site's own list (`GET /maps`, asked once when the page starts, so no new dependence: until it answers (or 8 seconds pass) Save and Make are held with "Checking the game's map names...", and when it does not come the dialog says that a library name cannot be checked). A name is compared in NFC form, with zero-width characters dropped and blanks counted once; a number at its end keeps its leading zeros ("Heaven 0105" goes on as "Heaven 0106"). A window of 601 to 1,000 pixels wraps the top bar (the name box on a line of its own) so no button is cut. The next free number is offered (`Name 2`, then `Name 3`...), never over 40 characters. **The slot of unsaved work** is one record that is not a map: the open map's bytes are written to it 1.5 seconds after the last change while the map is not saved, and it is emptied when the map is saved, downloaded or replaced; a new visit finds it and asks. Every read and write is guarded: a browser that refuses the database (a private window, blocked data) leaves the page as it was before E5, with the question of the browser before it is closed. A saved draft is listed, opened, copied and deleted in My maps (E6).
- **Submit for approval and My submissions** (E7). The dialog takes the bytes from one answer of the page (`fileBytes()`, then the core's check of exactly those bytes), so what is judged is what is sent; the button is off unless that check works, the file is within the size of its kind (512 KB, 4 MiB), the door answers and the texts are fine (the name as the server wants it: 3 to 60 characters of letters, digits, spaces and ' - _ . ! & ( ) , ; the maker 1 to 24; the note 280; no < or >; the server judges them again). The door is asked once when the dialog opens (`GET /submissions` with no token: 401 says it is on, 503 `submissions_off` or a 404 that it is not). The query is built with `encodeURIComponent` (a space is %20, a plus stays a plus). The token that the server makes is kept in a database of its own, `ants-mapmaker-sent` (the drafts' database is never touched or upgraded), with a record for each submission (the server's view plus the bytes sent) and the maker's name; a browser that keeps nothing still sends, and says to copy the status link. A status link is `mapmaker.html#sent=<token>`: opened, the address loses the fragment (`history.replaceState`) and a question asks "This link adds submissions made by someone else to this browser. Add them?" before anything is added; the tokens that were added are marked as linked, their rows say "Added from a link", and a send never uses a linked token (it goes out with this browser's own token or none, and the server makes a fresh one). Every sentence that came from the server or the owner is put in with `textContent`. The owner renames and the maker has no say; the limits (3 a day for an address, 200 waiting) are the server's, and the dialog says them in plain words.
- **My maps** (E6). The list is a screen inside `#editor` that sits over the editor (the top bar and the tools are put away while it shows, so the keyboard cannot reach them; dialogs open above it and make it inert); on a phone it flows with the page. It asks the store for the drafts (`list`, newest first), reads each one's kind and size from its bytes and its verdict from the core's check, and fills the pictures and verdicts one row at a time so a long list never freezes the page. **Open** hands a copy of the saved bytes to the same `setMap` as every other way to a new map, so the history starts again, the name box shows the saved name (which stays taken) and the next Save offers the next number; the question about unsaved drawing comes first. **Copy...** is the Copy dialog given the saved map as its source (the open map is not touched and the name check still counts it). **Delete...** is allowed for the player's own saved copy only, through `store.remove`, whose one request is a delete on the `drafts` store (the page never touches the slot of unsaved work or a library map with it); the question names the map, says it cannot be brought back and that downloads and the game's maps are not touched, and **Keep it** has the focus. A record that cannot be read (or has no name) still gets a row with Delete only, asked about as "This unreadable saved map", and a delete always takes the key the record itself has. Later: the list reads every saved map's bytes at once (lazy loading and a stored size summary would spare big drafts). A top bar of eight buttons (since Submit for approval...) wraps up to 1,200 pixels (the name box on its own line) and is a little tighter from 1,201 to 1,330, so none is cut and none covers the name or the kind tags.
- **Play this map** (T1). A test game or unlisted online room on the map as it is in the editor, in a **new tab** (`window.open`, the opener kept). The dialog has two mode tabs: **Against bots** (1 player on this device) and **With other players** (host an online room with a share link). The map maker's tab is not touched at all: the map, its Undo history, the tool, the view and the one slot of unsaved work are all still in that tab, so "Back to editor" is only the game's or room's tab closing (the browser shows the map maker again), and a line says that you are back. A game on the same tab would have left the page and could only have brought back the saved bytes, not the history; one tab is also the one way that a refresh of the game cannot reach the editor. **The bytes** are the open file's own bytes (the same array that the checker judges and that the one slot of unsaved work keeps), copied once when Start is pressed (a stroke afterwards does not reach the game) and kept by the map maker's tab under a random id (the last three); they are never written again by a script of the page (no `rewrite`: the core's rewrite wants all four colors, a test game of two does not) and never put in an address. On **Against bots**, the game page (`/play.html?testmap=<id>&seats=<four letters>`) asks its opener for that id (`window.opener.antsTestGameHandoff`, the same origin and the same Cross-Origin-Opener-Policy on every page of the site), writes the bytes into the game's maps folder under the one name `playtest.lvl` (the map's own name is never a file name, and nothing of it reaches the drafts or the library: the game page never touches the browser's database) and starts the game as a game on this computer: `--map ... --play --player <your seat> --bot <seat>:<level> ...`, no `--alone`, no teams. The four letters are in the game's seat order (Green, Red, Blue, Black): `y` you (exactly one), `e`, `m`, `h` a bot (at least one), `n` nobody; nothing else of the address reaches the game (`tests/scripts/web_lobby_check.js` and `web_mapmaker_play_check.js` run thousands of random addresses). On **With other players**, the lobby tab (`/lobby.html?testroom=<id>`, `web/front/rematch.js`) asks its opener for the bytes, uploads them to `POST /test-maps?kind=classic|extended&name=<encoded>` (the server's test-map door, which works with the submissions door switched off; it checks the map with the core, keeps the canonical file of up to 64 unlisted test maps `<Stem> ~test-<8hex>.lvl` for 6 hours with limits of their own, without touching the submission queue or `/maps`, serves `/maps/files/` and `/maps/previews/` to players in the room, and omits test-map matches from replays, `/live` and `/history`: [`MAP_SUBMISSIONS.md`](MAP_SUBMISSIONS.md) "Test maps"; a map over 65,536 cells, such as 400 x 400, or one that starts more than 300 ants is refused there with a sentence, which the dialog says before the upload, turning its room button off, and can be played in **Against bots** on this device, where the dialog only warns that a map of more than 300 ants may run slowly), sets the room's map and marks any color without a hill or starting ants as `Nobody`, and shows the top `Test room` strip (`◀ Back to editor` for the host, `Custom map room` for guests). **A room is made only with the map.** When the hand-over or the upload fails, the page makes no room at all (never an ordinary Treasure room): it stays as the page looks before it has a room, and the same strip, as a warning, says why in plain words and sends the host back to the editor (no new buttons: the strip's `◀ Back to editor` is the only one). The words are `failWords` and `TAB_CLOSED` in `web/front/rematch.js`: the submissions door off (503 `submissions_off`) "Sending maps is not switched on on this server right now."; busy, too many tries (429) or the site's own limit (a 503 that is not JSON) "Too many test maps just now. Wait a minute and press Play this map again in the editor." (the game server's limits of an hour and of held test maps, 429 `too_many_tests` and `test_limit`, say their own sentence instead); an editor tab that was closed or lost (no opener, a closed one, one without the hand-over) "The editor tab was closed. Go back to the editor and press Play this map again."; anything else the server's own sentence (cut to 200 characters, text only) or "The server could not prepare this test map (answer N).", each with "Go back to the editor." A room that the page has to make again (the room was closed, the server restarted, the link was lost for long: `onWelcome` with `created`) gets the test map sent again (`frontStrip().remade()`), unless the host has picked another map by hand. A test match is not recorded, so in a room on a test map the front page's footer line says that ("This room plays a test map from the Map Maker. The match is not recorded, and no result or name is kept.") instead of the line about recordings. A **reload** of the game's tab takes the same hand-over again and starts the same game from the start; a tab whose map maker is closed shows a card ("This test game cannot start") with a way to the map maker. The page does not count a test game for the front page's numbers (`antsReportLocalGame` is replaced), saves nothing and keeps no score. **The verdict** is the checker's: the map core's `checkMap` and first reading of the same bytes. Refused: a Classic map of more than 90 rows or an Extended map larger than 512 x 512 (262,144 cells, up to 1,024 a side, 4 MiB), a finding that stops the map and is about no color (the check's own sentences are listed), and fewer than two colors that each have a hill and starting ants. A color whose hill or starting ants are missing (the check's `hill_missing`, `hills_several`, `hill_without_entrance`, `starting_ants_missing` or a stop about that color) cannot be used: its row says why and only Empty is open. A browser that does not open the tab is told so. The strip's text and the dialog's are text only; a map's name is put in with `textContent`. On a phone every answer and button is 44 pixels, the Menu entry is gold with its sentence, and the strip wraps to two lines.
- **On a phone** there is no room for the palette beside the map: every tool that has a palette shows one button (the chosen tile; the team, with the number of ants; the stages) that opens the same choices as a sheet with their names (the Bigger tool has its list of 29 only as that button and sheet, on a desktop too: there is no room for so many beside the map), and the steppers (the ants, the stages) are 44 pixels each way. Held upright the page scrolls when the screen is too short (the map keeps at least about 190 pixels); held sideways the tools sit in two columns and the buttons of the map's bar wrap into two rows, so every control is inside its card down to 667 x 375 (the opt-in browser check measures nine sizes).

**The check.** The check of the page is the core's `checkMap` on the bytes as they are: after a change the side panel's line is run again when the hand has rested for 0.6 seconds, and the Check button runs it at once and shows the card. Download hands over a map that has not been changed as it came, and a map that was drawn on as the core writes it (`rewrite`), so it stays a valid file; the page still has no way to write over a file.
