# Workflow

How a change travels from a commit to a release: which tests run when, how work is merged and deployed, how the version moves, how the changelog is written. The rules for contributors and agents are in [`AGENTS.md`](../AGENTS.md) (rule 1: branches, pull requests, the merge; rule 2: zero warnings, all tests passing; rule 6: the web build, the version and the build id; rule 8: Pacific times; "How much checking": the tiers; "Working style": short documents, American spelling, which `tools/check_hygiene.py` checks); this page is the practical version.

## The three test tiers

| Tier | When | What | How | Time |
|---|---|---|---|---|
| **Quick** | after every change, before every commit | the asset, simulation, network-core, bot and application MODEL suites that finish in seconds, plus the repository checks (the version / changelog consistency check and the python tests of `tests/scripts`) | `./run_tests.sh --fast` | about 25 seconds of test time on a 10-core Mac, plus the build of what it needs |
| **Full** | for every pull request, and every push to `main`: GitHub Actions runs it on its own machines; this is the one full gate | everything: all suites of `./run_tests.sh`, the E2E runner, the script suites (start script, server end to end), ctest on Linux (GCC), macOS (Apple clang) and Windows (MSVC 2022 and 2026), the web and the server image | open the pull request, watch the run (`.github/workflows/ci.yml`) | CI 11 to 13 minutes; a pull request of web pages, documents and their tests only gets the [light checks](#light-checks-for-web-and-document-pull-requests) |
| **Deep** | only for changes to the network protocol, the simulation's rules or fairness (what a player can see or do), and now and then on a schedule | mutation checks (`tools/mutate.py`, below), AddressSanitizer + UBSan (`./run_tests.sh --asan`, locally: **CI has no sanitizer job**), soak runs (`map_sweep`, `bot_arena` tournaments, `test_lockstep`), the opt-in browser checks (`tests/scripts/test_web_aspect.sh`, `test_web_hidden.sh`), an independent review | by hand, as the change needs | as long as it takes |

`./run_tests.sh --fast` is the answer to "did I break something obvious"; it does not run the slow suites (the lock-step soak, the server, the worker bot, the network application, the E2E runner, the script suites): CI does, for every pull request, and `./run_tests.sh --sim` (or a single test program) runs the suites of one area when a change is in that area. The options (`--sim`, `--app`, `--tools`, `--list`, `--asan`, `--jobs N`, ... and how `--fast` combines with them) are in [`TESTING.md`](TESTING.md) ("Running Specific Suites").

**CI is the one full gate.** Before a batch is merged, the green CI run on the exact commit of its pull request stands in for a local full `./run_tests.sh`, the local Docker builds and the GCC 12 container (CI builds both images; the server image is Debian 12 with GCC 12). A local full run or a local Docker build stays available and is used when CI cannot show something: a hang that needs a debugger, a change to a Dockerfile that must be tried before it is pushed, AddressSanitizer and UBSan.

**The runner is parallel.** `./run_tests.sh` runs independent suites at the same time, up to as many as the machine has cores (`--jobs N` changes it, `--serial` is the old one-at-a-time run with live output). Each suite's output is kept in a buffer of its own and printed in the order of the table, with the times and the totals as before, and the result of every suite is the same as in a serial run. Every suite has a temporary folder of its own (`TMPDIR`) and the tests ask the system for free ports, so nothing is shared; a suite that must be alone, or share a lock, or take several job slots says so in the table's last column (`exclusive`, `lock=NAME`, `weight=N`; `cost=SECONDS` says how long it takes, the longest start first). The measured time of the last run is kept in the build folder. The times of a parallel run grow with the load of the machine. `tests/scripts/test_ants_server.sh` (the server end to end) is six parts, `--part NAME` runs one (`--list-parts`), and `tests/scripts/run_python_tests.py` runs every test class of `tests/scripts` in a process of its own, the long ones (its `COSTS`) first (`--shard K/N` runs slice K of N slices of the same cost, as CI's Linux jobs do; `--skip-linux-only` leaves out the page groups of `LINUX_ONLY`, which CI's macOS job does not need).

What a typical change can break decides what is in the quick tier: the rules and their golden cases, the command layer and the state hash, the room, TCP and WebSocket transports, the screens and the pictures (HUD, layout, zoom, fingerprints). What takes minutes and only a network, server or bot change can break stays in the full tier.

A new test must fail without the code it tests (change the code back and see it fail); a change to the network, the rules or fairness also gets the deep tier and an independent review. A change to a screen gets one combined review per batch.

**Mutation checks.** `tools/mutate.py SPEC.json` changes the code on purpose, one mutant at a time (`file`, the `old` text that must occur once, the `new` text, the CMake targets to `build`, the `test` command, an optional `expect`), builds, runs the test and puts the file back, always (also after an error, a timeout or Ctrl-C). A mutant is caught when the test fails and survived when it passes; a table and a JSON report (`SPEC.report.json`) say which. The unmutated tree is built and tested before the first mutant, every `--baseline-every N` mutants (default 10) and at the end: if that fails (a stale object of an earlier mutant: a Mac's make compares file times in whole seconds), the results are not reported. `--keep-going` goes on after a mutant that does not compile or times out, `--timeout` limits one mutant, `--check` only validates the file. Its own tests: `tests/scripts/test_mutate_tool.py`.

## Tools never touch the map library

The maintainer's rule: no tool changes, re-saves, repairs, re-renders or deletes a map of the library (the two folders `Original-Ants/` and `Community-Maps/`; the approved maps that the game server keeps in its own results folder are the server's), and no tool writes over the file it reads. Every tool that writes a path it is given asks first (`tools/library_guard.hpp` for the C++ tools, `tools/library_guard.py` for the python ones) and, when the answer is no, says why in plain words, exits with 2 and writes nothing (all its refusals are made before it opens or cuts a file): `lvl_tool` (`rewrite`, `convert` with or without `--rows` and `--columns`, and `blank`: OUT is another file than IN and never in the library), `map_sweep --out`, `bot_arena --out` and `--save-replays`, `community_maps.py repair` and `build` (the folder they write and every file in it: `cp -al Community-Maps copy` makes a folder of second names), `map_previews.py` (its pictures and index: for the library itself it refuses), `make_art.py --out`, `map_atlas.py` (OUT) and `mutate.py` (the file of a mutant and the report). A path is the library when a folder of it, or the file, is named Original-Ants or Community-Maps in any case (Windows and macOS fold case; Linux is held to the same names), as written (`..` and relative paths taken out) and again after its links are followed (a symbolic link to the folder or to a file in it); when a folder above it is this checkout's own library folder; or when it is a file with more than one name (a hard link may be the other name of a library map); a symbolic link is followed to where a write would land, also when its target is not there yet. Reading the library stays fine, and a copy of a map anywhere else may be rewritten. The tests run on a temporary copy of the layout, never on the real library (`lvl_tool --selftest`, `map_sweep --selftest`, `bot_arena --selftest`, `tests/scripts/test_library_guard.py`), and `tests/data/library_guard_mutants.json` breaks the guard on purpose. The library itself changes only by the maintainer's decision.

## Branches, pull requests and releases

1. **Work happens on a branch and is committed often**, with a clear message each time, and `./run_tests.sh --fast` runs before each commit. The branch is pushed and its pull request opened when the work is done.
2. **One pull request per piece of work**; a release is one pull request, titled "vX.Y.Z - title", whose body is the changelog entry and what to try (`tools/release.py ... --open-pr --try "..."` can do it). CI runs on the pull request; a push to a branch that has no pull request runs nothing. A newer push cancels the older run of the same branch. A pull request that changes only web pages, documents and their tests gets the light checks (below).
3. **`main` is protected.** It takes a change only through a pull request whose five checks pass on a branch that is up to date with `main`; the checks are the jobs **Linux (GCC)**, **macOS (Apple clang)**, **Windows (MSVC 2022)**, **Windows (MSVC 2026)** and **Web (Emscripten, Docker image)** (the first two are small jobs that look at the result of the jobs behind them, the legs of the Linux and macOS tests, and fail when any leg failed, was cancelled or did not run); only merge commits are allowed (so the tested commits stay as they are), force pushes and deletion are off, the rules apply to administrators too, and a merged branch is deleted. Renaming or splitting one of those jobs in `ci.yml` needs the branch protection changed in the same release (`tests/scripts/test_ci_workflow.py` keeps the names).
4. **A finished pull request is merged with a merge commit** once (for code) it is reviewed with every finding fixed and its five checks pass on the last commit; the maintainer may comment or ask to hold before that. A merge to `main` reaches the beta site through the host's own update (see "Deploy" below); CI does not wait for a quiet server.
5. A change that changes what players see edits the page of `docs/` that owns that topic (`README.md` links them all). A change to the protocol or the rules edits the page that owns it (`docs/NETWORK_PORT.md` for the protocol), in place: it replaces the sentence it makes wrong and adds no chapter. As-built notes, measurements and review findings go in the pull request description, not in `docs/`. Every change that goes live writes its changelog entry under `## Next` in `CHANGELOG.md`, which `tools/release.py` turns into the pull request's release ("The changelog", below); a change that goes nowhere needs none.
6. `main` stays releasable: never merge a state in which `./run_tests.sh --fast` or CI fails.
8. **Branches that were never merged are cleaned up by hand now and then.** GitHub deletes the branch of a merged pull request by itself; a branch with no pull request for a week is reported by the coordinator and either gets a pull request or is deleted by the maintainer in the GitHub page (an agent cannot delete a branch).

**Releasing.** `tools/release.py X.Y.Z "title" [--date YYYY-MM-DD] [--dry-run]` writes `VERSION`, turns the top `## Next` section of `CHANGELOG.md` (the draft that the release's own pull request holds, see below) into `## vX.Y.Z - date - title`, updates the README's version line, and runs `tools/check_version_consistency.py` (before and after; it refuses, with a message and with nothing written, when there is no draft or the files disagree). `--dry-run` shows the diff; `--open-pr [--try TEXT ...] [--draft]` then runs `gh pr create` with the title and the entry. The tool is tested on scratch copies of the files (`tests/scripts/test_release_tool.py`).

## Light checks for web and document pull requests

For a **pull request** (never a push to `main`, never a manual run) whose changed files are **all** of the light kinds, CI skips the macOS job and the two Windows jobs; Linux (all its jobs) and the web job run as always. The first job of the run, "Which checks does this change need?", decides with `tools/ci_light.sh` (plain shell and `git diff` against the merge base of the pull request and its base, and again against the merge base with `main` when that is another commit: retargeting a pull request starts no new run, so a pull request against another branch that carries code which `main` lacks is full, and stays so when it is retargeted; a renamed file counts under both names, a deleted one counts, a bumped submodule counts; the decision and every changed file are in the log; tested by `tests/scripts/test_ci_light.py`):

| Light | Full: anything else, among it |
|---|---|
| `web/`, `docs/`, `CHANGELOG.md`, `README.md`, `tests/data/*_mutants.json`, and the page tests `tests/scripts/test_web_*` and `tests/scripts/web_*` (files of that folder only, not in a folder below it), except the files named under "What the skipped jobs read" | `VERSION` (a change that goes live is never light), `CMakeLists.txt`, `cmake/`, `src/`, `include/`, `tools/`, `hub/`, the Dockerfiles and compose files, `.github/`, `third_party/`, `Community-Maps/`, `Original-Ants/`, `run_tests.*`, the C++ tests, the other tests and helpers of `tests/scripts` (macOS runs most of them and the two shell suites), the other files of `tests/data`, the files named below, and every path that is not listed |

Unknown is full. So are a pull request with no changed file, a history without a merge base (with its base or with `main`), a `main` that is not there, a git that fails, and a first job that fails (everything then runs). The job reads the commit ids of the event and nothing else of it (no title, branch name or body reaches a script), and its permissions stay `contents: read`.

**What the skipped jobs read.** macOS and the two Windows jobs build the game and run the C++ tests (ctest, on all three systems), the tool self-tests, the E2E runner and, on macOS, the two script suites. None of these reads a light file, because the few that they read are full: ctest reads the room-code alphabet (`web/front/lobby_rules.js`) and needs the six pictures of the original maps (`web/front/preview_*.png`); the server script of the macOS job (`tests/scripts/test_ants_server.sh`) reads the two pages (`web/lobby.html`, `web/shell.html`) and runs the lobby page against the real server and the native game in the fake browser of `tests/scripts/web_page_harness.js`, with `web/shapes.js` and the scripts of the page that the harness loads (`web/front/lobby_net.js`, `player_name.js`, `lobby_chat.js`, `rematch.js`, `game_modes.js`, `game_type.js`, `map_picker.js`, `web/home/home.js`, `web/home/games.js`), by the node checks `web_fill_check.js`, `web_lobby_server_check.js` and `web_lobby_handoff_check.js`. So a change to the lobby page is full; a change to the Map Maker, the admin page, the history, replay and match pages, Home's chat, a document or a page test is light. `tests/scripts/test_ci_light.py` finds the C++ and the scripts that name a file of `web/` or `docs/` and fails when the list is not whole.

**What a light pull request does not get.** macOS also runs most of the python tests (all but the `LINUX_ONLY` groups), and these read pages and documents: the repository checks read every document, `CHANGELOG.md`, `README.md` and the lists of mutants, and the page tests read the pages. Linux runs every one of the same tests in every run, light ones too, so a light pull request is checked by them; what it does not get is their second run on macOS, which could show a difference between the systems only (another version of node, say), and the next push to `main` runs everything. What a checkout there shows and Linux does not, a name that Windows or macOS cannot hold (two names that differ only in case, a reserved or forbidden name, a path that is too long), is refused on Linux for every pull request, light ones too: `tools/check_portable_paths.py`, run by `tests/scripts/test_portable_paths.py` among the python tests.

What is skipped: **macOS (Apple clang)** and its two jobs are *Skipped*, which GitHub counts as passing for a required check. The two Windows jobs are not skipped as a whole: a matrix job that a job-level `if` skips is reported once under the unexpanded template of its name (seen in a test run), so **Windows (MSVC 2022)** and **Windows (MSVC 2026)** would never be reported and `main` would wait for them for ever; they run for a few seconds on a small Linux machine and skip every step.

## Deploy

CI does not deploy. The production site syncs from `main` through the host's own automatic update of the stack (`docker-compose.stack.yml`); a merged pull request is live when that update next runs. Nothing in CI waits for the checks of `main` or for a quiet game server, and the update recreates the game server's container, which ends the matches that run: the site gives no promise of uptime. Every image of the page and of the game server carries the build id of the commit, so each commit recreates them; the chat hub is recreated only when its own files changed ([`HUB.md`](HUB.md), "Deploys").

*Switching to a webhook later.* To let CI start the update, turn the host's automatic update off, keep the stack's webhook address as a repository secret, and add a last job to `ci.yml` that needs every other job, runs for a push to `main` only, and sends one POST to the address (read from the environment, never printed and never put on a command line). A wait for a quiet server can poll the site's public `GET /busy` ([`NETWORK_PORT.md`](NETWORK_PORT.md)) before the call. Each piece needs its own tests, and `tests/scripts/test_ci_workflow.py` currently asserts that the workflow has no deploy job and no secret.

## Version policy

The version is the single line of the file [`VERSION`](../VERSION) (`MAJOR.MINOR.PATCH`). CMake generates the C++ header `ants_app/version.hpp` from it; nothing else writes the version by hand except the two places that name the current release for readers (the top release heading of `CHANGELOG.md` and the version line of `README.md`), which `tools/check_version_consistency.py` compares with the file (`./run_tests.sh --fast` and CI run it, and it names the file that disagrees); `tools/release.py` writes all three together.

- `VERSION` moves in the pull request of **each change that goes live** (it touches something the site serves or runs: the sources, `web/`, `hub/`, the Dockerfiles, the stack file): **PATCH** by default (0.12.1, 0.12.2, ...); **MINOR** (the patch goes back to 0: 0.13.0) in the pull request that moves the simulation's rules number or the network protocol number, that is, when an old and a new game cannot play together or a recording needs the old rules kept beside the new ones (the version then shows it: a 0.13 game does not play with 0.12), and when the maintainer calls a change a milestone; **MAJOR** stays 0 during the beta and becomes 1.0.0 when the maintainer ends the beta (the maintainer's word, nothing else decides it). A change that goes nowhere (documents, tests, other tools) leaves it alone. The pull request writes its entry under `## Next` and runs `tools/release.py X.Y.Z "title"`; when `main` took the number first, merge `main` in, keep its entry, put yours above it under `## Next` and run the tool again with the next number.
- The **network protocol number** (`include/ants_net/protocol.hpp`) moves separately and by its own rule: whenever a game of the previous number could not play with the new one.
- Every **build** is identified by its build id, the short git commit, whatever the version says: `ants --version`, `ants_server --version`, the server's first log line, the footer of the web page ("Version vX.Y.Z - build abc1234 (YYYY-MM-DD HH:MM PT)", with the Pacific build date and time) and the footer of the changelog page show it. The corner plate (the version beside the frame rate, bottom right, in every state) shows the version only. A build outside a git checkout has the id `unknown`, or the one given with `-DANTS_BUILD_ID=<text>`.
- The Docker images take the id from the build argument `ANTS_BUILD_ID` (`docker build --build-arg ANTS_BUILD_ID=$(git rev-parse --short HEAD) .`; a compose file's `build.args`), else from the commit that the clone's `.git/HEAD`, `.git/packed-refs` and `.git/refs` name (the build context holds those files and nothing else of `.git`, see `.dockerignore`), else from the UTC build time (`YYYYMMDD-HHMM`). The build log says which of the three it used (`docker/resolve_build_id.sh`).
- The test that guards the version checks its **format** (`vMAJOR.MINOR.PATCH`, the three numbers agree with it, the build id is a word), never its value.

## The changelog

[`CHANGELOG.md`](../CHANGELOG.md) is short, one entry per release, newest first, in a fixed template that is at the top of that file (copy it from there).

An entry is 5 - 15 lines, in plain words. No test counts, no mutation or review lists: those belong in commit messages and in the documents. A pull request that goes live writes its entry (the same template, for players) under a section headed exactly `## Next` (no version, no date) above the newest release, and `tools/release.py` turns that section into the entry with the pull request's version ("Version policy", above); a pull request that goes nowhere has no entry. The site builds the file into `changelog.html` with `tools/changelog_to_html.py`, linked from the game page. The page is the whole list of releases (all that a browser without JavaScript gets); an inline script of the generator shows it ten releases to a page (five on a phone) under tabs named by the versions they hold, with a Newer / Older bar below, and the address of a release (`#v0-12-39` or `#v0.12.39`) opens the page that holds it, so Back and Forward move between pages ([`TESTING.md`](TESTING.md) lists its tests). The releases before v0.12.118 are only in git history.

## Speed: compiler caches

When [ccache](https://ccache.dev) is installed, CMake uses it for every compile (`-DANTS_USE_CCACHE=OFF` switches it off; it is never used with MSVC, with a launcher you set yourself, as CI does, or for the web build). A fresh clone, another worktree or a clean build folder then compiles from the cache: the test and tool sources get the folders of the checkout from one tiny generated source (`tests/common/ants_test_paths.hpp`), not from compile definitions, so that they compile to the same object in every folder (`tests/scripts/test_cmake_paths.py` fails when a definition carries a folder). Set `CCACHE_BASEDIR` (or `base_dir` in `ccache.conf`) to the folder that holds your checkouts so that several of them share hits, and keep the cache size modest on a small disk (`max_size`). CI keeps the ccache folder of the Linux and macOS jobs (every leg restores it and builds what it needs in about a minute), and the sccache folder of the two Windows jobs (Ninja under the MSVC environment, sccache as the launcher), keyed by the runner and the commit and restored from the latest older one; a cache saved by a pull request is visible to that pull request only, one saved on `main` to all, so the first run after a merge to `main` warms the next pull requests.

## Browser checks without Docker

The opt-in browser checks that need only the page (`test_web_aspect.sh`, `test_web_edge.sh`, `test_web_touch.sh`, `test_web_home.sh`, `test_web_camera.sh`, `test_web_changelog.sh`, `test_web_replay_lock.sh` and `test_web_replay_map.sh`, which also need a recording: its header says how to make one) need a running copy of the web image, and a session that has no Docker daemon (a cloud session) cannot build one. `tools/web_without_docker.py` makes the same pages without it and runs a command against them:

```text
sudo apt-get update && sudo apt-get install -y nginx                    # once
tools/web_without_docker.py -- tests/scripts/test_web_aspect.sh          # build, serve on 127.0.0.1:19980, run, stop
tools/web_without_docker.py --context ../other-worktree -- tests/scripts/test_web_home.sh
```

It replays the Dockerfile on the machine (`FROM`, `ARG`, `ENV`, `WORKDIR`, `COPY` with `.dockerignore` and `--from`, `RUN`; `/src`, `/usr/share/nginx/html`, `/etc/nginx` and `/srv/community-maps` live under `scratch/web_without_docker/fs`), so the pages are stamped and checked by the Dockerfile's own commands. Emscripten (the version of the `FROM` line) is installed with emsdk the first time (a few minutes, kept in `.cache/ants-web` of the home folder; a run that is cut short is finished by the next one), and its ports (SDL2, SDL2_ttf, FreeType, HarfBuzz) come from git tags and Emscripten's own mirror, because such a session may not download GitHub archives (github.com and storage.googleapis.com must be reachable). nginx serves the files with the real `docker/nginx.conf`. The command gets `ANTS_WEB_URL`, and `CHROME` when it is not set: a script that starts Playwright's headless shell (Chromium's new headless mode stops giving a page the mouse once the page has left fullscreen, which fails the aspect check), else Chromium, with the mouse of a desktop (a headless browser on a machine with no mouse has no pointer that hovers, and the page hides what is for a mouse) and, as root, `--no-sandbox`. `--reuse` serves the last build, `--keep` leaves nginx running, `--build-arg` takes the Dockerfile's `ANTS_BUILD_ID`.

It does not replace CI's `docker build`, which stays the gate for the image (the runner stage, `nginx -t`, the image checks), and it is no use on macOS or Windows (use Docker there). It starts no game server, but nginx answers `/maps/all` (the list of the game's map names, which the Map Maker asks for when it starts) at once from the maps of the image, so that no name is looked up and no resolver waits (the other routes of the game server answer 404 after a second); `test_web_home.sh` leaves out its parts that play, and `test_web_hidden.sh`, `test_web_prediction.sh` and `test_web_rejoin.sh` say SKIP and exit 0 without one, which is no pass. The ports are not the archives that Emscripten checks by hash, so a change of the Dockerfile or of an Emscripten port still needs the real build. A `RUN --mount=type=cache` is played without the mount (this tool has no cache, and the Dockerfile's `ENV CCACHE_DIR` becomes a folder of the scratch space, so that the replay never trims or fills the machine's own compiler cache), the stage `emsdk-warm` (system packages, Emscripten's libraries and ports, which the tool installs itself) is not played, and a Dockerfile instruction that it does not know (`ADD`, `ONBUILD`, any other `RUN` flag, ...) is an error, never a step that is left out. Its tests: `tests/scripts/test_web_without_docker.py`.
