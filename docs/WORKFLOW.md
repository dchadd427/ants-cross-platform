# Workflow

How a change travels from a commit to a release: which tests run when, how work is merged and deployed, how the version moves, how the changelog is written. The rules for contributors and agents are in [`AGENTS.md`](../AGENTS.md) (rules 1 and 1b: branches, pull requests, `STATUS.md`; rule 2: zero warnings, all tests passing, short documents; rule 6: the web image; rule 7: the version and the build id; rule 11: the tiers); this page is the practical version.

## The three test tiers

| Tier | When | What | How | Time |
|---|---|---|---|---|
| **Quick** | after every change, before every commit | the asset, simulation, network-core, bot and application MODEL suites that finish in seconds, plus the repository checks (the version / changelog consistency check and the python tests of `tests/scripts`) | `./run_tests.sh --fast` | well under a minute on a 10-core Mac (it also builds what it needs) |
| **Full** | for every pull request, and every push to `main` and `staging`: GitHub Actions runs it on its own machines; this is the one full gate | everything: all suites of `./run_tests.sh`, the E2E runner, the script suites (start script, server end to end), ctest on Linux (GCC), macOS (Apple clang) and Windows (MSVC 2022 and 2026), the web and the server image | open the pull request, watch the run (`.github/workflows/ci.yml`) | CI about 10 minutes |
| **Deep** | only for changes to the network protocol, the simulation's rules or fairness (what a player can see or do), and now and then on a schedule | mutation checks (`tools/mutate.py`, below), AddressSanitizer + UBSan (`./run_tests.sh --asan`, locally: **CI has no sanitizer job**), soak runs (`map_sweep`, `bot_arena` tournaments, `test_lockstep`), the opt-in browser checks (`tests/scripts/test_web_aspect.sh`, `test_web_hidden.sh`), an independent review | by hand, as the change needs | as long as it takes |

`./run_tests.sh --fast` is the answer to "did I break something obvious"; it does not run the slow suites (the lock-step soak, the server, the worker bot, the network application, the E2E runner, the script suites): CI does, for every pull request, and `./run_tests.sh --sim` (or a single test program) runs the suites of one area when a change is in that area. `./run_tests.sh --list` shows what a choice of options runs. The other options are `--assets`, `--sim`, `--app`, `--e2e`, `--tools` (the repository checks), `--asan` and `--clean`; `--fast` combines with them (`--sim --fast`).

**CI is the one full gate.** Before a batch is merged, the green CI run on the exact commit of its pull request stands in for a local full `./run_tests.sh`, the local Docker builds and the GCC 12 container (CI builds both images; the server image is Debian 12 with GCC 12). A local full run or a local Docker build stays available and is used when CI cannot show something: a hang that needs a debugger, a change to a Dockerfile that must be tried before it is pushed, AddressSanitizer and UBSan.

**The runner is parallel.** `./run_tests.sh` runs independent suites at the same time, up to as many as the machine has cores (`--jobs N` changes it, `--serial` is the old one-at-a-time run with live output). Each suite's output is kept in a buffer of its own and printed in the order of the table, with the times and the totals as before, and the result of every suite is the same as in a serial run. Every suite has a temporary folder of its own (`TMPDIR`) and the tests ask the system for free ports, so nothing is shared; a suite that must be alone, or share a lock, or take several job slots says so in the table's last column (`exclusive`, `lock=NAME`, `weight=N`; `cost=SECONDS` says how long it takes, the longest start first). The measured time of the last run is kept in the build folder. The times of a parallel run grow with the load of the machine. `tests/scripts/test_ants_server.sh` (the server end to end) is five parts, `--part NAME` runs one (`--list-parts`), and `tests/scripts/run_python_tests.py` runs every test class of `tests/scripts` in a process of its own.

What a typical change can break decides what is in the quick tier: the rules and their golden cases, the command layer and the state hash, the room, TCP and WebSocket transports, the screens and the pictures (HUD, layout, zoom, fingerprints). What takes minutes and only a network, server or bot change can break stays in the full tier.

A new test must fail without the code it tests (change the code back and see it fail); a change to the network, the rules or fairness also gets the deep tier and an independent review. A change to a screen gets one combined review per batch.

**Mutation checks.** `tools/mutate.py SPEC.json` changes the code on purpose, one mutant at a time (`file`, the `old` text that must occur once, the `new` text, the CMake targets to `build`, the `test` command, an optional `expect`), builds, runs the test and puts the file back, always (also after an error, a timeout or Ctrl-C). A mutant is caught when the test fails and survived when it passes; a table and a JSON report (`SPEC.report.json`) say which. The unmutated tree is built and tested before the first mutant, every `--baseline-every N` mutants (default 10) and at the end: if that fails (a stale object of an earlier mutant: a Mac's make compares file times in whole seconds), the results are not reported. `--keep-going` goes on after a mutant that does not compile or times out, `--timeout` limits one mutant, `--check` only validates the file. Its own tests: `tests/scripts/test_mutate_tool.py`.

## Branches, pull requests and releases

1. **Agents work on a branch and commit often** with a clear message, and run `./run_tests.sh --fast` before each commit. They do not push and do not open pull requests.
2. **The coordinator pushes the branch and opens ONE pull request per release batch** (one to three a day, not one per task): the title is "vX.Y.Z - title", the body is the changelog entry and what to try (`tools/release.py ... --open-pr --try "..."` can do it). CI runs on the pull request; a push to a branch that has no pull request runs and deploys nothing. A newer push cancels the older run of the same branch.
3. **`main` is protected.** It takes a change only through a pull request whose five checks pass on a branch that is up to date with `main`; the checks are the jobs **Linux (GCC)**, **macOS (Apple clang)**, **Windows (MSVC 2022)**, **Windows (MSVC 2026)** and **Web (Emscripten, Docker image)**; only merge commits are allowed (so the tested commits stay as they are), force pushes and deletion are off, the rules apply to administrators too, and a merged branch is deleted. Renaming or splitting one of those jobs in `ci.yml` needs the branch protection changed in the same release (`tests/scripts/test_ci_workflow.py` keeps the names).
4. **The coordinator merges the pull request with a merge commit when the checks pass**; the owner may comment or ask to hold before that. A merge to `main` redeploys the beta site (through the deploy job below, once the owner has switched it on): the job waits for a moment in which no match runs (three hours at the most), then restarts the site.
5. A batch that changes what players see updates `README.md`, `CHANGELOG.md`, `STATUS.md` and, when the protocol or the rules changed, `docs/NETWORK_PORT.md`, in the same pull request. `STATUS.md` always carries the date and time of its last update (Pacific time).
6. `main` stays releasable: never merge a state in which `./run_tests.sh --fast` or CI fails.
7. **Finished work goes to `staging` for the owner to try** (the staging site, below); the pull request to `main` follows when the owner is happy.

**Releasing.** `tools/release.py X.Y.Z "title" [--date YYYY-MM-DD] [--dry-run]` writes `VERSION`, turns the top `## Next` section of `CHANGELOG.md` (the draft, see below) into `## vX.Y.Z - date - title`, updates the README's version line and the "current release" of `STATUS.md` with a Pacific time stamp, and runs `tools/check_version_consistency.py` (before and after; it refuses, with a message and with nothing written, when there is no draft or the files disagree). `--dry-run` shows the diff; `--open-pr [--try TEXT ...] [--draft]` then runs `gh pr create` with the title and the entry. The tool is tested on scratch copies of the files (`tests/scripts/test_release_tool.py`).

## Deploy from CI and the staging site

**The deploy job** (`deploy` in `ci.yml`) runs for a push to `main` (a merged pull request), or to `staging`, after the other jobs of the run passed. It waits for an idle game server (below), then calls the Portainer webhook of the stack that follows the branch, but only when the push changed something that the site serves or runs (`tools/deploy_filter.py`, tested by `tests/scripts/test_deploy_filter.py`):

- **counts:** a file that a Dockerfile copies from the build context and `.dockerignore` lets through (the sources, `cmake/`, `include/`, `web/`, `asset_catalog/`, `Original-Ants/`, `docker/nginx.conf`, `CHANGELOG.md`, `docs/CHANGELOG_ARCHIVE.md`, `tools/changelog_to_html.py`, `VERSION`, `CMakeLists.txt`), the Dockerfiles, `.dockerignore`, and the stack file of the site (`docker-compose.stack.yml`; for staging `docker-compose.staging.yml`);
- **does not count:** documents (`README.md`, `STATUS.md`, `AGENTS.md`, `docs/` except the changelog archive), `.github/`, `tests/`, the other tools, the other compose files. A push of those only is skipped, because a deploy restarts the site.

The list is derived from the real Dockerfiles and `.dockerignore`, so a new `COPY` line is noticed by itself. The base of the comparison is the last run of the workflow that passed on the branch (a push whose run a newer push cancelled is not forgotten), the job only calls the webhook while the push is still the tip of the branch, the address is a secret that is read from the environment and never printed or put on a command line (`tools/deploy_webhook.sh`: a POST with timeouts and three retries), and without the secret the job says "deploy secret not set: skipped" and succeeds, so **nothing is deployed from CI until the owner sets the secret**.

**The wait for an idle server.** A deploy recreates the game server's container and ends every match that runs, so before the webhook the job polls the site's public `GET /busy` (`{"matches": N, "players": M}`: the rooms whose match loads or runs, and the people in rooms; [`docs/NETWORK_PORT.md`](NETWORK_PORT.md); `docker/nginx.conf` routes it like `/ws`) once a minute (`tools/deploy_wait.py`, tested by `tests/scripts/test_deploy_wait.py` and `tests/scripts/test_nginx_conf.py`). It goes on **as soon as `matches` is 0** (people who wait in a room that has not started are not a match), **after `DEPLOY_MAX_WAIT_MINUTES`** whatever runs (a repository variable, 180 by default, 300 at the most: the log says "DEPLOYING ANYWAY" and what was running), or **when the address has not answered properly for five minutes** (the site is down anyway). A refused connection, a timeout, an HTTP error and a page that is not the two counts are "no answer", never "idle": the first deploy of a build that has `/busy` meets a site that has none yet and waits those five minutes once. A newer push cancels a job that waits (the job has a concurrency group of its own, `deploy-<branch>`, with `cancel-in-progress`, and the run's group cancels the older run); after the wait the job calls the webhook only while its push is still the tip of the branch. Re-running the deploy job of an older run cancels a newer one that waits: re-run the newest. A match that starts in the seconds between the last poll and the restart is still ended (there is no drain mode in the server yet). The address is the public site's (`https://beta.playants.org/busy`, a workflow default; the variable `DEPLOY_BUSY_URL` replaces it) and is never printed; the staging deploy polls `STAGING_BUSY_URL` and does not wait while that is not set; a job that waits is a job that runs (a public repository's runner minutes are free).

*To switch the deploy on (the owner):* (1) in Portainer, turn on the webhook of the production stack and copy its address (it is a secret; the stack's own Git polling must stay off, or it deploys by itself); (2) add the address as the repository secret `PORTAINER_WEBHOOK_URL` (Settings, Secrets and variables, Actions); (3) then delete the repository webhook that calls Portainer today (Settings, Webhooks), so that a push deploys once, after the tests, and not before them; (4) optionally, under Variables (not secrets): `DEPLOY_MAX_WAIT_MINUTES` (how long a deploy waits for a quiet server; 0 does not wait), `DEPLOY_BUSY_URL` (only when the site is not the public beta site) and `STAGING_BUSY_URL`. To check it, read the log of the Deploy job after a merge: "deploy wait: poll ..." lines, then "called, HTTP 2xx", or the reason for a skip ("skip: only files that no image contains changed" or "deploy secret not set").

**The staging site** is a second copy of the whole site that runs on the same machine next to the production one, for trying finished work. `docker-compose.staging.yml` has the same two services as `docker-compose.stack.yml` and shares nothing with it: container names `ants-beta-staging` and `ants-server-staging`, host ports 19981 (web page), 4003 (game port), 4004 (WebSocket) and 4011 (control interface; the last two on the loopback address) against production's 19980, 4001, 4002 and 4010, volumes `ants-staging-results` and `ants-staging-maps`, and a network `ants-staging-network` of its own (so the page's nginx finds only the staging server under the name `ants-server`). The pages say "staging" in the title and the footer (the build argument `ANTS_SITE_LABEL`, empty for production). The ports can be changed with `ANTS_STAGING_PORT`, `ANTS_STAGING_SERVER_PORT`, `ANTS_STAGING_SERVER_WS_PORT` and `ANTS_STAGING_SERVER_CTL_PORT` in the stack's environment; the other variables are those of `docker-compose.stack.yml`, with the staging stack's own values.

*To set it up (the owner):* (1) in Portainer: Stacks, Add stack, Repository: this repository, reference `refs/heads/staging`, compose path `docker-compose.staging.yml`, its own environment variables; turn on its webhook and add the address as the repository secret `PORTAINER_STAGING_WEBHOOK_URL` (the deploy job then updates it for every push to `staging`; it deploys at once, and waits for the staging server's matches only when the variable `STAGING_BUSY_URL` is `https://<the staging host>/busy`); (2) in the reverse proxy, add a host for the staging subdomain of the public site that forwards to the staging web port of the machine (19981), with WebSocket upgrades on and the same TLS as the main host (the page's own nginx passes `/ws` to the staging game server, so one upstream is enough); (3) add the DNS record of the staging subdomain, pointing where the main host's does. The coordinator pushes the finished branch to `staging` (it may be force-pushed: `staging` holds whatever is being tried); the owner tries it there; the batch's pull request to `main` follows.

## Version policy

The version is the single line of the file [`VERSION`](../VERSION) (`MAJOR.MINOR.PATCH`). CMake generates the C++ header `ants_app/version.hpp` from it; nothing else writes the version by hand except the three places that name the current release for readers (the top release heading of `CHANGELOG.md`, "current release" in `STATUS.md`, the version line of `README.md`), which `tools/check_version_consistency.py` compares with the file (`./run_tests.sh --fast` and CI run it, and it names the file that disagrees); `tools/release.py` writes all four together.

- `VERSION` is bumped for a **batch or a milestone**, not for every push: **MINOR** for player-visible features, **PATCH** for a batch that only fixes.
- The **network protocol number** (`include/ants_net/protocol.hpp`) moves separately and by its own rule: whenever a game of the previous number could not play with the new one.
- Every **build** is identified by its build id, the short git commit, whatever the version says: `ants --version`, `ants_server --version`, the server's first log line, the footer of the web page ("Version v0.1.0 - build abc1234") and the head of the changelog pages show it. The corner plate shows the version only. A build outside a git checkout has the id `unknown`, or the one given with `-DANTS_BUILD_ID=<text>`.
- The Docker images take the id from the build argument `ANTS_BUILD_ID` (`docker build --build-arg ANTS_BUILD_ID=$(git rev-parse --short HEAD) .`; a compose file's `build.args`), else from the commit that the clone's `.git/HEAD` and `.git/refs` name (the build context holds those files and nothing else of `.git`, see `.dockerignore`), else from the UTC build time (`YYYYMMDD-HHMM`). The build log says which of the three it used (`docker/resolve_build_id.sh`).
- The test that guards the version checks its **format** (`vMAJOR.MINOR.PATCH`, the three numbers agree with it, the build id is a word), never its value.

## The changelog

[`CHANGELOG.md`](../CHANGELOG.md) is short, one entry per release, newest first, in a fixed template (it is also at the top of that file):

```text
## vX.Y.Z - YYYY-MM-DD - title

**For players:**
- 1 - 6 bullets: what a player or the owner of a server sees or can do now

**Rules / network:** only if the rules of the simulation or the network protocol changed: what, and the protocol number

**Fixes:**
- optional, one line each

**Details:** [commits](link to the commit range), [detailed notes](docs/CHANGELOG_ARCHIVE.md)
```

An entry is 5 - 15 lines, in plain words. No test counts, no mutation or review lists: those belong in commit messages and in the documents. Work that is merged but not yet released is collected under a section headed exactly `## Next` (the same template, no version, no date) above the newest release; `tools/release.py` turns it into the next entry. The detailed history of every release up to v0.1.0 is [`docs/CHANGELOG_ARCHIVE.md`](CHANGELOG_ARCHIVE.md) (frozen). The site builds both files into `changelog.html` (the short page, the default) and `changelog_archive.html` with `tools/changelog_to_html.py`, linked to each other and from the game page.

## Speed: compiler caches

When [ccache](https://ccache.dev) is installed, CMake uses it for every compile (`-DANTS_USE_CCACHE=OFF` switches it off; it is never used with MSVC, with a launcher you set yourself, as CI does, or for the web build). A fresh clone, another worktree or a clean build folder then compiles from the cache: the test and tool sources get the folders of the checkout from one tiny generated source (`tests/common/ants_test_paths.hpp`), not from compile definitions, so that they compile to the same object in every folder (`tests/scripts/test_cmake_paths.py` fails when a definition carries a folder). Set `CCACHE_BASEDIR` (or `base_dir` in `ccache.conf`) to the folder that holds your checkouts so that several of them share hits, and keep the cache size modest on a small disk (`max_size`). CI keeps the ccache folder of the Linux and macOS jobs, and the sccache folder of the two Windows jobs (Ninja under the MSVC environment, sccache as the launcher), keyed by the runner and the commit and restored from the latest older one; a cache saved by a pull request is visible to that pull request only, one saved on `main` to all, so the first run after a merge to `main` warms the next pull requests.
