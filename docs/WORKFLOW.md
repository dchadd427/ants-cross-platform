# Workflow

How a change travels from a commit to a release: which tests run when, how work is merged and deployed, how the version moves, how the changelog is written. The rules for contributors and agents are in [`AGENTS.md`](../AGENTS.md) (rule 1: branches, pull requests, the merge; rule 2: zero warnings, all tests passing; rule 6: the web build, the version and the build id; rule 8: Pacific times; "How much checking": the tiers; "Working style": short documents); this page is the practical version.

## The three test tiers

| Tier | When | What | How | Time |
|---|---|---|---|---|
| **Quick** | after every change, before every commit | the asset, simulation, network-core, bot and application MODEL suites that finish in seconds, plus the repository checks (the version / changelog consistency check and the python tests of `tests/scripts`) | `./run_tests.sh --fast` | about 25 seconds of test time on a 10-core Mac, plus the build of what it needs |
| **Full** | for every pull request, and every push to `main` and `staging`: GitHub Actions runs it on its own machines; this is the one full gate | everything: all suites of `./run_tests.sh`, the E2E runner, the script suites (start script, server end to end), ctest on Linux (GCC), macOS (Apple clang) and Windows (MSVC 2022 and 2026), the web and the server image | open the pull request, watch the run (`.github/workflows/ci.yml`) | CI about 10 to 15 minutes |
| **Deep** | only for changes to the network protocol, the simulation's rules or fairness (what a player can see or do), and now and then on a schedule | mutation checks (`tools/mutate.py`, below), AddressSanitizer + UBSan (`./run_tests.sh --asan`, locally: **CI has no sanitizer job**), soak runs (`map_sweep`, `bot_arena` tournaments, `test_lockstep`), the opt-in browser checks (`tests/scripts/test_web_aspect.sh`, `test_web_hidden.sh`), an independent review | by hand, as the change needs | as long as it takes |

`./run_tests.sh --fast` is the answer to "did I break something obvious"; it does not run the slow suites (the lock-step soak, the server, the worker bot, the network application, the E2E runner, the script suites): CI does, for every pull request, and `./run_tests.sh --sim` (or a single test program) runs the suites of one area when a change is in that area. The options (`--sim`, `--app`, `--tools`, `--list`, `--asan`, `--jobs N`, ... and how `--fast` combines with them) are in [`TESTING.md`](TESTING.md) ("Running Specific Suites").

**CI is the one full gate.** Before a batch is merged, the green CI run on the exact commit of its pull request stands in for a local full `./run_tests.sh`, the local Docker builds and the GCC 12 container (CI builds both images; the server image is Debian 12 with GCC 12). A local full run or a local Docker build stays available and is used when CI cannot show something: a hang that needs a debugger, a change to a Dockerfile that must be tried before it is pushed, AddressSanitizer and UBSan.

**The runner is parallel.** `./run_tests.sh` runs independent suites at the same time, up to as many as the machine has cores (`--jobs N` changes it, `--serial` is the old one-at-a-time run with live output). Each suite's output is kept in a buffer of its own and printed in the order of the table, with the times and the totals as before, and the result of every suite is the same as in a serial run. Every suite has a temporary folder of its own (`TMPDIR`) and the tests ask the system for free ports, so nothing is shared; a suite that must be alone, or share a lock, or take several job slots says so in the table's last column (`exclusive`, `lock=NAME`, `weight=N`; `cost=SECONDS` says how long it takes, the longest start first). The measured time of the last run is kept in the build folder. The times of a parallel run grow with the load of the machine. `tests/scripts/test_ants_server.sh` (the server end to end) is six parts, `--part NAME` runs one (`--list-parts`), and `tests/scripts/run_python_tests.py` runs every test class of `tests/scripts` in a process of its own.

What a typical change can break decides what is in the quick tier: the rules and their golden cases, the command layer and the state hash, the room, TCP and WebSocket transports, the screens and the pictures (HUD, layout, zoom, fingerprints). What takes minutes and only a network, server or bot change can break stays in the full tier.

A new test must fail without the code it tests (change the code back and see it fail); a change to the network, the rules or fairness also gets the deep tier and an independent review. A change to a screen gets one combined review per batch.

**Mutation checks.** `tools/mutate.py SPEC.json` changes the code on purpose, one mutant at a time (`file`, the `old` text that must occur once, the `new` text, the CMake targets to `build`, the `test` command, an optional `expect`), builds, runs the test and puts the file back, always (also after an error, a timeout or Ctrl-C). A mutant is caught when the test fails and survived when it passes; a table and a JSON report (`SPEC.report.json`) say which. The unmutated tree is built and tested before the first mutant, every `--baseline-every N` mutants (default 10) and at the end: if that fails (a stale object of an earlier mutant: a Mac's make compares file times in whole seconds), the results are not reported. `--keep-going` goes on after a mutant that does not compile or times out, `--timeout` limits one mutant, `--check` only validates the file. Its own tests: `tests/scripts/test_mutate_tool.py`.

## Branches, pull requests and releases

1. **Work happens on a branch and is committed often**, with a clear message each time, and `./run_tests.sh --fast` runs before each commit. The branch is pushed and its pull request opened when the work is done.
2. **One pull request per piece of work**; a release is one pull request, titled "vX.Y.Z - title", whose body is the changelog entry and what to try (`tools/release.py ... --open-pr --try "..."` can do it). CI runs on the pull request; a push to a branch that has no pull request runs and deploys nothing. A newer push cancels the older run of the same branch.
3. **`main` is protected.** It takes a change only through a pull request whose five checks pass on a branch that is up to date with `main`; the checks are the jobs **Linux (GCC)**, **macOS (Apple clang)**, **Windows (MSVC 2022)**, **Windows (MSVC 2026)** and **Web (Emscripten, Docker image)**; only merge commits are allowed (so the tested commits stay as they are), force pushes and deletion are off, the rules apply to administrators too, and a merged branch is deleted. Renaming or splitting one of those jobs in `ci.yml` needs the branch protection changed in the same release (`tests/scripts/test_ci_workflow.py` keeps the names).
4. **A finished pull request is merged with a merge commit** once (for code) it is reviewed with every finding fixed and its five checks pass on the last commit; the owner may comment or ask to hold before that. A merge to `main` redeploys the beta site (through the deploy job below, once the owner has switched it on): the job waits for a moment in which no match runs (three hours at the most), then restarts the site.
5. A change that changes what players see edits the page of `docs/` that owns that topic (`README.md` links them all). A change to the protocol or the rules edits the page that owns it (`docs/NETWORK_PORT.md` for the protocol), in place: it replaces the sentence it makes wrong and adds no chapter. As-built notes, measurements and review findings go in the pull request description, not in `docs/`. Every change that goes live writes its changelog entry under `## Next` in `CHANGELOG.md`, which `tools/release.py` turns into the pull request's release ("The changelog", below); a change that goes nowhere needs none.
6. `main` stays releasable: never merge a state in which `./run_tests.sh --fast` or CI fails.
7. **Finished work goes to `staging` for the owner to try** (the staging site, below); the pull request to `main` follows when the owner is happy.

**Releasing.** `tools/release.py X.Y.Z "title" [--date YYYY-MM-DD] [--dry-run]` writes `VERSION`, turns the top `## Next` section of `CHANGELOG.md` (the draft that the release's own pull request holds, see below) into `## vX.Y.Z - date - title`, updates the README's version line, and runs `tools/check_version_consistency.py` (before and after; it refuses, with a message and with nothing written, when there is no draft or the files disagree). `--dry-run` shows the diff; `--open-pr [--try TEXT ...] [--draft]` then runs `gh pr create` with the title and the entry. The tool is tested on scratch copies of the files (`tests/scripts/test_release_tool.py`).

## Deploy from CI and the staging site

**The deploy job** (`deploy` in `ci.yml`) runs for a push to `main` (a merged pull request), or to `staging`, after the other jobs of the run passed (five on `main`, four on `staging`, which has no MSVC 2022 build). It waits for an idle game server (below), then calls the Portainer webhook of the stack that follows the branch, but only when the push changed something that the site serves or runs (`tools/deploy_filter.py`, tested by `tests/scripts/test_deploy_filter.py`):

- **counts:** a file that a Dockerfile copies from the build context and `.dockerignore` lets through (the sources, `cmake/`, `include/`, `web/`, `asset_catalog/`, `Original-Ants/`, `docker/nginx.conf`, `CHANGELOG.md`, `tools/changelog_to_html.py`, `VERSION`, `CMakeLists.txt`), the Dockerfiles, `.dockerignore`, and the stack file of the site (`docker-compose.stack.yml`; for staging `docker-compose.staging.yml`);
- **does not count:** documents (`README.md`, `AGENTS.md`, `docs/`), `.github/`, `tests/`, the other tools, the other compose files. A push of those only is skipped, because a deploy restarts the site.

The list is derived from the real Dockerfiles and `.dockerignore`, so a new `COPY` line is noticed by itself. The base of the comparison is the last run of the workflow that passed on the branch (a push whose run a newer push cancelled is not forgotten), the job only calls the webhook while the push is still the tip of the branch, the address is a secret that is read from the environment and never printed or put on a command line (`tools/deploy_webhook.sh`: a POST with timeouts and three retries), and without the secret the job says "deploy secret not set: skipped" and succeeds, so **nothing is deployed from CI until the owner sets the secret**.

**The wait for an idle server.** A deploy recreates the game server's container and ends every match that runs, so before the webhook the job polls the site's public `GET /busy` (`{"matches": N, "players": M}`: the rooms whose match loads or runs with a person in it (a room that a restart brought back also for its first five minutes), and the people in rooms; [`docs/NETWORK_PORT.md`](NETWORK_PORT.md); `docker/nginx.conf` routes it like `/ws`) once a minute (`tools/deploy_wait.py`, tested by `tests/scripts/test_deploy_wait.py` and `tests/scripts/test_nginx_conf.py`). It goes on **as soon as `matches` is 0** (people who wait in a room that has not started are not a match), **after `DEPLOY_MAX_WAIT_MINUTES`** whatever runs (a repository variable, 180 by default, 300 at the most: the log says "DEPLOYING ANYWAY" and what was running), or **when the address has not answered properly for five minutes** (the site is down anyway). A refused connection, a timeout, an HTTP error and a page that is not the two counts are "no answer", never "idle": the first deploy of a build that has `/busy` meets a site that has none yet and waits those five minutes once. A newer push cancels a job that waits (the job has a concurrency group of its own, `deploy-<branch>`, with `cancel-in-progress`, and the run's group cancels the older run); after the wait the job calls the webhook only while its push is still the tip of the branch. Re-running the deploy job of an older run cancels a newer one that waits: re-run the newest. A match that starts in the seconds between the last poll and the restart is still ended (there is no drain mode in the server yet). The address is the public site's (`https://beta.playants.org/busy`, a workflow default; the variable `DEPLOY_BUSY_URL` replaces it) and is never printed; the staging deploy polls `STAGING_BUSY_URL` and does not wait while that is not set; a job that waits is a job that runs (a public repository's runner minutes are free).

*To switch the deploy on (the owner):* (1) in Portainer, turn on the webhook of the production stack and copy its address (it is a secret; the stack's own Git polling must stay off, or it deploys by itself); (2) add the address as the repository secret `PORTAINER_WEBHOOK_URL` (Settings, Secrets and variables, Actions); (3) then delete the repository webhook that calls Portainer today (Settings, Webhooks), so that a push deploys once, after the tests, and not before them; (4) optionally, under Variables (not secrets): `DEPLOY_MAX_WAIT_MINUTES` (how long a deploy waits for a quiet server; 0 does not wait), `DEPLOY_BUSY_URL` (only when the site is not the public beta site) and `STAGING_BUSY_URL`. To check it, read the log of the Deploy job after a merge: "deploy wait: poll ..." lines, then "called, HTTP 2xx", or the reason for a skip ("skip: only files that no image contains changed" or "deploy secret not set").

**The staging site** is a second copy of the whole site that runs on the same machine next to the production one, for trying finished work. `docker-compose.staging.yml` has the same two services as `docker-compose.stack.yml` and shares nothing with it: container names `ants-beta-staging` and `ants-server-staging`, host ports 19981 (web page), 4003 (game port), 4004 (WebSocket) and 4011 (control interface; the last two on the loopback address) against production's 19980, 4001, 4002 and 4010, volumes `ants-staging-results` and `ants-staging-maps`, and a network `ants-staging-network` of its own (so the page's nginx finds only the staging server under the name `ants-server`). The pages say "staging" in the title and the footer (the build argument `ANTS_SITE_LABEL`, empty for production). The ports can be changed with `ANTS_STAGING_PORT`, `ANTS_STAGING_SERVER_PORT`, `ANTS_STAGING_SERVER_WS_PORT` and `ANTS_STAGING_SERVER_CTL_PORT` in the stack's environment; the other variables are those of `docker-compose.stack.yml`, with the staging stack's own values.

*To set it up (the owner):* (1) in Portainer: Stacks, Add stack, Repository: this repository, reference `refs/heads/staging`, compose path `docker-compose.staging.yml`, its own environment variables; turn on its webhook and add the address as the repository secret `PORTAINER_STAGING_WEBHOOK_URL` (the deploy job then updates it for every push to `staging`; it deploys at once, and waits for the staging server's matches only when the variable `STAGING_BUSY_URL` is `https://<the staging host>/busy`); (2) in the reverse proxy, add a host for the staging subdomain of the public site that forwards to the staging web port of the machine (19981), with WebSocket upgrades on and the same TLS as the main host (the page's own nginx passes `/ws` to the staging game server, so one upstream is enough); (3) add the DNS record of the staging subdomain, pointing where the main host's does. The coordinator pushes the finished branch to `staging` (it may be force-pushed: `staging` holds whatever is being tried); the owner tries it there; the batch's pull request to `main` follows.

## Version policy

The version is the single line of the file [`VERSION`](../VERSION) (`MAJOR.MINOR.PATCH`). CMake generates the C++ header `ants_app/version.hpp` from it; nothing else writes the version by hand except the two places that name the current release for readers (the top release heading of `CHANGELOG.md` and the version line of `README.md`), which `tools/check_version_consistency.py` compares with the file (`./run_tests.sh --fast` and CI run it, and it names the file that disagrees); `tools/release.py` writes all three together.

- `VERSION` moves in the pull request of **each change that goes live** (it touches something the site serves or runs, see the deploy filter above): **PATCH** by default (0.12.1, 0.12.2, ...), **MINOR** when the owner calls the change a milestone. A change that goes nowhere (documents, tests, other tools) leaves it alone. The pull request writes its entry under `## Next` and runs `tools/release.py X.Y.Z "title"`; when `main` took the number first, merge `main` in, keep its entry, put yours above it under `## Next` and run the tool again with the next number.
- The **network protocol number** (`include/ants_net/protocol.hpp`) moves separately and by its own rule: whenever a game of the previous number could not play with the new one.
- Every **build** is identified by its build id, the short git commit, whatever the version says: `ants --version`, `ants_server --version`, the server's first log line, the footer of the web page ("Version vX.Y.Z - build abc1234") and the footer of the changelog page show it. The corner plate (the version beside the frame rate, bottom right, in every state) shows the version only. A build outside a git checkout has the id `unknown`, or the one given with `-DANTS_BUILD_ID=<text>`.
- The Docker images take the id from the build argument `ANTS_BUILD_ID` (`docker build --build-arg ANTS_BUILD_ID=$(git rev-parse --short HEAD) .`; a compose file's `build.args`), else from the commit that the clone's `.git/HEAD`, `.git/packed-refs` and `.git/refs` name (the build context holds those files and nothing else of `.git`, see `.dockerignore`), else from the UTC build time (`YYYYMMDD-HHMM`). The build log says which of the three it used (`docker/resolve_build_id.sh`).
- The test that guards the version checks its **format** (`vMAJOR.MINOR.PATCH`, the three numbers agree with it, the build id is a word), never its value.

## The changelog

[`CHANGELOG.md`](../CHANGELOG.md) is short, one entry per release, newest first, in a fixed template that is at the top of that file (copy it from there).

An entry is 5 - 15 lines, in plain words. No test counts, no mutation or review lists: those belong in commit messages and in the documents. A pull request that goes live writes its entry (the same template, for players) under a section headed exactly `## Next` (no version, no date) above the newest release, and `tools/release.py` turns that section into the entry with the pull request's version ("Version policy", above); a pull request that goes nowhere has no entry. The site builds the file into `changelog.html` with `tools/changelog_to_html.py`, linked from the game page. The releases before v0.0.90 are only in git history.

## Speed: compiler caches

When [ccache](https://ccache.dev) is installed, CMake uses it for every compile (`-DANTS_USE_CCACHE=OFF` switches it off; it is never used with MSVC, with a launcher you set yourself, as CI does, or for the web build). A fresh clone, another worktree or a clean build folder then compiles from the cache: the test and tool sources get the folders of the checkout from one tiny generated source (`tests/common/ants_test_paths.hpp`), not from compile definitions, so that they compile to the same object in every folder (`tests/scripts/test_cmake_paths.py` fails when a definition carries a folder). Set `CCACHE_BASEDIR` (or `base_dir` in `ccache.conf`) to the folder that holds your checkouts so that several of them share hits, and keep the cache size modest on a small disk (`max_size`). CI keeps the ccache folder of the Linux and macOS jobs, and the sccache folder of the two Windows jobs (Ninja under the MSVC environment, sccache as the launcher), keyed by the runner and the commit and restored from the latest older one; a cache saved by a pull request is visible to that pull request only, one saved on `main` to all, so the first run after a merge to `main` warms the next pull requests.

## Browser checks without Docker

The opt-in browser checks that need only the page (`test_web_aspect.sh`, `test_web_edge.sh`, `test_web_touch.sh` and `test_web_home.sh`) need a running copy of the web image, and a session that has no Docker daemon (a cloud session) cannot build one. `tools/web_without_docker.py` makes the same pages without it and runs a command against them:

```text
sudo apt-get update && sudo apt-get install -y nginx                    # once
tools/web_without_docker.py -- tests/scripts/test_web_aspect.sh          # build, serve on 127.0.0.1:19980, run, stop
tools/web_without_docker.py --context ../other-worktree -- tests/scripts/test_web_home.sh
```

It replays the Dockerfile on the machine (`FROM`, `ARG`, `ENV`, `WORKDIR`, `COPY` with `.dockerignore` and `--from`, `RUN`; `/src`, `/usr/share/nginx/html` and `/etc/nginx` live under `scratch/web_without_docker/fs`), so the pages are stamped and checked by the Dockerfile's own commands. Emscripten (the version of the `FROM` line) is installed with emsdk the first time (a few minutes, kept in `.cache/ants-web` of the home folder; a run that is cut short is finished by the next one), and its ports (SDL2, SDL2_ttf, FreeType, HarfBuzz) come from git tags and Emscripten's own mirror, because such a session may not download GitHub archives (github.com and storage.googleapis.com must be reachable). nginx serves the files with the real `docker/nginx.conf`. The command gets `ANTS_WEB_URL`, and `CHROME` when it is not set: a script that starts Playwright's headless shell (Chromium's new headless mode stops giving a page the mouse once the page has left fullscreen, which fails the aspect check), else Chromium, with the mouse of a desktop (a headless browser on a machine with no mouse has no pointer that hovers, and the page hides what is for a mouse) and, as root, `--no-sandbox`. `--reuse` serves the last build, `--keep` leaves nginx running, `--build-arg` takes the Dockerfile's `ANTS_BUILD_ID` and `ANTS_SITE_LABEL`.

It does not replace CI's `docker build`, which stays the gate for the image (the runner stage, `nginx -t`, the image checks), and it is no use on macOS or Windows (use Docker there). It starts no game server: `test_web_home.sh` leaves out its parts that play, and `test_web_hidden.sh`, `test_web_prediction.sh` and `test_web_rejoin.sh` say SKIP and exit 0 without one, which is no pass. The ports are not the archives that Emscripten checks by hash, so a change of the Dockerfile or of an Emscripten port still needs the real build. A Dockerfile instruction that it does not know (`ADD`, `ONBUILD`, `RUN --mount`, ...) is an error, never a step that is left out. Its tests: `tests/scripts/test_web_without_docker.py`.
