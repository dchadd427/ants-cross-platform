# The chat hub

`ants-hub` is the site's global chat: a small service of its own, next to the game server and never in its thread. Python 3.12 or newer, standard library only (the image is 3.12; `python -m hub` refuses to start on an older one, with a message: on 3.11 a logout or a forget raced a handshake that was in progress, and a socket of the ended login stayed open), about four thousand lines (`hub/`). It speaks JSON over one WebSocket, `wss://<site>/hub/ws`, keeps the last 50 lines in memory and, in SQLite for moderation, the newest 200 lines and none older than seven days, and enforces every limit below itself. Reading is open to everybody. Writing needs a login with Discord ([Login](#login): the one scope `identify`; the id, the username and the display name are all that is kept); a hub that is not given the settings of a Discord application tells every client `login:false` and is read-only for all.

The pages never need the hub: the site, the rooms and the games list work whether or not it runs, and the chat shows "offline" and retries.

## The protocol

Text frames, each a JSON object with a `t`. Version 1 (`v` in the welcome).

| Direction | Message | Meaning |
|---|---|---|
| up | `{"t":"say","text":"..."}` | a line of chat (needs a login) |
| up | `{"t":"ping"}` | keep-alive; the answer is `online` |
| up | `{"t":"who"}` | watch the list of the front page's players ([Presence](#presence)); the answer is the whole list at once |
| up | `{"t":"here","at":"look"\|"wait"\|"play", ...}` | what this visitor is doing (a login is needed), for the list |
| up | `{"t":"say","text":"/..."}` | a moderator's command, in the same frame as a line ([Moderation](#moderation)): `/mute username minutes`, `/unmute username`, `/del id`, `/kick username`, `/ban username`, `/unban username`, `/bans` |
| up | `{"t":"pick","pick":"display"\|"username"}` | which of its two names the account is shown by ([Names](#names); a login and a display name are needed): the hub stores it and closes every socket of the account, and the page connects again and reads the new name in the welcome |
| down | `{"t":"welcome","v":1,"you":{"name","mod","role","k"[,"pick","other"]}\|null,"login":bool,"presence":true,"me":n,"online":n,"history":[line,...]}` | first message: who you are (`null` for a reader): `name` is the name that is shown, `role` is `none`, `mod` or `admin` (from Discord, never from a page: [Roles](#roles)) and `mod` is true for both roles (a page that reads only `mod` keeps working), `k` the key of the account for this run of the hub, and, only where the account has a display name as well, `pick` (the name that is shown: `display` or `username`) and `other` (the name that is not); whether this hub has a login at all, whether it has the list of players, for a login `me`, the number of the account's own row in that list (a reader has none), how many people are here, the last 50 lines oldest first |
| down | `{"t":"you","you":{...}}` | the whole `you` again, to every socket of an account whose role changed (a promotion, a removal, a role that ran out: [Roles](#roles)) |
| down | `{"t":"line","id","at","who","text","mod"[,"role"],"k"[,"u"][,"sys"]}` | a new line (`at` is seconds since 1970, `who` the name that the account was shown by when it wrote the line, `mod` true for a moderator or an administrator, `role` (`mod` or `admin`, absent for a person with no role) the role that the author had when it wrote the line, in the history too: a mark for the pages, never a reason to allow anything, `k` the key of its author; `u`, the author's username, only in the copy that goes to a moderator and only where it is not `who`; `sys` is `true` only for a line of the hub's own, `who` is then `system` and `k` is empty: [the named line](#moderation)) |
| down | `{"t":"del","id":n}` | take line `n` off the screen |
| down | `{"t":"ok","c":c}` | the private answer to a moderator's command that was done: `c` is `mute`, `unmute`, `del`, `kick`, `ban` or `unban` (`/bans` is answered by `bans`); nobody else is told anything |
| down | `{"t":"bans","rows":[{"u","at"},...]}` | the private answer to `/bans`: the newest 50 bans, each by the username that the ban was made with and the time (seconds since 1970); never an account id |
| down | `{"t":"bye","why":"kicked"\|"banned"}` | to every socket of a person who was kicked or banned, just before the hub closes it (close code 1000, the same word as its reason): the page knows that it was not a failure of the network |
| down | `{"t":"online","n":n}` | the number of people here (an account once, however many tabs; a socket without a login is one guest), sent when it changes (at most every 5 seconds) and as the answer to `ping` |
| down | `{"t":"who","full":bool,"n","g","more","rows":[row,...],"gone":[id,...]}` | the list of players: the whole list (`full`) or what changed ([Presence](#presence)); only to a socket that asked |
| down | `{"t":"err","code":c}` | the last message was refused; the page owns the words |

Error codes: `login` (a reader tried to write, or to say where it is), `rate`, `quota` (the account has said the lines of its hour or of its day), `muted`, `banned`, `long`, `empty`, `young` (a Discord account younger than 7 days, from its id), `bad` (the message cannot be read, the line holds `<` or `>`, a moderator's command is wrong or there is nothing to do (a person who is not muted or not banned, one who is banned already, a line that is gone), or a command word comes from an account with no role), `power` (a moderator's command that the role may not do, or not to that person: [Moderation](#moderation)), `role` (the role of the one who acts or of the one acted on could not be confirmed with Discord just now, or the one who acts no longer holds it), `who` (no one here has that username, or two do, or a `/kick` of a person who is not in the chat), `here` (a `here` is not what a page says: the chat's codes are for its lines, and a page that reads this one for a line of its own would be wrong), `pick` (a `pick` that is not done: not one of the two words, past the limit, or an account with no display name to choose; the same rule as for `here`: no line's code). A reader or a member gets no other reply to a good `say` than the `line` that everybody gets, and none to a good `here`, whoever sent it.

The protocol stays at version 1 (the new frames and codes are additive: a page ignores a frame and a code that it does not know, an older page reads `mod`, which is true for both roles, and a refused command is one more `err` that it does not show): a page that does not know `who` ignores it, and a hub that has no list does not say `presence`, so a page that has the list sends nothing to it.

## Limits

All in `hub/limits.py` (`Limits`), all enforced by the hub.

| What | Limit |
|---|---|
| frame from a client | 2 KB of payload; text only, in one piece (a fragment, a binary frame, a frame over 2 KB closes the socket: 1003, 1003, 1009) |
| a chat line | 200 code points after the text rules (NFC) and 800 bytes |
| writing | a burst of 3, then one line every 2 seconds, for an account across all its tabs; and 5 lines a second (a burst of 50) for all accounts together. An account also has a budget of 200 lines for the hour and 1,000 for the day, each filling up again steadily (one line every 18 seconds, one every 86.4); what is over is answered `quota`, and a moderator's command is never held back by it. The budgets are kept in memory: a restart of the hub gives every account its budget again |
| the same text twice | within 30 seconds the second is dropped (`rate`); a dropped line costs no token |
| mistakes | an `err` or an unreadable message is a mistake; 20 within a minute close the socket with 1008. A `rate` that comes from the limit of all accounts together or from a full database, and a `quota`, are not the client's doing and are not counted |
| frames of any kind | a burst of 10, then 5 a second for a socket; the rest are mistakes. A refusal that is not counted as a mistake (`rate` from the limit of all accounts together, from a full or a locked database, and `quota`) is not free: it costs the socket one frame of this budget more, so a client that keeps asking runs out of it twice as fast, and then it is a mistake per frame |
| sockets | 8 for each client address (an IPv6 address counts as its /64), 500 in all; the ninth gets 429, the 501st 503, before the upgrade |
| the list of players | 200 named people in the list (moderators first, then those who wait, play, look) and a count of the rest; the changes go to every socket that asked in one frame, never sooner than 2 seconds after the last send, whatever happens (the clock looks once a second, so a send comes 2 or 3 seconds after the last; a person who flaps and a crowd that comes and asks are one change); a change of more than 50 rows is sent as the whole list; a socket gets the whole list again only after 10 seconds (a second ask too soon costs it a frame more, like any refusal that is not a mistake); a `here` that is wrong is a mistake |
| the roles' lookups | one at a time, two a second (a burst of 5), and by Discord's rate-limit headers (an empty bucket waits for its reset, a 429 for its `retry_after`, at most a minute, for every lookup); 3 seconds to connect and 6 for a call, 32 KB of answer; each person who is here every 180 seconds (plus or minus a tenth), a role believed for that, a tenth more and 60 seconds more; a token, a server or an access that Discord refuses: no call for 10 minutes; at most 2,000 people in memory ([Roles](#roles)) |
| a moderator's action | the roles of the one who acts and of the one acted on are answered by Discord no more than 60 seconds ago, or both are asked again and the action waits for them, 3 seconds at the most, before anything else in the queue of the lookups (the same two a second, the same holds, the same pause, and from a share of their own, a burst of 10 and one more a second for the whole hub, so that a moderator who asks for many cannot use up the lookups that everybody's role holds on to; and a share for each moderator, across all its sockets, a burst of 3 commands that wait and one more every 5 seconds, so that one moderator cannot spend the share of the others: a command over it is refused `rate` and counts as a mistake of the socket; this share and the budget of kicks and bans (below) are each kept by the run's key of the account, which is made new at every start, and never by its id); one that cannot be had, or whose share is spent, refuses the action (`role`); a socket has one command waiting at a time (a second is `rate`, not counted as a mistake) |
| kicks and bans | a moderator has a burst of 5 and one more every 10 seconds, across all its sockets, because each is a line for everybody; the kick or the ban over it is done all the same (its `ok` and its row of the log are there) and only its line for everybody is not made, so that the history is not pushed out |
| the moderators' log | 30 days and 10,000 rows, the newest ([The moderators' log](#the-moderators-log)) |
| the switch of the name | `pick`: a burst of 3, then one every half minute, for an account across all its tabs (each one makes every socket of the account connect again); a `pick` that is refused is a mistake of the socket |
| keep-alive | the hub pings every 25 seconds; a socket that sends nothing for 60 seconds is closed (1001) |
| handshake | 10 seconds to send the request head, 8 KB at most, 64 connections that have not finished it (the login layer has 5 seconds to answer, and a handshake that waits for it keeps its place among the 64 meanwhile; a late or failing login is a reader) |
| a slow reader | a socket with 128 KB unsent is dropped; a socket that was closed with output still unsent is cut after 5 seconds |
| history | the last 50 lines, sent on connect; the database keeps the newest 200 lines and none older than 7 days (whichever limit is smaller deletes first; a newcomer is never shown a line past them). From 90% of 64 MB (the pages of `hub.db` that hold something, plus its log file) the hub deletes the oldest lines, 2,000 lines a second, down to 80% ([Data](#data)), so that the size guard stays a last resort: no new line is kept at 64 MB itself (`rate`; the pages that deleted lines free count as room again, though the file does not shrink; a mute, a ban and a deletion are never refused for it) |
| new sockets | nginx lets 5 a second through for each client address (a burst of 10) and 16 open at a time; beyond that is 503 and 429 before the hub is asked |
| the pictures | one fetch at a time for an account, 2 at a time and 32 waiting, a burst of 5 and then one a second for the hub, 3 seconds to connect and 6 in all, 49,152 bytes read and 32,768 kept, 2,000 pictures and 8 MiB; `/hub/pic/`: 20 a second for an address (a burst of 240, in nginx and in the hub) |
| the login's pages | `/hub/login` and `/hub/callback`: 10 a minute for each client address (a burst of 10 in the hub, of 6 in nginx), 6 logins that wait for Discord at one time (the 7th is answered at once), 10 seconds for Discord's two calls in all, 10,000 logins started and not finished, 10 logins kept for an account and 100,000 in all (the oldest go); `/hub/me`, `/hub/logout`, `/hub/forget`: a burst of 20, then one every 3 seconds |

## The handshake

nginx (see [the site's nginx](#the-sites-nginx)) passes `GET /hub/ws` for a socket, and the five pages of [the login](#login). The hub checks, in this order, and answers with JSON and a closed connection (`{"error":"..."}`): the method (405), the **Origin**, which must be exactly the site's (`ANTS_HUB_PUBLIC_URL`; 403 for anything else and for none, and a hub that was not told its site lets nobody in), **Sec-Fetch-Site**, which a browser sets and which must be `same-origin` where it is there at all (403 `fetch_site`), no body (400), `Upgrade: websocket` with `Connection: Upgrade` (426), version 13 (426), a valid key (400), the 500 socket total (503) and the 8 sockets of the address (429). The request head is read strictly: CRLF only, no folded lines, no control characters, at most 60 headers, and the headers the hub believes at most once. Extensions and subprotocols are never negotiated. Who the socket is comes last, from the login's cookie of the handshake ([Login](#login)), and holds for the life of the socket.

The client address is the `X-Client-Address` that nginx sets (an IP address; anything else falls back to the connection's own). `GET /hub/healthz` answers `{"ok":true}` for the image's health check; nginx does not route it. The 64 connections that have not finished their handshake are a shared pool: through nginx a connection reaches the hub only with a complete head. The services on the stack's network trust each other, so put only containers you trust on it (the stack's services and the proxy).

## Frames

`hub/ws.py` is the whole WebSocket (RFC 6455, the server side of text frames, about 150 lines). A client frame must be masked, have no reserved bit, use a known opcode and the shortest length form; control frames are at most 125 bytes and whole; text must be UTF-8. A broken stream gets a close frame with the RFC's code (1002 broken, 1003 not taken, 1007 not UTF-8, 1009 too big), and the frames that came whole before the break are still handled. A frame over the cap is refused from its header, before its payload is read. The parser never raises (`Parser.feed` returns frames and sets `error`) and keeps at most one header and one frame.

## Text rules

What a visitor types is data (`hub/text.py`). In order: NFC; every blank (space, tab, line end, other space characters, line and paragraph separators) becomes one plain space and runs collapse; control characters, format characters (the bidirectional controls, zero-width characters, joiners, the byte order mark, tag characters), surrogates, private use and unassigned code points are removed, and so are the letters that draw as blanks (the Hangul fillers, the braille blank, the combining grapheme joiner, the Khmer inherent vowels, the musical null notehead); more than 4 combining marks in a row are cut; NFC again. Then: nothing left, or nothing but combining marks (a variation selector or the Khitan filler shows nothing by itself), is `empty`; over the limits is `long`; a `<` or `>` is `bad` (checked on the result, so nothing can hide one). There is no markup, no link detection and no mention: the page shows the text with `textContent` only and puts a `bdi` or an isolating `dir` around names and lines, because right-to-left letters still reorder what is next to them.

## Names

A person has a **username**, the one name that Discord keeps unique (lower-case letters, digits, `_` and `.`, 2 to 32 characters: the hub refuses a login and an identity with any other), and may have a **display name**, which the person chooses freely at Discord (`global_name`: any text of up to 32 characters, null when none was set, not unique, and changed by the person at any time: the hub sees a change at the next login). The chat shows one of the two, as the person picks: the display name by default where there is one that may be shown, else the username. A name that is shown is **never a key**: two accounts can show one name, so a line is its author's by `k` (a keyed hash of the account that is made new at every start of the hub), a row of the list is told by its number, and a moderator addresses an account by its username.

A display name goes through one rule, `clean_shown` in `hub/text.py`, which takes text of any kind and size (more than 128 code points, or anything that is not text, is not read at all): NFKC (so that the letter forms of fancy fonts and full-width letters are the plain letters); every blank is one space; control, format, private use, unassigned and surrogate code points and the letters that draw as blanks are removed; letters and decimal digits stay, so do `.`, `_`, `-` and `'` (the curly apostrophes and the dashes of a phone's keyboard become the plain ones); a combining mark stays only after a letter or a digit, two in a row at most, and never a variation selector or a mark that encloses; everything else goes (emoji and symbols, the rest of the punctuation, the other numbers). Then NFC, the ends trimmed, the name cut at 32 code points. What is left is no display name when it has fewer than 2 code points, no letter and no digit, or reads as a reserved name. **A display name that does not pass is never a reason to refuse or fail a login**: the account is shown by its username, and nothing else happens.

A name that could pass for the hub's own voice (`RESERVED` in `hub/text.py`: `mod`, `admin`, `system` and a few more) is refused as a username (a page of its own says why) and is no display name. So are its lookalikes, which are read as `squash()` reads them: dots, underscores, hyphens, apostrophes and spaces are ignored, accents are taken off, a digit is read as the letter that it looks like (`admin.`, `adm1n`, `system_`, `a.d.m.i.n`, `Ad-min`), and so is each of the Cyrillic and Greek letters and the dotless i that are drawn like a Latin letter (`LOOKALIKE_LETTERS`, in both cases). Digits at the end are not read as anything (`system32`, `hub99` and `ants1998` are fine: a lookalike gains nothing, because a moderator is marked by the hub's `mod` flag, by Discord id, never by a name, and real people have such names), and only the whole name is read (`Admin Dave` is a name).

## Presence

The list of the front page's players ([HOME_SCREEN.md](HOME_SCREEN.md#the-players-list)): who has the front page open right now (`hub/presence.py`). The pages never need it: a hub without it, or none, leaves the page's list off and everything else as it is.

**What it holds.** For each person: the name that the chat shows (from the login, not from the page: the display name or the username, as the account picked; never the username of an account that chose not to show it, because the list is one frame for every page), `mod` if the account moderates and `role` (`mod` or `admin`) beside it, where the person is (looking, waiting, playing) and, for an account that may chat, the room's map file name, seats and code. The name, `mod` and `role` are the hub's own; where the person is, and the room's details, are what the person's page said, checked for their shape and nothing more: text from a stranger. Nothing that a person typed into the chat is in it, and nothing else about a person.

**Who is in it.** A socket that was let in with a login is a named person: the name that the chat shows (a username, `[a-z0-9_.]{2,32}`, or a display name that the rule of [Names](#names) left as it is, which no bidirectional or zero-width character can be part of), once for an account however many tabs it has, marked `mod` for a moderator of the chat. A socket without a login is a guest: counted, never named; so is an account that is **banned** from the chat (counted once, listed as a guest). A muted account, or one that is too new to chat (`young`), is named like any other and keeps none of the room's details (below). A socket that never said what it does is looking. Of the sockets of one account the one that does the most is the account's row (a match, then a room, then looking; the newer word between two that do the same). "Playing" is a page that said so while its socket is open: the game page holds no socket to the hub, so a person whose tab went to the game is out of the list until they are back on the front page.

**What a page says.** `{"t":"here","at":"look"|"wait"|"play"}`: not in a room, in a room that has not started, in a match. A page that calls its room public may add `"pub":true` and then the room's `map` (a file name exactly as the game takes it, `net::valid_map_name`: printable ASCII, 5 to 64 characters, none of `/ \ : * ? " < >` or `|`, no leading dot, ending in `.lvl` or `.LVL`; spaces and dots inside are fine, and five maps of the community have two spaces in their names), `n` (colors that play, 0 to 4), `of` (colors in the match, 1 to 4, not less than `n`) and, for a room that waits, its `code` (lower case letters, digits, `-` and `_`, 1 to 32: the code that the game server lists for a public room; the page says it only for the host of the room, so that the Join is on the host's row). A room that is not public, and a visitor who is looking, keep nothing but `at`; a match keeps `map` and `n`; **a code is never kept for a match or for a room that was not said to be public**, so a private room's code is never in the list. A field of the wrong kind or size is refused with `err` `here` (a mistake of the socket, nothing changes); a guest that says it gets `login`. What a page says is text from a stranger and is not checked against the game server: a page that lies is a page that lies. So the hub keeps the room's details only for an account that may chat (a banned, a muted or a too new account has `at` and nothing else: what it says is taken and not shown), and the receiving page draws a map's name only for an original map or for a room that the game server's own list (the Games list) shows under the same name, and offers a Join only where that list has the room's code: never the hub's words.

**What the hub sends.** To a socket that sent `{"t":"who"}`: the list as it was last sent (`"full":true`), then what changed, as one frame that every socket that asked gets at the same moment and never sooner than 2 seconds after the last send, whatever happens: the hub's clock looks once a second, so a send comes 2 or 3 seconds after the last; changes that come in between are one frame, and a person who flaps, a crowd that comes and a page that asks bring nothing forward. The first page to ask when nobody is watching (the list has not been looked at since the last watcher went) gets the list as it is now. A change of more than 50 rows is the whole list again. `rows` holds `{"i","name","at"}` and, where they apply, `"mod":true`, `"pub":true`, `"map"`, `"n"`, `"of"` and `"code"`; `i` is a number that names the row while the person is here (never the account's id: a name is not unique, so the number and not the name tells one row from another), and the welcome of a login says which one is its own (`me`), so that a page leaves that row out of its groups; `n` is the number of people (everybody named and every guest, the asker among them: the same number as `online`), `g` the guests and `more` the named people that are not in `rows`. In a change `rows` are the rows to set and `gone` the numbers to drop. Order: moderators, then those who wait, those who play, those who look, each by name; past 200 named people the rest are only counted. The number of people is counted again only when a socket opens or closes (and at least once a second), so that a ping is answered from the last count.

**What is kept.** Nothing, and for no longer than a socket is open: the list is the hub's memory of its open sockets, a person is out of it one send after their socket closes, nothing is written to the database or to the log (the log has the counts of sockets and never a name, a map or a code), and a restart starts with an empty list that fills as the pages say where they are. Who is banned or muted is read from the database when a ban or a mute changes (its own counter of them says so at every look) or when the soonest mute runs out, and a database that does not answer leaves what it said last.

**Abuse.** A `here` is one frame of the socket's budget (a burst of 10, then 5 a second, the rest are mistakes, 20 of them close the socket) and costs the hub a dictionary entry; a flood of them changes the list at most once for the next send, and a flood of `who` gets the whole list once every 10 seconds. The sends are as many as the sockets that asked, one every 2 or 3 seconds at the most, so the most that a crowd can make the hub write is the list (200 rows: 60 KB at the very most, with the longest shown name (32 code points of four bytes each), map and code that a row can have, and about 23 KB for rooms as they are) to each of the 500 sockets every 2 to 3 seconds (15 MB a second at the very most), and a socket that cannot read it is dropped by the 128 KB rule.

## Moderation

**The page.** The front page's chat reads all of these ([HOME_SCREEN.md](HOME_SCREEN.md#the-chat-dock)): the role in `you` and the `you` frame, `/help` (the page's own, never sent), a private answer in words for `ok`, `bans` and each of `power`, `role`, `who`, `rate` and `bad`, the hub's own line (only `sys: true` makes one), and a plain notice for `bye`. It writes an administrator's name in red and a moderator's in yellow, from `you.role`, from `role` on a line and from `role` on a row of the players list (a hub that sends `mod` only is read as a moderator); a moderator or an administrator is also shown the number of each line (the number that `/del` takes) and the username that the hub sends in `u`.

Mutes, bans and deletions are kept by account id in `hub.db`, so they survive a restart, a new session and a rename. A banned account can still read. Change bans and mutes only with `hub.admin` or the chat commands: a writer that does not raise the counter in `meta` (see Data) may go unseen by a running hub until the next counted change or a restart.

From a terminal on the machine (no network door; run it as the image's own user, which `docker exec` does by default, so that the database files stay the hub's):

```text
docker exec ants-hub python -m hub.admin list [--lines N]      bans, active mutes, the newest lines with their ids
docker exec ants-hub python -m hub.admin mute ACCOUNT MINUTES  (0 lifts a mute; at most a year)
docker exec ants-hub python -m hub.admin ban ACCOUNT
docker exec ants-hub python -m hub.admin unban ACCOUNT
docker exec ants-hub python -m hub.admin del LINE_ID
docker exec ants-hub python -m hub.admin log [--days N] [--lines N]   the moderators' log
docker exec ants-hub python -m hub.admin status                how full the database is
docker exec ants-hub python -m hub.admin purge [--keep-lines N]   free space at once
```

`ACCOUNT` is a **username** (`@name` when the name is all digits): the one name that is unique, found in the account's profile, which its last login made; or the account's **reference** (16 hex characters: [the moderators' log](#the-moderators-log)), which `list` and `log` print for every account, so an account that has no profile yet (it has not logged in since profiles were kept) is addressed by it; or, for a script that has it, an account id (digits, no leading zero). **No command ever prints an account id**: a Discord id is like a password, so `list`, `log`, and the answer of every command print the reference (a mute or a ban that a moderator made before the references were used has an id as the one who made it: it is printed as its reference too), and a wrong use is answered without the words that were typed. A name that the chat shows is never taken for a username. `list` shows the name that a line was written under and, in brackets, the account's username where that is another. A mute or a ban counts from the account's next line; a deleted line leaves every screen within two seconds (the hub looks every two seconds); a ban does not close the sockets that a running hub has open (the chat's `/ban` does). What the command line does is written to the moderators' log too, with `terminal` as the one who did it, and it has full power over everybody. Exit status: 0 done, 1 nothing to do, 2 wrong use.

`status` prints one line: what is in use of the 64 MB (the pages that hold something), the size of the log file (it counts for the limit as well, and is told on its own so that a long one is seen), how much of the rest is free to reuse (the pages that deleted lines left), and the lines kept with the time of the oldest. `purge` does by hand what the hub does by itself from 90%: it deletes the oldest lines (the moderators' and the deleted ones last, the newest 1,000 never), a chunk of 2,000 at a time with a tenth of a second between two chunks, so that the hub's own writes go on (SQLite's wait for the write lock is not fair: a tool that took the lock again at once would keep it), until the database is at 80% of its limit, and prints the status line before and after; `--keep-lines N` (100 or more, what a page shows) keeps the newest N lines instead and deletes all the rest. It exits 1 with "nothing to purge" when there is nothing to delete, and with "a reader holds the log file" when another program has `hub.db` open for reading, so that the log file cannot be cut ([Data](#data)).

In the chat, an account whose role is `mod` or `admin` ([Roles](#roles)) may type these commands, in any case (the text rules fold a run of blanks, a tab or a trailing blank to what the command needs), a username (the one that is unique) where a person is named, and nothing after them:

| Command | Who | What it does |
|---|---|---|
| `/mute username minutes` | mod, admin | the person cannot write for 1 to 10080 minutes; stored |
| `/unmute username` | mod, admin | lifts the mute (`bad` if there is none) |
| `/del id` | mod, admin | takes a line off every screen and out of the history; a line of one's own always may go (it is no power over a person and no entry of the log); a line of the hub's own may not |
| `/kick username` | mod, admin | closes the person's sockets and ends their login ([Kick](#kick)); the person must be in the chat |
| `/ban username` | admin | the hub's ban ([Ban](#ban)); `bad` if the person is banned already |
| `/unban username` | admin | lifts a ban: by the username, or by the name that the ban was made with when the person's profile is gone (the names that `/bans` shows) |
| `/bans` | admin | the newest 50 bans, in a private `bans` frame |

A command is not a chat line; it is never shown to anybody, and a good one is answered with `ok` to the one who typed it. A line that starts with one of these words (in any case) from an account that holds no role, or whose role is not known yet, is refused `bad` and never posted, so that a command never shows for everybody to read; any other line that starts with `/` is text. A moderator sees the username next to the name that a line shows, where they differ (`u`, in the copy of a line that a moderator is sent, live and in the history; nobody else is ever sent a username that the account chose not to show). The username means the account that is in the chat with it; when nobody is, it is the one account whose profile has it (a profile is kept 35 days after the last login); when two accounts are, or when nobody is and no one profile has it, the command is refused `who`: use the command line with the reference. A command from a banned or a muted account is refused before anything else (`banned`, `muted`).

**Who may act on whom.** There is one table, `allowed` in `hub/chat.py`: a **moderator** acts on people who hold no role; an **administrator** acts on people who hold no role and on moderators; **nobody acts on an administrator** (administrator against administrator is refused: two of them could silence each other and the chat cannot settle who is right; admins are appointed in Discord, so a dispute is settled there, or from the command line, which keeps full power; it also means that one administrator login cannot silence the others), **nor on the account in `ANTS_HUB_OWNER`** (always an administrator) **nor on themselves**. A command that the role does not have (a moderator's `/ban`, `/unban` or `/bans`) or that is not allowed on that person is refused `power`. Nothing is read from a client for it: the roles come from Discord ([Roles](#roles)).

**The fresh check.** Before any action the hub looks at the last answer of Discord about the role of the one who acts and of the one acted on (a `/del` of one's own line needs only the first). If either answer is older than **60 seconds**, or there is none, it asks Discord about **both** at once, first in the queue of the lookups, and waits for the answers at most 3 seconds; then it decides on those answers and does what was asked, with no wait between the decision and the action. A lookup that fails (Discord down, slow, busy, refusing, or an answer that is not a member's) or is late **refuses the action** (`role`, not counted as a mistake of the socket; nothing is done and nothing is logged), and so does an answer that says that the one who acts holds no role any more: a role that is only believed is never enough for an action (it is for showing the page, for the grace of [Roles](#roles)). The target need not be here, and Discord is asked about a person who is not in the chat when a moderator acts on them: a person who is not in the chat is found by the username of their profile, and their role is asked of Discord with the id that the database holds for that profile (the id is in the request and nowhere else: not in a log line, a frame, an error or the log of moderators). A person who is not in the server at all holds no role, and that is an answer. So a moderator can act on a person who is not here only when Discord says, now, that the person holds no role; and during an outage nobody, the owner account included, can act on a person whose role was not answered within the last minute (the command line is the fallback). A command that waits runs as a task of its own: the chat goes on, one command of a socket waits at a time (a second is `rate`), and nothing is written to a socket that closed meanwhile.

#### Kick

`/kick` **closes every chat socket of the person and ends every login of the account** (the cookie of the browser stops working): each socket is sent `{"t":"bye","why":"kicked"}` and closed (1000). There is **no timer**: the person is logged out and has to log in with Discord again, which they may do at once, and may write at once; a kick that is made again is made again. A kick is for a person who is in the chat (`who` otherwise). It is not stored beyond the log: kick is not mute (stays, cannot write for a time, stored) and not ban (stored, until lifted).

#### Ban

`/ban` is the hub's ban, the one that `hub.admin ban` makes: by account id, until `/unban` or `hub.admin unban`, no address (the hub keeps none). It stops writing (`banned`) and the entry in the list of players (the person is listed as a guest); **it also closes the sockets at once**, each sent `{"t":"bye","why":"banned"}`; the person can still log in and read like any visitor, since reading is public anyway, and their logins are not ended. A banned moderator keeps the Discord role but cannot use it (the ban is checked before a command).

#### The named line

When a kick or a ban was **done** (never for a command that was refused, whatever the reason), everybody in the chat is shown a line of the hub's own: `<name> was kicked.` or `<name> was banned.`, as `{"t":"line","who":"system","text":"alice was kicked.","mod":false,"k":"","sys":true,...}`. It names the person by the name that they are shown by (their display name or username, as they picked) and **never the moderator** (who did it is in the moderators' log only, by reference). `system` is a reserved name that no account can have, so the line cannot be mistaken for a person's; `sys` lets a page draw it as the hub's own, and a page that does not know it shows a line from `system`. **It is kept like any other line**: it is a row of `lines` with the empty account and the name `system`, in the history that a newcomer is sent, in the 200 newest lines and the 7 days, and deleted by the same purge; it can be deleted from the command line (not from the chat). A database that refuses it costs the line and never the action, which is done already; the same holds for the moderator's budget of these lines (see [Limits](#limits)): over it, the action is done and answered and logged, and only its line is not made. **Forget me does not remove it** (it is the hub's line, not the person's), and it goes with the other lines within 7 days.

## Roles

Who may moderate is decided by the roles that a person holds in the project's Discord server and by nothing that a page says. There are two, the administrator's and the moderator's: an account that holds either one may type the commands of [Moderation](#moderation), a person who holds both is an administrator, and the account in `ANTS_HUB_OWNER` is always one, with no call to Discord (it needs no answer about itself for an action; the person it acts on does: [Moderation](#moderation)). The welcome's `you` carries `role` (`none`, `mod`, `admin`; `mod` is true for both), and a live `{"t":"you","you":{...}}` follows when it changes (the lines that a moderator writes are marked `mod` and the list of players shows them first, for both roles).

**The lookup** (`hub/roles.py`, `hub/discord.py`). With the bot's token the hub asks `GET /api/v10/guilds/<server>/members/<account>` (the bot is a member of the server; the call needs no privileged intent and no gateway connection) and reads the `roles` of the answer. The answer must be a member: `roles` a list of at most 250 ids and, if there is a `user`, its `id` the one asked about; anything else is a failed check. A person who is not in the server (404 with Discord's code 10007) holds no role, and that is an answer. The token goes in one header, to `discord.com` only (https, the certificate checked, 3 seconds to connect and 6 for a call, 32 KB at most, no redirect followed), as a local of the call; an error carries a kind and a status and nothing else.

**When.** Before an action of a moderator (the fresh check of [Moderation](#moderation)) the roles of the two people are asked at once, before anything else. At the handshake of a login the person goes to the front of the queue and the welcome says the last answer that is known (`none` for a person who is new); the answer follows as a `you` frame. Then everybody who has a socket open is asked again every `ANTS_HUB_ROLE_RECHECK_SECONDS` (180, 60 to 3600; plus or minus a tenth, so that a crowd that came together is spread out), so a promotion or a removal arrives within about that long, with no new login. A person with no socket is not asked about. The queue: role holders who are more than 30 seconds overdue; sockets that were just let in (a page that reconnects while its checks fail keeps the delay of the retries); people who hold a role or lost one in the last hour; everybody else, who wait longer (up to about nine minutes) when the hub is busy, never the role holders. One request is made at a time, two a second (a burst of 5) and by Discord's rate-limit headers (an empty bucket waits for its reset; a 429 waits for its `retry_after`, at most a minute, for every lookup; a wait that cannot be read is the longest one): far below the 50 a second that Discord gives a bot, which the bot's other uses share.

**Fail closed.** A role is believed for the interval, a tenth more (the latest that a check can be due) and 60 seconds more (258 by default); after that the person is `none` until Discord answers, and the pages are told. A Discord that does not answer, is busy or sends what is not a member is a failed check: never a role and never "no role" (the person keeps what they had, until the grace runs out); it is tried again after 15, 30 and 60 seconds, then at the normal pace, with one `roles_down` line in the log (at most one in 10 minutes) and `roles_up` when it answers again. A person whose Discord account was deleted (404, code 10013) is not in any server: it holds no role, and that is an answer. A token, a server or an access that Discord refuses (401, 403, or 404 with the code for an unknown server) stops every call for 10 minutes, takes everybody's role away but the owner account's, and writes one `warning`; then one call tries again. Chat is never held up by any of it: the chat asks `role_of`, a dictionary look with no I/O, and the lookups run in a task of their own with a time limit on every request; if that task ever ends, the clock says so in the log (with the other `error` lines of the roles, at most one in 10 minutes) and starts it again, and the roles run out meanwhile.

**What is kept.** Memory only: one small entry for each person with a socket open, and for a few minutes after the last one closes (a page that reloads keeps its role), at most 2,000; nothing in the database. The token, the server's id and the roles' ids are read from the settings once, and a person's Discord id is like a password: it is used to log the person in and to ask Discord for the roles, and is in no log line, frame, error text, representation of the state or answer (an error of a call to Discord is a kind and a status and has no cause that could hold the request's address; the log replaces any number of 15 digits or more).

**Setting it up.** (1) In Discord's developer portal, on the Bot page of the application, copy the token (the bot must be a member of the server; the token may be the one that the bot's other uses have: **resetting it in the portal stops those uses**, so look for the stored one first); (2) in Discord with Developer Mode on, copy the server's id and the ids of the two roles; (3) put `ANTS_HUB_DISCORD_BOT_TOKEN`, `ANTS_HUB_DISCORD_GUILD`, `ANTS_HUB_ROLE_ADMIN` and `ANTS_HUB_ROLE_MOD` in the stack's environment (the token **only** there, never in a file of this repository, a chat or a pull request) and, for the account that must keep its powers when Discord does not answer, `ANTS_HUB_OWNER`; (4) redeploy: the start line says `roles_configured=1`, and a person who holds a role gets a `you` frame with it within seconds of connecting (the welcome itself says `none` for a hub that was just started). If the first lookup is refused with 403 (`kind=access` in the log), turn on the Server Members intent for the bot in the developer portal and try again. The hand list `ANTS_HUB_MODS` is not read any more (a leftover value only logs one warning): the people who were on it have powers when they hold a role in Discord.

## The moderators' log

Every action that a moderator or an administrator does in the chat and that is **done** (a mute, an unmute, a deleted line that is not their own, a kick, a ban, an unban), and every one that `hub.admin` does (a mute, an unmute, a ban, an unban, a deleted line; the one who did it is `terminal`), leaves one row in the table `modlog` of `hub.db`, in the same step as the action: when (`at`), who did it (`actor`), what (`action`), to which account (`target`, empty where there is none) and a detail (the minutes of a mute, the number of a line). A refused command leaves no row. Where the row has an account it has its **reference**, **never the Discord id**: the first 16 hex characters of HMAC-SHA256 of the id, keyed with a secret that belongs to the hub (32 random bytes, made by the store the first time that a database is opened and kept in `hub.db`, table `secrets`; it is never printed, logged or sent). `hub/pseudo.py` is the one function that makes a reference, so that the tables that still hold an id can be moved to it by a later change. The same account has the same reference for as long as the database is the same, so the log can say that two actions were done to one person, and it says nothing of the id to anybody who reads its rows without the secret (a copy of the whole of `hub.db` holds the secret and the ids both: the references protect the rows when they are shown or copied alone, not the file). The store refuses a row whose actor or target is not a reference (or `terminal`) and whose action or detail is not one of the plain forms, so that an id cannot get in by a mistake of a caller. The `by` that a ban, a mute and a deleted line keep, for an action in the chat, is the reference as well.

It is kept **30 days and at most 10,000 rows** (the newest): the rows past the cap go in the step that adds the next, and the hub's hourly purge deletes the rows past 30 days and past the cap, with the lines and the mutes that are over. It is in no frame and no page can ask for it. It is **read only from the terminal**: `docker exec ants-hub python -m hub.admin log [--days N] [--lines N]` prints it newest first, the actor and the target as references and, where the account still has a profile, its username. **Forget me does not remove it**: its rows hold no name and no id and are what makes an action reviewable; the profile goes, so the log names nobody afterwards, and the rows go with their 30 days. The Legal page ([web/legal.html](../web/legal.html)) says so.

## Data

The hub, the login and the command line reach the data only through the interface of `hub/store/base.py`: lines, deletions (a counter that only goes up), purge, mutes and bans (with a counter of their changes that only goes up), logins, forget and size. A store that cannot do one now (locked, full, out of reach) raises `StoreError`, which is the only error a caller catches. `hub/store/sqlite.py` is the one backend and the default; what only it has (the log file's cut, `secure_delete`) stays on its class. `tests/scripts/test_hub_store_contract.py` runs the same checks against any backend. The rest of this section describes the SQLite one.

`/data/hub.db` (SQLite, WAL, file mode 600; the volume `ants-hub-data`): `lines` (id, time, account id, the name that was shown, text, the author's role when it wrote the line, a deletion mark), `mutes`, `bans`, `sessions` (the logins, below), `profiles` (below), `pictures` (below), `secrets` (the key of the references) and `modlog` ([the moderators' log](#the-moderators-log)). The schema is version 4 (`PRAGMA user_version`): a file of an earlier version is migrated at its first open (the two tables are added and the secret is made; nothing else is touched), and a hub of an earlier version refuses a file of version 4 ("from a newer hub"), so keep a copy of `hub.db` before an upgrade that may be rolled back. **The role on a line** needs no step of the schema: the column that held the moderator's flag (`mod`) holds the role that the author had when it wrote the line, 0 (none), 1 (a moderator) or 2 (an administrator). A line of before is a 1 or a 0 and is shown as it was (an administrator's line of before is a moderator's); a hub of an earlier version reads the 2 as the flag that it knows (any value that is not 0 is true, in its pages and in the purge's own condition), so a rollback shows an administrator's line as a moderator's and loses nothing. A line shows the role that its author had when it wrote it (a person who loses the role keeps the mark on the lines that they wrote while they held it, until the lines go in 7 days); the role of the moment is never taken from a line, because the powers are decided only by the fresh check. A rollback that keeps the data is one line, run in the container before the older hub starts: `python -c "import sqlite3; c=sqlite3.connect('/data/hub.db'); c.execute('PRAGMA user_version=3'); c.commit()"` (the two new tables are additive; the older hub does not trim `modlog`, and an upgrade again picks it up). A line is kept only while it is among the newest 200 lines (every line counts: a moderator's line and a line that a moderator deleted too) and for up to 7 days, and then deleted for good; whichever limit is smaller deletes first. The store takes the lines past the newest 200 out in the step that keeps a new line (at most 8 at a time, so one chat line never waits for a long delete), so the table holds 200 lines; a file that holds more (one written by an earlier version) is cut down by the hub's purge, which runs at the first tick after a start and then every hour, 2,000 lines at a time and again at once while a chunk was full, together with the lines past their 7 days (a long backlog goes over several seconds, not in one wait), the freed pages are zeroed (`secure_delete`) and the log file is cut; when a reader (for example `hub.admin list`) holds the file at that moment, the cut is tried again every 10 seconds, and once at every start. **The store makes room by itself.** From 90% of the 64 MB (`db_max_bytes`: the pages of `hub.db` that hold something, plus its log file) the hub's clock deletes the oldest lines, 2,000 a second, until the pages that hold something are down to 80%: the moderators' lines and the lines that a moderator deleted last, and the newest 1,000 never (a page shows 100, the hub keeps 50; with the 200 lines that the store keeps, this is the last resort that it was meant to be, and the 64 MB are not reached); the log file is cut after each chunk. A program that holds `hub.db` open for reading (a backup tool, a shell that was left open) keeps the log file from being cut, and a chunk of 2,000 lines would add some megabytes of pages to it: while the log file cannot be cut and is over 16 MB the hub deletes no more lines, asks again every 10 seconds, and says `database_full_a_reader_holds_the_log_file` in its log (at most once in 10 seconds) when the limit is reached meanwhile. Mutes, bans, the deletion counter, the logins, the profiles and the moderators' log are not touched. The lines go in the order of their numbers, which is also the order of their time and of their pages, so the pages they leave are whole and free, the lines that follow use them, and the file stops growing (a deletion from the middle, such as a forget, leaves pages that still hold lines, which count as in use until the oldest lines have gone past them). At the 64 MB itself no new line is kept (`rate`): that guard is the last resort, so the hub does not fill the volume by itself, and the log says `database_full_and_no_line_to_delete` once a minute if nothing may go; `python -m hub.admin status` and `purge` are the same from a terminal ([Moderation](#moderation)); when the disk refuses a write, or another process holds the database's write lock for longer than the hub waits (0.3 seconds), the line or the moderator's command is not done and the sender is told: `rate` for a line (not counted as a mistake, the line did not cost a token, and the same text may be tried again at once) and `bad` for a command, the socket stays, and one `error` line (the class of the error, never the text) is logged every 10 seconds at the most; the command line says "the database refused it" in one line. Any other database error closes the socket that caused it (1011). Deletions are numbered by a counter in `meta` that a purge cannot lower, so a mod's `/del` still reaches every screen after old lines were purged. Every ban, unban and mute (the command line's too) raises another counter in `meta`: that is how the hub knows that the two lists changed without reading them at every look of the front page's list. A purge that fails (another process holds the write lock, the disk refuses) is tried again after a minute, and the hub's writes wait at most 0.3 seconds for another process, so the one thread is never held for seconds. A line that a moderator deleted stays, marked, until it is past the newest 200 lines or its 7 days are up: a deletion is a mark on a line that the pages show, and the pages show 100 at most, so the line is among the newest 200 for as long as a page can show it; a moderator's `/del` and the command line's `del` work on any line that is still there, and the counter in `meta` that numbers the deletions never goes down when the line is taken out. The last 50 lines that are not deleted, not past their time and among the newest 200 are the history after a restart. A login (`sessions`) holds the SHA-256 of its cookie's value, the account id, the username as it was when the visitor logged in, and the time it ends; the hub deletes the ones that ran out with the lines past their time. **A profile** (`profiles`: account id, username, display name or none, which of the two is picked, and the time of the login that last refreshed it) is made or refreshed at every login (the pick stays, and is the display name for a new profile and for one that had no display name and now has one); it is what the hub reads at a handshake to name the socket (a login from before profiles were kept has none, and is shown by its username until its next login), and what a moderator's `/mute` and the command line look a username up in (an account is found only when exactly one profile has the username). A profile is deleted by Forget me, and by the hub's hourly purge when no login has refreshed it for 35 days (a login lasts 30), and the table keeps at most 100,000 (the ones refreshed longest ago go, as the logins do). Lines keep the name that they were written with. Nothing else about a person is stored. **Forget and logout leave nothing in the log file:** a forget cuts the log file (`hub.db-wal`) before it answers, so that the lines, the name and the hashes of the logins are in neither file (the freed pages are zeroed, and when a reader holds the file the cut is tried again every 10 seconds); the end of a login (a logout, a login that replaces the old one of a browser, one that the caps push out) has the cut done within 10 seconds, one cut for any number of them. **The schema is 3** (`PRAGMA user_version`; the `sessions` table came with it). A hub of an earlier version does not start on such a database (`RuntimeError: hub.db is from a newer hub (schema 3)`), so a rollback of the hub to a version before the login needs the volume of before it (or a new volume): the file is never changed back. **The `pictures` table is additive too** (`ref` the account's keyed reference, `show` 1, 0 for the person's off or 2 for a block, `name`, `png`, `until` the end of the login that fetched it, `at`): no version of the schema came with it (`user_version` stays 4), a hub of the version before opens the same file and never looks at it, and its Forget me does not delete a picture, so the purge deletes every one past `until` and `GET /hub/pic/` serves none past it; after a rollback that is for good, with the hub stopped, `python -c "import sqlite3; c=sqlite3.connect('/data/hub.db'); c.execute('PRAGMA secure_delete=ON'); c.execute('DROP TABLE pictures'); c.commit()"` (the pragma first, so that the bytes are zeroed whatever this SQLite is built with). **The `profiles` table is additive and came with no new version**: it is made when a hub opens a file that has none, and a hub of the version before it opens the same file, ignores the table, and works as it did (the chat shows usernames; a name is addressed as it was). What that hub leaves behind: its Forget me does not know the table, so the profile of an account that forgot itself there stays until the purge of a hub that has profiles deletes it, 35 days after the account's last login.

## Login

The hub core asks a `Sessions` object (`hub/session.py`) who is on the other end of a handshake: `identify(headers)` returns an `Identity(account_id, name, young, session, expires, username, pick, other)` or `None`. An account id is digits (1 to 20: a Discord id), `name` is the name that is shown (`username` when there is no display name to choose), `young` says the account is too new to write, `pick` and `other` are set only for an account that has both names. The hub believes an identity only when the username is a username and the name that is shown is that username or a display name that `valid_shown` leaves as it is. `identify` is a coroutine (a real login looks something up); the hub waits 5 seconds for it. Without the settings of a Discord application the hub has `NoLogin`: nobody is identified, the welcome says `login:false`, and the hub is read-only for everyone. With them it has `DiscordLogin` (`hub/login.py`, `hub/discord.py`); the core and its tests do not change.

**What is asked of Discord, and what is kept.** The one scope `identify` (the visitor's id, username, display name and the short code of the profile picture: `GET /users/@me` carries `global_name` and `avatar` with that scope, null for a person who set none), through the authorization code grant: the visitor is sent to `https://discord.com/oauth2/authorize` with `client_id`, `response_type=code`, `scope=identify`, `redirect_uri=<ANTS_HUB_PUBLIC_URL>/hub/callback`, a `state` and `prompt=none` (a visitor who agreed before does not see the consent page again). The code that comes back is exchanged by the hub, never by the page (`POST /api/v10/oauth2/token`, a form body with the client secret), and the access token is used once, for `GET /api/v10/users/@me`. **Only the id, the username and the display name are kept.** The access token and the refresh token are local variables of one function and are gone when it returns; the email and everything else of the answer are never looked at, and the picture's short code is checked for its shape, used once for the one fetch of [Pictures](#pictures) and never kept. Every answer of Discord is data: https only, the certificate checked, 3 seconds to connect, 6 for a call and 10 for the two, no redirect followed, at most 32 KB read, JSON of the shape that was asked for or no login (a username that is not a username, an id that is not an id, a token that is not a plain word; a display name of any kind is accepted as data and cleaned, so it is never a reason for no login; the answer as a whole is still held to its 32 KB). PKCE is not used: Discord's reference for the authorization code grant mentions it once, in passing (a warning at the implicit grant), and describes no parameter for it; its guide for web logins says a server-side client authenticates with its client secret and that PKCE is for public clients such as native and mobile apps. The login is therefore held by the `state` (below), and the client secret that only the hub has.

**The pages** (nginx passes these five and the socket; `hub/login.py`):

| Page | What it does |
|---|---|
| `GET /hub/login?next=home\|room` | a random 128-bit `state` is kept in the hub (one use, 10 minutes, at most 10,000 at a time) and in a cookie `__Host-ants_oauth` (`Secure; HttpOnly; SameSite=Lax`, because Discord's way back is a navigation from another site), and the visitor is sent to Discord. Only a request of the front page's own button (or the address typed: `Sec-Fetch-Site` `same-origin` or `none`, or none at all) starts a login; a link or an image of another site (`cross-site`, `same-site`) gets a small page, and nginx turns it away before it spends the visitor's allowance, as does the hub (a hostile page cannot use up a visitor's tries). `next` is one of two words, and the way back is `/` or `/#room`: never an address that was sent |
| `GET /hub/callback?code&state` | the state of the cookie, of the address and of the hub must be one, the hub forgets it at once (one callback for a state, whatever it ends in), the code is exchanged, a login is kept and the visitor goes back to the front page with the cookie `__Host-ants_hub`. A replayed callback, a code that Discord has seen, a state that ran out, a missing or doubled cookie, a visitor who said no at Discord, a Discord that is down: a small page with a link back (`Login unavailable, try again later` for a Discord that does not answer or answers wrongly), never a login, and the sockets of everybody else are never held up |
| `GET /hub/me` | `{"login":true,"you":{"name","mod","role","k"[,"pick","other"]}\|null}` (the welcome's `you`), `no-store`; only for the front page's own request. The front page and the game page ask it for the name to play under ([`PLAY_IN_BROWSER.md`](PLAY_IN_BROWSER.md#your-name)) |
| `POST /hub/logout` | ends this login (the row is deleted, the cookie cleared, the sockets that it let in are closed with 1000) |
| `POST /hub/forget` | ends every login of the account and deletes every chat line that it wrote (not the hub's own line that said it was kicked or banned: that goes with the other lines, within 7 days) (the screens drop them at once) and its profile, and wipes the name from its mute and its ban (the screens are told of the newest 100 of the lines, one `del` frame each: a page keeps 100 lines at most, and a forget of 300,000 lines must not be 300,000 frames for every socket on the hub's one thread; the database work for the largest backlog that the limits allow holds the hub for under a second). A ban or a mute stays, by id: **neither a logout nor forgetting lifts one** |

`/hub/me`, `/hub/logout` and `/hub/forget` answer only what the front page itself asked: the `Origin` must be the site's (a POST always has one) **and** `Sec-Fetch-Site` must be `same-origin` (403 otherwise, nothing done); a body is refused (400), a query is 404. The cookie is also `SameSite=Strict`, so a request of another site does not carry it at all.

**The cookie.** `__Host-ants_hub=<32 hex digits>; Path=/; Max-Age=2592000; Secure; HttpOnly; SameSite=Strict`: 128 random bits, 30 days, of which only the SHA-256 is kept (a copy of the database logs nobody in), a new value for every login (a value that a visitor already had is never taken over, and the old row is deleted), at most 10 for an account. The `__Host-` prefix makes a browser refuse the cookie unless it is `Secure`, has `Path=/` and no `Domain`, and stops a sibling subdomain from setting or replacing it ("cookie tossing"); that is why the path is `/` and not `/hub`, and why nginx narrows what it passes on: a cookie of the site goes to every request of the site, so [nginx](#the-sites-nginx) passes the login's cookie to the five pages and the socket only, passes no other cookie to the hub, and drops the Cookie header at the game server's doors (`/ws`, `/busy`; the admin page's API gets its own cookie and no other). `HttpOnly`: the page never reads it. A cookie that comes twice, or has the wrong shape, is nobody's.

**A socket's identity** is fixed at the handshake from the cookie and holds for its life: it ends with the login (logout and forget close the sockets of the login or of the account; so does the end of the 30 days, within a second), and a socket never changes who it is. The welcome's `you` is `{name: <the name that is shown>, mod, role, k}`, and for an account that has both names `pick` and `other`; the page reads nothing else. A switch between the two names ends every login's sockets, because a socket's name is fixed at its handshake as its identity is. A banned account can log in and read; it cannot write (`banned`), and a mute stands too. An account younger than `ANTS_HUB_MIN_ACCOUNT_DAYS` (7; the age is in the id's first 42 bits, so no call is needed) gets `young` and cannot write.

A visitor's username is untrusted text: it must be a Discord username (`[a-z0-9_.]{2,32}`) or the login is refused with a page that does not show it; a username that could pass for the hub's own voice, or a lookalike of one, is refused with a page of its own that says why ([Names](#names)). The display name is untrusted text too, and is cleaned by its own rule; it is never a reason for a page that refuses. Both are only ever written into a JSON body, never into a header, a page or the log.

**What the site's operator does once.** (0) **Before the login goes live:** name the reverse proxy in front of the site in `docker/trusted-proxies.conf` (see [Behind a reverse proxy](#behind-a-reverse-proxy)), so that the limits per address count each visitor's own address. (1) Create a Discord application in Discord's developer portal (a name, a picture) and read its client id; (2) under OAuth2, add the redirect `https://<the site>/hub/callback`, and one for each other copy of the site that you run; (3) put the client id and the client secret in the stack's environment (`ANTS_HUB_DISCORD_CLIENT_ID`, `ANTS_HUB_DISCORD_CLIENT_SECRET`), the secret **only** there, never in a file of this repository, a chat or a pull request; (4) optionally the privacy and terms links of the application, which can be [`/legal`](../web/legal.html); who may moderate is set up in [Roles](#roles). The hub calls `discord.com` over https, so its container needs outbound network access. Then redeploy the stack, log in once on the real site, and look at the hub's log for a `login` line. Real Discord is never asked by the tests; this step is the first time it is. **Try it with a fresh Discord account** that never authorized the application: the hub asks with `prompt=none`, which is meant to show a first-time visitor the consent page, and that is not verified against the real Discord; if Discord answers such a visitor with an error instead, they see "Login cancelled", and the `prompt` parameter (`hub/discord.py`) is what to change.

**The page** (`web/home/chat.js`, [HOME_SCREEN.md](HOME_SCREEN.md#the-chat-dock)): the Log in button shows only when the welcome says `login:true` and has no `you`, and it is a full navigation to `/hub/login?next=home` (the Room's way is `next=room`), so the tab leaves for Discord and comes back to the same screen; the page's own session storage (`ants.lobby`) is untouched, so the seat of a room is taken back as after any reload. Log out and Forget me are `fetch` POSTs of the page itself; after either the page connects again, as a reader. The dropdown that the account's chip opens (the name, Log out, Forget me) has, for an account that has a display name as well, one more button, which says which name the chat shows and offers the other; it is the message `pick` over the socket that is open, and the hub's answer is to close the sockets of the account, after which the page connects again and reads the new name.

## Pictures

After a login has been answered, the hub fetches one small copy of the account's Discord picture, in the background (`hub/pictures.py`, `hub/discord.py` `picture()`): the login never waits for it and never fails because of it. The address is `https://cdn.discordapp.com/avatars/<id>/<code>.png?size=64`, made in one place from constants and the two parts, each matched against its shape right there (an id is digits, a code is 32 hex digits, `a_` before them for an animated one, whose `.png` is the still picture); a part of another shape makes no request at all. The call is the login's own client: https, certificate checked, 3 seconds to connect and 6 in all, no redirect followed, 49,152 bytes read in all and 32,768 kept, no cookie or token sent. It is kept only when the status is 200, the type is exactly `image/png` and the file is a PNG whose every chunk is whole (lengths fit, CRCs match), whose header comes first and says 8 to 128 pixels and a depth the color allows, and that ends with IEND and nothing after it, and whose data is a whole zlib stream that inflates to exactly the rows that the header says (never inflated past that). The hub then writes its own copy: the header, PLTE, tRNS, the data and the end, nothing else (text, EXIF, color profiles and animation chunks are dropped); the pixels are not decoded. Any other outcome keeps the letter and leaves an older copy as it was, but a 404, which deletes it. No retry: the next login is the retry, and a new login always gets its fetch. An account has one fetch waiting or running at a time (logins that come meanwhile are one), two run at a time, 32 wait (the rest are dropped), a burst of 5 and then one a second for the whole hub; a dropped fetch is counted and told, at most every 10 seconds, as `picture kind=busy dropped=<count>`.

The copy is a row of the additive table `pictures` in `hub.db` (below), by the account's reference, with a random 128-bit name that is new at every login and made from nothing of the account, the code or the bytes. `GET /hub/pic/<name>.png` answers it: `image/png`, `nosniff`, `default-src 'none'; sandbox`, `Cross-Origin-Resource-Policy: same-origin`, `private, max-age=86400, immutable`, the same on every answer; a name that is not 32 lower-case hex digits, is not known, is not shown or is past its login's 30 days is a JSON 404 (`no-store`); 20 a second for an address (a burst of 240). Anyone who has the name may fetch it: it cannot be guessed. It is deleted with the last logout, a kick, Forget me, a switch to off or a block (a person's `off` is remembered 400 days after the last login; a block stays, like a ban), a ban, and by the hourly purge when the login ran out: the store's rule is no login, no picture, so whatever ends an account's last login (a logout, the callback that replaces a browser's login of another account, the purge, the cap of logins) takes the picture with it. A fetch that ends after any of these keeps nothing, and a picture's time is cut to the end of the account's last login. No picture is fetched for a switched off, blocked or banned account. At most 2,000 pictures and 8 MiB: a new one that does not fit takes the room of the ones fetched longest ago. Nothing derived from an id is in a name, a table, a log line or an error; the log says `picture kind=ok|none|down|type|big|shape` (`busy` with the count of dropped fetches, `bug` with the class of an error) and nothing else. nginx keeps the answer's file for as long as the address is asked for (it goes five minutes after the last request) though it is not served after its five minutes.

## Logs

One line for each event on standard output: `<time> <event> key=value ...`. A line never holds a secret, a cookie, a chat line, a name, an account id or a whole address: values are cut to plain characters and a number of 15 digits or more (an id) is replaced, and a connection is told apart by a tag, a keyed hash of its address that changes with every start. The start line lists the settings that are safe (the port, the origin, whether the roles are on (`roles_configured`), whether an owner account is set, the interval of the role checks, whether the login is on, the age limit), and a `note` line says that sockets are counted for each address that nginx names. `open` and `gone` say `sockets`, the number of open sockets (the `online` of the protocol counts people). An `error` with `where=command` is a bug in a moderator's command that waited for a lookup, by its kind only (at most one line in 10 seconds). An `error` with `where=roles` is a bug in the roles' own work, by its kind only (`worker_ended` when the task of the lookups ended and was started again), at most one line in 10 minutes, and one with `where=loop` is a task that failed and was never read, by its kind only (asyncio's own report, which holds the text of the error, is never printed). An `error` with `where=presence` is a bug in the list's own work or in the count of people that the clock hands the chat, by its kind only, and not one line for every tick however long it goes on: the clock goes on with the rest. The login writes `login`, `logout` and `forget` (a tag, never an account), `login_note` with `kind=display` and the class of an error if the cleaner of a display name ever failed (the login went on without a display name), and `roles_down` with a kind (`down` or `busy`: Discord did not answer, or asked for time; not more than one line in 10 minutes) and `roles_up`, a `warning` with `what=discord_roles_refused`, a kind (`token`, `access`, `guild`) and Discord's status when Discord refuses what the roles asked with, a `warning` when the roles' settings are given in part, and one for a leftover hand list of moderators, which is not read (nothing in them but the kind and the status: no token, server, role or account), `picture` with a kind (`ok`, `none`, `down`, `type`, `big`, `shape`, `busy` with the count of dropped fetches, `bug` with the class of the error) and nothing else, and `login_failed` with a kind (`rejected`, `config`, `busy`, `down`, `name`, `database`, `bug`) and Discord's status: nothing that Discord or the visitor sent is in a line, not the code, the state, the token, the cookie, the id or the name. nginx writes no access log for `/hub/ws` and the pages of the login, nor for its answers when the hub is not there (its default format would write the address, the referrer and the browser of every handshake, and the address of `/hub/callback` holds the code and the state; nginx logs a request with the settings of the place where it ends), and the error log of `/hub/login` and `/hub/callback` holds the serious errors only (nginx writes the whole request line, query and all, into the error of a request that a missing upstream fails). The container's log is rotated by docker (`json-file`, 3 files of 10 MB). A `crowded` line (sockets and groups, no address) is written every minute while one address group holds more than 6 sockets. `tests/scripts/test_hub_server.py` and `tests/scripts/test_hub_login.py` start the real process with canary values for every secret (and a fake Discord) and read its log.

## The stack and the site's nginx

`ants-hub` is the third service of `docker-compose.stack.yml` (own volume): built from `Dockerfile.hub` (slim Python, a non-root user, bytecode made at build time), `read_only`, `cap_drop: [ALL]`, `no-new-privileges`, `pids_limit: 32`, `mem_limit: 192m`, a tmpfs at `/tmp`, a health check (`python -m hub.health`), no published port. It has no `ANTS_BUILD_ID` argument: an image depends on `hub/` only, so a deploy that changes nothing there builds the same image and the chat is not restarted.

### The site's nginx

`docker/nginx.conf` has the chat's door, `location = /hub/ws`, and five pages of the login (below): the door is a GET without a query, the name `ants-hub:4040` resolved per request through Docker's resolver (so the site starts, and works, without the hub), 5 new sockets a second for each address (a burst of 10; 503 beyond) and 16 open at a time (429 beyond), 120 seconds of read timeout (the hub pings every 25), no buffering, no access log (one exception, below). The hub gets only the headers of the upgrade, `Origin`, the login's cookie (picked out of the whole `Cookie` header by its name and shape, so that no other cookie of the visitor, the admin page's among them, reaches the hub), `Sec-Fetch-Site` and the one `X-Client-Address` that nginx sets from the connection; nothing else of the visitor's request, and no header of that name from a visitor. A hub that is not there is a JSON 503 `{"error":"hub_off"}`, never a page of the site. nginx counts an IPv6 client by its whole address and the hub by its /64, so for a visitor who has a /64 the hub's 8 are the limit that matters.

A seventh door, `/hub/pic/<name>.png`, is the one regular expression (`^/hub/pic/[0-9a-f]{32}\.png\z`, before the locations of the static images): a GET without a query, a request of another site (`Sec-Fetch-Site` `cross-site` or `same-site`) is 403, no cookie and no header of the visitor's reaches the hub, no access log, 20 a second for an address (a burst of 240; 429), and the answer is kept 5 minutes for everybody (`proxy_cache`, a 404 is not kept), so the hub is asked once for a picture in five minutes whatever the number of viewers; the hub's headers pass and its `nosniff` is hidden so that each is there once; a picture that was deleted can still be answered from the cache for up to 5 minutes. The page policy is unchanged (`img-src 'self'`).

The pages of [the login](#login) are exact locations of the same kind (the name resolved per request, only the one method, the checks before anything is passed on, no body, `proxy_redirect off`, no access log): `/hub/login` (a GET; gets `Sec-Fetch-Site` and the address), `/hub/callback` (a GET; gets the cookie of the state and the address; 15 seconds of read timeout, for the 10 that the hub gives Discord), `/hub/me`, `/hub/logout` and `/hub/forget` (the login's cookie, `Origin`, `Sec-Fetch-Site: same-origin` required here as well, no query). The first two have 10 a minute for each address (a burst of 5 more; the hub has the same), the others 20; over the limit is 429, and for the two that the browser navigates to a small page with a link back, as is a hub that is not there (503, "Login unavailable, try again later"); the other three answer with the JSON of the chat's door. The login's cookie is for the path `/`, so a browser sends it to every request of the site, and nginx makes sure that it goes to the hub's pages and nowhere else: no door passes the visitor's headers on whole (the game server's `/ws` is given the headers of its handshake and nothing else, `/busy` the `Host`, every other door only the few that its block names), and the admin page's API gets its own cookie (`ants_admin`) and no other. `tests/scripts/test_nginx_hub_login.py` checks every proxy block of the file for it, and runs the real blocks. **The one exception to "no access log":** a request that nginx itself refuses before it has chosen a place (a `Cookie` header over 8 KB is 400, an address over 8 KB is 414) is written by the site's stock access log with its whole request line, query included. For `/hub/callback` that line can hold a `code` and a `state`. Neither is of any use to a reader of the log: the hub refuses a callback without the visitor's own `HttpOnly` state cookie, the state is good for one use and ten minutes, and a code is good once and only with the application's client secret. It is still worth knowing for anybody who keeps the site's access logs for long. It is not closed in `docker/nginx.conf`: that would mean a conditional `access_log` for the whole server, which changes what the site logs for every other page.

### Behind a reverse proxy

The hub counts sockets for each address that nginx puts in `X-Client-Address`, and nginx takes that address from the connection it sees. Behind a reverse proxy, name the proxy in `docker/trusted-proxies.conf` ([SERVER.md](SERVER.md#behind-a-reverse-proxy): the image's list names a proxy at a private address, and says what that assumes and how to add a proxy at a public address) so that the limits per address count each visitor's own address. The hub says it at every start (a `note` line) and writes a `crowded` line when one address group holds more than 6 sockets.

An address group is a /64 for IPv6. The hub keeps at most 500 sockets in all and drops a socket after 60 seconds of silence, and nginx lets 5 new sockets a second in for each address; limits beyond those belong at the proxy in front, which is outside this service.

### Deploys

The host's own update rebuilds the stack from the clone of `main` ([`WORKFLOW.md`](WORKFLOW.md), "Deploy"), and every image of the page and of the game server carries the build id of the commit (`docker/resolve_build_id.sh`: the commit named by the clone's `.git`), so **a hub-only change also rebuilds and recreates the page and the game server** (the game server brings its matches back from the restart records; the page is away for a moment). The hub has no build id: its container is recreated only when `hub/` or `Dockerfile.hub` changed, so an update for something else does not restart the chat. There is no way to update one service of the stack alone; a change that must not touch the game server waits for an update that would happen anyway.

CI builds the image in the Web job, starts it with the stack's flags, waits for `healthy`, runs the command line against its volume and checks that a socket from another site gets 403.
