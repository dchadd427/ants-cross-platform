# The chat hub

`ants-hub` is the site's global chat: a small service of its own, next to the game server and never in its thread. Python 3.12 or newer, standard library only (the image is 3.12; `python -m hub` refuses to start on an older one, with a message: on 3.11 a logout or a forget raced a handshake that was in progress, and a socket of the ended login stayed open), about four thousand lines (`hub/`). It speaks JSON over one WebSocket, `wss://<site>/hub/ws`, keeps the last 50 lines in memory and, in SQLite for moderation, the newest 200 lines and none older than seven days, and enforces every limit below itself. Reading is open to everybody. Writing needs a login with Discord ([Login](HUB_LOGIN.md#login): the one scope `identify`; the id, the username and the display name are all that is kept); a hub that is not given the settings of a Discord application tells every client `login:false` and is read-only for all.

The pages never need the hub: the site, the rooms and the games list work whether or not it runs, and the chat shows "offline" and retries.

The hub also holds the keys that let a person's own AI work in the person's open Map Maker tab, and the relay to that tab: [`MAP_AI.md`](MAP_AI.md).

## The protocol

Text frames, each a JSON object with a `t`. Version 1 (`v` in the welcome).

| Direction | Message | Meaning |
|---|---|---|
| up | `{"t":"say","text":"..."}` | a line of chat (needs a login) |
| up | `{"t":"ping"}` | keep-alive; the answer is `online` |
| up | `{"t":"who"}` | watch the list of the front page's players ([Presence](#presence)); the answer is the whole list at once |
| up | `{"t":"here","at":"look"\|"wait"\|"play", ...}` | what this visitor is doing (a login is needed), for the list |
| up | `{"t":"dm"\|"dmopen"\|"dmread"\|"dmdel"\|"dmreport",...}` | private messages ([HUB_MESSAGES.md](HUB_MESSAGES.md#the-frames); a login is needed) |
| up | `{"t":"seen","upto":n}`, `{"t":"clearalerts"}`, `{"t":"note","k":"join",...}` | the account's list of alerts ([HUB_PEOPLE.md](HUB_PEOPLE.md#alerts-the-accounts-list); a login is needed): read up to a number, emptied, or a person who joined the account's room (told by the account's own page) |
| up | `{"t":"say","text":"/..."}` | a command, in the same frame as a line: a single `/` makes it one and `//` says a line that starts with a slash ([HUB_COMMANDS.md](HUB_COMMANDS.md#the-commands): `/help`, `/invite`, `/msg`, `/follow`, `/unfollow`, `/ignore`, `/unignore`, `/bots`). The moderators' ([Moderation](HUB_COMMANDS.md#moderation)): `/mute username minutes`, `/unmute username`, `/del id`, `/kick username`, `/ban username`, `/unban username`, `/bans`, `/mutes`, `/nopic username`, `/pic username`; a person may be named by `#line` or `row:n` instead of a username, and `/ban username purge` also takes their lines of the last hour off every screen |
| up | `{"t":"pick","pick":"display"\|"username"}` | which of its two names the account is shown by ([Names](#names); a login and a display name are needed): the hub stores it and closes every socket of the account, and the page connects again and reads the new name in the welcome |
| up | `{"t":"pics","on":true\|false}` | the switch of the account's Discord picture ([Pictures](HUB_PICTURES.md); a login is needed, and a hub without the Discord login does not know the frame): off deletes the copy at once, on asks for the picture again (at once where the roles' check does not carry it, else at its next check, a few minutes: [Pictures](HUB_PICTURES.md#refreshing-while-logged-in)) and shows nothing until it arrives or the next login, or the end of a fetch that is still on its way; a change is answered by the whole `you` to every socket of the account, a request for the state that it is in by the whole `you` to the asking socket |
| down | `{"t":"welcome","v":1,"you":{"name","mod","role","k"[,"pick","other"[,"next"]]}\|null,"login":bool,"presence":true,"me":n,"online":n,"history":[line,...]}` | first message: who you are (`null` for a reader): `name` is the name that is shown, `role` is `none`, `mod` or `admin` (from Discord, never from a page: [Roles](HUB_ROLES.md#roles)) and `mod` is true for both roles (a page that reads only `mod` keeps working), `k` the key of the account for this run of the hub, and, only where the account has a display name as well, `pick` (the name that is shown: `display` or `username`) and `other` (the name that is not); whether this hub has a login at all, whether it has the list of players, for a login `me`, the number of the account's own row in that list (a reader has none), how many people are here, the last 50 lines oldest first |
| down | `{"t":"you","you":{...}}` | the whole `you` again, to every socket of an account whose role changed (a promotion, a removal, a role that ran out: [Roles](HUB_ROLES.md#roles)) or whose picture arrived, went or was switched ([Pictures](HUB_PICTURES.md)) |
| down | `{"t":"line","id","at","who","text","mod"[,"role"],"k"[,"u"][,"sys"][,"m"]}` | a new line (`at` is seconds since 1970, `who` the name that the account was shown by when it wrote the line, `mod` true for a moderator or an administrator, `role` (`mod` or `admin`, absent for a person with no role) the role that the author had when it wrote the line, in the history too: a mark for the pages, never a reason to allow anything, `k` the key of its author; `u`, the author's username, only in the copy that goes to a moderator and only where it is not `who`; `sys` is `true` only for a line of the hub's own, `who` is then `system` and `k` is empty: [the named line](HUB_COMMANDS.md#moderation)); `m` (marks, [HUB_PEOPLE.md](HUB_PEOPLE.md#mentions)) lists the names that the hub found after an `@` in the text, `[start, length, key]` in UTF-16 units |
| down | `{"t":"del","id":n}` | take line `n` off the screen |
| down | `{"t":"ok","c":c}` | the private answer to a moderator's command that was done: `c` is `mute`, `unmute`, `del`, `kick`, `ban`, `unban`, `nopic` or `pic` (`/bans` is answered by `bans`, `/mutes` by `mutes`); nobody else is told anything |
| down | `{"t":"bans","rows":[{"u","at"},...]}` | the private answer to `/bans`: the newest 50 bans, each by the username that the ban was made with and the time (seconds since 1970); never an account id |
| down | `{"t":"mutes","rows":[{"u","until","i"?},...]}` | the private answer to `/mutes` (moderators and administrators): up to 50 mutes that are on, the one that ends first at the top; `u` is the username that the mute was made with, `until` the end (seconds since 1970), `i` the person's row number in the Players list, only when the person is here now; never an account id or a reference |
| down | `{"t":"cmds","rows":[{"w","a","d","g"},...]}` | the commands that this account has ([HUB_COMMANDS.md](HUB_COMMANDS.md#the-cmds-frame)): after the welcome of a login, and again after the `you` that a change of role makes, to every socket of the account; never to a reader, never a row above the account's role |
| down | `{"t":"follows","rows":[...]}` | the people that the account follows, to its own sockets only ([HUB_PEOPLE.md](HUB_PEOPLE.md#follows)); `{"t":"msgs"\|"msg"\|"thread"\|"dmx"\|"dmreported",...}`: private messages ([HUB_MESSAGES.md](HUB_MESSAGES.md#the-frames)) |
| down | `{"t":"alerts","rows":[...]}`, `{"t":"alert","row":{...}}` | the account's list of alerts, whole (after the welcome of a login, and again when it changed) and one new alert at once, to every socket of the account ([HUB_PEOPLE.md](HUB_PEOPLE.md#alerts-the-accounts-list)); never to a reader |
| down | `{"t":"reply","c":word,"r":code,...}` | the private answer to a command of [HUB_COMMANDS.md](HUB_COMMANDS.md#the-answers) (`unknown` for a word that is not the account's own, `rate`, `help`, `invite`, `msg`, `follow`, `unfollow`, `ignore`, `unignore`, `bots`), to the asking socket only |
| down | `{"t":"bye","why":"kicked"\|"banned"}` | to every socket of a person who was kicked or banned, just before the hub closes it (close code 1000, the same word as its reason): the page knows that it was not a failure of the network |
| down | `{"t":"online","n":n}` | the number of people here (an account once, however many tabs; a socket without a login is one guest), sent when it changes (at most every 5 seconds) and as the answer to `ping` |
| down | `{"t":"who","full":bool,"n","g","more","rows":[row,...],"gone":[id,...]}` | the list of players: the whole list (`full`) or what changed ([Presence](#presence)); only to a socket that asked. A row's `at` is `look`, `wait`, `play`, or `away` (a person whose last socket closed a short while ago) |
| down | `{"t":"err","code":c}` | the last message was refused; the page owns the words |

Error codes: `login` (a reader tried to write, or to say where it is), `rate`, `quota` (the account has said the lines of its hour or of its day), `muted`, `banned`, `long`, `empty`, `young` (a Discord account younger than 7 days, from its id), `bad` (the message cannot be read, the line holds `<` or `>`, or a moderator's command is wrong or there is nothing to do: a person who is not muted or not banned, one who is banned already, a line that is gone), `power` (a command that the role has, aimed at a person that it may not act on: [Moderation](HUB_COMMANDS.md#moderation); a command that the role does not have is no `err`: it is `reply unknown`), `role` (the role of the one who acts or of the one acted on could not be confirmed with Discord just now, or the one who acts no longer holds it), `who` (no one here has that username, or two do, or a `/kick` of a person who is not in the chat), `here` (a `here` is not what a page says: the chat's codes are for its lines, and a page that reads this one for a line of its own would be wrong), `pics` (a `pics` that is not done: not a true or a false, past the limit, or the operator blocked the picture), `pick` (a `pick` that is not done: not one of the two words, past the limit, or an account with no display name to choose; the same rule as for `here`: no line's code). `img` and `imgid` ([HUB_IMAGES.md](HUB_IMAGES.md#what-goes-over-the-wire)). A reader or a member gets no other reply to a good `say` than the `line` that everybody gets, and none to a good `here`, whoever sent it.

The protocol stays at version 1 (the new frames and codes are additive: a page ignores a frame and a code that it does not know, an older page reads `mod`, which is true for both roles, and a refused command is one more `err` that it does not show): a page that does not know `who` ignores it, and a hub that has no list does not say `presence`, so a page that has the list sends nothing to it.

## Limits

All in `hub/limits.py` (`Limits`), all enforced by the hub.

| What | Limit |
|---|---|
| frame from a client | 16 KB of payload (the longest line takes about 4 KB in a page's frame, 12 KB where a client writes every character as a `\u` escape); text only, in one piece (a fragment, a binary frame, a frame over 16 KB closes the socket: 1003, 1003, 1009) |
| a chat line | 1,000 code points after the text rules (NFC) and 4,000 bytes |
| writing | a burst of 10, then one line every half second (two a second), for an account across all its tabs; and 10 lines a second (a burst of 100) for all accounts together. An account also has a budget of 600 lines for the hour and 3,000 for the day, each filling up again steadily (one line every 6 seconds, one every 28.8); what is over is answered `quota`, and a moderator's command is never held back by it. The budgets are kept in memory: a restart of the hub gives every account its budget again |
| the same text twice | within 30 seconds the second is dropped (`rate`); a dropped line costs no token |
| mistakes | an `err` or an unreadable message is a mistake; 20 within a minute close the socket with 1008. A `rate` that comes from the limit of all accounts together or from a full database, and a `quota`, are not the client's doing and are not counted |
| frames of any kind | a burst of 10, then 5 a second for a socket; the rest are mistakes (lines at the pace that an account may keep, 10 at once and then two a second, do not use it up). A refusal that is not counted as a mistake (`rate` from the limit of all accounts together, from a full or a locked database, and `quota`) is not free: it costs the socket one frame of this budget more, so a client that keeps asking runs out of it twice as fast, and then it is a mistake per frame |
| sockets | 8 for each client address (an IPv6 address counts as its /64), 300 in all; the ninth gets 429, the 301st 503, before the upgrade |
| the list of players | 200 named people in the list (moderators first, then those who wait, play, look) and a count of the rest; the changes go to every socket that asked in one frame, never sooner than 2 seconds after the last send, whatever happens (the clock looks once a second, so a send comes 2 or 3 seconds after the last; a person who flaps and a crowd that comes and asks are one change); a change of more than 50 rows is sent as the whole list; a socket gets the whole list again only after 10 seconds (a second ask too soon costs it a frame more, like any refusal that is not a mistake); a `here` that is wrong is a mistake |
| the roles' lookups | one at a time, two a second (a burst of 5), and by Discord's rate-limit headers (an empty bucket waits for its reset, a 429 for its `retry_after`, at most a minute, for every lookup); 3 seconds to connect and 6 for a call, 32 KB of answer; each person who is here every 180 seconds (plus or minus a tenth), a role believed for that, a tenth more and 60 seconds more; a token, a server or an access that Discord refuses: no call for 10 minutes; at most 2,000 people in memory ([Roles](HUB_ROLES.md#roles)) |
| a moderator's action | the roles of the one who acts and of the one acted on are answered by Discord no more than 60 seconds ago, or both are asked again and the action waits for them, 3 seconds at the most, before anything else in the queue of the lookups (the same two a second, the same holds, the same pause, and from a share of their own, a burst of 10 and one more a second for the whole hub, so that a moderator who asks for many cannot use up the lookups that everybody's role holds on to; and a share for each moderator, across all its sockets, a burst of 3 commands that wait and one more every 5 seconds, so that one moderator cannot spend the share of the others: a command over it is refused `rate` and counts as a mistake of the socket; this share and the budget of kicks and bans (below) are each kept by the run's key of the account, which is made new at every start, and never by its id); one that cannot be had, or whose share is spent, refuses the action (`role`); a socket has one command waiting at a time (a second is `rate`, not counted as a mistake) |
| kicks and bans | a moderator has a burst of 5 and one more every 10 seconds, across all its sockets, because each is a line for everybody; the kick or the ban over it is done all the same (its `ok` and its row of the log are there) and only its line for everybody is not made, so that the history is not pushed out |
| the commands | for an account across its tabs: `/bots` starts a burst of 3, then one every 10 seconds; `/bots status` and `stop` a burst of 5, then one every 2 seconds; the other commands and every word that is no command of its own a burst of 10, then one every 2 seconds; 50 people ignored; the call to the game server 3 seconds to connect, 10 in all, 128 KiB of answer, one at a time for an account and two for the hub ([HUB_COMMANDS.md](HUB_COMMANDS.md#limits-of-the-commands)) |
| alerts, invitations and mentions | [HUB_PEOPLE.md](HUB_PEOPLE.md#limits) |
| follows and room alerts | [HUB_PEOPLE.md](HUB_PEOPLE.md#limits) |
| private messages and reports | [HUB_MESSAGES.md](HUB_MESSAGES.md#limits) |
| the moderators' log | 30 days and 10,000 rows, the newest ([The moderators' log](HUB_ROLES.md#the-moderators-log)) |
| the switch of the name | `pick`: a burst of 3, then one every half minute, for an account across all its tabs (each one makes every socket of the account connect again); a `pick` that is refused is a mistake of the socket |
| keep-alive | the hub pings every 25 seconds; a socket that sends nothing for 60 seconds is closed (1001) |
| handshake | 10 seconds to send the request head, 8 KB at most, 64 connections that have not finished it (the login layer has 5 seconds to answer, and a handshake that waits for it keeps its place among the 64 meanwhile; a late or failing login is a reader) |
| a slow reader | a socket with 256 KB unsent is dropped (more than the largest welcome, about 212,000 bytes: 50 lines of 4,000 bytes and the longest names, and 8 more lines; the welcome and the longest list of players together, about 280,000 bytes, are more, so a reader whose connection took none of them is dropped and connects again). With every socket stalled at that limit, 300 sockets took 135 MB of the container's 192 MB and 500 took 175 to 200 MB, which is why there are 300; a socket that was closed with output still unsent is cut after 5 seconds |
| history | the last 50 lines, sent on connect; the database keeps the newest 200 lines and none older than 7 days (whichever limit is smaller deletes first; a newcomer is never shown a line past them). From 90% of 64 MB (the pages of `hub.db` that hold something, plus its log file) the hub deletes the oldest lines, 2,000 lines a second, down to 80% ([Data](HUB_LOGIN.md#data)), so that the size guard stays a last resort: no new line is kept at 64 MB itself (`rate`; the pages that deleted lines free count as room again, though the file does not shrink; a mute, a ban and a deletion are never refused for it) |
| new sockets | nginx lets 5 a second through for each client address (a burst of 10) and 16 open at a time; beyond that is 503 and 429 before the hub is asked |
| the pictures and their switch | a fetch, a store, a door and a switch of their own: every number is in [HUB_PICTURES.md](HUB_PICTURES.md#limits) |
| the login's pages | `/hub/login` and `/hub/callback`: 10 a minute for each client address (a burst of 10 in the hub, of 6 in nginx), 6 logins that wait for Discord at one time (the 7th is answered at once), 10 seconds for Discord's two calls in all, 10,000 logins started and not finished, 10 logins kept for an account and 100,000 in all (the oldest go); `/hub/me`, `/hub/logout`, `/hub/forget`: a burst of 20, then one every 3 seconds |

## The handshake

nginx (see [the site's nginx](#the-sites-nginx)) passes `GET /hub/ws` for a socket, and the five pages of [the login](HUB_LOGIN.md#login). The hub checks, in this order, and answers with JSON and a closed connection (`{"error":"..."}`): the method (405), the **Origin**, which must be exactly the site's (`ANTS_HUB_PUBLIC_URL`; 403 for anything else and for none, and a hub that was not told its site lets nobody in), **Sec-Fetch-Site**, which a browser sets and which must be `same-origin` where it is there at all (403 `fetch_site`), no body (400), `Upgrade: websocket` with `Connection: Upgrade` (426), version 13 (426), a valid key (400), the 500 socket total (503) and the 8 sockets of the address (429). The request head is read strictly: CRLF only, no folded lines, no control characters, at most 60 headers, and the headers the hub believes at most once. Extensions and subprotocols are never negotiated. Who the socket is comes last, from the login's cookie of the handshake ([Login](HUB_LOGIN.md#login)), and holds for the life of the socket.

The client address is the `X-Client-Address` that nginx sets (an IP address; anything else falls back to the connection's own). `GET /hub/healthz` answers `{"ok":true}` for the image's health check; nginx does not route it. The 64 connections that have not finished their handshake are a shared pool: through nginx a connection reaches the hub only with a complete head. The services on the stack's network trust each other, so put only containers you trust on it (the stack's services and the proxy).

## Frames

`hub/ws.py` is the whole WebSocket (RFC 6455, the server side of text frames, about 150 lines). A client frame must be masked, have no reserved bit, use a known opcode and the shortest length form; control frames are at most 125 bytes and whole; text must be UTF-8. A broken stream gets a close frame with the RFC's code (1002 broken, 1003 not taken, 1007 not UTF-8, 1009 too big), and the frames that came whole before the break are still handled. A frame over the cap is refused from its header, before its payload is read. The parser never raises (`Parser.feed` returns frames and sets `error`) and keeps at most one header and one frame.

## Text rules

What a visitor types is data (`hub/text.py`). In order: NFC; every blank (space, tab, line end, other space characters, line and paragraph separators) becomes one plain space and runs collapse; control characters, format characters (the bidirectional controls, zero-width characters, joiners, the byte order mark, tag characters), surrogates, private use and unassigned code points are removed, and so are the letters that draw as blanks (the Hangul fillers, the braille blank, the combining grapheme joiner, the Khmer inherent vowels, the musical null notehead); more than 4 combining marks in a row are cut; NFC again. Then: nothing left, or nothing but combining marks (a variation selector or the Khitan filler shows nothing by itself), is `empty`; over the limits is `long`; a `<` or `>` is `bad` (checked on the result, so nothing can hide one). There is no markup, no link detection and no mention: the page shows the text with `textContent` only and puts a `bdi` or an isolating `dir` around names and lines, because right-to-left letters still reorder what is next to them.

## Names

A person has a **username**, the one name that Discord keeps unique (lower-case letters, digits, `_` and `.`, 2 to 32 characters: the hub refuses a login and an identity with any other), and may have a **display name**, which the person chooses freely at Discord (`global_name`: any text of up to 32 characters, null when none was set, not unique, and changed by the person at any time: the hub sees a change at the next login). The chat shows one of the two, as the person picks: the display name by default where there is one that may be shown, else the username. Where the person is a member of the Discord server that the roles' check asks about, the **server nickname** (`nick` of the member answer, text or null) comes first: the name that is shown is the nickname, else the display name, else the username (a person who picked the username keeps it, and the nickname is then the other name). The nickname is read from the member answer that the roles' check already makes (`hub/roles.py` `tell_names`, which also reads `user.global_name` there): no call of its own, none for a person who is not a member or on a hub whose roles are off, and it goes through `clean_shown` like any display name (one that is not usable, or is the username itself, is none). It is kept in memory on the account's roles entry and as the profile's display name (the existing column: no schema change); a login writes the display name again, and the next check of the roles puts the nickname back. At a check that finds a changed name, `hub/chat.py` `names_changed` updates the profile and every open socket of the account gets the new name and a whole `you` frame (the identity of the socket is replaced; no reconnect); lines that were written keep their name. Where a shown nickname follows a display name, `you.next` is that display name, which a page whose game cannot take the nickname tries before the username (`web/front/player_name.js`). Nothing of this is logged. A name that is shown is **never a key**: two accounts can show one name, so a line is its author's by `k` (a keyed hash of the account that is made new at every start of the hub), a row of the list is told by its number, and a moderator addresses an account by its username.

A display name goes through one rule, `clean_shown` in `hub/text.py`, which takes text of any kind and size (more than 128 code points, or anything that is not text, is not read at all): NFKC (so that the letter forms of fancy fonts and full-width letters are the plain letters); every blank is one space; control, format, private use, unassigned and surrogate code points and the letters that draw as blanks are removed; letters and decimal digits stay, so do `.`, `_`, `-` and `'` (the curly apostrophes and the dashes of a phone's keyboard become the plain ones); a combining mark stays only after a letter or a digit, two in a row at most, and never a variation selector or a mark that encloses; everything else goes (emoji and symbols, the rest of the punctuation, the other numbers). Then NFC, the ends trimmed, the name cut at 32 code points. What is left is no display name when it has fewer than 2 code points, no letter and no digit, or reads as a reserved name. **A display name that does not pass is never a reason to refuse or fail a login**: the account is shown by its username, and nothing else happens.

A name that could pass for the hub's own voice (`RESERVED` in `hub/text.py`: `mod`, `admin`, `system` and a few more) is refused as a username (a page of its own says why) and is no display name. So are its lookalikes, which are read as `squash()` reads them: dots, underscores, hyphens, apostrophes and spaces are ignored, accents are taken off, a digit is read as the letter that it looks like (`admin.`, `adm1n`, `system_`, `a.d.m.i.n`, `Ad-min`), and so is each of the Cyrillic and Greek letters and the dotless i that are drawn like a Latin letter (`LOOKALIKE_LETTERS`, in both cases). Digits at the end are not read as anything (`system32`, `hub99` and `ants1998` are fine: a lookalike gains nothing, because a moderator is marked by the hub's `mod` flag, by Discord id, never by a name, and real people have such names), and only the whole name is read (`Admin Dave` is a name).

A person may also choose a **nickname** (3 to 16 characters, unique, one alphabet) and a **tag** (2 to 5 letters and digits), and a guest may type a name for the games: the rules, the limits, what the hub keeps (`nicknames`, `nick_hold`, `login_claim`, `lines.tag`), the `name` frame and the pass for the game server are in [`HUB_NICKNAMES.md`](HUB_NICKNAMES.md). The nickname is the name that is shown (the switch between the display name and the username is not offered to an account that has one); an account that has chosen none, whose shown login name (the display name, or the username when that is what it shows) is a lookalike of somebody's nickname, is shown by its username, and by "username (Discord)" when that is one too.

## Presence

The list of the front page's players ([HOME_SCREEN.md](HOME_SCREEN.md#the-players-list)): who has the front page open right now (`hub/presence.py`). The pages never need it: a hub without it, or none, leaves the page's list off and everything else as it is.

**What it holds.** For each person: the name that the chat shows (from the login, not from the page: the display name or the username, as the account picked; never the username of an account that chose not to show it, because the list is one frame for every page), `mod` if the account moderates and `role` (`mod` or `admin`) beside it, where the person is (looking, waiting, playing) and, for an account that may chat, the room's map file name, seats and code. The name, `mod` and `role` are the hub's own; where the person is, and the room's details, are what the person's page said, checked for their shape and nothing more: text from a stranger. Nothing that a person typed into the chat is in it, and nothing else about a person.

**Who is in it.** A socket that was let in with a login is a named person: the name that the chat shows (a username, `[a-z0-9_.]{2,32}`, or a display name that the rule of [Names](#names) left as it is, which no bidirectional or zero-width character can be part of), once for an account however many tabs it has, marked `mod` for a moderator of the chat. A socket without a login is a guest: counted, never named; so is an account that is **banned** from the chat (counted once, listed as a guest). A muted account, or one that is too new to chat (`young`), is named like any other and keeps none of the room's details (below). A socket that never said what it does is looking. Of the sockets of one account the one that does the most is the account's row (a match, then a room, then looking; the newer word between two that do the same). "Playing" is a page that said so while its socket is open: the game page holds no socket to the hub, so a person whose tab went to the game is out of the list until they are back on the front page.

**What a page says.** `{"t":"here","at":"look"|"wait"|"play"}`: not in a room, in a room that has not started, in a match. A page that calls its room public may add `"pub":true` and then the room's `map` (a file name exactly as the game takes it, `net::valid_map_name`: printable ASCII, 5 to 64 characters, none of `/ \ : * ? " < >` or `|`, no leading dot, ending in `.lvl` or `.LVL`; spaces and dots inside are fine, and five maps of the community have two spaces in their names), `n` (colors that play, 0 to 4), `of` (colors in the match, 1 to 4, not less than `n`) and, for a room that waits, its `code` (lower case letters, digits, `-` and `_`, 1 to 32: the code that the game server lists for a public room; the page says it only for the host of the room, so that the Join is on the host's row). A room that is not public, and a visitor who is looking, keep no details; a page that says `"pub":false` (a private room or match) adds the mark `priv` to its row (a fact: never a map, seats or code; kept for an account that may not chat too), and a page that says `"solo":true` with `"at":"play"` (a game against the computer) has `solo` and its `map` in its row; a match keeps `map` and `n`; **a code is never kept for a match or for a room that was not said to be public**, so a private room's code is never in the list. A field of the wrong kind or size is refused with `err` `here` (a mistake of the socket, nothing changes); a guest that says it gets `login`. What a page says is text from a stranger and is not checked against the game server: a page that lies is a page that lies. The page that says it is the front page or, in a match, the game page (a second socket of the same account: the one that does the most is the account's row, so Playing wins over Looking, and a closed front-page socket leaves the game page's word standing). So the hub keeps the room's details only for an account that may chat (a banned, a muted or a too new account has `at` and the private mark and nothing else: what it says is taken and not shown), and the receiving page draws a map's name only for an original map or for a room that the game server's own list (the Games list) shows under the same name, and offers a Join only where that list has the room's code: never the hub's words.

**The room, for invitations.** A page that waits in a room may add `inv` to its `here`: what it holds and what it is for are in [HUB_PEOPLE.md](HUB_PEOPLE.md#invitations).

**What the hub sends.** To a socket that sent `{"t":"who"}`: the list as it was last sent (`"full":true`), then what changed, as one frame that every socket that asked gets at the same moment and never sooner than 2 seconds after the last send, whatever happens: the hub's clock looks once a second, so a send comes 2 or 3 seconds after the last; changes that come in between are one frame, and a person who flaps, a crowd that comes and a page that asks bring nothing forward. The first page to ask when nobody is watching (the list has not been looked at since the last watcher went) gets the list as it is now. A change of more than 50 rows is the whole list again. `rows` holds `{"i","name","at"}` and, where they apply, `"mod":true`, `"pub":true`, `"map"`, `"n"`, `"of"` and `"code"`; `i` is a number that names the row while the person is here (never the account's id: a name is not unique, so the number and not the name tells one row from another), and the welcome of a login says which one is its own (`me`), so that a page leaves that row out of its groups; `n` is the number of people (everybody named and every guest, the asker among them: the same number as `online`), `g` the guests and `more` the named people that are not in `rows`. In a change `rows` are the rows to set and `gone` the numbers to drop. Order: moderators, then those who wait, those who play, those who look, each by name; past 200 named people the rest are only counted. The number of people is counted again only when a socket opens or closes (and at least once a second), so that a ping is answered from the last count.

**Away.** When the last socket of an account closes, its row stays for `away_seconds` (600, ten minutes) as `{"i","name","at":"away"}` with `mod`, `role` and `pic` as before and nothing of a room (no `pub`, `map`, `n`, `of`, `code`, `priv` or `solo`), so that a person who minimizes the browser, or whose phone puts the page to sleep, is still in the list. A socket of the account that opens within that time takes the row back with the same number `i` (the welcome says it in `me`) and the row says what the page says. After the time the row goes as it always did (a `gone`). Away rows come last in their group order (a moderator's stays with the moderators), count in `more` but not in `n` (the number of people who are here now, the same as `online`), and are kept in memory only, at most `away_max` (500: the oldest go first). A guest is never kept. A kick, a ban (also one made while the person is away), a logout, a forget-me and a login that ran out take the row at once. A page that does not know the word `away` leaves the row out (the web page of this repository before this change drew no row for a value it did not know, and kept the row's last look until the next `gone`).

**What is kept.** Nothing, and for no longer than a socket is open (an Away row, for `away_seconds` after it closes): the list is the hub's memory of its open sockets, a person is out of it one send after their socket closes (or after the Away time), nothing is written to the database or to the log (the log has the counts of sockets and never a name, a map or a code), and a restart starts with an empty list that fills as the pages say where they are. Who is banned or muted is read from the database when a ban or a mute changes (its own counter of them says so at every look) or when the soonest mute runs out, and a database that does not answer leaves what it said last.

**Abuse.** A `here` is one frame of the socket's budget (a burst of 10, then 5 a second, the rest are mistakes, 20 of them close the socket) and costs the hub a dictionary entry; a flood of them changes the list at most once for the next send, and a flood of `who` gets the whole list once every 10 seconds. The sends are as many as the sockets that asked, one every 2 or 3 seconds at the most, so the most that a crowd can make the hub write is the list (200 rows: 60 KB at the very most, with the longest shown name (32 code points of four bytes each), map and code that a row can have, and about 23 KB for rooms as they are) to each of the 500 sockets every 2 to 3 seconds (15 MB a second at the very most), and a socket that cannot read it is dropped by the 128 KB rule.

## Logs

One line for each event on standard output: `<time> <event> key=value ...`. A line never holds a secret, a cookie, a chat line, a name, an account id or a whole address: values are cut to plain characters and a number of 15 digits or more (an id) is replaced, and a connection is told apart by a tag, a keyed hash of its address that changes with every start. The start line lists the settings that are safe (the port, the origin, whether the roles are on (`roles_configured`), whether an owner account is set, the interval of the role checks, whether the login is on, the age limit), and a `note` line says that sockets are counted for each address that nginx names. `open` and `gone` say `sockets`, the number of open sockets (the `online` of the protocol counts people). An `error` with `where=command` is a bug in a moderator's command that waited for a lookup, by its kind only (at most one line in 10 seconds). An `error` with `where=roles` is a bug in the roles' own work, by its kind only (`worker_ended` when the task of the lookups ended and was started again), at most one line in 10 minutes, and one with `where=loop` is a task that failed and was never read, by its kind only (asyncio's own report, which holds the text of the error, is never printed). An `error` with `where=presence` is a bug in the list's own work or in the count of people that the clock hands the chat, by its kind only, and not one line for every tick however long it goes on: the clock goes on with the rest. The login writes `login`, `logout` and `forget` (a tag, never an account), `login_note` with `kind=display` and the class of an error if the cleaner of a display name ever failed (the login went on without a display name), and `roles_down` with a kind (`down` or `busy`: Discord did not answer, or asked for time; not more than one line in 10 minutes) and `roles_up`, a `warning` with `what=discord_roles_refused`, a kind (`token`, `access`, `guild`) and Discord's status when Discord refuses what the roles asked with, a `warning` when the roles' settings are given in part, and one for a leftover hand list of moderators, which is not read (nothing in them but the kind and the status: no token, server, role or account), `picture` lines ([HUB_PICTURES.md](HUB_PICTURES.md)), and `login_failed` with a kind (`rejected`, `config`, `busy`, `down`, `name`, `database`, `bug`) and Discord's status: nothing that Discord or the visitor sent is in a line, not the code, the state, the token, the cookie, the id or the name. nginx writes no access log for `/hub/ws` and the pages of the login, nor for its answers when the hub is not there (its default format would write the address, the referrer and the browser of every handshake, and the address of `/hub/callback` holds the code and the state; nginx logs a request with the settings of the place where it ends), and the error log of `/hub/login` and `/hub/callback` holds the serious errors only (nginx writes the whole request line, query and all, into the error of a request that a missing upstream fails). The container's log is rotated by docker (`json-file`, 3 files of 10 MB). A `crowded` line (sockets and groups, no address) is written every minute while one address group holds more than 6 sockets. `tests/scripts/test_hub_server.py` and `tests/scripts/test_hub_login.py` start the real process with canary values for every secret (and a fake Discord) and read its log.

## The stack and the site's nginx

`ants-hub` is the third service of `docker-compose.stack.yml` (own volume): built from `Dockerfile.hub` (slim Python, a non-root user, bytecode made at build time), `read_only`, `cap_drop: [ALL]`, `no-new-privileges`, `pids_limit: 32`, `mem_limit: 192m`, a tmpfs at `/tmp`, a health check (`python -m hub.health`), no published port. It has no `ANTS_BUILD_ID` argument: an image depends on `hub/` only, so a deploy that changes nothing there builds the same image and the chat is not restarted.

### The site's nginx

`docker/nginx.conf` has the chat's door, `location = /hub/ws`, and five pages of the login (below): the door is a GET without a query, the name `ants-hub:4040` resolved per request through Docker's resolver (so the site starts, and works, without the hub), 5 new sockets a second for each address (a burst of 10; 503 beyond) and 16 open at a time (429 beyond), 120 seconds of read timeout (the hub pings every 25), no buffering, no access log (one exception, below). The hub gets only the headers of the upgrade, `Origin`, the login's cookie (picked out of the whole `Cookie` header by its name and shape, so that no other cookie of the visitor, the admin page's among them, reaches the hub), `Sec-Fetch-Site` and the one `X-Client-Address` that nginx sets from the connection; nothing else of the visitor's request, and no header of that name from a visitor. A hub that is not there is a JSON 503 `{"error":"hub_off"}`, never a page of the site. nginx counts an IPv6 client by its whole address and the hub by its /64, so for a visitor who has a /64 the hub's 8 are the limit that matters.

The pages of [the login](HUB_LOGIN.md#login) are exact locations of the same kind (the name resolved per request, only the one method, the checks before anything is passed on, no body, `proxy_redirect off`, no access log): `/hub/login` (a GET; gets `Sec-Fetch-Site` and the address), `/hub/callback` (a GET; gets the cookie of the state and the address; 15 seconds of read timeout, for the 10 that the hub gives Discord), `/hub/me`, `/hub/logout` and `/hub/forget` (the login's cookie, `Origin`, `Sec-Fetch-Site: same-origin` required here as well, no query). The first two have 10 a minute for each address (a burst of 5 more; the hub has the same), the others 20; over the limit is 429, and for the two that the browser navigates to a small page with a link back, as is a hub that is not there (503, "Login unavailable, try again later"); the other three answer with the JSON of the chat's door. The login's cookie is for the path `/`, so a browser sends it to every request of the site, and nginx makes sure that it goes to the hub's pages and nowhere else: no door passes the visitor's headers on whole (the game server's `/ws` is given the headers of its handshake and nothing else, `/busy` the `Host`, every other door only the few that its block names), and the admin page's API gets no cookie at all: the gate asks the hub with the login's cookie, and the game server is shown only the gate's pass. `tests/scripts/test_nginx_hub_login.py` checks every proxy block of the file for it, and runs the real blocks. **The one exception to "no access log":** a request that nginx itself refuses before it has chosen a place (a `Cookie` header over 8 KB is 400, an address over 8 KB is 414) is written by the site's stock access log with its whole request line, query included. For `/hub/callback` that line can hold a `code` and a `state`. Neither is of any use to a reader of the log: the hub refuses a callback without the visitor's own `HttpOnly` state cookie, the state is good for one use and ten minutes, and a code is good once and only with the application's client secret. It is still worth knowing for anybody who keeps the site's access logs for long. It is not closed in `docker/nginx.conf`: that would mean a conditional `access_log` for the whole server, which changes what the site logs for every other page.

### Behind a reverse proxy

The hub counts sockets for each address that nginx puts in `X-Client-Address`, and nginx takes that address from the connection it sees. Behind a reverse proxy, name the proxy in `docker/trusted-proxies.conf` ([SERVER.md](SERVER.md#behind-a-reverse-proxy): the image's list names a proxy at a private address, and says what that assumes and how to add a proxy at a public address) so that the limits per address count each visitor's own address. The hub says it at every start (a `note` line) and writes a `crowded` line when one address group holds more than 6 sockets.

An address group is a /64 for IPv6. The hub keeps at most 300 sockets in all and drops a socket after 60 seconds of silence, and nginx lets 5 new sockets a second in for each address; limits beyond those belong at the proxy in front, which is outside this service.

### Deploys

The host's own update rebuilds the stack from the clone of `main` ([`WORKFLOW.md`](WORKFLOW.md), "Deploy"), and every image of the page and of the game server carries the build id of the commit (`docker/resolve_build_id.sh`: the commit named by the clone's `.git`), so **a hub-only change also rebuilds and recreates the page and the game server** (the game server brings its matches back from the restart records; the page is away for a moment). The hub has no build id: its container is recreated only when `hub/` or `Dockerfile.hub` changed, so an update for something else does not restart the chat. There is no way to update one service of the stack alone; a change that must not touch the game server waits for an update that would happen anyway.

CI builds the image in the Web job, starts it with the stack's flags, waits for `healthy`, runs the command line against its volume and checks that a socket from another site gets 403.
